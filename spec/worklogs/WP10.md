# WP10 — Derived stats + full end-to-end regression (Headless MVP milestone)

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase D, WP10.

## Goal

A complete, validated mundane priority-built character, computed headlessly end to end:
`src/chummer5/engine/derived.py` — initiative, physical/mental/social limits, condition monitor
boxes as pure functions of finalized attributes — plus the full-character regression test that
makes headless MVP complete.

## Log

### 2026-07-17 — Legacy cross-reference: six formulas, all straightforward once you know where to
look

Read `legacy/Chummer/Backend/Characters/Character.cs`'s `LimitPhysical`/`LimitMental`/
`LimitSocial`, `PhysicalCM`/`StunCM`, and `InitiativeValue`/`InitiativeDice` getters directly
(searched for `LimitPhysical`, `PhysicalCM\b`, `int InitiativeValue` to find each). Every formula
is a plain function of already-known attribute totals — no branch relevant to MVP's mundane,
non-AI, cyberware-free scope beyond the `IsAI` special cases (irrelevant: MVP never builds an A.I.,
per the Project Overview's metatype-category exclusion already established in WP2/WP6):

- `LimitPhysical = ceil((STR*2 + BOD + REA) / 3)`
- `LimitMental = ceil((LOG*2 + INT + WIL) / 3)`
- `LimitSocial = ceil((CHA*2 + WIL + Essence) / 3)`
- `PhysicalCM = 8 + ceil(BOD / 2)`
- `StunCM = 8 + ceil(WIL / 2)`
- `InitiativeValue = REA + INT + WoundModifier`, floored at 0 (`WoundModifier` always 0 in MVP
  scope — chargen never tracks damage)
- `InitiativeDice = min(base 1 + Σ improvements, 5)` (`CharacterSettings.MinInitiativeDice`/
  `MaxInitiativeDice` field defaults)

All six (well, seven counting the two Initiative pieces separately) add a
`ImprovementManager.ValueOf(this, Improvement.ImprovementType.<Whatever>)` term at the end — the
Project Overview's own Improvement engine section explicitly names this as the reason WP5 only
modeled `ATTRIBUTE`/`SKILL` initially ("more are added when a later WP's derived stat actually
needs one (e.g. initiative, limits in WP10)"), so this WP is exactly that trigger. Added 7 new
`ImprovementType` members (`INITIATIVE`, `INITIATIVE_DICE`, `PHYSICAL_LIMIT`, `MENTAL_LIMIT`,
`SOCIAL_LIMIT`, `PHYSICAL_CM`, `STUN_CM`) to `chummer5.engine.improvements` rather than leaving
`derived.py`'s formulas as bare attribute arithmetic with no Improvement hook — same "thread it
through even though nothing produces one yet" precedent WP6 set for `Character.improvements`
itself. Unlike `ATTRIBUTE`/`SKILL`, these are character-wide totals with no natural per-instance
target (legacy's own `ImprovementManager.ValueOf` calls for these take no target parameter either),
so `derived.py` resolves each against a fixed sentinel target (`""`) rather than adding a second,
untargeted resolution path to `ImprovementIndex` for a distinction nothing in MVP scope currently
needs — documented in `ImprovementType`'s own docstring so a future reader isn't surprised by the
empty-string target.

Confirmed every formula against the core rulebook's own "Final Calculations" table too (p.
100-101, `pdftotext -layout`) — byte-for-byte match, including the "round up" instruction applying
to the whole Inherent Limits calculation (not per-term) and specifically calling out "round up
Essence to the nearest whole number prior to calculating the cost" for Social Limit. See
`spec/rulebooks/learnings.md`'s new WP10 entry for the extracted table and the cross-reference to
`IntegerExtensions.DivAwayFromZero` (confirmed by reading the extension method: for the
non-negative dividend/divisor every one of these formulas ever produces, it's exactly ceiling
division — there's no live case in MVP scope where the "round half away from zero on ties" nuance
that name implies would differ from plain `ceil`, since none of these inputs are ever negative or
exactly at a rounding boundary that "away from zero" vs. "towards positive infinity" would treat
differently).

### 2026-07-17 — A real save-format trap: Essence is not `attribute_value("ESS")`

Went looking for a way to cross-check Social Limit's `Essence` term against `Yeti-#ffffff2.chum5`
directly and found something worth flagging loudly. `metatypes.xml` has an `essmin`/`essmax`/
`essaug` triple per metatype like every other attribute (checked: all 5 SR5 core metatypes have
`essmax = 6`), and WP2's `metatypes.py` loader already parses it into `Metatype.attributes["ESS"]`
alongside every other attribute. That made `character.attribute_value("ESS")` look like the
obvious thing to call — except `ESS` isn't in `ALLOCATABLE_ATTRIBUTES` (no priority letter ever
funds it), so that call would silently compute `metatype minimum (0) + 0 points spent + 0
improvements = 0`. Before writing that bug, checked Yeti's own `<attribute name="ESS">` element in
the save file directly: `<totalvalue>1</totalvalue>` — neither 0 nor 6, and Yeti has zero
cyberware/bioware (confirmed directly, see below), so its *real* Essence is 6.000 exactly, not 1.

Traced this in the legacy C#: `Character.Essence()` (`Character.cs`, ~line 28005 — the getter
`LimitSocial` actually calls) is a wholly separate decimal computation from
`CharacterAttrib.TotalValue` for the attribute named "ESS". The `.chum5` attribute element with
that name isn't wired to the real Essence value at all — it's effectively vestigial for this
project's purposes. This means `chummer5.engine.derived.social_limit` cannot use
`character.attribute_value("ESS")`; it uses a fixed `BASE_ESSENCE = 6` constant instead, justified
by: MVP has no cyberware/bioware (`Essence()`'s only reduction sources — checked directly, its only
special-case branch besides those is a "fixed Essence" Improvement type this project doesn't
model), and all 5 SR5 core metatypes share the same Essence maximum (6). Recorded in both this
worklog and `spec/rulebooks/learnings.md`'s new WP10 entry so a future agent grepping `.chum5`
files for "ESS" doesn't rediscover this the hard way (or worse, silently ship the `attribute_value
("ESS")` bug this WP almost did).

**Confirmed zero cyberware/bioware across the curated corpus before trusting "no augmentation"
generally.** Checked `<cyberwares>` child-element counts for all 11 mundane fixtures directly (not
just Yeti): only 3 of 11 (`Rez0luti0n2.0`, `Serpent`, `Yeti-#ffffff2`) have zero cyberware; the
other 8 have between 3 and 16 entries. This doesn't change anything WP10 actually asserts (no
`.chum5` field stores a computed derived-stat value to diff against regardless — see below — so
augmentation-vs-not was never going to gate a fixture comparison the way it did for WP6's
per-attribute check), but it's worth recording since a future WP validating Essence-dependent
content against the wider corpus would need the same "only Serpent/Yeti/Rez0luti0n2.0 are actually
cyberware-free" filter WP6 already applies for attribute augmentation, for the same underlying
reason.

### 2026-07-17 — No `.chum5` field stores any of these six values — same gap WP7 found for dice
pools

Checked a full attribute/character-level tag scan of `Yeti-#ffffff2.chum5` for anything
limit/CM/initiative-shaped: found only `<limitmodifier>`/`<limitmodifiers>` (Improvement-sourced
limit *modifiers*, always empty for Yeti — no MVP-supported quality produces one), `<physicalcmfilled>`/
`<stuncmfilled>`/`<matrixcmfilled>` (damage *taken*, not the box *total*), and
`<essenceatspecialstart>` (which, per the module docstring's Essence finding above, is also not a
generally reliable value — it's `decimal.MinValue`, i.e. "never set," for every purely mundane
fixture with no Magic-enabling quality, confirmed for `Barrett`/`Blindfire` alongside Yeti's own
set value). None of `LimitPhysical`/`LimitMental`/`LimitSocial`/`PhysicalCM`/`StunCM`/
`InitiativeValue`/`InitiativeDice` are themselves ever written to the save format — they're
recomputed by the legacy UI on load, not persisted. This is the same gap WP7 hit for the skill dice
pool formula (no stored value to diff against), so WP10's tests follow the same resolution:
formulas proven via hand-computed expected values (`tests/unit/test_derived.py`, using real
`create_character` output so the numbers are grounded in real metatype/priority data, not
fabricated), plus one worked, fully-hand-verified example built from `Yeti-#ffffff2.chum5`'s own
recorded attribute totals in the new full-regression test.

### Design decisions

- **`derived.py` functions take a bare `Character`, no separate `allocation`/`selection` argument**
  — unlike `chummer5.engine.skills`/`qualities`/`resources`, every one of these seven formulas is a
  pure function of already-finalized attribute values (`Character.attribute_value()`), with no
  additional selection state (skill points, quality picks, contacts) to consult. This is the
  simplest possible signature consistent with what the formulas actually need — no
  forward-compatibility parameter added for content this WP doesn't build.
- **New `ImprovementType` members resolve against a fixed sentinel target (`""`)`, not a second
  "untargeted" resolution method on `ImprovementIndex`.** `ImprovementIndex.resolve()`'s
  `(type, target)` index shape was built for `ATTRIBUTE`/`SKILL`, where different instances
  (different attribute codes, different skill names) genuinely need different targets. None of
  WP10's 7 new types have more than one instance per character, so reusing the existing method
  with a placeholder target avoids adding a second code path to `ImprovementIndex` for a
  distinction that has no real content to exercise yet — if a later WP's Improvement source
  produces one of these with a genuinely per-instance shape (unlikely, given the legacy engine's
  own `ValueOf` calls for them take no target either), that would be the trigger to reconsider this,
  not a speculative addition now.
- **`BASE_ESSENCE = 6` is a module-level constant, not derived from `metatype.attributes["ESS"]
  .maximum` at call time.** Even though the data is present and would give the same answer for
  every SR5 core metatype, reading it live would wrongly imply Essence is metatype-derived the way
  BOD/STR/etc. are (min + points + improvements) — it isn't; it's `essmax` minus cyberware/bioware
  cost, and MVP models none of the latter. A named constant with a docstring explaining exactly why
  is clearer than a formula that happens to produce the right number for the wrong conceptual
  reason.
- **No `Character` field added for any derived stat, and no single `DerivedStats` bundling
  dataclass.** Every prior WP (WP7/WP8/WP9) already established "the selection/computation module
  doesn't need to be stored on `Character` itself" as the pattern — WP10 has even less reason to
  break it, since these are pure, cheap-to-recompute functions with no state to persist at all.
  Introducing a bundling dataclass (`DerivedStats(initiative=..., physical_limit=..., ...)`) was
  considered and rejected: nothing in this WP's scope or the Implementation Plan's acceptance
  criteria calls for one, and it would be pure structure with no behavior — a future UI WP (WP17,
  the character-sheet view) is a more natural place to decide whether to bundle these for display,
  once there's an actual consumer shaping that decision.

## Outcome

WP10 complete — **headless MVP milestone reached.** `chummer5.engine.derived` adds Initiative
(value + dice), the three Inherent Limits (Physical/Mental/Social), and both Condition Monitors
(Physical/Stun) as pure functions of a finalized `Character`, all six formulas confirmed against
both the legacy C# (`Character.cs`) and the core rulebook's own Final Calculations table
byte-for-byte. `ImprovementType` gained 7 new members so these formulas compose with the
Improvement engine the same way attributes/skills already do, even though nothing in MVP's current
content produces one yet. The notable finding: Essence must be read as a fixed constant (6, the
shared SR5-core-metatype maximum, since MVP has no cyberware/bioware to reduce it), never via
`character.attribute_value("ESS")` — that attribute exists in the data layer for schema
completeness but isn't wired to the character's real Essence value in the legacy engine either, and
`Yeti-#ffffff2.chum5`'s own save data (`<totalvalue>1</totalvalue>` on an attribute whose real value
is 6.000) would have made that bug easy to ship unnoticed. The new full end-to-end regression test
builds `Yeti-#ffffff2.chum5` through every engine module (metatype/attributes, skills, contacts,
resources, derived stats) in one pass — the acceptance criterion for headless MVP.
