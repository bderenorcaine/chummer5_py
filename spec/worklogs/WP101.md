# WP101 — The i18n key layer

Phase W's fifth WP adds the machinery for translating the UI: string catalogs, a lookup with
fallbacks, a `_()` template global, a session locale, and a language picker. It deliberately
converts almost no existing strings. That is WP102's job.

## What landed

- **`chummer5.data.lang`** is a loader in the style of the other `chummer5.data` modules:
  - `load_locale_strings(locale)` reads `legacy/Chummer/lang/<locale>.xml`, normalised, and overlays
    `src/chummer5/lang/<locale>.xml` on it. The result is a frozen mapping.
  - `normalise_winforms_text` does the normalising: `&File` → `File`, `&&` → `&`, and a spaced
    `&` is left alone.
- **`src/chummer5/lang/en-us.xml`** is the project catalog. It holds four `Web_*` keys: the
  picker labels and the two theme names.
- **`src/chummer5/lang/README.md`** holds the key rules:
  - reuse a legacy key only on an exact text-and-role match;
  - project keys are `Web_<Area>_<Name>`;
  - interpolation uses one key with named placeholders;
  - texts are plain text;
  - game-data names are not keys (WP103).
- **`chummer5.web.i18n`**:
  - `translate(locale, key, *args, **kwargs)` falls back from the locale to English, then to
    `⟦Key⟧` with a logged warning. A placeholder mismatch returns the raw text with a warning
    rather than raising.
  - `request_locale(request)` is read-only: it never creates a session, and it caches the locale on
    `request.state`.
  - `jinja_translate` is the `_` global. It is registered in `catalogs.py`, the one injection
    point the phase file identified.
- **`chummer5.web.prefs`**:
  - `Locale(tag, html_lang, label)`; its label is the language's own name for itself, not a key.
  - `LOCALES`, which holds English only, plus `DEFAULT_LOCALE`.
  - `Theme.label` became `label_key`.
- **`ChargenSession.locale`** holds the session's choice.
- **`base.html`**:
  - `<html lang="{{ html_lang }}">`.
  - The title bar's prefs area now has two `<select>`s, theme and language, each with its own
    `hx-post`. WP100 put the post on a wrapping `<form>`; I moved it onto the selects so the two
    can go to different routes.
- **`POST /ui/prefs/locale`** validates against `prefs.LOCALES_BY_TAG`, read at call time so a test
  can offer a stub locale. It answers `HX-Refresh: true`.
- **Docs**:
  - `Project Overview.md`'s "i18n key layer from day one" claim is struck through and corrected
    in place, with a date.
  - The decisions-log entry records the mechanism.
- **Tests**:
  - `tests/unit/test_web_i18n.py` has 13 tests.
  - `test_web_themes.py`'s picker test was re-pointed from the `<form>` to the theme `<select>`.

## Decisions

### Dict lookup over gettext

The full comparison is in the decisions log. What tipped it was WP103. Game-data translations
exist only as `<locale>_data.xml`, keyed by English name, and gettext would have been a second
mechanism next to whatever reads those. The same loader shape now covers both.

### Two layers, and the `Web_` prefix

The legacy catalog is used as shipped: I did not copy or edit it. Project keys live in their own
file in the same schema and override on a clash. The `Web_` prefix guarantees there is never a
clash, and a test checks that no project key is a legacy key. The prefix also tells a reader which
layer to edit.

The legacy texts are WinForms captions, so 104 of them carry a mnemonic `&` and 8 an escaped `&&`.
These are normalised on load, and only on the legacy layer. Project texts are literal, and a test
pins that difference.

### Missing is visible, untranslated is not

A key missing from a non-English catalog is the normal state of a partial translation, so it falls
back to English silently. A key missing from English is a bug: it renders `⟦Key⟧`, never blank,
and logs a warning naming the key and both locales. That is the entry's "visible and diagnosable"
acceptance.

### English only, picker anyway

The loader can read de-de and the other legacy locales today. Offering them now would render pages
that are about 99% English fallback, which is worse than not offering them. The picker still ships
(it is a deliverable) with its one entry, and `prefs.LOCALES` is where a locale gets added once
WP102/103 give it coverage.

### The picker's own strings, and nothing else

The entry says to convert nothing (WP102). The picker is this WP's own new UI, so its labels go
through `_()` from the start. They are also what the acceptance test needs: a page that visibly
renders through a non-English stub catalog.

## Traps hit

- **`--` inside an XML comment is a parse error.** My first project catalog had one in its header
  comment, and 273 tests failed at once, because every page render loads the catalog. That is
  exactly the failure a translator's typo would cause, so
  `test_every_project_catalog_parses_and_owns_only_web_keys` now parses every project catalog on
  its own, and names the file.
- **Theme labels.** WP100's `Theme.label` held English text in Python. That is the "strings that
  hide outside templates" class WP102 warns about, so it became `label_key` here rather than being
  left for WP102 to find.

## Verification

- `pytest` 1403 passed (13 new). `ruff check`/`ruff format --check` clean; `mypy src` clean.
- A test renders `/` under a stub `xx-test` locale whose catalog holds only the two picker labels.
  Those labels come out translated, the theme names fall back to English, and the page gets
  `<html lang="x-test">`.
- Checked in a browser: the title bar renders `Theme [Classic|Sketch]  Language [English]` with
  `lang="en-US"` and no console errors.
