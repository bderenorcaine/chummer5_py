# WP107 — Quality instances: levels, repeats, and per-instance choices

Phase X's first WP, and a pure plumbing one: nothing new is offered. A quality selection stops being
a set of unique ids and becomes a tuple of *instances*, so that the rated qualities (Focused
Concentration, Gremlins, High Pain Tolerance, ...) and the repeatable ones (Addiction, Allergy,
Prejudiced, ...) that WP114/WP115 will offer have somewhere to live.

## What landed

- **`Quality.max_rating` / `Quality.repeatable` / `Quality.include_in_limit`** in
  `chummer5.data.qualities`. `<limit>` has three shapes in the SR5 slice: an integer (5 rated
  qualities plus the Indomitable trio), `False` (28 repeatables), and absent/`True`. The one formula,
  Ambidextrous's `{arm} - 1`, reads as 1.
- **`QualityPickRequest` / `QualityPick`** in `chummer5.engine.qualities`. This is the same
  request/resolved split `CyberwarePurchaseRequest` uses. `create_quality_selection` takes requests,
  and a bare id string is still accepted as shorthand. `QualitySelection.qualities` is a tuple of
  picks, and WP55's `quality_text` map is gone, folded into `QualityPick.text`.
- **Validation per instance.** Rating within `1..max_rating`. A once-only or rated quality appears
  once. A repeatable quality never appears twice with the same `(text, choice)`. Both 25-Karma caps
  sum `karma × rating`. Rows linked by `<includeinlimit>` share one level cap.
- **`apply_quality_improvements`** multiplies each flat bonus by the rating. Indomitable (Mental) 2
  is +2 Mental limit.
- **Save format version 2.** `quality_picks` replaces `quality_ids` and `quality_text`. Version 1 is
  still read, and migrated exactly.
- **Legacy import** folds repeated nodes of a rated quality into one pick's rating.
- **Quality UI.** A Rating column with a number stepper for rated qualities. Each repeatable quality
  has an "(another)" row under its committed instances. The character sheet shows "Indomitable
  (Mental) 2" and "Codeblock (Matrix Perception)".

## Decisions

### Indomitable's shared cap comes from the data, not a name check

The first draft enforced the rulebook's "up to three levels" across Mental/Physical/Social by name
prefix. Reading the legacy engine's limit check turned up the reason it never needed that:
`qualities.xml` gives each Indomitable row an `<includeinlimit>` naming the other two, and
`SelectionShared.cs` sums them. Parsing that block generally is smaller than the special case and
covers any later catalog row with the same shape. Indomitable is the only SR5 quality that carries
one. Indomitable was already offered, but only at rating 1. The cap only became reachable in this WP,
because this is the WP that gives it a stepper.

### The legacy format has no quality rating

The plan said to map `.chum5` `<rating>` onto the pick. There is no such field on a quality node.
All 35 `<rating>` tags in the corpus belong to adept powers. Legacy writes one `<quality>` node per
level instead: `Glessner.chum5` has three Focused Concentration nodes, and `Apex Predator.chum5` has
two Gremlins nodes. So import counts repeats of a rated quality. For a repeatable quality each node
stays its own instance, and `<extra>` supplies the text, as before.

### Form field names keep their pre-WP107 shape for the first instance

A row's key is the bare quality id for a quality's first instance and `id:n` after that. The
checkbox value is the key, and the detail and rating inputs are `quality_text_<key>` and
`quality_rating_<key>`. So every once-only quality posts exactly the fields it did before, and none
of the existing web tests needed to change. A repeatable quality always renders one blank extra row.
The player adds an instance by filling it in, so no add button or extra endpoint is needed.

### The text rule moved from "id-keyed map" to "per pick"

WP55 rejected an orphaned `quality_text` entry, meaning text keyed to an unselected quality. That
failure mode cannot exist when the text sits on the pick itself. What remains are the two directions
that still mean something: a `SELECT_TEXT` pick without text, and text on a pick that doesn't use
it. A rating box that isn't a number becomes rating 0, so the engine's range message reports it and
the route doesn't need its own.

### `apply_quality_improvements` accepts both shapes

It serves both a player's picks and a metatype's free qualities, which are plain `Quality` rows. It
takes `Quality | QualityPick` and treats a bare `Quality` as rating 1. Wrapping the metatype grants
at every call site would have touched four modules for no behavioural difference.

## Traps hit

- My first repeatable round-trip test used two Code of Honor instances. That is 30 Karma, over the
  negative cap. It was switched to two Codeblocks (20). It is a reminder that repeatables make the
  25-Karma cap reachable from a single catalog row, which it never was before.
- `_quality_selection_context` lost its positional `quality_ids` argument. `shell.py` and the
  talent/spell docstrings referenced it and were updated.
