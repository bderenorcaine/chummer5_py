# WP11 — Native save format

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase E, WP11.

## Goal

Persist and reload a character in the project's own format: `src/chummer5/io/save_format.py`, a
JSON format mirroring the domain model, with round-trip tests (build → save → load → equal).

## Log

### 2026-07-17 — What "mirroring the domain model" has to mean, given no bundling type exists yet

Read every engine module built so far (`character.py`, `skills.py`, `qualities.py`,
`resources.py`) before writing anything. Confirmed: chargen state is spread across five separate
objects with no existing aggregate --- `Character` (metatype, priority letters, attribute points,
`ImprovementIndex`), `SkillAllocation`, `QualitySelection`, `ContactSelection`,
`ResourcesSelection` --- built independently by five different `create_*` functions, each taking
plain selections (priority letters, point mappings, id lists) as parameters. WP10's own worklog
explicitly declined to add a bundling dataclass for exactly these five, reasoning "a future UI WP
... is a more natural place to decide whether to bundle these for display, once there's an actual
consumer shaping that decision." Persistence turned out to be that consumer, one WP earlier than
WP10 guessed (WP17's UI, not WP11's save format) --- a save file has to be *some* single
serializable unit.

This settled the format's actual shape: **save the selections each `create_*` function already
takes, not the objects those functions produce.** Two things ruled out saving the built objects
directly: `Character.improvements` is a mutable `ImprovementIndex` with no JSON-shaped
representation (and no `__eq__`, which mattered later --- see below), and every built object holds
references into a shared, separately-loaded catalog (`Metatype`, `Quality`, `Skill`) that a save
file shouldn't have to re-encode. This also turns out to match the legacy `.chum5` format's own
design almost exactly: WP4/WP7/WP10's fixture research already established repeatedly that no
`.chum5` file stores a *computed* value (dice pool, limit, condition monitor, or even a skill's
final rating) --- only the raw inputs those formulas consume, recomputed at load time by the UI.
This project's native format does the same thing on purpose, not by accident: `CharacterSave` holds
exactly the parameters `create_character`/`create_skill_allocation`/`create_quality_selection`/
`create_contact_selection`/`create_resources_selection` already accept, and `build_character()`
reconstructs everything else by calling straight back into those same, already-validated functions.
One direct consequence worth flagging: a save file can never smuggle in a value the engine itself
wouldn't accept from a fresh selection, because loading *is* fresh construction --- there is no
separate "trust this file's numbers" code path to audit.

### 2026-07-17 — `Character` has no usable `__eq__`, so "equal" means something narrower for it

While writing the round-trip test, the first draft asserted `built_before == built_after` on the
whole `BuiltCharacter` bundle and it failed even though every value was correct. Traced it: `dataclass
(frozen=True)` on `Character` auto-generates `__eq__` from its fields, one of which is
`improvements: ImprovementIndex` --- and `ImprovementIndex` (WP5) defines no `__eq__` of its own, so
two independently-built indexes with identical contents are never `==` (falls back to identity).
This isn't a bug to fix here: WP5/WP6 never needed `ImprovementIndex` equality for anything, and
every existing fixture test already works around exactly this by comparing
`Character.attribute_value()` outputs rather than `Character` instances (see
`test_yeti_priority_build_matches_engine_end_to_end` in `tests/integration/test_character_fixtures.py`,
pre-dating this WP). `SkillAllocation`/`QualitySelection`/`ContactSelection`/`ResourcesSelection`
carry no such unindexed state, so those four *do* compare equal by value with a plain `==` --- only
`Character` needed the narrower `attribute_value()`-based comparison, documented directly on
`BuiltCharacter`'s docstring so a future reader doesn't rediscover this by watching a test fail for
a non-obvious reason.

### 2026-07-17 — `format_version`: the one place this WP deliberately adds up-front scaffolding

This project's stated bias is against defensive/forward-compatibility code with no current
consumer (see `Project Overview.md`'s general engineering principles and this repo's own
established pattern of only adding an `ImprovementType` member when something produces one). A save
*file*, though, is data that outlives the code that wrote it by construction --- unlike an
in-memory object, it can persist across a future schema change (magic/resonance chargen, cyberware,
career mode) that this WP's format doesn't yet need to model. Checked the legacy format for
precedent rather than assuming: every `.chum5` fixture carries an `<appversion>` tag (e.g.
`5.202.55`), confirming this isn't a novel concern. Added `FORMAT_VERSION = 1` and made
`from_json`/`_dict_to_save` reject anything else outright with a clear `ValueError` --- not a
migration shim (there is nothing to migrate from yet), just a version tag with an enforced check, so
a later WP that changes the schema has an actual signal to branch on instead of silently
misreading an old file.

### 2026-07-17 — No rulebook consultation needed this WP

Unlike WP2-WP10, this WP is pure persistence/serialization plumbing over an already-validated
engine --- no new SR5 rule is interpreted, so `spec/rulebooks/learnings.md` gets no new entry this
time (the first WP since WP1 for which that's true).

### Design decisions

- **`CharacterSave` lives in `chummer5.io.save_format`, not `chummer5.engine`.** It bundles five
  engine modules' inputs together, but its shape is driven entirely by "what does a JSON file need
  to hold", not by any new rule the engine itself enforces --- `create_character_save()` does no
  validation of its own (see below), unlike every `engine.create_*` function. Keeping it in `io`
  keeps the engine layer exactly as WP6-WP10 left it: five independent modules, no forced coupling
  between them.
- **`create_character_save()` performs no validation.** Every value it wraps is re-validated by
  `build_character()`'s calls into the existing `create_*` functions regardless of where the
  `CharacterSave` came from (hand-authored, loaded from JSON, round-tripped) --- duplicating those
  checks on the way into `CharacterSave` would be a second copy of the same logic with no new
  guarantee, since a save file's contents are only ever trusted as far as `build_character` accepts
  them, never before.
- **`Contact` is reused directly from `chummer5.engine.resources`, no save-format-local copy.** It
  was already a frozen dataclass of exactly `str`/`int`/`bool` fields with no engine state to strip
  out before serializing --- introducing a parallel `ContactSave` type would be pure duplication.
- **`build_character()` takes the four static catalogs (`metatypes`, `priorities`, `skills`,
  `qualities`) as parameters rather than loading them itself**, mirroring how every `engine.create_*`
  function already takes its catalog as a parameter instead of calling a loader internally --- the
  save format module composes the existing pattern rather than introducing a new one.
- **Raises `ValueError` (not `KeyError`/`StopIteration`) for an unresolvable metatype name and for
  a wrong/missing `format_version`.** Both are system-boundary checks on a file that could in
  principle be hand-edited or from a stale build --- fits this project's own rule that boundary
  validation belongs at the boundary, unlike internal call sites that trust their own invariants.

### Implementation

- `src/chummer5/io/save_format.py` (new): `FORMAT_VERSION`; `CharacterSave` (frozen dataclass:
  metatype name, heritage/attributes/skills/resources priority letters, attribute/skill/group
  point mappings, quality ids, contacts, gear names); `create_character_save()` (plain-mapping →
  immutable-field constructor, no validation); `to_json()`/`from_json()` (explicit dict-shaped
  (de)serialization, not a generic `dataclasses.asdict`, so the wire format is pinned rather than
  an accident of Python's dataclass internals); `BuiltCharacter` (bundles the five reconstructed
  engine artifacts); `build_character()` (re-runs `create_character` + `create_quality_selection`/
  `apply_quality_improvements` + `create_skill_allocation` + `create_contact_selection` +
  `create_resources_selection` from a `CharacterSave` and the four static catalogs).
- `tests/unit/test_save_format.py` (new): synthetic JSON round-trip tests (full selection set, an
  all-empty edge case), a wire-shape spot check (`to_json` output's actual dict keys/values, not
  just round-trip self-consistency), and two rejection tests (unknown `format_version`, missing
  `format_version`).
- `tests/integration/test_save_format_fixtures.py` (new, named `_fixtures` — see Verification
  below): builds a `CharacterSave` from `Yeti-#ffffff2.chum5`'s recorded selections (reusing
  `test_character_fixtures.py`'s extraction logic for metatype/priority letters, skill allocation,
  contacts), then the `build → save → load → equal` acceptance test itself: build once, round-trip
  the save through `to_json`/`from_json`, build again from the reloaded copy, and assert every
  by-value-comparable artifact matches (`SkillAllocation`, `QualitySelection`, `ContactSelection`,
  `ResourcesSelection`, via plain `==`) plus `Character`'s `attribute_value()` outputs match both
  each other and Yeti's own legacy-recorded totals.

## Outcome

WP11 complete. `chummer5.io.save_format` adds the project's native save format: `CharacterSave`
holds exactly the selections every existing `engine.create_*` function already takes (metatype
name, priority letters, attribute/skill point mappings, quality ids, contacts, gear names) rather
than any computed value, `to_json`/`from_json` (de)serialize it through an explicit, pinned dict
shape with an enforced `format_version`, and `build_character()` reconstructs the full
`Character`/`SkillAllocation`/`QualitySelection`/`ContactSelection`/`ResourcesSelection` set by
calling straight back into WP6-WP9's already-validated construction functions. The notable finding:
`Character` can't be compared with a plain `==` because its embedded `ImprovementIndex` has no
`__eq__` of its own (a pre-existing WP5 fact, not a regression introduced here) --- the round-trip
test works around this the same way every prior fixture test already does, via
`attribute_value()` comparisons, now documented directly on `BuiltCharacter` for the next WP that
reaches for `==` on a `Character` and gets a surprising `False`. The acceptance criterion itself
(`build → save → load → equal`) is proven both synthetically (`tests/unit/test_save_format.py`)
and against `Yeti-#ffffff2.chum5`, the same priority-build fixture WP6/WP7/WP9/WP10 already treat as
this project's one real end-to-end regression anchor.
