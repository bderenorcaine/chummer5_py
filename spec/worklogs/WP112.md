# WP112 — Attribute rules: one at natural maximum; Exceptional Attribute and Lucky

This WP closes Step Two's two remaining attribute rules.

## What landed

- **`ImprovementType.ATTRIBUTE_MAXIMUM`** (target: an attribute code) and
  **`Character.attribute_maximum(code)`**, which is the metatype maximum plus the Improvement.
  `natural_attribute_value` caps at it, `attribute_augmented_maximum` adds it too (keeping the +4
  headroom), and the MAG cap and the cyberlimb `{AGIMaximum}`/`{STRMaximum}` bound read it.
  `attribute_maximum_bonuses()` returns the nonzero raises for re-validation.
- **Two qualities offered.** `_classify_bonus` recognises `<specificattribute><name/><max/>` (Lucky)
  and `<selectattributes><selectattribute><excludeattribute/><max/>` (Exceptional Attribute) as the
  new `attribute_maximum` flat bonus. It also recognises `<notoriety>`, but only *alongside* another
  supported child, so Bad Luck and Blandness stay unoffered. `Quality.choice_kind = "attribute"` and
  `choice_excludes` describe Exceptional Attribute's choice. `create_quality_selection` now
  validates choices: Exceptional Attribute needs an attribute from `attribute_choices` (MAG only for
  a magic user), and any quality without a `choice_kind` rejects a choice. The offered count goes
  from 24 to 26.
- **`create_character`** takes `maximum_bonus`, `previous_attribute_points` and `karma_points`. The
  range check reads the raised maximum. The one-at-natural-maximum rule rejects a submission that
  itself raises an attribute to its maximum while another is already there. It is scoped by
  `previous_attribute_points`, so fresh builds (save load, legacy import) and edits that don't
  touch the at-maximum set aren't checked.
- **`build_character`** gets the raises from the *requests*
  (`requested_attribute_maximum_bonuses`) before any quality is committed, because attributes are
  built first.
- **The attributes route** passes the committed raises, the previous points and the Karma points.
  The attribute rows show the raised maximum.
- **The Qualities page** has an attribute dropdown for Exceptional Attribute, and the sheet shows
  "Exceptional Attribute (STR)".

## Decisions

### The rule is scoped to what the submission changed

This mirrors WP52's check in `create_karma_attribute_points` for the same reason. A character
already in breach, such as a legacy import or a save from before this WP, must stay editable. An
attribute "raised to its maximum by this submission" is one at its maximum now that wasn't under
`previous_attribute_points`. Fresh builds pass no previous points and are never checked. WP135
reports those breaches instead.

### The raised maximum is what "at maximum" means

The checklist's "(or one higher with Exceptional Attribute)" is read as: with Exceptional Attribute
(STR), STR's maximum *is* 7 for a Human. So STR 6 isn't at maximum and BOD may sit at 6 beside it.
The Karma-side check in `create_karma_attribute_points` switched to `attribute_maximum` as well, so
the two paths agree.

### A choice is now validated, not just carried

WP107 made `choice` an uninterpreted slot. This WP is the first to interpret it, and the rule it
sets is that a quality without a `choice_kind` rejects a choice. This is the same "stale/tampered
field" discipline as free text. WP107's round-trip test moved to Exceptional Attribute.

### `<notoriety>` is only recognised in company

Treating it as a fully supported child would have made the six qualities whose *only* bonus is a
Notoriety shift offerable here, with no registry notes. Requiring at least one other supported
child keeps them for WP114/WP115, and lets Lucky through.

## Traps hit

- `test_reconfirming_priorities_with_a_lower_attributes_budget_flags_the_existing_spend` bought BOD,
  AGI and REA all to the Human maximum in one post, which is precisely what the new rule rejects.
  WP52's docstring had even recorded that the pure-priority path never enforced this. The test now
  spends the same 15 points legally.
- The paragraph-reflow helper broke a code line in WP110 and a separator comment here. Both were
  fixed by hand. The helper now skips obvious code.
