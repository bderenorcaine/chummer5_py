# WP12 — Legacy `.chum5` import

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase E, WP12.

## Goal

Bring a real legacy character into the new engine, for MVP-covered content only: extend WP4's
parser into a real import path for mundane, priority-built, MVP-feature-only legacy saves.
Acceptance: successfully imports `Yeti-#ffffff2.chum5`; imports of saves with out-of-scope content
(magic, cyberware, etc.) fail with a specific, itemized error rather than silently dropping data.

## Log

### 2026-07-17 — The acceptance criteria contradict each other under a literal reading, and the
resolution is Yeti's own build

Read every prior worklog referencing `Yeti-#ffffff2.chum5` (WP4, WP6, WP7, WP9, WP10) before writing
anything, because the Implementation Plan's own corpus note and `tests/fixtures/README.md` both flag
something that looks like a direct conflict with this WP's acceptance bar: Yeti is a **Technomancer**
(`<resenabled>True</resenabled>`, `<prioritytalent>Technomancer</prioritytalent>`), and the Project
Overview's MVP scope statement pairs magic and resonance together as one exclusion ("No magic/
resonance priority (no adepts, mages, technomancers) in MVP"). Taken completely literally, "reject
out-of-scope content" would have to reject Yeti — but the very next sentence in the Implementation
Plan says import must *succeed* on Yeti specifically. These can't both be satisfied by a naive
"resonance content -> reject" rule.

The resolution wasn't a judgment call so much as a discovery: WP6 through WP10 already answered this
question, repeatedly, by construction. Every one of those WPs builds a real `Character`/
`SkillAllocation`/`ContactSelection`/etc. from Yeti's own recorded data and simply never *consumes*
anything Resonance-specific — RES was excluded from `ALLOCATABLE_ATTRIBUTES` in WP6, no
Resonance-linked skill got special handling in WP7, the Technomancer quality was never selected in
WP8/WP9/WP10 because it was never in the MVP-offered catalog to begin with. None of those WPs treated
"this fixture is technically a Technomancer" as a blocker; they treated it as "this fixture has some
fields we don't read." So the real, already-established distinction isn't "magic/resonance content
present" vs. "absent" — it's "does ignoring this content make an already-imported value **wrong**,
or merely **incomplete**." Resonance content is the second kind for every value MVP actually computes
(nothing derived — attribute totals, dice pools, limits, condition monitors — depends on RES or
Compiling); cyberware/bioware and an active Magic tradition are the first kind, and *those* are what
the acceptance criterion's "magic, cyberware" examples actually name. This WP's blocking-vs-excluded
split (see the module docstring in `src/chummer5/io/legacy_import.py`) makes that distinction
explicit and mechanical rather than leaving it as an implicit reading of five other worklogs.

### 2026-07-17 — Cross-checking the whole corpus, not just the curated 11, before deciding what's
actually testable

The curated 11 mundane fixtures (`tests/fixtures/mundane_chum5.py`) all satisfy `magenabled=False` by
definition, so none of them can exercise the "Magic enabled -> reject" path, and only Yeti among them
is `buildmethod=Priority` (the other 10 are `SumtoTen`, itself a rejection reason). Checked the wider
34-file corpus at `legacy/Chummer.Tests/TestFiles/` directly for `buildmethod=Priority` combined with
other properties, to find real (not synthetic) fixtures for each rejection path:

- **`Miko.chum5`** and **`Wesson.chum5`**: both `Priority`-built *and* `magenabled=True`, with
  `gameplayoption=Standard`, zero cyberware, and no metavariant — i.e. clean on every other axis.
  Picked `Miko.chum5` for `test_rejects_magic_enabled_priority_character` specifically because it
  isolates exactly one blocking reason, so the test can assert the *exact* single-item `reasons`
  tuple rather than just "raises with some Magic-related text in it somewhere."
- No fixture in the full 34-file corpus is both `Priority`-built and has cyberware, or is
  `Priority`-built with a non-`Standard` `gameplayoption` — the corpus simply doesn't contain that
  combination. Those two blocking reasons (plus the metavariant check, and the multi-reason
  itemization itself) are proven with hand-built synthetic `LegacyCharacter`s in
  `tests/unit/test_legacy_import.py` instead, the same "prove the mechanism in isolation when no real
  fixture happens to exercise it" pattern WP8 used for the negative-quality karma cap.
- Confirmed the cyberware/bioware presence check by inspecting a real `<cyberwares>` entry directly
  (`Barrett.chum5`): both Cyberware and Bioware items live under the same `<cyberwares>` wrapper,
  distinguished only by an inner `<improvementsource>` tag (`Cyberware` vs. `Bioware`), not by a
  separate top-level element. This means a single "does `<cyberwares>` have any children" check
  (`LegacyCharacter.has_cyberware`, added to WP4's parser this WP) already covers both cases — no
  need to parse individual entries or distinguish the two, since MVP models neither.

### 2026-07-17 — Import validates by building, not just by reshaping

The first draft of `import_legacy_character` stopped at producing a `CharacterSave` (WP11's format)
and left "does this actually reconstruct into a working character" to whatever code called it next.
Reconsidered: WP11 already proved `CharacterSave` -> `BuiltCharacter` round-trips correctly and
re-runs every `create_*` function's own validation, so there's no reason for *this* WP's "successfully
imports" claim to mean anything weaker than "the save this produces actually builds." Changed
`import_legacy_character`/`import_chum5` to call `build_character()` internally and return the
resulting `BuiltCharacter` alongside the `CharacterSave` in `ImportResult`, so a caller (and this
WP's own tests) gets a ready-to-use character, and any `create_*` validation failure this module's
own checks didn't anticipate surfaces immediately, at import time, rather than being deferred to
whatever later code happens to call `build_character` on the saved file.

### 2026-07-17 — No rulebook consultation needed this WP

Same as WP11: this is import/conversion plumbing over an already fully-validated engine (WP6-WP10)
and an already-validated save format (WP11) — no new SR5 rule is interpreted, only "which of the
rules already implemented does a given legacy file's content actually exercise." `spec/rulebooks/
learnings.md` gets no new entry.

### Design decisions

- **Blocking checks are collected into one itemized list, not raised as separate exceptions per
  issue.** `UnsupportedLegacyCharacterError.reasons` is a tuple built by checking every condition
  before raising, once, rather than the more naive "raise on the first problem found" — verified by
  `test_itemizes_every_blocking_reason_in_one_pass` (a synthetic character failing 3 checks at once
  reports all 3). This directly satisfies the acceptance criterion's "specific, itemized error"
  wording, and avoids a fix-one-rerun-find-the-next loop for a real file with multiple issues.
- **`has_cyberware` extends `LegacyCharacter` (WP4's dataclass) rather than being computed by
  re-parsing the file inside `legacy_import.py`.** The Implementation Plan's own WP12 deliverable
  description is "extends WP4's parser into a real import path" — read literally, meaning WP4's
  parser itself is allowed (expected) to grow the raw fields this WP needs, keeping "what does the
  file literally say" (WP4's stated contract) as the single place that reads `.chum5` XML directly.
- **Unsupported qualities/skills are excluded and reported (`ImportResult.dropped_*`), not
  blocking.** Considered making any non-MVP-offered quality a hard rejection (a strict reading of
  "MVP-feature-only legacy saves" from the Implementation Plan's deliverable description) but
  rejected it: it would make Yeti itself unimportable (none of its 6 real qualities are MVP-offered),
  directly contradicting the "successfully imports Yeti" acceptance criterion. This also matches
  WP3/WP8's own established precedent for the *same* underlying problem shape (a quality's bonus
  grammar MVP doesn't parse) — "exclude cleanly and say so," not "reject the whole selection."
- **No general gear import; `gear_names=()` unconditionally.** WP9's `STARTER_GEAR_CATALOG` is a
  deliberately small, non-representative stub (5 items) and WP10 already found Yeti's real gear
  purchases aren't reconstructable against it. This isn't a new scope cut this WP is introducing —
  it's the Project Overview's own explicit MVP exclusion ("full gear catalog beyond a basic purchase
  flow"), so there's genuinely nothing for an import path to attempt here yet.
- **`import_chum5(path, ...)` is a thin wrapper over `import_legacy_character(legacy, ...)`, not the
  only entry point.** Mirrors WP4's own two-tier shape (`load_chum5(path)` vs. operating on an
  already-parsed `LegacyCharacter`) — useful directly for this WP's own tests, which build synthetic
  `LegacyCharacter`s to test the blocking-reasons logic without needing a real file on disk for every
  case (see the Log's "no real fixture exercises this combination" note above).

### Implementation

- `src/chummer5/io/legacy_chum5.py` (extended): `LegacyCharacter` gains `has_cyberware: bool`
  (`<cyberwares>` has any children — covers both Cyberware and Bioware entries, see Log); `load_chum5`
  parses it via new helper `_has_children()`.
- `src/chummer5/io/legacy_import.py` (new): `UnsupportedLegacyCharacterError` (`.reasons: tuple[str,
  ...]`); `_blocking_reasons()` (build method, gameplay option, Magic, cyberware/bioware, metavariant
  checks); `ImportResult` (`save`, `built`, `dropped_qualities`, `dropped_skills`);
  `import_legacy_character()` (the core transform: attribute points, skill points/group points with
  the same strict-skill-groups logic WP7's fixture tests already validated, MVP-offered-only quality
  filtering, contacts, then `build_character()` to prove it's real); `import_chum5()` (path -> parse
  -> import convenience wrapper).
- `tests/unit/test_legacy_import.py` (new): synthetic `LegacyCharacter`s covering each individual
  blocking reason, the "Resonance is not blocking" case, the multi-reason itemization case, and the
  excluded-not-blocking quality/skill drop-and-report behavior.
- `tests/integration/test_legacy_import_fixtures.py` (new — see Verification below for the naming
  note): the Yeti end-to-end acceptance test (attribute totals, dropped-quality set, skill/group
  rating, contacts, resources budget, all cross-checked against `LegacyCharacter`'s own recorded
  values); the SumToTen-rejection test (`Barrett.chum5`); the real-fixture Magic-rejection test
  (`Miko.chum5`).

## Outcome

WP12 complete. `chummer5.io.legacy_import` adds a real, validated import path from legacy `.chum5`
saves into this project's native format: `import_chum5()`/`import_legacy_character()` convert a
`LegacyCharacter` (WP4) into a `CharacterSave` (WP11) and immediately build it through
`build_character()`, so "successfully imports" means the result is a working `Character`/
`SkillAllocation`/`QualitySelection`/`ContactSelection`/`ResourcesSelection` set, not just a
correctly-shaped file. The acceptance criteria's apparent tension — "import Yeti" (a Technomancer)
vs. "reject out-of-scope content like magic" — resolves via a blocking-vs-excluded split established
by re-reading WP6-WP10's own precedent: content that would make an already-computed value silently
*wrong* (non-Priority build method, non-Standard gameplay option, Magic enabled, cyberware/bioware
presence, metavariants) is rejected outright with an itemized `UnsupportedLegacyCharacterError`;
content MVP simply doesn't model but that doesn't corrupt anything it does compute (Resonance/
Technomancer content, non-MVP-offered qualities, unresolvable skill ids) is excluded from the import
and reported via `ImportResult.dropped_qualities`/`dropped_skills` rather than either blocking the
whole import or vanishing with no trace. Proven against real fixtures wherever the corpus has one
(`Yeti-#ffffff2.chum5` for the success path, `Barrett.chum5` for the build-method rejection,
`Miko.chum5` — outside the curated mundane 11 — for an isolated real-data Magic rejection) and
synthetically for the reasons no real fixture combination happens to exercise.
