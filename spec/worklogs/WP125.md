# WP125 — Knowledge and Language completion

This WP closes the three Knowledge/Language gaps:

- Active skill points can pay for ranks past the free pool (p. 88).
- Karma can buy a new Knowledge or Language skill from rating 0 (p. 107).
- Knowledge and Language skills can take specializations, 1 point or 7 Karma each (p. 88, p. 107,
  p. 148, p. 150).

## Research

See the learnings entry. The plan's acceptance names Rob's "Dakota language to 2 (2 Karma)". That
turns out to be a raise of the Dakota 1 he bought in Step Five, which WP53 already handles, so it
got a test rather than new code.

## What landed

- **Engine** (`engine/knowledge.py`):
  - `KnowledgeSelection` gains `specializations` and `active_points_used`.
  - `create_knowledge_selection` takes `specializations` and `active_points_available`. It accepts
    a non-native pick at rating 0. It charges a point per specialization, and a specialization's
    pick must be native or rated 1+.
  - The spend past the free pool must fit the Active points available.
  - `KarmaKnowledgeSelection` gains `specializations`. `create_karma_knowledge_selection` takes
    `karma_specializations`: 7 Karma each, with Uneducated's percent applied. It rejects a second
    specialization, and a rating-0 pick that no Karma raises.
  - Shared helpers: `knowledge_points_spent`, and name resolution that rejects an ambiguous name.
    That name resolution was already WP53's rule for Karma points.
- **Engine** (`engine/skills.py`): `create_skill_allocation(knowledge_active_points=)` counts the
  overflow against the individual-skill budget. `knowledge_active_points(character)` reads it off
  the committed selection.
- **Save**: `knowledge_specializations` and `karma_knowledge_specializations`, name-keyed and
  additive, with no version bump. `build_character` bounds the Knowledge overflow by the whole
  Skills budget first. It then passes `active_points_used` to `create_skill_allocation`, which does
  the exact check.
- **Web**:
  - The Knowledge page has point and Karma specialization columns for both tables, and shows the
    specialized pool as "X (Y)". It adds the line "Active skill points used: N / M".
  - `active_points_left` gives the Knowledge step the Active points the Skills step leaves.
  - The Skills page's "points remaining" subtracts the Knowledge overflow, and its validators
    include it.
  - The sheet shows "Corporations (Evo)".
  - Two new strings.

## Decisions

- **Free pool first.** The book doesn't order the two pools. Spending the free one first is the
  only order that never wastes points, because the free pool can buy nothing else.
- **The overflow is derived, not stored.** It's `max(0, spent − free)`. Storing it would be a
  second source of truth that goes stale when INT or LOG changes.
- **Both steps check the same inequality** (Active spend + Knowledge overflow ≤ Skills budget).
  Whichever step is submitted second rejects. Each page's WP19 re-check shows the other's warning
  after an edit elsewhere.
- **Specializations are keyed by name**, like WP53's Karma points. The picks have no ids, and each
  list's names are unique.
- **A native language may be specialized** (see the learnings).
- **Legacy import is unchanged.** It never imported Knowledge Karma (the same standing cut as
  Active-skill Karma), so a Karma-bought rating-0 legacy skill is still skipped. A legacy spend
  past the free pool now imports instead of failing.

## Traps

- **An Active overspend made Knowledge stale too.** "Active points left" went negative, and a
  0-point overflow then "exceeded" it. `active_points_left` clamps at 0, so the Skills step's own
  warning is the only one. `test_a_stale_section_is_marked_on_its_own_tab` caught it.
- **Tests assumed the free pool was the whole budget.** Three existing tests expected a 6-rank spend
  over 4 free points to be rejected. With Skills C's 28 Active points it now fits, so they now
  overspend both pools.
- **Save plumbing.** The web save builder (`routes/character.py`) builds the `CharacterSave` from
  the live `Character` separately from `save_format`. New save fields have to be threaded there
  too, or the round trip silently drops them.
