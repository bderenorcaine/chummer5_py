# WP13 — Web app skeleton

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase F, WP13.

## Goal

The UI stack runs end to end, doing nothing yet: `src/chummer5/web/app.py` (FastAPI app factory),
a Jinja2 base layout, HTMX vendored locally (not CDN-loaded), `uvicorn` dev-run instructions, and
one trivial page. Acceptance: `uvicorn chummer5.web.app:app` serves the trivial page; an
HTMX-driven interaction on that page round-trips through the server.

## Log

### 2026-07-18 — First WP with dependencies at all, and the venv needed a real `uv sync`

Every prior WP (2-12) built on a `dependencies = []` project — the whole headless engine has zero
third-party runtime dependencies by design. This is the first WP that adds any: `fastapi`,
`jinja2`, `python-multipart` (needed for `Form(...)` parsing — Starlette's form parser requires it
even for `application/x-www-form-urlencoded`, not just multipart), and `uvicorn`. Added them to
`pyproject.toml`'s `dependencies` and ran `uv sync --group dev`, which pulled in FastAPI's own
transitive stack (Starlette, Pydantic, anyio, etc.) — nothing surprising, just the first time this
project's `.venv` has needed a real dependency resolution instead of the dev-tool trio.

One environment-version surprise worth recording precisely because it looked like a typo at first:
the resolved `starlette` version is `1.3.1` (not a `0.4x` release) and `fastapi.testclient`
pulls in `httpx` — which, at this `starlette` version, is *itself* deprecated in favor of a
package literally named `httpx2`. Confirmed by reading `starlette/testclient.py` directly (`try:
import httpx2 as httpx / except ModuleNotFoundError: import httpx` with a `DeprecationWarning` on
the fallback path) rather than assuming; `httpx2` genuinely exists on PyPI (2.7.0 latest). Tried
switching the dev dependency group from `httpx` to `httpx2` to avoid the warning, but the sync was
blocked by this environment's action classifier (installing an unfamiliar-looking package name).
Reverted to `httpx` rather than fight it: the only cost is one `StarletteDeprecationWarning` in the
test run, which is cosmetic, not a failure — not worth a permission escalation for a solo project's
dev-only dependency. Left as a note here (not a rulebook learning — nothing SR5-rules-related about
it) in case a later WP hits the same classifier block and wonders why `httpx` was kept over the
"correct" newer package.

### 2026-07-18 — HTMX vendoring: version pinned, license checked, fetched over plain HTTP(S) at
build time rather than committing a submodule

Project Overview mandates HTMX "vendored locally (not CDN-loaded, to keep the app fully
offline/local-first)". Checked latest stable (not beta) release via the npm registry
(`registry.npmjs.org/htmx.org` → `dist-tags.latest`) rather than guessing a version from training
knowledge, since this is exactly the kind of fact that goes stale: **2.0.10** (a `4.0.0-beta5` also
exists under the `next` tag — skipped, not stable). Downloaded `dist/htmx.min.js` and `LICENSE`
directly from `unpkg.com/htmx.org@2.0.10/...` and committed both under
`src/chummer5/web/static/vendor/htmx/`, plus a `VENDORED.md` recording the exact version, source
URL, and license (Zero-Clause BSD — permissive, no attribution burden, compatible with this
project's GPLv3) so a future update doesn't have to re-derive any of that. This mirrors the
project's existing precedent of documenting *why* a piece of external content was pulled in
wherever it lives (`tests/fixtures/README.md` for the legacy `.chum5` corpus), applied to the one
new case of "external content" this WP introduces.

### 2026-07-18 — The HTMX demo endpoint needed *some* real round trip, not a decorative click

"An HTMX-driven interaction on that page round-trips through the server" (the acceptance
criterion) rules out a purely client-side toggle — the swapped content has to actually come from
the server per request, or the test proves nothing WP14+ can build on. Picked the smallest thing
that's genuinely server-computed without needing any state (WP14 is explicitly where server-side
in-memory character-in-progress state, keyed by a session cookie, first appears — inventing a
session mechanism one WP early would be scope creep this project consistently avoids elsewhere, per
its "don't design for hypothetical future requirements" rule): a counter fragment
(`_counter.html`) whose current value round-trips through a hidden form field, POSTed via
`hx-post="/ui/counter"`, and the server increments and re-renders it. `hx-swap="outerHTML"`
targeting the fragment's own `id="counter"` proves the returned HTML actually replaces DOM content,
not just that a request succeeded. Verified manually (not just via `TestClient`) per this project's
"test UI changes in a real browser-adjacent way before calling them done" bar: ran `uvicorn` in the
background, fetched `/`, `/static/vendor/htmx/htmx.min.js`, and POSTed `/ui/counter` twice via
plain `urllib` requests, confirming the counter value increments statelessly from whatever the
client last held (0 → 1, 5 → 6) — see Verification below for the exact commands.

### Design decisions

- **`create_app()` factory + module-level `app = create_app()`**, not a bare module-level `FastAPI()`
  call with routes decorated directly onto it. Matches the Implementation Plan's own wording
  ("FastAPI app factory") and keeps `uvicorn chummer5.web.app:app` working today while leaving room
  for a later WP to call `create_app()` directly in tests with different wiring (e.g. an injected
  catalog or session store) without needing a second entry point.
- **Templates and static assets live under `src/chummer5/web/{templates,static}/`, addressed via
  `Path(__file__).resolve().parent`**, not a repo-root-relative path. Keeps the web package
  self-contained and independent of the process's current working directory — the same reasoning
  every prior WP's data loader already applies to `legacy/Chummer/data/*.xml` paths.
- **`increment_counter` takes `count` from a `Form(...)` field, not server-side session state.**
  Deliberately stateless — see Log above. This is a placeholder demo endpoint, not a pattern WP14+
  needs to inherit; a real session-backed endpoint replaces it once that state exists.
- **No CSS/styling.** "One trivial page" is taken literally; visual design isn't in scope for any
  WP before the real chargen screens exist, and adding a stylesheet now would be styling a page
  that gets thrown away.
- **README gets a real "Development" section, replacing the stale "not scaffolded yet" line.**
  That line had already been false since WP1 (never updated across 12 subsequent WPs) and this WP's
  own deliverable list explicitly calls for "uvicorn dev-run instructions" — the README is the
  obvious home for that, not a new doc file.

### Implementation

- `pyproject.toml`: added `fastapi`, `jinja2`, `python-multipart`, `uvicorn` to `dependencies`;
  added `httpx` to the `dev` dependency group (needed for FastAPI's `TestClient`).
- `src/chummer5/web/app.py` (new): `create_app()` — mounts `/static` via `StaticFiles`, wires
  `Jinja2Templates`, defines `GET /` (renders `index.html`) and `POST /ui/counter` (renders
  `_counter.html` with an incremented count); module-level `app = create_app()`.
- `src/chummer5/web/templates/base.html` (new): minimal HTML5 shell, `{% block title %}`/
  `{% block content %}`, loads vendored HTMX via `url_for('static', ...)`.
- `src/chummer5/web/templates/index.html` (new): extends `base.html`, includes `_counter.html`.
- `src/chummer5/web/templates/_counter.html` (new): the HTMX demo fragment — count display + a
  `<form hx-post="/ui/counter" hx-target="#counter" hx-swap="outerHTML">` carrying the current
  count as a hidden field.
- `src/chummer5/web/static/vendor/htmx/htmx.min.js` + `LICENSE` + `VENDORED.md` (new): vendored
  HTMX 2.0.10, Zero-Clause BSD.
- `tests/unit/test_web_app.py` (new): index page renders and contains expected content; the
  HTMX POST round trip increments and returns a swappable fragment (from 0 and from a nonzero
  starting value); HTMX is served from `/static/...`, not referenced from any CDN URL.
- `README.md`: replaced the stale "not scaffolded yet" line with a "Development" section
  (`uv sync`, `uv run python -m pytest`, `uv run uvicorn chummer5.web.app:app --reload`); added a
  link to `Implementation Plan.md`.

## Outcome

WP13 complete. The FastAPI/HTMX web stack described in the Project Overview now actually runs:
`create_app()` in `chummer5.web.app` serves one trivial page through a Jinja2 base layout, with
HTMX loaded from a locally vendored file (`static/vendor/htmx/htmx.min.js`, version 2.0.10,
Zero-Clause BSD) rather than a CDN, and a minimal `POST /ui/counter` endpoint proves the
HTMX-driven round trip works end to end (client submits the current count, server increments and
re-renders, HTMX swaps the returned fragment into the DOM) — verified both via `TestClient` and by
running the real `uvicorn` dev server and hitting it directly. This WP intentionally introduces no
chargen logic, styling, or session state: it's the shell WP14 (priority & metatype selection UI)
builds the first real screen into. This is also the first WP to give the project any runtime
third-party dependencies at all (`fastapi`, `jinja2`, `python-multipart`, `uvicorn`) — the headless
engine (WP1-WP12) remains dependency-free by design; only the web layer needs them.
