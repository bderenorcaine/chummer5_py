# WP137 — Accounts and invite codes

Invite-only registration, login, logout and a password change, behind a hosted-mode login gate.
The admin CLI is `python -m chummer5.admin`. Local mode is unchanged: the whole existing suite
passes untouched (1783 tests at the time).

## What landed

- **`chummer5.accounts`** (no web imports; the CLI and the web layer both call it):
  - `CHUMMER5_MODE` (`app_mode()`) and `CHUMMER5_SESSION_DAYS` (default 30).
  - scrypt hashing. The format is `scrypt$n$r$p$salt$key`, so parameters can rise later. The default
    is N=2^17, r=8, p=1, with `maxmem` set explicitly, since hashlib's 32 MiB default refuses N=2^17.
    Comparison uses `hmac.compare_digest`.
  - Username rules (3-32 of `[A-Za-z0-9_.-]`, unique case-insensitively via `COLLATE NOCASE`).
    Passwords need 10 characters minimum, with 1024 as a cap on scrypt input.
  - Invite codes: 16 Crockford-base32 characters (80 bits), printed as `XXXX-XXXX-XXXX-XXXX`, and
    accepted in any case, with or without dashes or spaces.
  - Sessions: a `token_urlsafe(32)` in the cookie and its SHA-256 in `auth_sessions`. Expiry slides,
    with at most one write per session per 5 minutes (`SESSION_REFRESH_INTERVAL`), and the cookie is
    re-sent when it slides.
  - `register`, `authenticate`, `change_password`, `reset_password`, `delete_user`,
    `ensure_local_user`. `AccountError` carries the i18n key of the message the page shows.
- **Store** (`chummer5.store`): schema v2 adds `users.must_change_password`. New methods cover
  invites, auth sessions, `register_user`, `set_password` (which also ends all of the user's
  sessions, in the same transaction), `list_users` and `set_user_prefs`. The `Store` now initializes
  itself on first use, so building an app opens no file.
- **Web**:
  - `chummer5.web.auth`: the `require_login` middleware, the cookie helpers, and `redirect()`
    (`HX-Redirect` for htmx, 303 otherwise).
  - `chummer5.web.routes.account`: `/login`, `/register`, `/logout` (POST), `/account/password`.
  - Templates `_auth_layout.html`, `login.html`, `register.html`, `password.html`. They use the
    same theme link, title bar and `.panel` as the shell.
  - The title bar shows the username (linking to the password page) and a logout button, in hosted
    mode only.
- **Prefs**: in hosted mode `/ui/prefs/*` also writes the user row, and every chargen-session
  lookup copies the row's theme and locale onto the session. `request_locale` prefers the user's.
- **`create_app(mode=None, store=None)`**: its lifespan initializes the store and, in local mode,
  creates the implicit `local` user. That user's hash is `!`, which nothing verifies against.
- **Deploy**: `Containerfile` gets `/data` + `CHUMMER5_DB`. `test-image.sh` adds hosted-mode checks
  (anonymous redirect, `/login`, an invite minted by `podman exec`, registration end to end,
  `users`). These are not run here, since podman is host-only.
- `tests/unit/test_accounts_wp137.py` (39 tests), plus the root `conftest.py`.

## Decisions and traps

See the decisions-log entry of the same date for the scope additions (password page, chargen
session keyed by login, `/data`). Traps hit:

- **Middleware order.** Starlette runs the *last-added* middleware first. `require_login` is
  registered after `_signal_chargen_changed`, so it is outermost, and a refused request never
  reaches a route.
- **`request.state` is shared between middleware and endpoint** (it lives in the ASGI scope). That
  is how the user and the chargen key reach `resolve_session`.
- **An htmx request must not get a 303.** The XHR follows it and swaps the login page into
  whichever element asked. It gets `HX-Redirect`, which htmx 2 handles before its
  `responseHandling` check.
- **The production image would not have booted.** The local-mode lifespan now creates the
  database, and the image's user can't write under root-owned `/app`.
- **`tests/conftest.py` broke `from tests.fixtures` imports.** The conftest moved to the repository
  root.
- Two existing guards caught real issues:
  - `test_web_no_bare_text` flagged the operator-facing `ValueError` text in the web layer. Mode
    parsing moved to `accounts`.
  - `test_no_project_key_is_an_orphan` didn't scan `accounts.py`, where the error keys live. It
    does now, following the WP135 precedent for `engine/validation.py`.
- A smoke run against real uvicorn showed `users` reporting "last login never" right after
  registration. `record_login` moved into `start_session`, so it covers every way a session begins.

## Verified by hand

uvicorn in hosted mode on a scratch DB, driven with curl:
- invite minted via the CLI;
- anonymous `/` → 303 `/login`;
- register → 303 `/`, and the shell renders with the username;
- `reset-password` → the old cookie is refused;
- the temp password logs in → `/account/password`;
- change → `/` renders;
- logout → `/login`, and the cookie is refused afterwards.

## Review follow-up (2026-10-03)

An Opus `/code-review high` of the WP137 commit found ten issues, none breaking the login flow.
Nine are fixed. The tenth is left to WP138.

- **Concurrent hashing could exhaust memory.** Each scrypt holds 128 MiB, and about 40
  thread-pool threads could run one at once. `_scrypt` now takes a slot from a process-wide
  `BoundedSemaphore(2)` (256 MiB peak). A request that waits more than 10 s gets
  `ServerBusyError`, a translated 503, rather than holding a pool thread indefinitely.
- **A bogus invite cost a full hash.** `register` now checks the invite first (cheap, and so that
  without one nobody can probe usernames), then the username, and only then hashes.
  `register_user` still decides both atomically.
- **The username `local` is reserved.** A login to any account no password opens (the local
  user's `!`) now runs the dummy hash, like an unknown user, so a fast answer no longer reveals that
  the account exists. `ensure_local_user` refuses to adopt a real account named `local`.
- **A bad `CHUMMER5_SESSION_DAYS` now stops a hosted start.** Before, it made every login a 500.
  Non-numbers, ≤0, nan, inf and >3650 are refused.
- **A password change no longer counts as a login.** It was stamping `last_login`.
- **One shared timestamp format.** `chummer5.store.stamp()` replaces `accounts._stamp`. The SQL
  expiry checks compare strings, so every writer must use one format.
- **One write transaction per login.** `create_auth_session` purges expired sessions, inserts,
  and stamps `last_login` together (it was three transactions).
- **Dead code removed.** `delete_user_sessions`, and `purge_expired_sessions` once it was folded
  into the login.
- **No hard-coded account paths.** The register routes use `REGISTER_PATH`, and every account
  link and form action in the templates is `url_for(<route name>)`.
- **Left for WP138: hosted chargen sessions outlive a login that ends other than by logout**
  (expiry, an admin reset, a password change from another device). WP138's idle eviction (default
  2 h) covers all of these. Its acceptance should include a session whose login was revoked.

The scrypt cost stays at N=2^17 (128 MiB, OWASP's listed scrypt minimum), now that concurrency is
bounded. OWASP lists N=2^15, p=3 (32 MiB) as equivalent if memory ever matters more. Existing
hashes carry their own parameters either way.
