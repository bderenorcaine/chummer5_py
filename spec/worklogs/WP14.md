# WP14 — Priority & metatype selection UI

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase F, WP14.

## Goal

First real chargen screen: assign priority letters to the 4 MVP categories (Talent forced to E,
not offered as a choice) and pick a metatype; server-side in-memory character-in-progress state
keyed by a session cookie. Acceptance: manual walkthrough creates a metatype+priority selection
that matches what WP6's engine would produce for the same inputs.

## Log

### 2026-07-18 — Building directly on WP6's engine functions, not re-deriving chargen logic in the web layer

The whole point of "rules engine first, UI last" (Project Overview) is that the UI is a thin layer
over an already-correct engine. `src/chummer5/web/app.py`'s `submit_priorities` route calls
`chummer5.engine.character.metatype_choices()` and `create_character()` directly — the exact same
functions WP6's own tests exercise — rather than reimplementing metatype filtering or budget
validation in the web layer. `create_character(choice, heritage_letter, attributes_letter,
PRIORITIES, {})` (empty `attribute_points`) is valid because WP6 deliberately doesn't require full
budget spend (see `spec/worklogs/WP6.md`) — so WP14 can build a real, valid `Character` the moment
metatype + priorities are confirmed, with attribute points still at 0, and WP15 replaces it with a
fuller `Character` once real point-spend exists. This is why the acceptance bar ("matches what
WP6's engine would produce for the same inputs") is satisfiable by construction: the UI doesn't
have a parallel implementation to drift out of sync with the engine, it *is* the engine, called
from a route handler.

### 2026-07-18 — Rulebook check: priority letters must be a no-duplicates assignment, not just an
implementation detail

The Implementation Plan's WP14 entry says "assign priority letters to the 4 MVP categories" but
doesn't spell out the constraint. Went to the legacy C# first (`SelectMetatypePriority.cs`) and
found `ManagePriorityItems`, a letter-swap mechanism triggered on every combo-box change — strong
evidence the "no duplicate letters" rule is real, not a UI nicety. Confirmed directly against the
rulebook (`pdftotext -layout`, "Step Two: Choose Metatype", p. 65): "The values assigned must be
different for each column ... and there can be no duplications." Recorded in
`spec/rulebooks/learnings.md`. Since MVP forces Talent to E unconditionally, the remaining four
columns only ever draw from {A, B, C, D} — `submit_priorities` validates the submitted 4 letters
are exactly that set (`sorted(submitted_letters) != sorted(PRIORITY_LETTERS)`), which is a
simplification of the general 5-letter rule that's exact for MVP's scope (Talent never varies) and
would need generalizing the moment magic/resonance chargen exists.

Didn't replicate the legacy UI's letter-swap auto-correction behavior (when you pick an
already-used letter for one column, the previously-holding column silently gets reassigned the
freed letter) — that's real UX polish but adds meaningful client-side-state complexity for a first
chargen screen. WP14 instead validates server-side and shows a plain error message on a duplicate
submission, redisplaying exactly what the player entered so they can fix it themselves. Simpler,
and nothing in the Implementation Plan's acceptance criteria calls for the swap UX specifically.

### 2026-07-18 — A real FastAPI gotcha: `Depends`-injected `Response` cookies don't merge into a
route that returns a `TemplateResponse` directly

First attempt used the textbook FastAPI pattern — a `get_session(request: Request, response:
Response)` dependency that calls `response.set_cookie(...)` when creating a new session, injected
via `Depends`. Cookie never showed up in the actual HTTP response; two tests failed
(`SESSION_COOKIE_NAME in response.cookies`, and a session-isolation test that relied on the cookie
existing at all). Traced it to `fastapi/routing.py`'s request handler: when the endpoint function
returns an actual `Response` instance (a `TemplateResponse` here, used by every route in this WP),
FastAPI does `response = raw_response` — a full replacement, not a merge — and only the
non-`Response`-returning code path afterward does `response.headers.raw.extend(solved_result
.response.headers.raw)` to fold the dependency-injected response's headers in. Routes that return
a value FastAPI itself wraps into a response (e.g. returning a `dict` for JSON) get the merge;
routes that return their own `Response` object directly don't. Confirmed by reading the source
directly rather than guessing from a stack trace. Fix: dropped `Depends` entirely for session
resolution — `resolve_session(request)` is a plain function each route calls, returning `(session,
new_cookie_value | None)`, and each route calls `.set_cookie()` on the actual `TemplateResponse` it
returns, right before returning it. Documented in `resolve_session`'s own docstring so a future WP
doesn't reintroduce the same bug by "cleaning up" back to the `Depends` pattern.

### 2026-07-18 — Removed WP13's counter demo entirely rather than keeping it alongside

WP13's own worklog said, of the `/ui/counter` placeholder: "a real session-backed endpoint replaces
it once that state exists" — this WP is that replacement. Deleted `templates/index.html` and
`templates/_counter.html`, renamed the page template to `chargen.html` (the `/` route now serves
real chargen content, not a placeholder — "index" no longer described what the page is), and
removed the `POST /ui/counter` route and its tests from `tests/unit/test_web_app.py` (rewritten for
this WP's actual routes; kept the one still-relevant assertion, "HTMX is vendored, not
CDN-loaded").

### Design decisions

- **`ChargenSession` is a plain mutable dataclass with sensible non-`None` letter defaults
  (A/B/C/D across Heritage/Attributes/Skills/Resources) and `metatype_id`/`character` defaulting to
  `None`.** A first-time visitor already sees a legal (if arbitrary) priority assignment to adjust,
  rather than an empty form — mirrors the legacy UI's own `SelectedIndex = 0` default-selection
  behavior on every combo box (checked in `SelectMetatypePriority.cs`).
- **`SessionStore` lives on `app.state.sessions`, created fresh inside `create_app()`, not a
  module-level singleton.** Every existing web test builds its own app via `TestClient(create_app())`
  — a module-level store would leak `ChargenSession` state across unrelated tests. The one test that
  needs two sessions against the *same* store (`test_sessions_are_isolated_per_cookie`) does so by
  wrapping one `create_app()` result in two separate `TestClient`s (two independent cookie jars, one
  shared `app.state.sessions`), not by hand-crafting cookie values — hand-crafting an arbitrary
  cookie string doesn't work with this design anyway, since `resolve_session` treats any cookie
  value with no matching store entry as "create a new session with a server-issued id", so a
  fabricated cookie value is simply discarded rather than adopted.
- **`resolve_session` returns `(session, new_cookie_value | None)` instead of setting the cookie
  itself.** Forced by the `Depends`-injected-`Response` gotcha above — this is the shape that lets
  each route set the cookie on the specific `Response` object it actually returns.
- **`create_character(choice, heritage_letter, attributes_letter, PRIORITIES, {})` (an empty
  attribute-points mapping) builds the confirmed `Character` immediately on metatype+priority
  submission, rather than deferring `Character` construction to WP15.** Reuses WP6's own "spending
  less than the budget is legal" invariant instead of inventing a separate WP14-only
  "provisional selection" data shape that WP15 would have to reconcile with `Character` later.
- **`_priority_form_context`'s letter/metatype-id parameters echo back whatever was just
  submitted (success or error), not the session's last-committed values.** On a validation error,
  the redisplayed form shows the player's actual (invalid) input so they can see and fix exactly
  what they picked, rather than silently snapping back to the last-confirmed state — a plain
  "resubmit and see your own input" UX, not a data-modeling choice.
- **`_metatype_select.html` is a standalone fragment, included by `_priority_form.html` and also
  served directly by `GET /ui/metatypes` for the HTMX swap.** One template backs both the initial
  render and the live update when Heritage changes (`hx-get="/ui/metatypes" hx-trigger="change"
  hx-include="this"` on the Heritage `<select>`), so the two code paths can't drift into rendering
  different markup for the same data.
- **No "karma" figure shown for metatype choices, even though `MetatypeChoice.karma` exists.**
  Checked every Heritage-letter A-D metatype option via `load_priorities()`: karma is 0 across the
  board for priority-based chargen (it's the *karma-build-method* cost, out of MVP scope per the
  Project Overview). Recorded as a WP14 learning rather than silently displaying an always-zero
  field. Only `special_attribute_points` (the number that actually varies and matters for EDG) is
  shown.

### Implementation

- `src/chummer5/web/session.py` (new): `SESSION_COOKIE_NAME`, `PRIORITY_LETTERS` (`("A", "B", "C",
  "D")`), `ChargenSession` (mutable dataclass: 4 priority letters, `metatype_id`, `character`),
  `SessionStore` (`create()`/`get()` over a process-lifetime dict).

  includes `_priority_form.html`.
- `src/chummer5/web/templates/_priority_form.html` (new): the 4 priority-letter `<select>`s +
  metatype `<select>` + submit button, error display, and a confirmed-character summary block.
- `src/chummer5/web/templates/_metatype_select.html` (new): the metatype `<select>` fragment,
  shared between the full form and the HTMX-swapped Heritage-change update.
- `src/chummer5/web/templates/index.html`, `_counter.html` (deleted): WP13's placeholder page and
  its demo endpoint's fragment, both superseded by this WP per WP13's own worklog.
- `tests/unit/test_web_app.py` (rewritten): index page + cookie issuance; default selection is
  already valid; `/ui/metatypes` fragment matches `metatype_choices()` for a given Heritage letter

  rejection; two independent `TestClient`s against one `create_app()` never see each other's

- `spec/rulebooks/learnings.md` (extended, **untracked** — see WP8/WP9's precedent for why
  `spec/rulebooks/` stays gitignored): two new WP14 entries — the no-duplicate-letters rulebook

## Outcome

WP14 complete: the web app's `/` route now serves a real chargen screen — assign priority letters
A-D to Heritage/Attributes/Skills/Resources (validated as a no-duplicates permutation, per the
rulebook's own "there can be no duplications" rule), pick a metatype from the options the chosen
Heritage letter actually offers (live-updated via HTMX when Heritage changes), and confirm to build
a real `Character` via WP6's `create_character()` directly. State persists server-side in an
in-memory `ChargenSession`, keyed by an opaque cookie, isolated per browser session. The notable
non-rules finding: FastAPI does not merge a `Depends`-injected `Response`'s cookies into a route
that returns a `TemplateResponse` (or any `Response` subclass) directly — routes have to set
cookies on the actual object they return instead, documented in `resolve_session`'s docstring so a
future refactor doesn't silently reintroduce a cookie that never reaches the browser.
