# WP142 — Production container, Caddy, backups, runbook

The last Phase Y WP. With it, the hosted app can be deployed: settings, a data volume, backups
(before every deploy, nightly, and off the server), a restore procedure, Caddy without
`basicauth`, and the runbook. The server steps themselves are the user's.

## What landed

- **`chummer5.store.backup`** (new):
  - `backup(store, dir, keep=)`: SQLite's online backup API, into a `.partial` file switched to
    DELETE journal mode and integrity-checked, then renamed to `chummer5-YYYYmmdd-HHMMSS.db` (UTC;
    `-1`, `-2` … within one second). It prunes only its own files.
  - `restore(store, file)`: verifies the file (integrity, a schema version, not newer than this
    code), then copies it over the live database through the same API.
- **Admin CLI:** `backup [DIR] [--keep N]` (default DIR: `backups/` beside the database, i.e.
  `/data/backups`) and `restore FILE [--yes]` (asks for `restore` unless `--yes`).
- **`deploy/deploy.sh`:**
  - It reads `~/chummer5/chummer5.env` on the server and passes it with `--env-file`. Without the
    file it deploys in local mode and says so.
  - It mounts the `chummer5-data:/data` volume, and backs up online before every swap
    (`--keep 30`; skipped quietly for pre-WP142 images).
- **`deploy/backup.sh`** (new): from the user's machine, it takes a backup on the server, streams
  it here with `podman exec … cat`, and checks it with the local `sqlite3` if there is one.
- **`deploy/Caddyfile.example`:** `basicauth` is gone (a comment points at the switch-over). It
  says what Caddy does with `X-Forwarded-For`.
- **`deploy/Containerfile`:** comments updated (why `--forwarded-allow-ips '*'` stays, and the
  volume's ownership comes from `/data`).
- **`deploy/test-image.sh`:** the hosted container runs on a fresh named volume. New checks: the
  database is on the volume, a backup is taken while the app runs, and that backup restores into
  a fresh volume through the documented `cat | restore` path. A third container serves `/login`
  from the restored volume and knows the user registered before the backup. Containers and
  volumes are cleaned up.
- **`spec/deployment.md`** (the runbook):
  - New picture, plus "First deploy" steps 5-9 (settings file, deploy, Caddy, the first invite,
    nightly backups).
  - New sections: "Switching to hosted mode" (from today's basicauth deployment), "Every later
    deploy", "Rolling back" (including across a schema change), "Backups" (the table, a systemd
    user timer), "Restoring", "Logs", and "Settings" (every `CHUMMER5_*` variable).
- **`spec/admin-primer.md`:** the backup and restore commands and a database section. The
  "planned" markers are gone, and the restart/redeploy notes are updated for the volume.
- **Tests:** `tests/unit/test_backup_wp142.py` (8 tests), covering:
  - a consistent snapshot under a concurrent writer;
  - pruning;
  - name collisions;
  - the restore round trip, including writing afterwards;
  - restoring an older schema (migrated on next use);
  - refusing garbage, a foreign database, a newer schema or a missing file;
  - the CLI's confirmation.

  Full suite: 1942.

## Verification

Split as the plan says.

**In the devcontainer** (Caddy 2.6.2, sqlite3):

- Hosted uvicorn ran with the Containerfile's exact flags, behind a Caddy built from
  `Caddyfile.example` (domain replaced by `localhost:8443` with `tls internal`).
- Through Caddy:
  - the CSP passes through, and registration lands on `/characters` with a `Secure` cookie;
  - a character is stored at the priority confirmation, and a `.chum5` upload imports;
  - the download is named `Yeti-_ffffff.json`;
  - a cross-origin POST gets 403;
  - after five failed logins with rotating spoofed `X-Forwarded-For` values, a sixth from
    "another address" is still throttled (429), because Caddy replaced the header.
- A backup taken while 20 Bio edits went through the app:
  - passed `sqlite3`'s integrity check, in DELETE journal mode;
  - restored into a fresh database file;
  - a second hosted instance served `/login` from it and logged in the pre-backup user.

**On the user's host only:** the image build, the volume's ownership on first mount, and the
whole `test-image.sh` run. The devcontainer can't run podman. The new checks were not run here.

## Decisions

See the decisions log (2026-10-03, WP142). In short:

- backup and restore live in the admin CLI;
- the settings live in a file on the server;
- every deploy backs up first;
- the nightly backup is a systemd user timer;
- `CHUMMER5_TRUSTED_PROXY` is moot with the image;
- no version bump.

## Traps hit

- **`Store` switches any file it opens to WAL.** A test that opened a fresh backup through
  `Store` before checking its journal mode saw `wal`. Check with plain `sqlite3` first.
- **Shell state doesn't carry between tool calls.** A second uvicorn started without
  `CHUMMER5_MODE` came up in local mode and wrote the implicit `local` user into the restored
  copy. The check was redone on a fresh copy.
- **Killing scratch servers by command-line pattern matched the invoking shell** (exit 144)
  twice. Match on the executable path at the start of `ps`'s args, collect the PIDs, then kill.
- A username must be 3-32 characters ("gm" isn't one), which only showed in the end-to-end run.
