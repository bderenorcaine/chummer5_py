# WP145 — Priorities redesign: leave-with-unconfirmed-changes dialog

The last WP of the Priorities redesign. A player can no longer leave the Priorities page
believing unconfirmed edits are in effect. Anything that would take the panel off the page while
it is dirty asks first: **Confirm and continue**, **Stay** (the default, and what Escape does),
or **Revert and continue**. A never-confirmed character sees **Discard and continue** instead.

## What landed

- **Server:**
  - `submit_priorities` sends `HX-Trigger-After-Settle: priorities-confirmed`, and only on
    success. That covers both success paths, the ordinary re-render and the first
    confirmation's whole-shell swap.
  - It is *not* `HX-Trigger`. `chummer5.web.app`'s middleware overwrites that header with
    `chargen-changed` on every successful POST, so the first idea in the phase file would have
    been silently lost.
  - After-settle means the swap is finished when the script resumes. htmx dispatches it on
    `body` when the triggering form was swapped away (checked in the vendored 2.0.10 source),
    so the first-confirm path still reaches the listener.
  - A refused first store (quota) and the 409 notices carry no signal.
- **Markup:** `<dialog id="priority-leave">`, the last child of `#priority-section`. It sits
  outside the `<form>`, since forms can't nest, and it never submits. It is re-rendered with the
  panel. Its wording and third button depend on whether a character exists. There are seven new
  `Web_Priorities_Leave*` keys.
- **`static/app.js`**, a WP145 section:
  - **Dirty:** status `changed`, or `unconfirmed` once the player has touched the form, or any
    edit newer than the last preview answer (the dirty window).
    - Edits are counted from the WP144 widgets (`requestPriorityPreview`) and from the Metatype
      and method dropdowns. Those are counted in the capture phase, so the count goes up before
      htmx sends the request the change triggers.
    - Each preview request records the count it went out with, and its swap marks that count
      answered. A panel arriving (navigation, method switch, Revert, CONFIRM) answers
      everything.
    - "Touched" survives the panel's own method switch and CONFIRM responses. It resets on
      Revert and on any other load of the panel.
  - **Triggers:**
    - `htmx:confirm`, capture phase: any request from outside the panel whose target contains
      the panel (step nav into `#page`, whole-shell swaps). Also any non-GET from outside it
      (the "New character" switch, which the server retargets onto the shell). Display
      preferences (`/ui/prefs/`) and background refreshes of other regions are excluded.
    - `click`, capture: plain same-tab links (the character list, the account page, the
      footer's links).
    - `submit`, capture: plain forms (logout).
    - `popstate`: the back and forward buttons.
    - `beforeunload`: reload, closing the tab, typed URLs. These get the browser's generic
      prompt.
  - **Confirm and continue:** submits the form through htmx (`requestSubmit`). It resumes only
    on the `priorities-confirmed` event. If the response doesn't carry the signal (an error, a
    refused store, a 409), the player stays and the error shows at the bottom as usual. The
    dialog's Confirm is enabled only while `data-priority-confirmable` is `true` *for the latest
    edit*. It re-syncs if a preview lands while the dialog is open.
  - **Revert/Discard and continue:** just continues. Nothing server-side changed, and the
    navigation replaces the panel.
- **Tests:** 12 more in `test_web_priorities_redesign_wp143.py`:
  - the dialog's markup, in both variants and after every kind of panel render;
  - the signal on both success paths, beside `chargen-changed`;
  - no signal for each kind of failed confirmation, including a quota refusal;
  - that the script still hooks every trigger.

  Full suite: 2024.

## Traps, and how they were handled

- **Coexisting with `tabs.js` (WP138).** Both listen to `htmx:confirm`. tabs.js loads first, so
  its bubble listener would run first. This one listens in the *capture* phase and, when it
  asks, calls `stopPropagation`, so tabs.js never sees that action. Continuing calls
  `issueRequest(true)`, which skips htmx's own `hx-confirm` as well. One action, one dialog.
  The cost: "New character" from a dirty Priorities page doesn't also give the multi-tab switch
  warning. When the panel isn't dirty, tabs.js behaves exactly as before.
- **The first confirmation replaces the shell**, so the control that started the navigation is
  detached. The resume function issues the held request if its element is still in the
  document. Otherwise it clicks the matching control in the new shell (same `hx-<verb>` and
  path). By then the panel is confirmed, so that click passes through. For a plain form (logout)
  it submits the new shell's copy, found by `action`.
- **The back button.** htmx assigns `window.onpopstate` at DOM-ready. `app.js` runs in `<head>`
  and adds its `popstate` listener earlier, so it runs first (handler-property listeners sit
  where they were first assigned) and `stopImmediatePropagation` stops htmx's restore. The
  listener pushes the Priorities URL back on top, with `{htmx: true}` so a later back still
  restores it, then asks. Continuing calls `history.back()` with a pass-through flag. The entry
  right under the one just pushed is where the player was headed, whether they pressed back or
  forward. **This is the least certain part** and can't be exercised here. If it misbehaves in
  a browser, the fallback the phase file allows is the `beforeunload`-style behaviour.
- **The language picker reloads the page** (WP101), so with a dirty panel it raises the
  browser's generic prompt. The phase file exempts the pickers from the custom dialog because
  they "don't leave the page". The theme picker doesn't. The language picker does reload, and
  silently dropping the edits there would be the failure this WP exists to prevent.
- **No `<dialog>` support** (pre-2022 browsers): the navigation simply proceeds, as before WP145.

## Manual browser checklist — not run here

Use a confirmed character ("changed" state) **and** a never-confirmed one ("unconfirmed" after
touching a tile, spinner, metatype or method) for each trigger:

1. **Step nav link** → dialog. Stay: nothing changes, the edits remain. Escape: the same.
   Revert: the target step opens, and Priorities, revisited, shows the confirmed state.
   Confirm: confirms, then opens the target step.
2. **Character list link and the account (password) link** → dialog, the same choices. A footer
   link opens in the same tab after continuing.
3. **Logout** (hosted mode) → dialog. Continue logs out.
4. **"New character"** (confirmed character, changed state) → only *this* dialog, never the
   multi-tab switch warning on top of it. Continuing creates the new character.
5. **No dialog when clean:** a fresh visit with no edits, right after a confirm, after Revert, and
   for an untouched never-confirmed page. Theme changes never ask.
6. **The dirty window:** make an edit and click a nav link within ~100 ms. The dialog appears
   (it must not slip through on the old status).
7. **Confirm disabled when not confirmable:** Sum-to-Ten off target, or "Choose metatype".
   Confirm in the dialog is greyed out, and Stay/Revert work.
8. **Confirm with a server error:** e.g. at the character quota on a first confirm. The dialog
   closes, the player stays, and the error shows at the bottom of the panel.
9. **First confirm through the dialog** (never-confirmed character, nav link): the shell is
   replaced, the title bar shows the stored character, and the target step opens.
10. **Back button** while dirty: the dialog appears and the URL stays on Priorities. Stay keeps
    everything. Continue goes back to the previous step. Then press back and forward again: the
    history still makes sense.
11. **Reload, closing the tab, typing a URL, and changing the language** while dirty: the
    browser's own "leave site?" prompt.
12. Look at the dialog in all four themes, light and dark, and at phone width.
