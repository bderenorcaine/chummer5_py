# WP147 — Qualities redesign: budget boxes, split table, autosave only

Third Phase Z redesign, the first without a sketch: the phase file's "Redesign 3" defaults, built
on WP146's Attributes page. No client script changed: the existing `change` / `number-input`
triggers still drive autosave.

## What landed

- **`_quality_selection.html`**: no `<details>` wrapper; a plain `<h1 class="page__heading">`
  ("Qualities", `String_Qualities`); two budget boxes (Positive, Negative) showing
  `remaining/25`; the "free from metatype" line; a Positive and a Negative table, each in its own
  `<section>` with a small heading and without the Category column; the Mentor Spirit fieldset as
  before; no submit button; error and stale-pick warning moved below the form.
  `#quality-selection` is still the swap target. Every input name is unchanged, so
  `_submitted_picks` and `submit_qualities` are untouched.
- **`routes/qualities.py`**: the context now carries `positive_rows` / `negative_rows` (split
  server-side from `_quality_rows`, not filtered in Jinja) and `positive_remaining` /
  `negative_remaining`; `quality_rows`, `positive_karma` and `negative_karma` left the context
  (nothing else read them). Each row gets a `dom_id`.
- **Stable ids**: `quality-<id>`, `quality-rating-<id>`, `quality-choice-<id>`,
  `quality-text-<id>`, plus `mentor-archetype`, `mentor-general-<option id>`,
  `mentor-skill-choice`, `mentor-power-target-<n>`. A repeat instance's row key is `<guid>:<n>`
  (`_row_key`); the id swaps `:` for `_`. Quality ids are GUIDs and never contain `_`, so ids stay
  unique. Vendored htmx 2.0.10 restores focus with `getElementById`, so any id character would
  have worked; `_` just keeps the ids safe for CSS selectors too.
- **i18n**: legacy `Label_SummaryPositiveQualities` / `Label_SummaryNegativeQualities` ("Positive
  Qualities" / "Negative Qualities", with real translations, e.g. German "Vorteile"). They are in
  the same family as WP146's `Label_SummaryPrimaryAttributes`, and serve as both box labels and
  section headings. The phase file suggested `String_SelectQuality_XPathQuery_*` (same English),
  but those are filter-menu labels; the summary keys fit better. Removed
  `Web_Qualities_PositiveKarma`, `Web_Qualities_NegativeKarma` and `Web_Qualities_Update`.
  `Web_Qualities_ColCategory` stays: the knowledge-skills table and the character sheet use it.
- **CSS**: WP146's `.attribute-budget*` classes became a shared "Budget boxes" section
  (`.budget-boxes`, `.budget-box`, `__label`, `__hint`, `__value`, `--over`), with the Attributes
  template and its tests updated in the same commit. The grid now uses `grid-auto-flow: column`
  with equal auto columns instead of a fixed `repeat(3, …)`, so it fits both two and three boxes.
  A new "Qualities page (WP147)" section: the 40rem column (same as Attributes; whether the
  five-column table fits at that cap without scrolling is on the browser checklist), the section headings, and per-table `overflow-x: auto` wrappers.
- **Tests**: seven old assertions on the "Positive/Negative Quality karma: x / 25" sentence now read
  the box values (remaining = 25 − spent). New `test_web_quality_page.py`: boxes start full and
  count down per pool, the over modifier per pool, every offered quality in exactly its own
  section, a repeatable negative quality's "add another" row in the Negative section, no submit
  button / no `<details>`, messages after the Mentor fieldset and `</form>`, unique and stable ids
  on every control including `_1`/`_2` repeat instances, the mentor ids. Full suite green
  (2037 passed); ruff and mypy clean.

## Follow-up: category dropdown (user ruling, 2026-10-17)

After the first landing, the user asked to switch between Positive and Negative with a dropdown,
like the Priorities method dropdown, instead of stacking both tables.

- **The dropdown is inside the form** (`name="quality_view"`, `id="quality-view"`), unlike
  Priorities, whose method dropdown deliberately sits outside its form. Here, switching *should*
  be an ordinary autosave POST. `submit_qualities` reads the view (anything unknown → Positive),
  and the re-render shows that category. So the switch needs no new endpoint and no script, keeps
  an error echo's unsaved picks, and keeps the view across every later autosave swap, because the
  select posts its value each time.
- **The other category stays rendered, with `hidden`.** This is the trap: if the inactive
  section were left out of the markup, the next autosave would post only the visible category's
  checkboxes and silently drop every pick in the other one. Hidden controls still submit. A test
  posts both categories' picks while viewing Negative and checks both stay committed.
- **The Mentor Spirit fieldset** is a Positive-quality detail, so it is `hidden` under Negative
  (and still posts).
- The section `<h2>` headings went: the dropdown names the category. The dropdown's options reuse
  `Label_Summary{Positive,Negative}Qualities` as literal keys (not built from the view name, so
  the literal-key i18n test sees them). It has a new `aria-label` key, `Web_Qualities_View`
  ("Quality type"). The CSS mirrors `.priority-page__method`.
- The view always opens on Positive when the player navigates to the page. It isn't kept in the
  session.

## Traps hit

- Unlike Attributes, an overspent box *is* reachable by posting: a rejected post re-renders the
  submitted picks (error echo), and the boxes count those. The tests use that path
  (Catlike + Lucky + Gearhead = 30 Positive; Uncouth + Insomnia (Full) = 29 Negative).
- Negative qualities store negative `karma`; the context already turns it into a positive
  magnitude, so `negative_remaining` is `25 − magnitude`. A test spells out the sign
  (`25 + Uncouth.karma`).
- The class rename shortened a line in the Attributes tests enough for `ruff format` to rewrap
  it; formatted as part of this WP.
