# WP148 — Skills redesign: tab strip, counters, active-skill tabs, specialization toggle

Fourth Phase Z redesign (`examples/ui/skills.png`), first of three WPs. This one covers the strip,
the counters, every active-skill tab, the Group and Special tabs, and the specialization toggle.
The Knowledge tab still shows the old knowledge fragment (WP149). Filtered, Rated and the portrait
dropdown are WP150.

## The tab mechanism: view tabs, not sub-tabs

WP98's tabs are one `PageSection` (= one fragment) per tab. That doesn't fit here. Ten tabs show
panels of two fragments: nine show part of `_skill_allocation.html` and one shows
`_knowledge_skills.html`, and WP150's Filtered/Rated will show parts of both. Splitting the active
form into nine fragments would have meant nine forms and nine POST routes.

So `shell.py` gained a second kind of tab, `PageTab`. It is a *view* onto the page's fragments.
`StepPage` got `tabs`, `tab_strip` (the strip template) and `tab_aliases`:

- The Skills page has `tabs=SKILLS_TABS`. Its two sections are mounted unwrapped (no
  `<section class="subpage">`), like a single-section page, and `StepPage.tabbed` is now false for a
  page with view tabs. Every WP98 code path (`resolve_tab`, `tabs_context`, `_page_tabs.html`)
  therefore runs only for Magic and Equipment. Their tests are unchanged apart from dropping
  Skills from their table.
- `_page.html` includes `page.tab_strip` (`_skills_tabs.html`) when it is set. Each fragment
  reads `skills_tab` and shows the matching panel. The other panels are `hidden` and stay in the
  form, so every autosave still posts every row.
- `GET /ui/page/skills/{tab}` accepts a view-tab slug or an alias (`active` → `combat`).
  `GET /ui/tabs/skills?tab=…` re-renders the strip for that tab. The strip's own `hx-get` carries
  the tab it was rendered for, so the refresh needs no session state, and the page remembers no
  tab: per the phase file, a nav click opens Combat.
- Each fragment's POST carries a hidden `skills_tab`. The skills route validates it against its
  own panel list (`SKILLS_TAB_SLUGS`, falling back to Combat). The route can't import `shell.py`,
  because `shell.py` imports it. The knowledge fragment defaults to visible when `skills_tab` is
  absent, which is the case for its own POST response.
- **Stale markers and issue links.** `PageTab.warning_keys` mark a tab the way a section's did.
  Combat carries `skill_budget_warning`, the page's landing tab, where the warning shows under the
  panel, and Knowledge carries `knowledge_budget_warning`. `validation_issues` asks
  `page.tab_for_warning(key)` for a page with view tabs. In `engine/validation.py` the
  unspent-group-points issue now names the `group` tab instead of `active`. The skill-points issue
  still says `active`, which resolves to Combat through the alias.
- **The knowledge sub-tab is retired already** (planned for WP149). With view tabs there is no
  sub-tab label left to show, so `Web_Tab_ActiveSkills` and `Web_Tab_KnowledgeLanguages` went now.
  The `knowledge` PageSection stays as the page's second fragment. In this design "section" means
  "fragment mounted on the page", not "tab". The `knowledge` slug is the Knowledge tab's own slug.

## Counters

`skills_tabs_context` builds S, G, Ka and Kn from the same committed figures as the resource panel
(`chargen_ctx["skills_remaining"]` and the rest; Ka is `character.karma_remaining` / 25). Each
counter is `remaining/of`, with `--over` below 0. S and G sit absolutely in the corner the first
tab's slant leaves free. Ka and Kn are a sibling of the filler, not its child, because the filler
is skewed and would skew them too.

So the old per-section figures are gone. The skills fragment no longer shows its own
"Karma remaining for skills: x / (25 − other sections' spend)" budget. Ka is the character's
leftover Karma, as the phase file says. Six tests that read the old sentences now read the counter
from `/ui/tabs/skills`, which is exactly what the browser does after an autosave. The WP60
regression test now checks that Ka shows the leftover after both an attribute and a skill Karma
spend.

## Panels and the toggle

- `_skill_allocation_context` groups rows into `skill_panels` (one per `CATEGORY_TABS` entry, in
  tab order) and `exotic_rows`. The sort is now by name only, because the Magical panel spans two
  categories and Arcana (Pseudo-Magical) would otherwise sort after every Magical Active skill.
- Each row has one specialization (`spec`), plus `spec_karma` and `spec_forced`. Forced means
  "own points < 1". That one test covers both p. 129 (you need the skill first) and p. 88 (a
  grouped skill can't be specialized in Step Five), because the engine already rejects own points
  alongside group points.
- `_parse_specializations` in the route applies **the same rule at parse time**: text goes to the
  Karma map when the toggle field is present *or* the skill has no point of its own in this
  submission. Without that, setting a specialized skill's points back to 0 would post the
  specialization as point-funded, and the engine would reject the whole form. The hidden
  `spec_karma_<id>` beside a disabled checkbox is still rendered, as the phase file asks, but the
  parse doesn't depend on it.
- **Behaviour change:** a specialization typed on a group-bought skill used to be rejected
  ("cannot add a specialization", WP50's test). Now it is a Karma specialization that breaks the
  group (WP53, 7 Karma). The old test was rewritten to say so. A specialization on an entirely
  unrated skill is still rejected (the Karma path needs a rating too).
- **Special tab:** an existing instance shows its Detail as plain text. Editing it would rename the
  instance key, so it isn't a field. The add row appears after **Add Special Skills**
  (`type="button"`, `hx-post` with `hx-vals='{"exotic_add": "1"}'`; JSON `hx-vals` needs no eval,
  so the CSP and `allowEval: false` are fine). The row stays while it holds anything, and closes
  once it commits. The add-row inputs gained ids and `aria-label`s.
- **Group tab:** Group Name (legacy `Skill_SortGroupName`), Components (member skills in catalog
  order, joined with `Web_List_Separator`), Group Points, Ka pts, and Rating (group points + Karma
  group points).
- **Resonance panel:** always empty. If reached by URL, it says "Technomancers are not supported
  yet." (`Web_Nav_ResonanceUnsupported`, reused).

## Arcana for Mundane characters

`offered_skills` adds `_PSEUDO_MAGICAL_SKILLS` for a Mundane character. `skill_purchase_rules`
blocks nothing for a mundane character, Arcana has no group (so `MUNDANE_SKILL_GROUPS` is
unchanged), and the free magic skill grant still uses `MAGICAL_SKILL_CATEGORIES`. The WP61
comment in `catalogs.py` now points at the 2026-10-25 decisions-log entry, which was written when
the WP was scoped.

## Placeholders and ids

- `first_example(skill)` returns the first suggested specialization **not in brackets**. The data
  has template entries such as `[Focus Type]` and `[Type]` (Disenchanting has nothing else), and
  "e.g. [Type]" would mislead. No usable example means no placeholder. Exotic Melee Weapon has no
  specializations in the data, so its Detail placeholder uses `Web_Skills_ExoticMeleeExample`
  ("Monofilament Whip"). Examples go through `dterm("skills.xml")`.
- `dom_id(key)` keeps a GUID as it is. Anything else, meaning an exotic key (`id|free text`) or a
  group name with a space, becomes `x` + the key's UTF-8 hex. That form is valid, CSS-safe and
  injective, so two keys can't collide.

## Traps hit

- `app.css` may not declare custom properties (`test_app_css_is_structure_only`: themes own every
  `--token`). The strip's 5rem/2.2rem sizes are literals, with a comment.
- The no-bare-text test flags multi-word string literals in web modules, including the category
  names.
- The old filter box and the "rated only" checkbox are gone, so their two tests went with them.
  WP150 brings both back as tabs. `applySkillFilter` in `app.js` is a harmless no-op until then
  (it returns early when `#skill-filter` is missing).
