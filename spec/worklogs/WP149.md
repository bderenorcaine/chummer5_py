# WP149 — Skills redesign: Knowledge tab (Knowledge and Language skills)

Second of the three Skills WPs. Knowledge & Languages became the Skills page's Knowledge tab: one
table, in which Language is one more category.

## What landed

- **`_knowledge_skills.html`**: one panel inside WP148's mechanism. `#knowledge-skills` is still
  the swap target (now `class="skills-fragment"`, like the active-skills fragment, not `.panel`),
  and a hidden `skills_tab=knowledge` is sent with every post. Columns: Name, Category (the four
  knowledge categories plus Language), Attribute (the category's linked attribute, "—" until one
  is chosen), Native, Kn pts, Ka pts, Rating, Specialization (WP148's toggle plus a text field),
  and Pool. Native is enabled only on a Language row, but its cell is always there. A native row's
  Kn/Ka inputs are disabled, because a native language has no rating to buy and the engine
  rejects Karma on one. The rows end in one blank row. **Add Knowledge Skill** (`type="button"`,
  `hx-vals='{"knowledge_add": "1"}'`) adds another, up to `MAX_KNOWLEDGE_TABLE_ROWS` (12 + 4,
  counted together). At the cap the button is disabled but stays in place. No `<details>`, no
  submit button; messages sit under the form. The budget sentences went. Kn and Ka are WP148's
  counters, and one help line states the Active points Knowledge uses past its free pool.
- **`routes/knowledge.py`**: `KnowledgeRow` (one table row), `_parse_rows` (the one
  `knowledge_*_<i>` series, trailing blank rows dropped), `_sort_rows` (sorts rows into
  `KnowledgeSkillPick` / `LanguageSkillPick` by category, plus the name-keyed Karma and
  specialization maps), `rows_from_picks` (committed picks back into rows),
  `_row_context` (pool, attribute, placeholders). The `language_*` fields and
  `_parse_languages` / `_parse_karma_points_by_name` / `_parse_text_by_name` are gone. The engine
  types and save format are unchanged, so saved characters load as before.
- **`data/skills.py`**: `load_knowledge_skills()` reads `skills.xml`'s `<knowledgeskills>`
  (195 entries, no `<source>` tags) with the same `_parse_skill`. It is exposed as
  `catalogs.KNOWLEDGE_CATALOG` and used only for placeholders. `first_example` moved from the
  skills route into `catalogs.py` so both routes share it.

## Decisions

- **Row order: page render vs. autosave echo.** The phase file asks for session order (Knowledge
  skills, then Languages) *and* for indexes that don't move when a row's category changes. The two
  conflict: re-sorting after the autosave that turns row 0 into a Language would move it to the end,
  and every id below it would then point at a different row, so htmx would restore focus into the
  wrong field. So only a page render uses session order. An autosave echoes the rows exactly as
  posted, interior blanks included. Nothing moves while the player edits, and the next page visit
  shows the tidy order.
- **A name may be on one row only** (`Web_Knowledge_DuplicateName`). The engine keeps Knowledge
  skills and Languages in separate lists and keys Karma and specializations by name, so "Elven"
  as both a Language and an Academic skill was legal until something name-keyed referred to it.
  With one table, a repeated name is refused up front instead.
- **The toggle's forced rule for knowledge:** Karma only when the row is not native and has no
  Kn-points rating (WP125's `_check_specialization`: a point-funded specialization needs rating
  1+ or a native language). `_sort_rows` applies the same rule.
- **Native drops with the category.** `_parse_rows` counts `knowledge_native_<i>` only on a
  Language row, so a row switched away from Language loses its Native flag even if a stale checkbox
  posts.
- **Placeholders.** For a blank name, a catalog entry from the row's category (or from the whole
  catalog when no category is set), picked by row index, so neighbouring rows differ. For the
  specialization, the first unbracketed suggestion of the entry whose name matches, ignoring case.
  An unmatched Language row gets Read/Write. Any other unmatched name gets nothing.
- The WP149 entry's "remove the `knowledge` PageSection" was already settled by WP148's design (see
  its worklog and the decisions log): the knowledge fragment stays the page's second section, and
  the sub-tab labels are already gone.

## i18n

New: `Web_Knowledge_Help`, `Web_Knowledge_ActivePointsUsing`, `Web_Knowledge_ColKnowledgePoints`
("Kn pts"), `Web_Knowledge_Add`, `Web_Knowledge_DuplicateName`. Reused: legacy
`Skill_SortCategory` ("Category") and `String_Name`; WP148's `Web_Skills_Example` and
`Web_Skills_ColKarmaPoints`. Removed: `Web_Knowledge_CategoryExamples`, `ActivePointsHelp`,
`ActivePointsUsed`, `FreeRemaining`, `FreeformHelp`, `KarmaHelp`, `KarmaRemaining`,
`KnowledgeSkills`, `LanguageSkills`, `SuggestedLanguages`, `Update`, and WP148's leftovers
`Web_Skills_ColKarmaSpec` and `Web_Skills_SpecPlaceholder`. `Web_Knowledge_Heading`,
`Web_Knowledge_NativeMarker` and `Web_Qualities_ColCategory` stay, because the character sheet uses
them.

## Tests

`test_web_knowledge.py` and `test_knowledge_wp125.py` now post Language rows as `knowledge_*`
rows with category Language, and read Kn/Ka from the strip's counters. New
`test_web_knowledge_tab_wp149.py` (10): the merged columns and Native enabled only on Language
rows; a row switched to and from Language committing to the right list, with Native dropped; the
native limit; the duplicate-name refusal; Add Knowledge Skill up to the combined cap (button
disabled, still present); the toggle committing a knowledge and a language specialization to the
right map, plus the forced case; placeholders (matched ignoring case, unmatched Language,
unmatched other, category-picked blank row, neighbours differing); Knowledge spending Active points
showing in S; index-based ids and the echo keeping the posted order, with a page render in session
order; no submit button and no `<details>`; messages after the form. Full suite green (2079);
ruff and mypy clean.
