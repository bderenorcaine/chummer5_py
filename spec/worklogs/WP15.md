# WP15 — Attribute & skill allocation UI

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase F, WP15.

## Goal

Spend attribute/skill points through the browser. Deliverables: point-spend forms with
HTMX-driven live remaining-points and dice-pool preview. Acceptance: manual walkthrough; values
match engine output for the same inputs.

## Log

### 2026-07-18 — Same "UI is a thin layer over an already-correct engine" precedent as WP14, applied twice

`POST /ui/attributes` calls `chummer5.engine.character.create_character` directly with the
submitted attribute-point mapping; `POST /ui/skills` calls
`chummer5.engine.skills.create_skill_allocation` directly with the submitted skill/group-point
mappings. Neither route re-derives budget math, the metatype-range cap, the chargen rating cap
(6), or the "strict skill groups" rule in the web layer — those are exactly the validations WP6/
WP7 already implemented and tested. This is what makes the WP's own acceptance bar ("values match
engine output for the same inputs") true by construction rather than something to separately
verify: the UI *is* the engine, called from a route handler, same as WP14's worklog already
established for `submit_priorities`.

### 2026-07-18 — A `MetatypeChoice` for `create_character` doesn't need re-deriving from the
Heritage/metatype catalog

`create_character`'s signature takes a `MetatypeChoice` (metatype + special_attribute_points +
karma), not just a `Metatype`. WP14's `submit_priorities` builds one by cross-referencing
`metatype_choices(heritage, METATYPES)` against the submitted metatype id, because at that point
nothing else exists yet. `submit_attributes` doesn't need to repeat that lookup: reading
`create_character`'s body shows it only ever reads `metatype_choice.metatype` and
`metatype_choice.special_attribute_points` (`karma` is unused inside the function) — both are
already stable fields on the session's own committed `Character` (set once at metatype
confirmation and never mutated by an attribute-only edit). So `submit_attributes` just constructs
`MetatypeChoice(metatype=session.character.metatype,
special_attribute_points=session.character.special_attribute_points, karma=0)` directly off the
existing `Character`, with no priority-table/metatype-catalog lookup at all. Confirmed by reading
`create_character`'s source before relying on this (not by inference) — flagging the reasoning
here so a future WP doesn't reintroduce the heavier lookup out of caution.

### 2026-07-18 — Mundane characters can never benefit from MAG/RES-linked skills, so they're
excluded from the allocation UI (not an engine change)

`skills.xml` has 12 skills linked to `MAG` or `RES` (Alchemy, Artificing, Banishing, Binding,
Compiling, Counterspelling, Decompiling, Disenchanting, Registering, Ritual Spellcasting,
Spellcasting, Summoning), all with `can_default = False`. MVP forces Talent to "Mundane"
(Project Overview's MVP scope) unconditionally, so a fresh character's `MAG`/`RES` attribute
values are always 0 and nothing in MVP's scope can raise them (no Talent choice, no magic
Improvements). `dice_pool()` doesn't crash for these — `character.attribute_value("MAG")` just
resolves to the metatype's `MAG` minimum (0 for every SR5 core metatype) — but the resulting pool
is permanently `rating + 0` with no defaulting fallback, i.e. a pick that can never do anything
useful for an MVP character. `chummer5.web.app.MUNDANE_SKILLS`/`MUNDANE_SKILL_GROUPS` filter these
out of what the allocation UI offers, for the same "excluded, not silently offered-but-broken"
reason WP2/WP3 exclude non-`SR5`-sourced metatypes/qualities from their catalogs. This is
deliberately a UI-layer curation, not a change to `create_skill_allocation` itself, which stays
fully generic (it would still accept points on a magic skill if a request bypassed the UI and
submitted one directly) — the exclusion belongs in the web layer because it's about what's worth
*offering* a mundane-only MVP player, not a rules validation the engine itself is responsible for.
Not a new rulebook citation (this follows directly from the Project Overview's existing "mundane
characters only" MVP-scope decision, not a fact that needed extracting from the PDF), so recorded
here rather than in `spec/rulebooks/learnings.md`.

### 2026-07-18 — Priority form's HTMX target had to widen from its own form to the whole
three-section body, and both the success *and* error paths of `submit_priorities` had to follow

WP14's `_priority_form.html` targeted only its own wrapper div. WP15 needs re-confirming
priorities to reset the (now potentially stale) attribute/skill sections too — a changed
Attributes or Skills letter invalidates whatever points were already spent against the old budget,
and a changed metatype invalidates attribute ranges. The natural fix is to widen the form's
`hx-target` to a new outer `#chargen-body` wrapper (`_chargen_body.html`, wrapping
`_priority_form.html` + `_attribute_allocation.html` + `_skill_allocation.html`) and have
`submit_priorities` reset `session.character`'s attribute points (already true — WP14's own
`create_character(choice, ..., {})` call already zeroes them) and `session.skill_allocation`
(new: set to `None`) on a successful submission.

The easy-to-miss part: HTMX resolves `hx-target` against the *current page's* DOM, then replaces
that element's `outerHTML` with whatever the response body contains — it does not care what the
response's own root element's `id` is. First pass only widened the target on the *success* path
and left the *error* path (duplicate-letter, metatype-not-offered) still rendering just
`_priority_form.html`. That would have swapped `#chargen-body`'s `outerHTML` with a bare
`<div id="priority-section">...</div>` on every validation error — silently deleting the
attribute/skill sections from the page (they'd only come back on the next full `GET /`). Caught
this before writing any test, by re-reading the swap semantics rather than assuming symmetry
between the two branches. Fix: `submit_priorities` now builds `_chargen_body_context` and renders
`_chargen_body.html` unconditionally (see `app.py`'s inline comment), with the error case's
`priority_ctx` alone carrying the echoed invalid submission while the attribute/skill portions of
the merged context reflect the session's untouched, still-committed state.

### 2026-07-18 — Echo-the-submission on error, mirrored from WP14, applied to both new forms

Same choice WP14 made for the priority form: on a validation error (over budget, over the
chargen rating cap, the strict-skill-groups conflict, ...), the redisplayed form shows exactly
what the player typed — not the last-committed values — so they can see and fix their actual
input. Implemented via a "display-only" construction that bypasses the engine's own validation:
`_attribute_allocation_context` builds its preview `Character` with `dataclasses.replace(character,
attribute_points=...)` rather than calling `create_character` again (which would raise on the very
input being displayed); `_skill_allocation_context` builds a throwaway `SkillAllocation` directly
from the submitted mappings for the same reason. `attribute_value()` still clamps to the metatype
maximum internally, so an over-budget preview shows a sane capped number rather than something
nonsensical — the *budget remaining* figure (computed separately, from the raw un-clamped
submitted points) is what actually goes negative and signals the problem.

### Design decisions

- **No client-side JS for the strict-skill-groups conflict.** A skill whose group also has points
  spent isn't disabled or greyed out in the form; submitting that combination just returns the
  engine's own `ValueError` message ("... cannot spend points directly while its group ... also
  has points spent (strict skill groups)") as the displayed error. Matches this project's existing
  "validate server-side, show a plain error, let the player fix it" pattern (WP14's duplicate-
  letter handling) rather than adding client-side state-tracking complexity for a first pass at
  this screen.
- **No specialization UI.** `chummer5.engine.skills.dice_pool`'s `specialized` parameter is a bare
  `bool` with no backing state on `SkillAllocation` (a deliberate WP7 scope cut — see
  `spec/worklogs/WP7.md`: specialization *cost* was never implemented, only the pool-formula
  bonus). WP15's dice-pool preview always calls `dice_pool(..., specialized=False)` — there's
  nothing in the engine yet for a specialization checkbox to feed into, so adding one would be UI
  for a feature the engine doesn't have. Revisit when/if a future WP adds specialization purchase
  to the engine.
- **`_parse_points` treats absent/zero/unparseable form fields identically (all "no entry" in the
  resulting sparse dict), but does *not* filter out negative values.** Matches the "absence means
  0" convention `attribute_points`/`skill_points`/`group_points` already use elsewhere in the
  engine; negative values are deliberately passed through so the engine's own "points spent must
  not be negative" check produces the rejection, rather than this function silently absorbing
  input the engine is already responsible for validating. Malformed non-integer input (a
  hand-crafted request bypassing the `<input type="number">` constraint) is silently dropped as
  "no entry" rather than surfaced as an error — a plain web-robustness choice, not a rules
  decision, since a real browser input never sends non-numeric text for these fields.
- **`_chargen_body_context` merges three per-section context dicts with `{**a, **b, **c}` rather
  than nesting them.** The only key both the priority section and the two new sections would
  naturally share is `"character"` — deliberately kept as a single shared key rather than
  namespaced (`attribute.character`, `skill.character`, ...) because on every code path that calls
  this merge function, all three sections' `character` value is either the same object or an
  equal-by-field `dataclasses.replace` copy of it (see the echo-on-error note above), so there's no
  actual divergence to protect against by namespacing. `"error"` deliberately *is* namespaced
  (`attribute_error`/`skill_error`, vs. the priority form's plain `error`) since those three error
  messages are genuinely independent and none should silently mask another.
- **Skill group form-field names use the raw group name (`group_Close Combat`, spaces and all),
  not a slugified version.** HTML `name` attributes containing spaces round-trip correctly through
  standard form URL-encoding (browser encodes the space on submit, Starlette decodes it back) —
  confirmed by testing rather than assumed, since it looked risky at first glance. Avoided adding
  a slug/reverse-slug-lookup layer for 11 group names that don't actually need one.

### Implementation

- `src/chummer5/web/session.py` (extended): `ChargenSession` gains `skill_allocation:
  SkillAllocation | None = None`; docstring extended to document the reset-on-reconfirm rule.
- `src/chummer5/web/app.py` (extended): `SKILLS` (module-level, parsed once), `MUNDANE_SKILLS`/
  `MUNDANE_SKILL_GROUPS` (MAG/RES-linked skills filtered out, see above); `_parse_points()` (sparse
  form-field parsing); `_attribute_allocation_context()`/`_skill_allocation_context()` (context
  builders for the two new fragments, both taking the *values to display* as explicit parameters
  rather than reaching into session state themselves, so they work identically for a clean render
  and an error-echo render); `_chargen_body_context()` (merges all three sections' context for
  `GET /` and a `POST /ui/priorities` response); `POST /ui/attributes` and `POST /ui/skills`
  routes (async, read `request.form()` directly rather than named `Form(...)` parameters, since
  the field set is data-driven — 9 attribute codes, ~64 skill ids, 11 group names — not a fixed
  small set FastAPI's per-parameter `Form(...)` binding fits well); `submit_priorities` extended to
  reset `session.skill_allocation` on success and to render `_chargen_body.html` on *every* path
  (error included — see the HTMX-target note above).
- `src/chummer5/web/templates/_chargen_body.html` (new): wraps the priority form, attribute
  allocation, and skill allocation fragments in one `#chargen-body` div — the priority form's own
  `hx-target`.
- `src/chummer5/web/templates/_attribute_allocation.html` (new): 9-row table (8 primary + EDG)
  with a point-spend `<input>`, computed value, and metatype range per attribute; remaining-budget
  line for both the primary and special-attribute-points pools; `hx-trigger="change, input
  delay:400ms"` for a live-typing update without spamming a request per keystroke.
- `src/chummer5/web/templates/_skill_allocation.html` (new): a skill-group table (11 mundane
  groups) and an individual-skill table (the ~64 mundane skills: name, linked attribute, group
  membership, point-spend input, computed rating, computed dice pool); same remaining-budget lines
  and HTMX trigger pattern as the attribute form.
- `src/chummer5/web/templates/_priority_form.html` (modified): outer wrapper id renamed
  `chargen-form` → `priority-section` (no longer its own HTMX swap target); its own `<h2>` moved in
  from `chargen.html`; form's `hx-target` retargeted to `#chargen-body`.
- `src/chummer5/web/templates/chargen.html` (simplified): now just includes `_chargen_body.html`
  under a bare `<h1>`.
- `tests/unit/test_web_attribute_skill_allocation.py` (new): placeholder-shown-before-confirmation
  for both new sections; full budget shown after confirmation; magic-linked skills absent from the
  rendered page; a valid attribute submission matches `create_character()`'s own output
  (`attribute_value`, remaining budget); an over-budget attribute submission is rejected *and*
  leaves the committed session state provably unchanged (checked via a follow-up `GET /`); a valid
  skill submission matches `create_skill_allocation()`/`skill_rating()`/`dice_pool()`'s own output;
  a skill-group submission's remaining-budget line reflects the spend (group-override mechanics
  themselves already covered by WP7's own unit tests, not re-proven here); the strict-skill-groups
  conflict and an over-budget skill submission are both rejected with the expected message;
  re-confirming priorities resets both the attribute and skill sections back to full budget; and
  hitting either new endpoint before any metatype/priorities confirmation returns the placeholder
  message rather than crashing.

## Outcome

WP15 complete: once a metatype and priorities are confirmed (WP14), the chargen page now shows
live attribute and skill allocation forms backed directly by WP6's `create_character` and WP7's
`create_skill_allocation`/`skill_rating`/`dice_pool`. Attribute points spend against the
Attributes-priority-letter budget and the metatype's own special-attribute-points (EDG) budget,
each attribute row showing its computed value and metatype range. Skill points spend against the
Skills-priority-letter's two pools (individual skills, skill groups), with each skill row showing
its resolved rating and dice pool, live-updated via HTMX as the player types (debounced) or changes
a value. Both forms reject invalid submissions (over budget, over the rating cap, the
strict-skill-groups conflict) with the engine's own error message and leave the last-committed
state untouched, echoing the player's actual (invalid) input back into the form — the same pattern
WP14 established for priority selection. Re-confirming priorities resets both sections, since a
changed Attributes/Skills letter or metatype invalidates the old spend. MAG/RES-linked skills are
excluded from the offered skill list, a UI-layer curation (not an engine change) that follows
directly from MVP's existing mundane-only scope. Verified via 10 new automated tests plus a full
manual walkthrough against a running dev server, covering both the happy path and every rejection
case.
