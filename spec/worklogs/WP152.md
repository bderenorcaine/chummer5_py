# WP152 — Spells redesign: Filtered and Known tabs, portrait dropdown

Second and last of the Spells WPs. Spells gets its Filtered and Known views and the narrow-width
dropdown, and WP150's view script now works for any page.

## What landed

- **Two more views** in `routes/spells.py`: `SPELL_MULTI_VIEWS` (`filtered`, `known`, labelled
  `Web_Spells_TabFiltered`/`TabKnown`) after the six categories, in `SPELL_VIEW_SLUGS`. The URL
  level, the `spells_tab` validation and the strip pick them up from there. A strip item is now
  built by `_tab_item`. A category tab names its `category` (a data term), a view tab its
  `label_key`, and the template's caller block renders whichever is set.
- **The views in `_spell_selection.html`:**
  - On Filtered/Known, all six panels show. Each sits under an `<h2 class="view-heading">` (the
    category's data term) and is marked `data-view-section`.
  - The fragment carries `data-view-scope="spells"` and `data-view-mode` (`filter` / `fixed` /
    empty).
  - Every row carries `data-view-key` (the spell id), `data-view-name` (the translated name in
    lower case) and `data-view-kept` (known).
  - Filtered's field (`#spell-filter`, `type="search"`, no `name`, `data-view-filter="spells"`)
    sits between the strip and the form, so typing never autosaves.
- **The dropdown:** the Spells strip now passes `select_id="spells-tab-select"`, so the shared
  macro renders the narrow block (F/C/Ka in one row, then the `<select>`). `.spells-page` became
  a container (`container-type: inline-size`), and `@container (max-width: 32rem)` swaps the strip
  for the narrow block. 32rem is where the strip stops fitting: eight 2.2rem tabs minus their 1px
  overlaps, plus the 5rem lean and the 9rem minimum filler, about 31.2rem.

## Making WP150's code page-agnostic

The phase file asked for the filter store, the fixed row set, section hiding and the dropdown to
work "keyed on data attributes, not on Skills ids". The Skills page had to change markup to get
there, but its behaviour is unchanged:

- **Attributes renamed on Skills:**
  - `data-skills-view` → `data-view-section`
  - `data-skill-key`/`-name` → `data-view-key`/`-name`
  - `data-skill-rating` → `data-view-kept`
  - Both fragments gained `data-view-scope="skills"` and `data-view-mode`.
  - `data-skills-tab` stays. The script no longer reads it, but WP148/WP150 tests and the nav walk
    use it to see which tab a fragment rendered. The new attributes sit *before* it, because
    those tests' regexes end at `data-skills-tab="…">`.
- **Kept is decided by the server.** The script used to test `Number(rating) > 0`. Now the
  template writes `data-view-kept`: Skills, rating above 0 (a Knowledge row: native, or a total
  above 0); Spells, known. Standing rule 7 says rules stay server-side.
- **Shared classes:** `.skills-panel__heading` → `.view-heading`, and `.skills-filter*` →
  `.view-filter*`. Their CSS moved into the shared view-tab section. The Skills ids
  (`skill-filter`, `skills-tab-select`) stay in the markup, but `app.js` no longer names them.
- **`app.js`:**
  - `viewQueries` and `viewKept` hold the state per scope.
  - `viewFragments(scope)`, `viewMode(scope)` and `narrowView(scope, keep)` read the markup.
  - `applyViewFilter` and `restoreViewFilter` drive Filtered, and `applyFixedView` drives
    Rated/Known.
  - One `htmx:load` handler walks every `[data-view-scope]` on the page. It drops a scope's fixed
    set once its mode isn't `fixed` (the player left the tab).
  - The dropdown handler matches any `.view-tabs__select` and clicks the matching
    `a.view-tab[href]` inside `select.closest(".view-tabs")`.
- **"Entering"** used to mean "the loaded element is or contains `.page--skills`". It is now
  "the loaded element contains a fragment of the scope, without being that fragment". That is
  the same test with the page class taken out:
  - A page render (tab link, history, reload; the initial load's `htmx:load` on `body`) holds the
    fragment, so it counts.
  - A fragment's own autosave swap *is* the fragment, so it doesn't count.
  - On Skills, a Knowledge autosave loads `#knowledge-skills`, which doesn't contain
    `#skill-allocation`, so it doesn't count either, as before. Neither do the strip refresh nor
    the out-of-band messages.
- **No JS runtime here.** There is no Node. I parsed `app.js` with `esprima`
  (`uv run --no-project --with esprima`) to catch syntax errors. Its behaviour is on the checklist.

## i18n

New: `Web_Spells_TabFiltered` ("Filtered"), `Web_Spells_TabKnown` ("Known"),
`Web_Spells_FilterLabel` ("Filter spells") and `Web_Spells_FilterPlaceholder` ("Part of a spell's
name"). I didn't reuse WP150's filter keys, because their text names skills. The dropdown's
label is the strip's ("Spells sections").

## Known limit

- Inherited from WP150: after an autosave on a view, the swapped-in fragment shows every row until
  `htmx:load` narrows it again. That should be invisible, because htmx fires it before the next
  paint, but it is on the checklist.
