# WP16 — Qualities, contacts & resources UI

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase F, WP16.

## Goal

Round out chargen inputs: quality picker (MVP-supported catalog only), contacts editor, nuyen
spend screen. Deliverables per the Implementation Plan: a quality picker, contacts editor, and
nuyen spend screen, backed by WP8's `create_quality_selection`/`apply_quality_improvements` and
WP9's `create_contact_selection`/`create_resources_selection`. Acceptance: manual walkthrough;
values match engine output for the same inputs.

## Log

### 2026-07-18 — Same "UI is a thin layer over an already-correct engine" precedent as WP14/WP15,
applied three more times

`POST /ui/qualities` calls `chummer5.engine.qualities.create_quality_selection` directly (which
itself narrows to `mvp_quality_catalog`'s 3-quality offered set internally — no need to pre-filter
in the web layer); `POST /ui/contacts` calls `chummer5.engine.resources.create_contact_selection`;
`POST /ui/resources` calls `chummer5.engine.resources.create_resources_selection`. None of the
three routes re-derive the 25-karma-per-side cap, the Connection/Loyalty ≥ 1 rule, or the nuyen
budget check — those are exactly the validations WP8/WP9 already implemented and tested. Same
reasoning WP14/WP15's own worklogs already recorded for `submit_priorities`/`submit_attributes`/
`submit_skills`.

### 2026-07-18 — The real finding this WP surfaced: `create_character` always builds a fresh,
empty `ImprovementIndex`, so a committed quality selection's bonuses can silently vanish

`chummer5.engine.character.create_character` (WP6) always returns a brand-new `Character` with
`improvements=ImprovementIndex()` — a fresh, empty index, every single call. WP15's
`submit_attributes` already calls `create_character` again on every attribute-point resubmission
(a real, working, previously-tested code path — nothing wrong with it *before* WP16). The moment
WP16 introduces qualities that actually populate `character.improvements` (Catlike's `+2 Sneaking`,
etc. — confirmed these land as `ImprovementType.SKILL` records, which `chummer5.engine.skills
.skill_rating` reads via `character.improvements.resolve(...)`), that combination becomes a real
bug: pick Catlike, then edit any attribute point, and the freshly-rebuilt `Character` silently
drops the Sneaking bonus, because the new `Character` object has never heard of the quality that
was applied to the *old* one. Caught this by reading `create_character`'s body before writing any
route code (the same "read the callee before relying on it" discipline WP15's own worklog flagged
for `MetatypeChoice`), not by a failing test discovered later — but a regression test
(`test_quality_improvements_survive_a_later_attribute_resubmission`) was written anyway once the
fix was in place, precisely because this is the kind of silent-data-loss bug that's easy to
reintroduce in a future WP without one.

Fix: `_relink_quality_improvements(character, session)` — a small helper called immediately after
every `create_character` call in a route that's mutating an *already-in-progress* session
(`submit_priorities`'s success branch, `submit_attributes`'s success branch), which re-applies
`session.quality_selection`'s Improvements onto the freshly built `Character` before it's stored.
Safe to call unconditionally (a no-op before any quality has ever been committed). Contacts and
resources needed no equivalent treatment — neither `create_contact_selection` nor
`create_resources_selection` writes to `character.improvements` at all, so there was nothing for
either of them to lose.

A related, smaller wrinkle inside `submit_qualities` itself (not the rebuild case above, but a
second, same-`Character`-object resubmission): `apply_quality_improvements` only ever *adds*
Improvements, so calling it twice for two different quality-checkbox submissions against the
*same* `Character` object (no intervening `create_character` rebuild) would double up any quality
that stayed selected across both submissions. `_replace_committed_qualities` handles this case —
it first removes every currently-held `ImprovementSource.QUALITY`-sourced Improvement (via
`ImprovementIndex.remove_source`) before re-applying the new selection, so re-submitting the
qualities form is idempotent for whatever's still checked. `_relink_quality_improvements` doesn't
need this removal step, since a freshly built `Character` from `create_character` never has any
Improvements to begin with.

### 2026-07-18 — Reset rules had to be reasoned per-section, not copied wholesale from WP15's
skill_allocation precedent

WP15 reset `skill_allocation` to `None` whenever priorities/metatype are reconfirmed, since the
Skills-letter budget it depends on can change. WP16 adds three more committed selections, and each
needed its own answer rather than blanket-copying that rule (see `ChargenSession`'s extended
docstring for the full reasoning, condensed here):
- **`quality_selection`: not reset.** None of the 3 MVP-offered qualities are metatype-gated, and
  the 25-karma-per-side cap is a fixed constant untouched by which priority letter funds what — a
  changed Heritage/Attributes/Skills/Resources letter or metatype has no bearing on whether an
  already-committed quality pick is still valid. Only its *Improvements* need re-landing on
  whatever `Character` object is current (see above) — the selection data itself survives.
- **`contacts`: not reset.** A contact's Connection/Loyalty is the player's own invention, checked
  only against a fixed ≥1 floor; only the *free-point budget display* depends on the character
  (CHA × 3), and that's recomputed fresh from `session.character` on every render
  (`_contacts_context` calls `character.attribute_value("CHA")` directly, never reads a cached
  figure), so there's nothing stale left over to reset.
- **`gear_names`: reset to `()`.** Mirrors `skill_allocation` exactly, for the same reason: the
  nuyen budget it spends against depends specifically on the Resources priority letter, which is
  one of the four letters reconfirmation can change (`test_reconfirming_priorities_with_a_new
  _resources_letter_resets_gear` — swapping Skills/Resources letters between two reconfirmations
  and checking the gear table comes back to `budget / budget`, not the stale spend).

### Design decisions

- **`_contacts_context`/`_resources_context` compute their displayed totals directly (`Contact
  .points`, `item.cost * quantity`) rather than calling `create_contact_selection`/
  `create_resources_selection` for display.** Both validating functions raise on the exact invalid
  input an error-echo render needs to show (a Connection-0 contact, an over-budget gear pick) — the
  same "manual, non-raising reconstruction for echoed invalid input" choice WP15 made for
  `_attribute_allocation_context`/`_skill_allocation_context`. The validating functions are still
  called, once, inside each `POST` route to decide whether to actually commit the submission.
- **Contacts use a fixed `MAX_CONTACT_ROWS = 8`-row table, no client-side add/remove.** Mirrors the
  fixed-row attribute/skill tables (WP15) rather than introducing the first bit of dynamic-DOM
  JavaScript this project would have needed — a blank `contact_name_{i}` row is simply "no contact
  here" to `_parse_contacts`, so unused rows cost nothing. 8 is a plain, generous-enough guess (no
  fixture in the mundane corpus has more than a handful of contacts); nothing about the engine caps
  contact count, so raising this constant later is a one-line change if it's ever too small.
- **Starter-gear quantities use a plain number input per catalog item (`gear_{item.name}`),
  expanded to that many repeats of the name before reaching `create_resources_selection`.** Reuses
  WP15's own finding that a raw catalog name — including one with a comma (`"Certified Credstick,
  Standard"`) — round-trips correctly as a form field name through standard URL-encoding; verified
  directly via `test_buying_two_of_a_repeatable_gear_item` rather than assumed, since a comma is a
  step further than WP15's own "spaces work" finding.
- **A negative or unparseable gear quantity clamps to 0 in `_parse_gear`, rather than being passed
  through for the engine to reject** (unlike `_parse_points`' negative-attribute/skill-point
  pass-through). There's no engine-level "negative quantity" concept for
  `create_resources_selection` to validate instead — repeating an item's name -3 times isn't a
  rejection this function is equipped to produce — so this is a plain web-robustness clamp, not an
  offloaded rule.
- **No "total karma spent so far" summary line anywhere yet**, even though qualities and contacts
  both now produce a karma figure. Nothing in MVP's engine (`chummer5.engine.derived`, the WP10
  headless milestone) computes an aggregate karma total across every source — that's character-
  sheet territory, explicitly WP17's deliverable ("finish and persist a character"), not something
  to invent ahead of it in this WP's three independent fragments.

  after `_skill_allocation.html`.
- `tests/unit/test_web_quality_contacts_resources.py` (new): placeholders shown before

  `+2 Sneaking` bonus in a follow-up skills render; **the regression test for the Improvement-index
  finding** — Catlike's bonus survives both a later attribute resubmission and a later priorities
  reconfirmation; unknown quality id rejected; a valid contact submission matches the engine's

  metatype/priorities confirmation without crashing.

## Outcome

WP16 complete: once a metatype and priorities are confirmed (WP14), the chargen page now also
shows a quality picker (the 3 MVP-offered qualities against the 25-karma-per-side cap), a contacts
editor (8 rows, free-point budget from CHA×3, karma cost beyond it), and a starter-gear spend
screen (5 hand-curated items, nuyen budget from the Resources priority letter) — all backed
directly by WP8's and WP9's engine functions, matching the "UI is a thin layer over an
already-correct engine" precedent WP14/WP15 established. The notable finding: `create_character`
always returns a `Character` with a fresh, empty `ImprovementIndex`, which — now that a real
quality selection can populate that index — meant a later attribute resubmission could silently
drop an already-committed quality's bonus. Fixed via `_relink_quality_improvements`, re-applying
the session's committed quality selection onto every freshly built `Character`, with a dedicated
regression test guarding against reintroduction. Verified via 15 new automated tests plus a full
manual walkthrough against a running dev server, covering the happy path, every rejection case, and
the cross-cutting Improvement-persistence behavior across both attribute edits and priority
reconfirmation.
