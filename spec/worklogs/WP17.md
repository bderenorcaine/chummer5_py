# WP17 — Character sheet + save/load UI (UI MVP milestone)

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase F, WP17.

## Goal

Finish and persist a character through the browser, start to finish. Deliverables per the
Implementation Plan: a read-only finished-character view (derived stats), save/download (native
format via WP11), load/upload (native format + legacy `.chum5` import via WP12). Acceptance: a
full manual walkthrough — create a mundane priority character in the browser end to end, save it,
reload it, and (separately) import `Yeti-#ffffff2.chum5` — all producing correct values.

## Log

### 2026-07-18 — The character sheet is a separate page, not another `_chargen_body.html` fragment

Every prior Phase F WP (14-16) added its section as a fragment inside `_chargen_body.html`,
HTMX-refreshed by its own `/ui/*` route. The character sheet doesn't fit that shape cleanly: it's
explicitly a *read-only* view of the aggregate state five independent routes (`/ui/priorities`,
`/ui/attributes`, `/ui/skills`, `/ui/qualities`, `/ui/contacts`, `/ui/resources`) can each change,
none of which currently know the sheet exists. Keeping it live-synced the way the other sections
sync with each other would mean adding an HTMX out-of-band swap to all six routes for a section
that isn't itself a form — real, ongoing coupling for every future WP that touches any of those six
routes, in exchange for "the sheet never needs a page load to catch up." Went with a separate
`GET /character/sheet` page instead: it always renders the session's *current* state fresh (no
staleness possible, since there's nothing to go stale — every render reads `session` directly), a
plain nav link (`base.html`) gets a player there, and none of the six existing routes needed to
change at all. This also matches the deliverable's own framing better than a fragment would have —
"finish and persist a character" reads as a distinct step after chargen, not a widget that updates
mid-keystroke the way attribute/skill points do.

### 2026-07-18 — `starlette.datastructures.UploadFile`, not `fastapi.datastructures.UploadFile`,
is what `await request.form()` actually returns

Every existing `POST /ui/*` route in this file reads `await request.form()` directly rather than
FastAPI's `File(...)`/`Form(...)` parameter injection (established back in WP15, for the
data-driven field-set reasons its own worklog gives). This WP is the first to need a real file
upload, and the first attempt (`isinstance(upload, fastapi.UploadFile)`) silently failed every
time — `form.get("save_file")` always returned an object of the right *shape* (`.filename`,
`.read()`) but the `isinstance` check was always `False`, so every upload fell into the "no file
chosen" branch regardless of what was actually posted. Traced this by checking the runtime type
directly rather than guessing: `fastapi.datastructures.UploadFile` is a subclass of
`starlette.datastructures.UploadFile` (confirmed via `.__mro__`), and `await request.form()` (a
plain Starlette method, since FastAPI's own wrapping only happens through its parameter-injection
path) returns instances of the *Starlette* class, which does not satisfy `isinstance(x,
fastapi.UploadFile)` — the inheritance only runs one direction. Fixed by importing `UploadFile`
from `starlette.datastructures` (already imported from there for `FormData`) instead of `fastapi`.
Caught by an actual failing manual `TestClient` check before any test was written, not inferred —
flagging here since it's an easy trap for a future WP that adds another upload route via the same
"read `request.form()` directly" pattern this file already established.

### 2026-07-18 — `build_character` already reapplies quality Improvements, so load/import needs no
`_relink_quality_improvements` call

WP16 found that `create_character` always returns a `Character` with a fresh, empty
`ImprovementIndex`, and every route that rebuilds a `Character` for an already-in-progress session
has to re-land the committed quality selection's bonuses via `_relink_quality_improvements`, or
they silently vanish. Checked whether `_apply_built_character_to_session` (this WP's equivalent
entry point, used by both `load_save` and `import_chum5_route`) needed the same treatment before
writing it — it doesn't: `chummer5.io.save_format.build_character` already calls
`apply_quality_improvements(character, quality_selection)` itself as part of building a
`BuiltCharacter` (confirmed by reading its body, the same "read the callee before relying on it"
discipline WP15/WP16 already established), so `built.character` arrives with the right
`ImprovementIndex` already populated. `_apply_built_character_to_session` sets
`session.character = built.character` directly, not a fresh `create_character` call — nothing more
to relink. This does mean a *subsequent* attribute edit after a load/import still needs the
existing relink path to work correctly, which it does unchanged: `session.quality_selection` is
also set (to `built.quality_selection`), so `submit_attributes`'s existing
`_relink_quality_improvements` call re-lands the same bonuses onto whatever new `Character`
`create_character` produces next, exactly as it already does for a quality picked through the UI
directly.

The manual walkthrough (see Verification) imports Yeti and then edits an attribute, but Yeti
carries none of the 3 MVP-offered qualities, so that alone only proves the relink call is a
harmless no-op after an import, not that a *loaded* quality's bonus specifically survives a later
attribute edit. Added a dedicated test for the narrower claim instead of assuming it from
inspection: `test_a_loaded_qualitys_bonus_survives_a_later_attribute_edit` builds a save carrying
Catlike (via the normal `/ui/qualities` route), loads it into a fresh session, confirms the sheet
shows the resulting Sneaking bonus, edits an unrelated attribute, and confirms the bonus is still
there afterward.

### Design decisions

- **`_character_sheet_context` calls `create_contact_selection`/`create_resources_selection`
  directly, unlike `_contacts_context`/`_resources_context`.** Those two avoid the real validating
  functions specifically to support echoing *invalid* input back into a form after a rejected
  submission (see WP16's worklog). The character sheet never echoes an in-progress submission —
  `session.contacts`/`session.gear_names` are only ever set by a route that already validated them
  — so calling the real functions here is always a no-op re-validation, just a convenient way to
  read `karma_cost`/`nuyen_remaining` without a third copy of that arithmetic.
- **The skills table on the sheet lists only skills with `skill_rating(...) > 0`**, unlike the
  full ~64-row allocation table on the chargen page. The sheet's purpose is "what does this
  character actually have", not "what could this character spend points on" — the latter is
  already the chargen page's job, one page away via the nav link.
- **`import_chum5`/`load_chum5` take a `Path`, not bytes, so the uploaded `.chum5` bytes are
  written to a `tempfile.NamedTemporaryFile` before calling `import_chum5`.** Considered widening
  `load_chum5`'s signature to accept a file-like object (`ET.parse` itself supports that), but
  that module's contract is deliberately "parse a file on disk" (it's also used directly by every
  fixture-backed test via a real path) — a temp file confined to this one web-layer caller is a
  smaller, more local change than adding a second accepted input shape to a lower-layer module for
  a single caller's convenience.
- **Malformed-upload handling at both `/character/load` and `/character/import-chum5` catches a
  specific tuple of exception types, not bare `Exception`.** `/character/load`:
  `(ValueError, KeyError, AttributeError)` — `ValueError` covers `json.JSONDecodeError` (invalid
  JSON) and `UnicodeDecodeError` (non-UTF-8 bytes, both real `ValueError` subclasses) plus
  `build_character`'s own validation failures; `KeyError` covers a syntactically-valid JSON object
  missing a required field; `AttributeError` covers a syntactically-valid JSON document that isn't
  an object at all (e.g. a bare JSON array — `_dict_to_save` calls `.get` on it, which a list
  doesn't have). `/character/import-chum5` separately catches `UnsupportedLegacyCharacterError`
  (WP12's own itemized-reasons exception) and `ET.ParseError` (malformed XML). Both are file-upload
  boundaries — arbitrary bytes from outside the process — where being explicit about which failure
  modes are "just a bad upload" (per this project's "only validate at system boundaries" rule)
  matters more than catching everything indiscriminately.
- **`_apply_built_character_to_session` is the single write path for both `load_save` and
  `import_chum5_route`.** Both ultimately produce the same `(CharacterSave, BuiltCharacter)` shape
  (WP11's `build_character` output; `ImportResult.save`/`ImportResult.built` for the legacy path is
  exactly that pair plus the dropped-content report), so one helper covers both call sites rather
  than duplicating the nine-field session assignment twice.

### Implementation

- `src/chummer5/web/app.py` (extended): new imports (`chummer5.engine.derived`'s seven functions,
  `chummer5.io.legacy_import`, `chummer5.io.save_format`, `tempfile`, `xml.etree.ElementTree`);
  `_character_sheet_context()` (derived stats + selection recap, echo-free); `_character_save
  _from_session()` (session -> `CharacterSave`, the save/download direction);
  `_apply_built_character_to_session()` (the load/import direction, shared by both new POST
  routes); `GET /character/sheet` (renders the full `character_sheet.html` page); `GET
  /character/save` (JSON attachment download, 400 if no character confirmed yet); `POST
  /character/load` (native-format upload, WP11's `from_json`/`build_character`); `POST
  /character/import-chum5` (legacy `.chum5` upload, WP12's `import_chum5`, itemizes dropped
  qualities/skills and blocking reasons in the response).
- `src/chummer5/web/templates/base.html` (modified): a `<nav>` with links to `/` and
  `/character/sheet`, added once so both pages get it via `{% extends %}`.
- `src/chummer5/web/templates/character_sheet.html` (new): full page wrapper (`{% extends
  "base.html" %}`), includes `_character_sheet.html`.
- `src/chummer5/web/templates/_character_sheet.html` (new): the fragment both the full page and
  the two POST routes render — metatype/priority-letter summary, attribute values, skills rated
  above 0, qualities, contacts, gear + nuyen remaining, the six derived stats (initiative
  value+dice, three limits, two condition monitors), quality/contact karma cost, a download link,
  and the two upload forms (`hx-encoding="multipart/form-data"`, targeting `#character-sheet`
  itself so a successful load/import re-renders the whole fragment in place). The upload forms
  render unconditionally (even with no character confirmed yet), since importing/loading is itself
  a valid way to *start* a session.
- `tests/unit/test_web_character_sheet.py` (new): placeholder before confirmation (with the
  upload forms still present); derived stats on the sheet match calling
  `chummer5.engine.derived`'s functions directly against an equivalently-built `Character`;
  download rejected (400) before confirmation; download returns a `Content-Disposition: attachment`
  JSON body that round-trips through `from_json`; a save downloaded from one session loads
  correctly into a completely fresh session (cross-checked via a follow-up `GET /`, not just the
  sheet); a loaded quality's Improvement bonus (Catlike's +2 Sneaking) survives a later attribute
  edit, the WP16-precedent regression case for this WP's own load path; a malformed upload is
  rejected without disturbing the session's existing character; empty file-field submissions to
  both upload routes show a prompt instead of crashing; a non-XML `.chum5` upload is rejected; the
  nav link is present on the index page.
- `tests/integration/test_web_character_sheet_fixtures.py` (new): imports
  `Yeti-#ffffff2.chum5` through the web route and cross-checks the rendered sheet's derived
  stats/contacts/nuyen figures against calling `chummer5.io.legacy_import.import_chum5` directly
  (the WP12 path, proven correct by its own fixture tests) — the acceptance criterion's headline
  case, done through the actual HTTP layer rather than only the engine; a second test confirms
  `Miko.chum5` (Magic enabled) is rejected through the web route with the itemized reason, and that
  a blocked import leaves no half-applied character behind.

  extended `app.py`, no new `.py` source files under `src/`).
- Manual browser-adjacent verification (per this project's UI-testing bar, beyond `TestClient`):
  ran `uv run uvicorn chummer5.web.app:app --host 127.0.0.1 --port 8123` in the background, drove
  it via plain `urllib` requests with real cookie jars (mirroring WP13-WP16's approach), covering
  the acceptance criterion's exact sequence:
  - Confirmed Human (Heritage A/Attributes B/Skills C/Resources D), spent BOD 4/AGI 3 → `GET
    /character/sheet` showed matching Initiative/Physical/Mental/Social Limit/condition-monitor
    figures and `0` karma cost on both qualities and contacts (none picked).
  - `GET /character/save` → `Content-Disposition: attachment; filename="character.json"`,
    body a JSON document with `"metatype_name": "Human"`, `"attribute_points": {"BOD": 4, "AGI":
    3}`.
  - Posted that downloaded file to `POST /character/load` from a **completely fresh cookie jar**
    (a new, never-visited session) → `"Character loaded."` shown, and a follow-up `GET /` on that
    same fresh session showed `"Confirmed: Human"` — the full chargen page, not just the sheet,
    picked up the loaded state.
  - Posted `Yeti-#ffffff2.chum5` to `POST /character/import-chum5` from a third fresh session →
    `"Character imported."` plus the dropped-qualities list (Technomancer/Infirm/Impassive/
    Paranoia/Faceless/Data Anomaly, matching WP12's own fixture test); the resulting `GET
    /character/sheet` showed `Human`, both of Yeti's real contacts (`JoJo`, `Ralph, Just Ralph`),
    and non-zero derived stats.
  Server process stopped afterward — `pgrep -f "uvicorn chummer5.web.app"` found no matches this
  time (the process tree's actual PIDs weren't matched by that pattern, a first for this project's
  worklogs), so fell back to enumerating `/proc/*/cmdline` directly for anything containing
  `uvicorn`, found 4 surviving PIDs (the `uv run` wrapper, the `uvicorn` worker, and two more from
  its process group) and `kill -9`'d each by number; confirmed via a follow-up `urllib` request
  that the port no longer accepts connections. Noting the `pgrep` miss explicitly in case a future
  WP hits the same thing and wants a starting point rather than rediscovering the `/proc` fallback
  from scratch.

## Outcome

WP17 complete — the UI MVP milestone. A player can now finish a mundane priority-built character
in the browser and view a read-only character sheet (`/character/sheet`) showing every WP10 derived
stat (initiative, the three Limits, both condition monitors) alongside a recap of every committed
selection (attributes, skills, qualities, contacts, gear/nuyen). The same page downloads the
character as this project's own native JSON format (WP11) and accepts either that native format or
a legacy `.chum5` file (WP12) back in, fully repopulating a session — including a brand-new one
that never went through the chargen form at all, which is how the acceptance criterion's "import
Yeti-#ffffff2.chum5" case actually starts. The character sheet is deliberately its own page rather
than another live-synced chargen fragment, since it's a read-only aggregate view six independent
routes can each affect, not a form of its own. The one real bug caught during manual verification
(`starlette.datastructures.UploadFile` vs. `fastapi.datastructures.UploadFile` — `isinstance`
against the wrong one silently rejected every real upload) is flagged in this worklog for any
future WP that adds another file-upload route via the same `await request.form()` pattern.
Verified via 15 new automated tests (13 unit, 2 integration against the real corpus) plus a full
manual walkthrough against a running dev server reproducing the Implementation Plan's exact
acceptance sequence: create → save → reload into a fresh session, and separately, import
`Yeti-#ffffff2.chum5` from scratch.
