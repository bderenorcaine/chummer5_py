# WP18 — Fold skill/quality/contact/resources selections into `Character`

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase G, WP18.

## Goal

Make `Character` the single aggregate representing a character-in-progress, so a quality
selection (etc.) is a property of the character, not sibling state independently threaded through
the web session, the save format, and legacy import. Deliverables per the Implementation Plan:
widen `Character` with four new optional fields (`skill_allocation`, `quality_selection`,
`contact_selection`, `resources_selection`); retire `save_format.py`'s `BuiltCharacter` wrapper;
update `legacy_import.py`'s `ImportResult` to wrap `Character` directly; drop the four now-redundant
`ChargenSession` fields, keeping only `character`; update every route/context-builder in `app.py`
and every affected test. Acceptance: `pytest`/`ruff`/`mypy` all green; WP17's own manual walkthrough
(create → save → reload into a fresh session; separately, import `Yeti-#ffffff2.chum5`) reproduced
with identical results — pure internal restructuring, no computed-value change.

## Log

### 2026-07-18 — Widening `Character` needs a `TYPE_CHECKING`-only import to avoid a circular
import

`chummer5.engine.skills`/`qualities`/`resources` each import `Character` from
`chummer5.engine.character` (to type their own `create_*` functions' `character` parameter). Adding
`skill_allocation: SkillAllocation | None` etc. as real fields on `Character` would need those three
modules' types imported *back* into `character.py` — a straightforward cycle at runtime. Resolved
with a `TYPE_CHECKING`-guarded import block: `character.py` already has `from __future__ import
annotations` (PEP 563), so every annotation in the module — including dataclass field types — is a
lazy string the `@dataclass` decorator never has to evaluate at class-definition time; only `mypy`
(which does static analysis, not import execution) ever needs the real names, and it does resolve
`TYPE_CHECKING` blocks. Confirmed clean both ways: `uv run python -m mypy src` reports no issues,
and the module imports fine at runtime (proven by the full test suite passing, not just by
inspection).

### 2026-07-18 — `contact_selection` needed a genuinely different carry-forward rule than
`quality_selection`, not just "store it as a field too"

The obvious first design was: give `_relink_quality_improvements` three siblings (one per new
field) that each do "if the old `Character` had one, re-attach it to the new one" — a uniform
`dataclasses.replace`. That's correct for `quality_selection` (a `QualitySelection`'s karma
totals are fixed data, no dependency on anything about the `Character` itself) and for
`resources_selection` (`create_resources_selection` doesn't even take a `character` parameter —
its nuyen budget depends only on the Resources letter and the gear catalog). It's **wrong** for
`contact_selection`: `ContactSelection.free_points`/`karma_cost` are derived from
`character.attribute_value("CHA")` (`FREE_CONTACT_POINTS_PER_CHARISMA`, see
`chummer5.engine.resources`), and the two routes that rebuild a `Character` from scratch
(`submit_priorities`, `submit_attributes`) are exactly the two places CHA can change (a metatype
swap or a fresh attribute-point spend). A plain re-attach would let a stored `ContactSelection`'s
`free_points` silently go stale the next time the sheet or the contacts form read it off
`character.contact_selection` directly, reintroducing exactly the kind of "computed value doesn't
match current character state" bug this WP's fold is supposed to prevent, not create. Caught this
by tracing `ContactSelection`'s own fields back to their formula (per `chummer5.engine.resources`'s
module docstring) before writing the carry-forward helper, not after. Fixed with a second, distinct
helper: `_relink_contact_selection` recomputes via `create_contact_selection(character,
previous_selection.contacts)` — the raw `contacts` tuple, not the stale numbers — so it's always
correct regardless of what changed about `character` in between. `_character_sheet_context` goes
one step further and never trusts a stored `contact_selection` at all for its own karma/free-point
display, recomputing fresh from `character.contact_selection.contacts` on every render — the same
"no-op re-validation, just convenient" pattern WP17 already used before this WP existed, kept
deliberately even though the fold made a stored, pre-computed value available, specifically so a
missed relink call somewhere else can never surface as a wrong number on the one page a player
actually reads final numbers from.

### 2026-07-18 — Decision: `submit_attributes`/`submit_priorities` still call `create_character()`
fresh; the switch to `dataclasses.replace`-in-place is left to WP19

The Implementation Plan explicitly allows either choice for WP18 alone. Kept the fresh-rebuild
shape for both routes in this WP, for two reasons: (1) the Phase G intro's own stated reason for
sequencing WP18 before WP19 is that WP19 is the one that benefits from switching to `replace`
in-place (an untouched field survives a `replace` call by reference automatically, with nothing to
re-link) — doing that switch here would just be doing WP19's job early, under WP19's own
acceptance criteria untested; (2) WP18's actual deliverable list never mentions changing
`submit_attributes`'s/`submit_priorities`'s construction strategy, only widening `Character` and
moving the *storage location* of the four selections — conflating the two risks a WP that's harder
to review as "pure restructuring, no behavior change" (this WP's own acceptance bar). Concretely,
this means `_relink_quality_improvements` and the new `_relink_contact_selection` remain necessary
in both routes for one more WP, exactly as the Implementation Plan's own wording anticipates
("`_relink_quality_improvements` stays necessary for that one route until WP19 lands"). Both
helpers were reshaped this WP regardless (see above) since the *fields* they populate moved from
`ChargenSession` onto `Character` — only their *necessity*, not their shape, is unchanged.

### 2026-07-18 — `_apply_built_character_to_session` shrank from a 9-line, 9-field assignment to a
2-line one

Before this WP, `build_character` returned a `BuiltCharacter` (`character` + 4 separate selection
objects), so `_apply_built_character_to_session` had to unpack all 5 and write 9 total
`ChargenSession` fields (4 priority letters + `metatype_id` + `character` + the 4 selections,
`contacts`/`gear_names` each needing a field-access step off `built.contact_selection`/
`built.resources_selection` first). Now that `build_character` returns one fully-populated
`Character` (via one `dataclasses.replace` call at the end of its own body — see
`chummer5.io.save_format`'s updated docstring) and `ChargenSession` only has `character` left to
set, that function is just: set the 4 pre-`Character` priority-letter fields + `metatype_id`, then
`session.character = built`. This is the concrete shape of the "five-field manual synchronization
problem" the Phase G intro describes going away — not a WP19 result, a WP18 one, since it falls out
directly from `Character` becoming the single aggregate rather than from any construction-strategy
change.

## Design decisions

- **`ChargenSession` keeps `heritage_letter`/`attributes_letter`/`skills_letter`/
  `resources_letter`/`metatype_id` as its own fields, not folded into `Character`.** These are
  genuinely pre-`Character` state: the very first page load has no `Character` yet but still needs
  a legal starting letter assignment (`DEFAULT_*_LETTER`), and `skills_letter`/`resources_letter`/
  `metatype_id` have no `Character`-side equivalent at all (only `heritage_letter`/
  `attributes_letter` are duplicated onto `Character` too, since `create_character` needs them for
  its own attribute-range/budget lookups — unchanged from WP6). Folding these in would need
  `Character` to exist before it can, so they stay exactly where they were.
- **No new "echo a rejected submission" scratch fields were needed on `ChargenSession`.** Checked
  this explicitly before assuming the fold was complete, since the Implementation Plan's WP18 entry
  flags it as something to watch for. Every existing echo-an-invalid-submission path
  (`_attribute_allocation_context`, `_skill_allocation_context`, `_quality_selection_context`,
  `_contacts_context`, `_resources_context` all take an `error=` kwarg) already worked by passing a
  *local* variable — the just-parsed, possibly-invalid form data — straight into the context
  builder on the `except ValueError` branch, never by writing it onto `session` first. That pattern
  is untouched by this WP: `session` was never the thing holding rejected input, so there was
  nothing to relocate.
- **`_character_sheet_context` reads `resources_selection` directly off `character.resources_
  selection` (falling back to a freshly-computed zero-spend selection when `None`), but
  recomputes `contact_selection` from scratch every render.** Asymmetric on purpose: the first has
  no character-state dependency to go stale against (see the log entry above), so trusting the
  stored value is free; the second does, so recomputing is the only way to guarantee correctness
  without also auditing every mutating route for a missed relink call.
- **`build_character`'s prior module-docstring paragraph explaining why `BuiltCharacter` existed
  was rewritten, not deleted**, to instead explain why it no longer needs to — a future reader
  hitting a stale reference to `BuiltCharacter` from an old commit message or a mental model should
  find the "here's what replaced it and why" note in the same place the original justification used
  to live.

## Implementation

- `src/chummer5/engine/character.py`: `Character` widened with `skill_allocation:
  SkillAllocation | None = None`, `quality_selection: QualitySelection | None = None`,
  `contact_selection: ContactSelection | None = None`, `resources_selection:
  ResourcesSelection | None = None`, each imported only under `TYPE_CHECKING` (see log). `Character`
  and `create_character`'s own docstrings rewritten to describe the fold and to point future edits
  at `dataclasses.replace`, not another `create_character` call, for advancing an in-progress
  character one stage at a time.
- `src/chummer5/io/save_format.py`: `BuiltCharacter` deleted; `build_character` now returns
  `Character` directly, attaching all four selections via one `dataclasses.replace` at the end of
  its existing body (the five `create_*` calls inside it are unchanged). Module docstring's
  `BuiltCharacter` paragraph rewritten to explain the retirement.
- `src/chummer5/io/legacy_import.py`: `ImportResult.built` retyped from `BuiltCharacter` to
  `Character`; `import_legacy_character`'s body needed no changes (it already just forwarded
  `build_character`'s return value verbatim).
- `src/chummer5/web/session.py`: `ChargenSession` drops `skill_allocation`, `quality_selection`,
  `contacts`, `gear_names`; keeps only `character: Character | None` alongside the 4 priority
  letters and `metatype_id`. Docstring rewritten to describe the fold and point at the new
  equivalent reads (`character.contact_selection.contacts if ... else ()`, etc.).
- `src/chummer5/web/app.py`:
  - `_relink_quality_improvements` now takes the carried-forward `QualitySelection | None`
    directly (not `session: ChargenSession`), re-attaches it via `dataclasses.replace`, and returns
    the updated `Character`.
  - New `_relink_contact_selection` recomputes a carried-forward `ContactSelection` against a
    freshly built `Character` (see log).
  - `_replace_committed_qualities` now also re-attaches `quality_selection` via `replace` and
    returns the updated `Character` (previously mutated `character.improvements` in place and
    returned nothing).
  - `submit_priorities`: captures `previous = session.character` before rebuilding; carries forward
    `quality_selection` (relinked) and `contact_selection` (recomputed) from `previous`;
    `skill_allocation`/`resources_selection` are left at their fresh-`Character` default of `None`
    (the reset), rather than being explicitly zeroed as separate session-field writes.
  - `submit_attributes`: same relink/recompute for quality/contacts as `submit_priorities`, plus an
    explicit `dataclasses.replace` carrying `skill_allocation`/`resources_selection` forward
    unchanged (neither depends on attribute points).
  - `submit_skills`/`submit_qualities`/`submit_contacts`/`submit_resources`: each now writes its
    committed selection onto `session.character` via `dataclasses.replace` instead of a same-named
    `session.x = ...` assignment.
  - `_character_sheet_context`, `_character_save_from_session`, `_chargen_body_context`,
    `_apply_built_character_to_session`: all read through `character.skill_allocation`/
    `quality_selection`/`contact_selection`/`resources_selection` instead of the retired
    `session.x` fields; `_apply_built_character_to_session` collapses to a straight
    `session.character = built` (see log).
  - Module docstring gets a new WP18 paragraph explaining the fold and the WP18/WP19 split
    decision.
- `tests/integration/test_legacy_import_fixtures.py`,
  `tests/integration/test_save_format_fixtures.py`,
  `tests/integration/test_web_character_sheet_fixtures.py`: updated the handful of
  `result.built.character`/`built_before.character` accesses (now just `result.built`/
  `built_before`, since `built`/`built_before` are `Character` directly); every other
  `built.skill_allocation`/`.quality_selection`/`.contact_selection`/`.resources_selection` access
  needed no change, since those fields exist directly on `Character` now under the same names.

## Outcome

WP18 complete. `Character` is now the single aggregate for a character-in-progress: metatype,
attributes, and (once committed) `skill_allocation`/`quality_selection`/`contact_selection`/
`resources_selection` all live on one object, rather than four of them being independently-threaded
`ChargenSession` siblings reunited only ad hoc via the now-retired `BuiltCharacter`. `ChargenSession`
itself shrinks to just `character` plus the handful of genuinely pre-`Character` priority-letter
state. The one real design question this WP surfaced beyond the Implementation Plan's own text --
whether a carried-forward selection can simply be re-attached to a freshly rebuilt `Character`, or
must be recomputed -- resolved differently for `contact_selection` (must recompute, since its
karma/free-point figures depend on `character.attribute_value("CHA")`) than for `quality_selection`/
`resources_selection` (safe to carry by reference, neither has a character-state dependency); a new
`_relink_contact_selection` helper captures the first case, alongside a reshaped
`_relink_quality_improvements` for the second. Per the Implementation Plan's own explicit
allowance, `submit_attributes`/`submit_priorities` still rebuild via `create_character()` rather
than `dataclasses.replace`-ing in place -- that switch, and the re-validate-instead-of-reset
behavior it enables, is left to WP19, which this fold was specifically sequenced to set up (see the
Phase G intro). `pytest`/`ruff`/`mypy` are all green (242 tests, no new failures, no behavioral
assertion changed in meaning), and a manual walkthrough reproduces WP17's exact acceptance sequence
plus two WP18-specific regression checks (a contact surviving an attribute edit; a contact/quality
surviving priority reconfirmation while skill/gear correctly reset) that didn't exist as explicit
checks before this WP.
