# WP19 — Re-validate instead of reset on priority/metatype reconfirmation

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase G, WP19.

## Goal

Replace `submit_priorities`'s prior behavior — silently discarding attribute points, skill
allocation, and gear spend outright on every reconfirmation — with keeping the player's existing
selections, re-validating them against the new budgets/ranges, and surfacing exactly what's now
invalid. Per the Implementation Plan: `create_character`/`create_skill_allocation`/etc. already
raise itemized `ValueError`s for over-budget or out-of-range spend, so this WP is "attempt the
update and surface the failure," not new validation logic. Depends on WP18 (folding every
selection onto `Character` itself is what makes "keep everything except the field that changed"
a `dataclasses.replace` call instead of a five-field manual synchronization problem).

## Log

### 2026-07-18 — `dataclasses.replace`-ing the previous `Character` in place turned out to make
almost the entire deliverable free, including a bug the old design would have reintroduced

The obvious first design (mirroring the old `create_character()`-fresh + relink-helpers shape)
was: keep calling `create_character` in `submit_priorities`, wrap it in a `try`/`except`, and on
failure hand-construct an "unchecked" `Character` that carries the invalid points forward for
display. Working through that plan surfaced two problems before writing any code: (1) it needs a
parallel hand-rolled "unchecked" constructor for `ResourcesSelection` too (to carry gear forward
across a Resources-letter drop without raising), meaning real, if small, new validation-adjacent
logic — exactly what the Implementation Plan's own wording says this WP isn't supposed to need;
(2) it does nothing for the exact problem the Phase G intro flagged WP18 as setting up: `Character`
still gets rebuilt fresh, so `_relink_quality_improvements` is still needed, and the old
`ImprovementIndex` is still thrown away and rebuilt from scratch every reconfirmation.

Switching to `dataclasses.replace(previous, metatype=..., heritage_letter=..., attributes_letter=
..., special_attribute_points=...)` instead resolves both at once, for a reason worth spelling out
because it isn't obvious from the Implementation Plan's text alone: `Character`
([character.py](../../src/chummer5/engine/character.py)) has **no `__post_init__` validation** —
every invariant (`attribute_points` fits the letter's budget, values fit the metatype's range) is
enforced only by `create_character`'s own checks at construction time, not by the dataclass itself.
That means a `replace()` call carrying an old, budget-violating `attribute_points` forward onto a
new `attributes_letter`/`metatype` **just works** — no exception, no unchecked-constructor
workaround needed. And because `replace()` copies every untouched field *by reference*
(`skill_allocation`, `resources_selection`, `quality_selection`, and — the one that actually
matters here — `improvements`), a previously-applied quality's `Improvement`s are simply still
there on the replaced `Character`. This is a strictly better foundation than the old
`create_character()`-fresh + `_relink_quality_improvements` shape, not just a shorter way to write
the same thing: calling `_relink_quality_improvements` on a `replace()`-based `Character` would be
an active bug, not a no-op — `apply_quality_improvements` only ever *adds* Improvements (documented
on `_replace_committed_qualities`, which has to remove-then-reapply for exactly this reason when a
quality selection itself changes), so re-applying an already-present bonus onto an
already-populated `ImprovementIndex` would double it. Caught this by tracing what `replace()`
actually leaves in `character.improvements` before deciding whether the relink call was still
needed, not by assuming WP18's helper was still safe to reuse verbatim just because it compiled.
Net effect: `submit_priorities` no longer calls `_relink_quality_improvements` at all (only
`_relink_contact_selection`, which is a genuine recompute, not a re-apply, and stays necessary
regardless — see below); `_relink_quality_improvements` itself is unchanged and remains necessary
for `submit_attributes`, which this WP deliberately leaves on its pre-existing
`create_character()`-fresh shape (see the design-decision entry below for why).

### 2026-07-18 — Validity needs to be re-derived on every render, not decided once at submission
time, or the warning would vanish on the next page load

`ContactSelection` already established the precedent this WP needed (WP18's
`_relink_contact_selection`/`_character_sheet_context`): don't trust a stored, possibly-stale
number, recompute fresh from the character's *current* state every time it's rendered. The natural
first instinct for this WP was to compute "is this now over budget" once, inside `submit_priorities`
itself, and pass a message string down into the response context. That works for the *immediate*
HTMX response to the reconfirming `POST`, but silently breaks the very next `GET /`: nothing about
`ChargenSession` would remember that the character was left in an over-budget state, so a plain
page reload would show the (still over-budget, unchanged) spend with no explanation at all — worse
than before this WP, which at least reset to something consistent. Fixed by moving the
re-validation entirely into the three render-time context builders instead
(`_attribute_allocation_context`/`_skill_allocation_context`/`_resources_context`, each gaining an
`*_budget_warning` key): each re-runs the corresponding `create_*` validator against the
character's own current letter/metatype and catches the `ValueError` purely to read its message,
discarding the exception itself. This means `submit_priorities` doesn't need to attempt any
validation at all — it unconditionally carries every selection forward, and whether that's still
valid is a property derived fresh by whatever renders it next, exactly like `_relink_contact_
selection`'s own reasoning. A nice side effect: this also made the "still valid" case free — a
same-letters reconfirmation just naturally produces no warning, without needing a separate
no-op-detection branch anywhere.

Guarded each re-validation on `error is None` (i.e., skip it when the *same* request's own
submission was just rejected by that section's own route, e.g. `submit_attributes` catching a
`ValueError` on a freshly-typed value) — otherwise the freshly-rejected value's message and the
freshly-recomputed "no longer fits" message would both fire for the same underlying fact, shown
twice with slightly different wording. This is also why the two message strings stay textually
distinct ("primary attribute spend N exceeds..." vs. "No longer fits since priorities were last
confirmed: primary attribute spend N exceeds...") — `attribute_error`/`skill_error`/
`resources_error` are for "you just typed something invalid this request," `*_budget_warning` is
for "this was fine when you entered it, but a priority change since then broke it," and a
template needs to be able to style/word them differently even though today both just render as a
`<p>` with a CSS class.

### 2026-07-18 — `_character_sheet_context` had its own latent staleness bug once gear stopped
being reset, caught by tracing (not just running) the resources path

WP18's `_character_sheet_context` reads `character.resources_selection.nuyen_budget`/
`.nuyen_remaining` directly off the stored object, on the reasoning (correct *at the time*,
documented in its own docstring) that `resources_selection` has no character-state dependency to
go stale against. That reasoning silently broke once this WP stopped resetting `resources_
selection` on a Resources-letter change: the stored object's own `nuyen_budget` field is computed
at the time it was built, against whatever letter was current *then* — after this WP, that can now
differ from `session.resources_letter` at render time. Concretely: buy gear at Resources D, swap to
Resources C, and the character sheet would keep showing D's budget forever, silently wrong, with no
exception to catch it (unlike the over-budget case, this doesn't even produce a negative number —
it just uses the wrong positive one). Not caught by any test failure — pytest's fixture-based
character-sheet tests never exercise a Resources-letter change after committing gear — caught by
deliberately re-reading every place `character.resources_selection` is read directly (not just the
places that raise) before considering the resources side of this WP done. Fixed with a new
`_resources_selection_for_display(letter, gear_names)` helper: recomputes a `ResourcesSelection`
from scratch against the given letter, without `create_resources_selection`'s budget check (needed
because the read-only character-sheet page must render an over-budget carry-forward, e.g. as a
negative `nuyen_remaining`, not crash on it). `_resources_context` never had this bug (it already
recomputed `nuyen_budget`/`nuyen_remaining` directly from its own `resources_letter` argument on
every call, never trusting the stored object's fields) — only the character sheet did.

### 2026-07-18 — Extended `_resources_context` with a `resources_budget_warning` too, beyond the
Implementation Plan's literal list of three context builders

The Implementation Plan's WP19 entry names exactly three context builders to extend:
`_priority_form_context`/`_attribute_allocation_context`/`_skill_allocation_context`. It doesn't
mention `_resources_context`, but the same entry's first bullet explicitly includes
"skill_allocation/gear_names" as carried-forward, re-validated state. Treated the three-item list
as illustrative, not exhaustive (the same paragraph also says "distinctly ... **where reasonable**"
about the message itself) — a stale gear purchase after a Resources-letter drop deserves the same
explanation a stale skill allocation gets, not silence just because the deliverable text's example
list happened to stop at three. Extended `_resources_context` the same way as the other two.

### 2026-07-18 — `_priority_form_context` itself doesn't compute the aggregate "something's stale"
banner; `_chargen_body_context` injects it into the merged context instead

The Implementation Plan says to extend `_priority_form_context` to "carry and render" the
stale-selection message. Doing that literally — adding a parameter to `_priority_form_context`
itself — would require its two call sites (`index()` and `submit_priorities()`) to compute the
three sections' `*_budget_warning` values *before* calling it, then call `_chargen_body_context`
again for the actual sections, duplicating each `create_*` re-validation call a second time per
request. Instead, `_chargen_body_context` (which already has to build all three sub-contexts to
render the sections themselves) computes `priority_stale_selections = bool(any of the three
warnings)` once and folds it into a copy of the `priority_ctx` dict it was handed, right before the
final merge. `_priority_form.html` is only ever rendered from that merged dict — it can't tell, and
doesn't need to, which Python function actually set the key. Documented this explicitly in both
functions' docstrings so a future reader searching for "where does `priority_stale_selections` get
set" doesn't spend time in `_priority_form_context` first.

### 2026-07-18 — Two existing tests directly encoded the old reset behavior and had to be rewritten,
not just left passing

`test_reconfirming_priorities_resets_attribute_and_skill_allocation`
(`tests/unit/test_web_attribute_skill_allocation.py`) and
`test_reconfirming_priorities_with_a_new_resources_letter_resets_gear`
(`tests/unit/test_web_quality_contacts_resources.py`) both asserted the pre-WP19 reset outright —
the Implementation Plan's own WP18 worklog even recorded this as the *correct*, verified behavior
at the time ("gear correctly reset, matching the documented reset rule"). Both were expected
failures once this WP's change landed (confirmed by running the suite before writing any new
tests, not assumed), and were rewritten rather than deleted: the first is now
`test_reconfirming_priorities_with_a_still_fitting_budget_keeps_the_allocation` (same scenario,
opposite assertion), and the second is `test_reconfirming_priorities_with_a_new_resources_letter_
keeps_gear` plus a new `test_reconfirming_priorities_with_a_lower_resources_budget_flags_the_
existing_gear` covering the actually-over-budget case the original test never exercised (a cheap
100¥ Meta Link never comes close to any Resources letter's budget, so the original test could only
ever demonstrate a full reset, never an over-budget carry-forward — the new test buys 70 Ares
Predator Vs, 50,750¥, to actually cross a budget boundary between Resources C and D).

### 2026-07-18 — Found, and deliberately did not fix, a pre-existing template crash unrelated to
this WP's own change

While walkthrough-testing with a deliberately garbage `skills_letter` value (not a WP19 scenario —
just probing edge cases), `POST /ui/priorities` 500'd: `_priority_form.html`'s "Confirmed: ..."
summary block renders `skills_priorities[selected.skills_letter]` using the *raw just-submitted*
letter (echoed for the duplicate-letter-error redisplay case), not the session's committed one.
`selected.skills_letter` is only ever guaranteed to be a real `PRIORITY_LETTERS` member when the
submission was actually accepted; the duplicate-letter check
(`sorted(submitted_letters) != sorted(PRIORITY_LETTERS)`) only rejects letters that aren't a valid
A-D *permutation*, not letters that aren't valid dictionary keys at all — a value like
`"E-doesnotexist"` fails neither check yet crashes the template lookup once `character` is already
non-`None` from an earlier successful confirmation. This predates WP19 entirely (the "Confirmed"
block and its `selected.*` indexing are untouched by this WP) and isn't part of WP19's stated scope
(input hardening on the priority form, not reconfirmation-reset behavior) — flagged here rather
than silently fixed in passing, per this project's "don't hide a real gap" precedent (see e.g.
WP8's negative-quality-catalog note, WP9's contact-karma-cap note), so a future WP can pick it up
deliberately instead of it being rediscovered from scratch.

## Design decisions

- **Only `submit_priorities` switches to `dataclasses.replace`-in-place; `submit_attributes` keeps
  its `create_character()`-fresh + relink-helper shape.** The Implementation Plan's WP19 entry
  only lists `submit_priorities`'s reset as the bug to fix ("only the two paths that do reset
  without needing to ... change"); `submit_attributes` never reset anything it didn't need to
  (quality/contacts were already correctly relinked under the old design), so there's no bug to
  fix there, and switching it too would be doing an unscoped generalization under this WP's
  acceptance bar rather than the specific, testable behavior change the Plan asks for. This does
  mean `submit_attributes` still discards and rebuilds `improvements` on every attribute edit
  (relying on `_relink_quality_improvements` to re-populate it) where `submit_priorities` no longer
  does — a real asymmetry between the two routes, left as a natural candidate for a future
  "generalize the replace-in-place shape" WP rather than folded into this one.
- **An over-budget-after-reconfirmation character does not block further chargen progress.** Per
  the Implementation Plan's own recommendation and its "don't require the full budget to be spent,
  validate at the boundary" precedent (already the rule for every `create_*` function in this
  codebase — none of them require full-budget spend, only reject *over*-budget spend at the point
  it's entered). Concretely: nothing prevents visiting `/character/sheet`, saving, or continuing to
  edit qualities/contacts/resources while an attribute or skill section sits over budget; the
  character sheet renders the (possibly negative) numbers as-is rather than erroring or hiding
  them. The alternative (blocking navigation until fixed) would need new cross-route state to track
  "is chargen currently blocked" and a set of routes to enforce it against — real new machinery
  this WP's own deliverable list doesn't ask for, to prevent a UX outcome (see a negative number,
  fix it, or don't) that's already how every other over/under-spend case in this app already
  behaves.
- **Validity is re-derived at render time by re-running the existing `create_character`/
  `create_skill_allocation`/`create_resources_selection` validators and discarding the exception
  object (keeping only its message), not by writing new comparison logic.** Directly satisfies the
  Implementation Plan's "this WP is 'attempt the update and surface the failure,' not new
  validation logic" -- the *only* validation that exists anywhere in this WP's diff is the three
  pre-existing `create_*` functions, called one extra time each, at render time instead of (or in
  addition to) submission time.
- **`resources_selection`'s carry-forward needed one genuinely new function
  (`_resources_selection_for_display`), unlike `skill_allocation`.** `SkillAllocation` carries no
  letter-derived fields of its own (`skill_points`/`group_points` only), so carrying the old object
  forward by reference is always safe -- every downstream read recomputes rating/pool/budget
  against the *current* `skills_letter` from outside the object. `ResourcesSelection` is different:
  it stores `resources_letter`/`nuyen_budget`/`nuyen_remaining` as its own fields, computed once at
  construction, so those readers that trust the stored fields (only `_character_sheet_context`, as
  it turns out -- see the log entry above) need a way to get an up-to-date `ResourcesSelection`
  without hitting `create_resources_selection`'s budget-exceeded exception. This is the one place
  in this WP that isn't just "call the existing validator and read the message" -- it's a genuine,
  if small, second constructor. Kept it minimal (a direct transcription of `create_resources_
  selection`'s own body minus the `raise`) rather than refactoring `chummer5.engine.resources` to
  share the two, since this WP's stated scope is the web layer's reconfirmation behavior, not new
  engine API surface.

## Implementation

- `src/chummer5/web/app.py`:
  - `submit_priorities`: on a valid metatype/letters submission with an existing `session.
    character`, builds the new `Character` via `dataclasses.replace(previous, metatype=...,
    heritage_letter=..., attributes_letter=..., special_attribute_points=...)` instead of
    `create_character(choice, heritage_letter, attributes_letter, PRIORITIES, {})` -- every other
    field (`attribute_points`, `skill_allocation`, `resources_selection`, `quality_selection`,
    `improvements`) carries forward by reference, unvalidated against the new letters/metatype.
    `_relink_quality_improvements` is no longer called here (would double-apply the already-present
    bonus); `_relink_contact_selection` still is (a genuine CHA-dependent recompute, unaffected by
    the `replace`-vs-`create_character` choice). The `previous is None` (very first confirmation)
    branch still constructs a plain `Character(...)` directly, since there's nothing to replace.
  - `_attribute_allocation_context`/`_skill_allocation_context`/`_resources_context`: each gains a
    `*_budget_warning` key, computed only when the `error` kwarg is unset, by re-running the
    matching `create_*` validator against the character's/session's current letter and catching
    `ValueError` for its message.
  - `_chargen_body_context`: computes `priority_stale_selections` (`True` if any of the three
    `*_budget_warning`s fired) and folds it into `priority_ctx` before the final merge.
  - `_priority_form_context`: docstring only (notes the key it receives from its caller; no
    parameter/behavior change).
  - `_resources_selection_for_display(letter, gear_names)`: new helper, an unchecked
    `ResourcesSelection` recompute for the character sheet (see design decisions).
  - `_character_sheet_context`: reads `resources_selection` via `_resources_selection_for_display`
    against `session.resources_letter`/the committed gear names, not directly off `character.
    resources_selection` (see log).
  - `_relink_quality_improvements`: docstring updated to note it's `submit_attributes`-only now.
  - `_relink_contact_selection`: docstring's "the two things that trigger a fresh
    `create_character()` call" wording updated (no longer accurate for `submit_priorities`).
  - Module docstring: new WP19 paragraph.
- `src/chummer5/web/session.py`: `ChargenSession`'s docstring rewritten -- the "attribute_points/
  skill_allocation reset, resources_selection reset" paragraph replaced with a description of the
  re-validate-in-place behavior and the render-time warning mechanism.
- `src/chummer5/web/templates/_attribute_allocation.html`,
  `_skill_allocation.html`, `_resources.html`: each gains a `{% if *_budget_warning %}` block
  (`class="warning"`, distinct from the existing `class="error"` block for `*_error`).
- `src/chummer5/web/templates/_priority_form.html`: gains a `{% if priority_stale_selections %}`
  block just below the existing `error` block.
- `tests/unit/test_web_attribute_skill_allocation.py`: rewrote the one test that asserted the old
  reset behavior; added two new tests (`test_reconfirming_priorities_with_a_lower_attributes_
  budget_flags_the_existing_spend`, `test_reconfirming_priorities_with_a_lower_skills_budget_
  flags_the_existing_spend`) covering the now-invalid transition for both attributes and skills.
- `tests/unit/test_web_quality_contacts_resources.py`: rewrote the resources-letter reset test;
  added `test_reconfirming_priorities_with_a_lower_resources_budget_flags_the_existing_gear`.

## Outcome

WP19 complete. `submit_priorities` no longer discards a player's attribute points, skill
allocation, or gear purchase on every metatype/priority reconfirmation — it carries every selection
forward via `dataclasses.replace` against the previous `Character` (which, as a side effect of
having no `__post_init__` validation, made the "invalid-pending" state the Implementation Plan
asks for essentially free) and re-derives whether each still fits the newly confirmed letters/
metatype fresh on every render, rather than deciding once at submission time. A carried-forward
selection that no longer fits is not reset and does not block further chargen progress — it renders
with its real (possibly negative) remaining-budget numbers plus a distinct "no longer fits since
priorities were last confirmed" message in the affected section(s), and an aggregate banner at the
top of the priority form when any section is affected; both clear automatically, on the very next
render, once the player edits that section back within budget. The switch to `dataclasses.replace`
also retired the need for `_relink_quality_improvements` in `submit_priorities` specifically (the
carried-forward `ImprovementIndex` already has the right bonuses; re-applying them would have
double-counted a quality's bonus, a real correctness bug the old create-fresh-then-relink shape
would have reintroduced if ported over naively) — `submit_attributes` is unchanged and still needs
that helper, a deliberate, documented scope boundary rather than an oversight. Fixed one
WP19-caused regression before it could ship (the character sheet's `resources_selection` reads
becoming stale once gear stopped resetting on a Resources-letter change) and flagged, without
fixing, one pre-existing and unrelated template crash on malformed priority-letter input found
during manual testing. `pytest`/`ruff`/`mypy` are all green (245 tests, 2 rewritten to match the
new behavior, 4 new covering the still-valid/now-invalid transitions for attributes/skills/
resources), and a manual walkthrough reproduces the Implementation Plan's exact acceptance scenario
plus the parallel still-valid case and the aggregate-banner/self-healing behavior beyond what the
Plan's text explicitly asked for.
