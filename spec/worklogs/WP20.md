# WP20 — Lifestyle selection

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase H, WP20.

## Goal

Add SR5's mandatory core-rulebook "Step Six" Lifestyle chargen step (rulebook, p. 369: "A character
must select one of the lifestyles below to be their primary Lifestyle"), paid from the same
Resources-priority nuyen budget the gear purchase already draws from — an oversight found during
post-MVP scoping (Project Overview's "gap found after MVP shipped" note), not a deliberate cut.
Deliverables per the Implementation Plan: a `lifestyles.xml` loader restricted to the 6 real SR5
starting tiers; an engine `LifestyleSelection`/`create_lifestyle_selection`; wiring into the shared
Resources nuyen budget; a web form; and threading through save format and legacy import.

## Log

### 2026-07-19 — Confirming the minimum-months rule needed the legacy C#, not just the rulebook
text

The rulebook's own "Lifestyle"/"Paying the Bills" sections (p. 369-370) establish that Lifestyle
cost accrues monthly and prepayment is allowed, but never state a numeric minimum/maximum in prose.
Found the actual floor/ceiling in `CharacterCreate.Designer.cs`'s `nudLifestyleMonths` control
(`Minimum = 1`, `Maximum = 100`) — a character-creation-screen-only field, distinct from
`SelectLifestyle.cs`'s own picker dialog, which has no months input at all and always constructs a
`Lifestyle` at `_intIncrements = 1`. The 100-month ceiling isn't arbitrary either: it's the exact
threshold "Buying a Lifestyle" (p. 370) uses to make a Lifestyle permanent ("a payment equal to 100
months' upkeep"), confirming the UI's cap and the rulebook's own "permanent purchase" rule are the
same boundary, not two unrelated numbers. Recorded the full trace in
`spec/rulebooks/learnings.md`'s new WP20 entry, including `Lifestyle.TotalCost`'s exact formula
(`GetTotalMonthlyCost() * Increments`) confirming `tier.monthly_cost * months` is the right formula
with no hidden multiplier for the plain-tier case this WP covers.

### 2026-07-19 — The legacy save format has no "which lifestyle is primary" flag; a real fixture
(`BLUE.chum5`) forced a concrete tie-breaking rule

Confirmed by reading `Lifestyle.cs` directly: there is no `IsPrimary`/equivalent field anywhere,
only a general `LifestyleType.Standard` that doesn't distinguish "the" primary Lifestyle from any
additional ones a character maintains (rulebook, p. 369: "They may elect to pay other lifestyle
costs as well... but must pay full cost on all lifestyles they maintain"). This matters concretely:
`BLUE.chum5` (one of the 11 curated mundane fixtures) has *two* `<lifestyle>` entries — an in-scope
`Medium` tier ("Redmond") and an out-of-scope `RF`-sourced "Bolt Hole" ("Grannies House
'Hollywood'"). Checked document order across all 11: the in-scope entry is always first. Adopted
"first `<lifestyle>` child in document order is primary" as this project's own convention
(documented in `legacy_import.py`'s module docstring, not silently assumed), rather than guessing at
a rule the format itself doesn't encode.

### 2026-07-19 — Deciding the shared-budget design before writing any web code: a separate
`LifestyleSelection` on `Character`, not nested inside `ResourcesSelection`

The Implementation Plan explicitly left open whether to widen `ResourcesSelection` with a
`lifestyle` field or keep a separate selection checked against the same remaining-budget number.
Widening `ResourcesSelection` was the more "obvious" shape (one object, one validated total), but
would have meant `chummer5.engine.resources` importing `chummer5.engine.lifestyle`'s types and
`ResourcesSelection`'s own name (already "the gear/resources answer") absorbing a second, separately-
committed selection with its own catalog and validation rules — a worse fit than the existing
5-selection-fields-on-`Character` shape WP18 already established. Went with a 6th sibling field,
`Character.lifestyle_selection: LifestyleSelection | None`, and gave `create_resources_selection` one
new keyword-only parameter, `lifestyle_cost: int = 0`, that folds an already-computed total into the
one joint over-budget check. This keeps `chummer5.engine.lifestyle` fully decoupled from
`chummer5.engine.resources` (no import either direction) while still centralizing "does this fit the
Resources letter's nuyen budget" in one place — the same principle Project Overview's Architecture
section states for `Character`'s attribute-point budgets, applied to a second joint constraint.
`lifestyle_cost` defaulting to `0` also meant every pre-WP20 call site (all of `chummer5.engine`,
every existing test) needed zero changes to keep behaving identically — confirmed by running the
suite before writing any new lifestyle-specific test, not assumed.

### 2026-07-19 — Web layer: threading `gear_cost`/`lifestyle_cost` across two peer sections turned
out to be the only genuinely new plumbing this WP needed

Chose a new peer section (`_lifestyle.html`, `POST /ui/lifestyle`) over folding into
`_resources.html`/`submit_resources`, despite both spending from one budget — SR5 frames "pick your
primary Lifestyle" and "buy gear" as two distinct decisions (a `<select>` + a months field vs. an
~5-row quantity table), and cramming both into one form/route would make `_resources_context`
responsible for two unrelated catalogs. The real cost of keeping them separate: each section's
context builder needs the *other* section's already-committed cost as a plain `int` to validate and
display the shared remaining budget correctly (`_resources_context` gained a `lifestyle_cost`
parameter; the new `_lifestyle_context` takes a mirror-image `gear_cost`) — `_chargen_body_context`
computes both once, from `character.resources_selection.nuyen_spent` /
`character.lifestyle_selection.total_cost`, and passes each into the other section's builder. This
is a deliberate, small amount of cross-section coupling (two `int`s passed across a function
boundary), not a shared-state redesign — each section still only touches its own catalog/template.

### 2026-07-19 — Found and accepted a real UX limitation: buying gear doesn't live-refresh the
Lifestyle section's own displayed remaining number (or vice versa)

Every HTMX form in this app targets only its own `<div>` (`hx-target="#resources"`,
`hx-target="#lifestyle"`, etc.) — a pattern established since WP15 and never revisited. Two sections
now share one *validated* budget (submitting either one always checks the true combined total via
`create_resources_selection`), but each section's own displayed "remaining" number is computed at
that section's own last render, not live-pushed when the *other* section changes. Concretely: buy
gear that uses 43,500 of a 50,000 budget, then separately view the Lifestyle section without
reloading the page — it still shows whatever remaining figure its last render computed, not knowing
gear now also exists. A full page reload (`GET /`) always recomputes both correctly, since
`_chargen_body_context` builds every section fresh from the same `Character` each time; this is the
same "recompute at render time, not push on write" property WP19 relies on for its
`*_budget_warning` mechanism. Considered adding an HTMX out-of-band swap so each route's response
also refreshes the other section, but that's new UI machinery this WP's own deliverable list doesn't
ask for, to fix a cosmetic staleness window that a page reload (or the section's own next edit)
already clears — documented in `_resources_context`'s docstring as a deliberate scope boundary
rather than silently left unexplained, the same "flag, don't hide" precedent WP19 set for its own
found-but-unfixed template crash.

### 2026-07-19 — `submit_attributes` needed one explicit line; `submit_priorities` needed none

`submit_priorities` (since WP19) rebuilds via `dataclasses.replace(previous, metatype=...,
heritage_letter=..., attributes_letter=..., special_attribute_points=...)` — `lifestyle_selection`,
untouched by that call, survives by reference automatically, exactly like `quality_selection`/
`resources_selection` already do. `submit_attributes` still calls `create_character()` fresh (WP18/
WP19's documented, deliberately-kept asymmetry), so it needed `lifestyle_selection=previous.
lifestyle_selection` added to its existing explicit `replace(...)` alongside `skill_allocation`/
`resources_selection` — a one-line addition once the asymmetry was already understood from WP19's
own worklog, not a new discovery.

## Design decisions

- **`Character.lifestyle_selection` is a 6th sibling selection field, not nested inside
  `ResourcesSelection`.** See the log entry above for the full reasoning — keeps
  `chummer5.engine.lifestyle` and `chummer5.engine.resources` mutually decoupled while still
  centralizing the joint nuyen-budget check in one function (`create_resources_selection`'s new
  `lifestyle_cost` parameter).
- **A save (`CharacterSave`) always carries a concrete `lifestyle_tier_name`/`lifestyle_months`,
  unlike `gear_names`/`quality_ids`/`contacts`, which are fine empty.** SR5 makes Lifestyle
  mandatory; there's no meaningful "no lifestyle yet" save state the way there is for "bought no
  gear". An in-progress `ChargenSession` that hasn't visited the Lifestyle form yet still needs a
  concrete value to save, so `_character_save_from_session` falls back to
  `DEFAULT_LIFESTYLE_TIER_NAME`/`DEFAULT_LIFESTYLE_MONTHS` ("Street", 1 — the rulebook's own free
  tier) rather than leaving the save unbuildable.
- **Legacy import treats a missing or out-of-scope primary Lifestyle as blocking, not
  excluded-and-reported.** Unlike a dropped quality/skill (incomplete but harmless), silently
  defaulting an imported character's real nuyen spend to a tier it never actually had (e.g. free
  Street) would misrepresent a real number, the same reasoning `legacy_import.py` already applies to
  cyberware/Magic/metavariants. Unlike those three, though, the *lifestyle catalog itself* is
  complete (all 6 real starting tiers, not a stub), so every one of the 11 curated fixtures' actual
  primary Lifestyle *is* faithfully reconstructable — confirmed by testing all 11, not just Yeti
  (see Verification).
- **The 100-month maximum is enforced, even though no fixture or acceptance scenario needs it.**
  Kept because it's a real, rulebook-grounded boundary (see the log entry on where it came from),
  not a speculative addition — cheap to include once confirmed, and a natural companion to the
  1-month minimum every legal selection already has to satisfy.
- **No HTMX out-of-band swap between `#resources` and `#lifestyle`.** A deliberate, documented scope
  boundary — see the log entry above. Validation is always correct (both routes check the true
  combined budget); only each section's own *display* of the other section's contribution can lag
  until the next full render.

## Implementation

- `src/chummer5/data/lifestyle.py` (new): `LifestyleTier` (`name`, `monthly_cost`, `source`,
  `page`); `load_lifestyles()` restricted to `source == "SR5"` and `STARTING_TIER_NAMES` (Street,
  Squatter, Low, Medium, High, Luxury) — excludes the "ID ERROR" placeholder and both Hospitalized
  entries.
- `src/chummer5/engine/lifestyle.py` (new): `LifestyleSelection` (`tier`, `months`, `total_cost`);
  `create_lifestyle_selection(tier_name, months, catalog)` validating the tier is known and
  `MIN_LIFESTYLE_MONTHS <= months <= MAX_LIFESTYLE_MONTHS` (1-100); `total_cost = tier.monthly_cost
  * months`. No budget check here — see design decisions.
- `src/chummer5/engine/character.py`: `Character` gains `lifestyle_selection: LifestyleSelection |
  None = None` (`TYPE_CHECKING`-only import, same pattern as the other 4 WP18 selections).
- `src/chummer5/engine/resources.py`: `ResourcesSelection` gains `lifestyle_cost: int = 0`;
  `create_resources_selection` gains a `lifestyle_cost: int = 0` keyword parameter, folded into the
  over-budget check (`gear_spent + lifestyle_cost > budget`) and into `nuyen_remaining`; the
  raised message distinguishes "gear spend" (unchanged wording, `lifestyle_cost == 0`) from "gear
  (…) + lifestyle (…) spend" (when nonzero).
- `src/chummer5/io/legacy_chum5.py`: new `LegacyLifestyle` (`base_lifestyle`, `months`,
  `monthly_cost`, `source`); `LegacyCharacter.lifestyles: tuple[LegacyLifestyle, ...]` (every
  `<lifestyle>` entry, raw, in document order); `load_chum5` wires it up.
- `src/chummer5/io/legacy_import.py`: `_blocking_reasons` rejects a missing or out-of-scope primary
  Lifestyle (`legacy.lifestyles[0]`, per the "first entry is primary" convention documented in the
  module docstring); `import_legacy_character`/`import_chum5` gain a `lifestyles` catalog parameter,
  threaded into `create_character_save`/`build_character`.
- `src/chummer5/io/save_format.py`: `CharacterSave` gains required `lifestyle_tier_name`/
  `lifestyle_months` fields; `build_character` gains a `lifestyles` catalog parameter, calls
  `create_lifestyle_selection` and feeds its `total_cost` into `create_resources_selection`'s
  `lifestyle_cost`, and attaches `lifestyle_selection` in its final `replace`.
- `src/chummer5/web/app.py`:
  - `LIFESTYLES = load_lifestyles()` (module-level, parsed once); `DEFAULT_LIFESTYLE_TIER_NAME =
    "Street"`, `DEFAULT_LIFESTYLE_MONTHS = MIN_LIFESTYLE_MONTHS`.
  - New `_parse_lifestyle_months` (malformed input clamps to 0, same "let the engine validate"
    pattern `_parse_gear` already uses for a negative quantity).
  - New `_lifestyle_context(character, resources_letter, tier_name, months, gear_cost, *,
    error=None)`: same `error`-gated re-validation shape as `_resources_context`, surfacing a
    `lifestyle_budget_warning` distinct from a request's own rejected submission.
  - `_resources_context`/`_resources_selection_for_display` gain a `lifestyle_cost` parameter,
    folded into the displayed/re-validated remaining budget.
  - `_character_sheet_context`/`_character_save_from_session`/`_chargen_body_context` all thread
    `lifestyle_selection` through (reading it directly off `character` — it has no character-state
    dependency to go stale against, unlike `contact_selection`).
  - New `POST /ui/lifestyle` route (`submit_lifestyle`), mirroring `submit_resources`'s shape:
    build+validate via `create_lifestyle_selection` then the joint `create_resources_selection`
    check; on success, `dataclasses.replace`s both `lifestyle_selection` and `resources_selection`
    onto `session.character`.
  - `submit_resources` now passes the character's current `lifestyle_selection.total_cost` (or 0)
    as `lifestyle_cost` into `create_resources_selection`.
  - `submit_attributes` carries `lifestyle_selection` forward alongside `skill_allocation`/
    `resources_selection` in its explicit `replace(...)`.
  - `download_save`/`load_save`/`import_chum5_route` pass `lifestyles=LIFESTYLES` into
    `build_character`/`import_chum5`.
- `src/chummer5/web/templates/_lifestyle.html` (new): tier `<select>` + months `<input>`, mirroring
  `_metatype_select.html`'s single-line option markup (needed for correct `selected` rendering) and
  `_resources.html`'s error/warning block shape.
- `src/chummer5/web/templates/_chargen_body.html`: includes `_lifestyle.html` between contacts and
  resources.
- `src/chummer5/web/templates/_character_sheet.html`: new "Lifestyle" section (tier/months/cost, or
  "None selected").
- `spec/rulebooks/learnings.md`: new WP20 entry (minimum-months rule, `TotalCost` formula,
  `<cost>`-is-a-monthly-rate save-format trap).
- Tests: `tests/unit/test_lifestyle.py` (new — loader + engine, synthetic/hand-checked),
  `tests/unit/test_web_lifestyle.py` (new — the `/ui/lifestyle` route, shared-budget interactions,

## Outcome

WP20 complete. Every mundane priority-built character now goes through SR5's mandatory primary-
Lifestyle purchase, drawing from the same Resources-priority nuyen budget the starter-gear purchase
already used — `chummer5.engine.lifestyle.create_lifestyle_selection` computes `tier.monthly_cost *
months`, and `chummer5.engine.resources.create_resources_selection`'s new `lifestyle_cost` parameter
is the one place the combined spend is validated against the budget, keeping the two engine modules
mutually decoupled. The web layer gained a full peer section (`POST /ui/lifestyle`,
`_lifestyle.html`) alongside Resources, wired into the same WP19-style render-time re-validation
(`lifestyle_budget_warning`, folded into the existing `priority_stale_selections` aggregate) and the
same carry-forward-by-reference behavior every other post-WP18 selection already gets from
`submit_priorities`'s `dataclasses.replace`-in-place. Save format and legacy import both thread the
selection through completely — and, unlike gear (a deliberately minimal stub), the Lifestyle catalog
is real and complete enough that every one of the 11 curated fixtures' actual primary Lifestyle is
faithfully reconstructable, which the new cross-corpus test exercises directly rather than settling
for Yeti alone. `pytest`/`ruff`/`mypy` are all green (277 tests, 29 more than before this WP), and a
real-HTTP manual walkthrough (confirm → buy gear → select a Lifestyle → save → reload into a fresh
session; separately, import `Yeti-#ffffff2.chum5`) reproduces the correct combined-budget numbers
throughout. One deliberate, documented scope boundary: gear and Lifestyle don't live-refresh each
other's displayed remaining-budget number via HTMX out-of-band swaps — both sections' actual
*validation* is always correct regardless, and a full page reload always shows fully consistent
numbers, so this is a cosmetic staleness window rather than a correctness gap, flagged here per this
project's "don't hide a real gap" precedent rather than silently left unexplained.
