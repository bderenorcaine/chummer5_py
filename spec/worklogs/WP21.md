# WP21 — Expand the starter-gear catalog to the full flat-cost SR5 equipment set

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase H, WP21.

## Goal

Grow `STARTER_GEAR_CATALOG` from the 5 hand-picked items WP9 introduced to the real SR5-core,
flat-cost gear/armor/weapon catalog — via a real XML loader (`chummer5.data.gear`) instead of a
hardcoded list, per the Implementation Plan's Phase H scoping (confirmed at "411 items" pre-research:
266 gear + 11 armor + 134 weapons, `source == "SR5"` and a plain integer `<cost>`, no
`Rating`/`FixedValues`/`Variable` formula).

## Log

### 2026-07-19 — Re-deriving the plan's pre-computed counts directly from the XML

Parsed `legacy/Chummer/data/{gear,armor,weapons}.xml` directly (`xml.etree.ElementTree`, not
`pdftotext` — this is schema/data-shape work, not a rules question; see Verification for why the
rulebook PDF wasn't needed this WP) to re-confirm the Implementation Plan's own research before
writing any loader code, the same "verify, don't assume" habit WP2/WP3/WP4 established for their own
pre-stated counts. Result matched exactly: 391 SR5-sourced `<gear>` entries (266 flat-cost — 125
excluded: 120 `Rating`-formula, 2 `FixedValues`, 1 `Variable`, and 2 more with a leading `+` sign —
`Card Reader`/`Biometric Reader`'s "+50"/"+200", a cost *added to a parent item's price* rather than
a standalone one, confirmed by their `<requireparent/>` tag); 12 SR5-sourced `<armor>` entries (11
flat-cost — 1 excluded: `Clothing`'s `Variable(20-100000)`); 134 SR5-sourced `<weapon>` entries, all
already flat-cost. 266 + 11 + 134 = 411, exactly the plan's number.

### 2026-07-19 — A genuine data problem the plan's headline number didn't anticipate: real
cross-file name collisions at different prices

Before wiring the loaded catalog into `chummer5.engine.resources`, checked whether `StarterGearItem`'s
name-keyed shape (`by_name = {item.name: item for item in catalog}` in both `create_resources_
selection` and the web layer) still holds up once the catalog grows from 5 items (guaranteed unique
by construction) to 411 pulled from three independent files. It doesn't, cleanly: 36 names appear
more than once across the 411 flat-cost items, and for 5 of them the duplicate has a **different**
cost — `Ballistic Shield` (1200 as `Armor`-category armor vs. 0 as an `Exotic Melee Weapons` weapon),
`Riot Shield` (1500 vs. 0), `Grapple Gun` (500 vs. 0), `Micro Flare Launcher` (175 vs. 0), and
`Vision Magnification` (250 as a standalone `Vision Enhancements` accessory vs. 0 as a
`<required>`-gated `Sensor Functions` component). A plain `dict` build silently lets the last-seen
entry win — for these 5 names, that's a coin-flip on parse order between the real price and 0,
which would have made buying "Grapple Gun" sometimes free depending on nothing the player did.

Traced why: every 0-cost weapons.xml side of these collisions carries a `<hide/>` tag — the legacy
data's own convention for "this weapon entry is an auto-granted profile, not something the player
picks directly" (e.g. buying the real, 1200¥ `Armor`-category "Ballistic Shield" auto-adds a
same-named, 0-cost `Exotic Melee Weapons` entry via `<addweapon>`, purely so the shield's
melee-attack stats — accuracy, damage, reach — exist somewhere for combat to reference). 18 of the
134 flat weapons and 29 of the 266 flat gear entries carry `<hide/>` in total. `Vision
Magnification`'s 0-cost duplicate isn't `<hide/>`-tagged, but is instead gated behind `<required>`
(only obtainable already-attached to a Sensors/Custom-category parent) — a related but distinct
"not independently purchasable" signal.

Resolution, implemented in `chummer5.engine.resources.build_starter_gear_catalog` rather than in
the loader itself (kept `chummer5.data.gear`'s own loaders as a literal, independently-testable
translation of each XML file, with the 411-count acceptance criterion satisfied literally): drop
every `hidden` gear/weapon entry outright (never a real standalone pick, regardless of whether it
happens to collide with anything), drop the 3 additive-stacking armor items (see below), and for
the one remaining non-hidden collision plus ~30 harmless same-cost duplicates (e.g.
`Grenade: Flash-Bang` priced identically as both `Ammunition` gear and a throwable weapon), keep
whichever entry has the higher cost. Verified this resolves all 5 real collisions correctly and is a
no-op for the harmless ones (see `tests/unit/test_gear.py`).

### 2026-07-19 — The 3 additive-stacking armor items, and why `armor_stacks` lives on the data
class rather than being silently dropped by the loader

Per the Implementation Plan's own instruction, checked `armor.xml`'s SR5-sourced `<armor>` field
directly: 8 of the 11 flat-cost entries have a plain single-rating value (`Armor Vest` → `9`, etc.);
3 (`Helmet` → `+2`, `Ballistic Shield` → `+6`, `Riot Shield` → `+6`) use a `+N` *additive* bonus
meant to stack on top of whatever armor is already worn — genuinely different math from a standalone
rating, and out of this WP's scope to model correctly. `chummer5.data.gear.load_armor` still parses
and returns all 11 (with `armor_stacks: bool` computed from whether the raw `<armor>` text starts
with a sign character), rather than filtering them out at the loader level — `build_starter_gear_
catalog` is what excludes `armor_stacks` items from what's purchasable, mirroring WP3's own
"raw data loader keeps everything + a classification flag; the engine layer decides what's offered"
precedent (`BonusSupport` there, `armor_stacks`/`hidden` here).

### 2026-07-19 — Web layer: category-grouped `<details>` sections, no new JS

`_resources.html`'s gear picker previously rendered one flat 5-row table. With 329 purchasable items
(411 loaded, minus 3 `armor_stacks` and minus every `hidden` entry — see above; some names also
collapse via the collision resolution) across 58 distinct categories, a flat table would be an
unusable wall of rows. Grouped `_resources_context`'s `gear_rows` into `gear_groups` (a list of
`{category, rows}`, built via `itertools.groupby` over `STARTER_GEAR_CATALOG` — already sorted by
`(category, name)` by `build_starter_gear_catalog`, so no re-sorting needed) and wrapped each group
in a `<details>` element in the template — a native, dependency-free collapse/expand mechanism
consistent with this project's "no JS build pipeline" stance (Project Overview's stack rationale).
A group auto-opens (`{% if group.rows | selectattr("quantity", "gt", 0) | list %}open{% endif %}`)
if it already contains a purchased item, so a returning player sees their existing picks without
having to remember which category they're filed under. Confirmed via a real HTTP walkthrough
(Verification) that all 58 categories render and that `assert item.name in response.text`-style
checks (already in `tests/unit/test_web_quality_contacts_resources.py`, unchanged) still hold —
`<details>` keeps its contents in the response body regardless of collapsed/open state, so nothing
needed changing there. `_character_sheet_context`'s own, unrelated `gear_rows` key (the short list of
*purchased* items shown on the finished-character sheet) was left untouched — no grouping need, and
renaming would have been a gratuitous, same-PR rename of something this WP didn't touch.

### 2026-07-19 — What this WP deliberately still doesn't do

Per the Implementation Plan's own explicit instruction: no Availability-cap enforcement (~57% of
SR5 gear and 69% of SR5 weapons carry a Restricted/Forbidden availability code that a real character
creation flow caps against a Priority-derived budget) — flagged as a deliberate, documented scope
cut in `chummer5.engine.resources`'s module docstring, the same pattern as the already-established
skill-karma and 7-point-contact cuts, not silently absent. Also still out of scope, unchanged from
WP9: Rating-scaled items (125 of 391 SR5 gear entries), and the `costfor` bulk-pricing field seen on
ammunition (`Ammo: APDS` costs 120¥ "for 10" rounds) — `chummer5.data.gear.Gear` doesn't expose it;
the existing "one purchase = one unit at `<cost>`" model treats it the same as every other flat item,
which is a pre-existing simplification (`create_resources_selection` has never modeled quantity-per-
purchase pricing) rather than a new gap this WP introduced.

## Design decisions

- **`chummer5.data.gear`'s loaders apply only the SR5 + flat-cost-shape filter — no `hidden`/
  `required`/`armor_stacks` exclusion.** Keeps each loader a literal translation of one XML file
  (matching WP2/WP3/WP20's precedent) and makes the 411-item acceptance count directly testable.
  `chummer5.engine.resources.build_starter_gear_catalog` is where "what's actually offered to buy"
  gets decided — the same layering WP3's `BonusSupport` classification/WP8's `mvp_quality_catalog`
  filter already established (raw data preserves everything + a flag; the engine layer curates).
- **Drop `hidden` entries unconditionally, not only when they collide.** Considered resolving only
  the 5 actual collisions (e.g. via a name-collision tie-break alone, with no `hidden` field at all)
  — rejected once it became clear that without also excluding `armor_stacks` armor from the
  candidate pool entirely, a `hidden` weapon-profile duplicate could still "win" a collision by being
  the *only* remaining candidate for that name (this is exactly what happened with `Ballistic
  Shield`/`Riot Shield` in an earlier draft: excluding the armor side for `armor_stacks` left the
  0-cost hidden weapon profile as the sole entry, so it silently got offered at 0¥ until caught by
  `tests/unit/test_gear.py::test_catalog_excludes_additive_stacking_armor`). Dropping `hidden`
  unconditionally is both simpler to reason about and correct regardless of what else does or
  doesn't get excluded elsewhere.
- **`StarterGearItem.category`/`.armor_rating` are optional fields defaulting to `None`,** per the
  Implementation Plan's explicit instruction, so every pre-WP21 caller/test constructing a bare
  `StarterGearItem(name, cost)` (several exist in `tests/unit/test_resources.py`) keeps working
  unchanged rather than needing a mechanical update everywhere.
- **`build_starter_gear_catalog` takes `Iterable[Gear]`/`Iterable[Armor]`/`Iterable[Weapon]` with
  empty-tuple defaults, and `STARTER_GEAR_CATALOG` itself is still a plain module-level constant**
  (`build_starter_gear_catalog(load_gear(), load_armor(), load_weapons())`), preserving every
  existing `from chummer5.engine.resources import STARTER_GEAR_CATALOG` call site
  (`save_format.py`, `legacy_import.py`, `web/app.py`) unchanged — the Implementation Plan's
  "existing gear-purchase fixture tests still pass unchanged" acceptance criterion, satisfied by
  construction rather than by special-casing each caller.
- **A new peer test file (`tests/unit/test_gear.py`), not folded into `test_resources.py`.** Mirrors
  WP3's own `test_qualities.py`/`test_skills.py` split (one test file per `chummer5.data` loader
  module) rather than growing `test_resources.py` — which already covers `create_resources_
  selection` itself — with loader-level assertions that belong with the loader.

## Implementation

- `src/chummer5/data/gear.py` (new): `Gear`/`Armor`/`Weapon` frozen dataclasses (`id`, `name`,
  `category`, `cost`, `hidden`, `source`, `page`; `Armor` additionally `armor_rating`/
  `armor_stacks`); `load_gear`/`load_armor`/`load_weapons`, each filtering to `source == "SR5"` and
  a flat (bare non-negative integer literal) `<cost>`; `_flat_cost` helper shared by all three.
- `src/chummer5/engine/resources.py`: `StarterGearItem` gains `category: str | None = None` and
  `armor_rating: int | None = None`; new `build_starter_gear_catalog(gear, armor, weapons)`
  (drops `hidden`/`armor_stacks` entries, resolves remaining name collisions by keeping the
  higher-cost entry, sorts by `(category, name)`); `STARTER_GEAR_CATALOG` now built from the real
  loaders instead of a hardcoded 5-item tuple. `create_resources_selection` itself is unchanged.
- `src/chummer5/web/app.py`: `import itertools`; `_resources_context` now groups `STARTER_GEAR_
  CATALOG` into `gear_groups` (`{category, rows}`) via `itertools.groupby` instead of a flat
  `gear_rows` list.
- `src/chummer5/web/templates/_resources.html`: wraps each category's table in a `<details>`
  element (auto-open if it already contains a purchased item), looping `gear_groups` → `group.rows`
  instead of a single flat `gear_rows` loop. `_character_sheet.html`'s unrelated `gear_rows` usage
  (purchased-items summary) is untouched.
- `tests/unit/test_gear.py` (new): loader counts (266/11/134/411), each cost-shape exclusion
  (`Rating`, `FixedValues`, `Variable`, `+N` modifier), `hidden`/`armor_stacks` flags on hand-checked
  real items, and `build_starter_gear_catalog`'s exclusions/collision-resolution/sort order/empty-
  input behavior.
- `tests/unit/test_resources.py`: updated the one pre-existing assertion that constructed expected
  `StarterGearItem`s without a `category` (`test_create_resources_selection_within_budget`) to
  match the now-real `Commlinks`/`Blades` categories.

## Outcome

WP21 complete. `chummer5.data.gear` loads the full SR5-core, flat-cost gear/armor/weapon set (411
items, exactly matching the Implementation Plan's own pre-research) directly from
`legacy/Chummer/data/{gear,armor,weapons}.xml`, replacing WP9's 5-item hardcoded stand-in.
`chummer5.engine.resources.build_starter_gear_catalog` turns that into a 329-item purchasable
catalog, resolving a real data subtlety the plan's headline number didn't anticipate: 5 items share a
display name with a different-cost, non-purchasable duplicate elsewhere in the SR5 data (an
auto-granted 0-cost weapon profile, or a `<required>`-gated 0-cost component) — every one is now
resolved to its real, independently-purchasable price, verified both by unit test and by an actual
HTTP purchase (`Grapple Gun` correctly costs 500¥, not 0¥). The 3 additive-stacking armor items
(Helmet, Ballistic Shield, Riot Shield) are excluded from what's offered, per the plan's explicit
instruction, confirmed absent from the rendered picker end to end. The web layer's gear picker is
now grouped into 58 collapsible `<details>` sections by category instead of one flat table, with no
new JavaScript. Every existing gear-purchase test (fixture-based and hand-authored) passes unchanged,
and the 5 original hand-picked items (`Meta Link`, `Certified Credstick Standard`, `Armor Jacket`,
`Ares Predator V`, `Combat Knife`) survive in the new catalog at identical names and costs.
`pytest`/`ruff`/`mypy` are all green (296 tests, 19 more than before this WP), and a real-HTTP manual
walkthrough (confirm → buy gear across categories → save → reload into a fresh session) reproduces
the correct combined numbers throughout. Deliberately, explicitly still out of scope (per the
Implementation Plan): Availability-cap enforcement, Rating-scaled items, and `costfor` bulk pricing.
