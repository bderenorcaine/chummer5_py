# WP23 — Grant metatype-inherent qualities for free (Low-Light Vision, Thermographic Vision, Resistance to Pathogens/Toxins)

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase H, WP23.

## Goal

Fix a real, previously-undiscovered gap surfaced by a user question while reviewing WP22: SR5
grants specific qualities automatically and for free to certain metatypes (Elf/Ork → Low-Light
Vision, Dwarf → Thermographic Vision + Resistance to Pathogens/Toxins, Troll → Thermographic
Vision; Human → none), and this engine modeled none of it. `chummer5.data.metatypes.Metatype`
never parsed the base `<metatype><qualities>` block at all — only `Metavariant` did, and
metavariants are entirely out of MVP scope. Directly connected to WP22: Low-Light Vision/
Thermographic Vision became purchasable there (`NO_EFFECT`), so a non-Human character could
spend karma re-buying a quality they should already have for free, with nothing to stop them.

## Log

### 2026-07-19 — Confirming the gap and its exact shape via the raw XML and legacy C#, before writing any code

Read `legacy/Chummer/data/metatypes.xml` directly: `<metatype><qualities><positive>/<negative>`
grants Elf/Ork → Low-Light Vision, Dwarf → Thermographic Vision + Resistance to Pathogens/Toxins,
Troll → Thermographic Vision, Human → nothing. Confirmed `chummer5.data.metatypes._parse_metatype`
never reads this block — `qualities_positive`/`qualities_negative` exist only on `Metavariant`
(all out of MVP scope). Traced the legacy engine's actual mechanism in `Character.cs` (~line
44348): `QualitySource.Metatype`, auto-granted at character-creation time by iterating
`qualities/positive/quality` off the metatype's own XML node, zero karma cost, excluded from the
karma cap and Positive/Negative quality totals elsewhere in the C# (`OriginSource ==
QualitySource.Metatype` checks throughout).

Also checked (and ruled out as a red herring) `<hide/>` on these same 3 quality entries in
`qualities.xml` — grepped `SelectQuality.cs`'s `BuildQualityList` for any `hide` filter and found
none; `<hide/>` there turned out to be used only by `SelectPACKSKit.cs` (pre-built kit generation),
unrelated to whether a quality shows in the manual picker. The real signal distinguishing
"auto-granted, don't offer for karma" is `<qualitysource>Metatype</qualitysource>` on an actual
character's save data, not anything in the static quality catalog itself.

### 2026-07-19 — `qualitysource=Metatype` is broader than "this metatype's real racial quality" — a fixture caught this before it shipped

Initial implementation of the legacy-import exclusion (skip any `qualitysource == "Metatype"`
quality outright) broke `tests/integration/test_legacy_import_fixtures.py::
test_imports_yeti_end_to_end`: Yeti's own `Technomancer` quality is tagged
`qualitysource=Metatype` in the raw `.chum5`, despite Yeti being Human (whose `qualities_positive`/
`qualities_negative` are both empty). Traced this to the legacy engine's broader use of the same
enum value for "auto-granted at chargen by something other than a manual quality pick" — which
also covers a Priority-Talent selection's Adept/Magician/Technomancer/Mystic Adept quality, not
just metatype race. Fixed by name-gating the exclusion: only skip (silently, since
`build_character` re-derives it) a `Metatype`-sourced legacy quality whose *name* actually appears
in the imported character's real metatype's racial-quality list; anything else
`qualitysource=Metatype` (like Yeti's Technomancer) still flows through the normal offered/dropped
check, landing in `dropped_qualities` exactly as it did before this WP. Added
`test_metatype_sourced_quality_not_matching_real_racial_list_still_dropped` specifically to pin
this distinction down, and `test_yeti_technomancer_quality` in `test_legacy_chum5.py` now asserts
`quality_source == "Metatype"` directly, so a future agent grepping for "Metatype" quality data
doesn't assume it always means "racial."

### 2026-07-19 — A second real data surprise: `<bp>` records the catalog karma value even for a quality that was never paid for

While writing a `qualitysource` test against `Blindfire.chum5`, initially assumed a `Metatype`-
sourced quality's `<bp>` (the tag `LegacyQuality.karma` reads) would be `0`. It isn't —
Blindfire's Low-Light Vision has `<bp>4</bp>`, the catalog's flat karma value, unchanged despite
never being an actual spend. The legacy engine's exclusion-from-karma-total happens elsewhere (by
checking `OriginSource`, not by zeroing `<bp>` in the save). This confirms
`chummer5.io.legacy_import`'s exclusion *must* key off `quality_source`, not a `karma == 0`
shortcut — which is exactly what the implementation already did, but the test's own first draft
had the wrong expected value until checked against the real XML.

### 2026-07-19 — `Rez0luti0n2.0.chum5` (the Dwarf fixture) is missing Resistance to Pathogens/Toxins entirely

Cross-checking `resolve_metatype_qualities` against all 5 curated non-Human fixtures found
`Rez0luti0n2.0.chum5` carries only Thermographic Vision, not the second Dwarf racial quality —
confirmed directly against the raw XML, not a parsing bug on this project's side. Recorded as a
known, pre-existing gap in that specific save (possibly an older Chummer version's data, or a
manual edit) rather than assumed to be something this WP's engine logic should reproduce; the
cross-fixture test (`test_resolve_metatype_qualities_matches_every_non_human_fixture`) asserts
only that each fixture's own `qualitysource=Metatype` names are a *subset* of what
`resolve_metatype_qualities` resolves, not an exact match, specifically because of this one case.

## Design decisions

- **`apply_quality_improvements` now takes a plain `Iterable[Quality]` instead of a
  `QualitySelection`, plus an optional `source_type: ImprovementSource = ImprovementSource.QUALITY`
  keyword.** The alternative (constructing a throwaway `QualitySelection` just to reuse the
  function for metatype-granted qualities) would have been more code and a more confusing call
  site for no benefit — every real caller only ever needed `.qualities` anyway. Every existing call
  site was updated to pass `selection.qualities` explicitly; behavior is identical for all of them
  (`source_type` defaults to the same `QUALITY` value they always used).
- **`ImprovementSource.METATYPE`** (reserved since WP5/WP6, never used until now) is what
  metatype-granted Improvements record under, not `QUALITY` — keeps `ImprovementIndex
  .remove_source` able to retract exactly a metatype's grants independently of a player's picks,
  which `_relink_metatype_qualities` (below) needs.
- **`resolve_metatype_qualities` grants regardless of `BonusSupport`, not restricted to
  `mvp_quality_catalog`'s `FLAT_BONUS`/`NO_EFFECT`.** Granting is unconditional SR5 rules, not a
  karma purchase the "never offer a quality whose effect is silently dropped" rule needs to
  protect. A `NOT_YET_SUPPORTED` metatype quality (Dwarf's Resistance to Pathogens/Toxins, whose
  toxin-resist effect this project models nowhere) is still granted and shown on the character
  sheet; its `flat_bonuses` tuple is simply empty, so `apply_quality_improvements` is naturally a
  no-op for it — the same "verified, not silently wrong" shape WP22's `NO_EFFECT` tranche already
  established, just reached by construction here instead of an explicit classification.
- **`Character.metatype_qualities` is populated by a dedicated `_relink_metatype_qualities`
  helper, called from both `submit_priorities` and `submit_attributes`** — mirroring
  `_relink_quality_improvements`/`_relink_contact_selection`'s existing pattern rather than baking
  resolution into `create_character` itself (which would have meant threading a quality catalog
  parameter through every one of its many call sites, including the whole test suite, for a
  concern every other selection already keeps separate from construction). Unlike
  `_relink_quality_improvements` (a player's selection, only ever carried forward unchanged),
  `_relink_metatype_qualities` always removes whatever it previously granted before re-resolving
  and re-applying — necessary because, unlike a quality pick, what belongs here can change out from
  under the character when `submit_priorities` swaps the metatype itself. Verified this exact edge
  case via a real HTTP walkthrough: reconfirming from Elf to Dwarf correctly drops Low-Light Vision
  and grants Thermographic Vision + Resistance to Pathogens/Toxins, with nothing left over from the
  old metatype.
- **`metatype_qualities` is not a `CharacterSave` field.** Consistent with `chummer5.io
  .save_format`'s own "selections, not derived values" principle (already stated in that module's
  docstring before this WP touched it) — it's 100% determined by `metatype` plus the current
  quality catalog, so persisting it would be redundant, frozen-at-save-time data; `build_character`
  re-derives it exactly like a freshly-built `Character` would, verified by a round-trip test that
  builds an Elf save with an empty `quality_ids`, serializes it to JSON, reloads it, and confirms
  `metatype_qualities` comes back populated anyway.
- **`offerable_quality_catalog(character, catalog)` is a thin filter, not a `create_quality_
  selection` signature change.** Passing its narrowed output straight into `create_quality_
  selection` is sufficient to enforce the exclusion, since that function already re-derives `mvp_
  quality_catalog` from whatever catalog it's given — an already-excluded quality simply isn't in
  the input to begin with. Used at both the picker-rendering site (`_quality_selection_context`)
  and the validation site (`submit_qualities`), so a tampered/stale form submission naming an
  already-granted quality's id is rejected the same way an unknown id already was ("not an
  MVP-offered quality id") — confirmed via a real HTTP walkthrough, not just the unit test.
- **Legacy import excludes `qualitysource=Metatype` qualities by name-match against the imported
  metatype's real racial list, not a blanket source-type skip** (see the Log's fixture-caught-this
  entry above) — the only way to keep Yeti's Technomancer correctly landing in `dropped_qualities`
  while an Elf's Low-Light Vision correctly doesn't.

## Implementation

- `src/chummer5/data/metatypes.py`: `Metatype` gains `qualities_positive: tuple[str, ...] = ()`/
  `qualities_negative: tuple[str, ...] = ()` (mirroring `Metavariant`'s existing fields);
  `_parse_metatype` now parses the base `<qualities>` block via the existing `_parse_quality_names`
  helper. Module docstring updated.
- `src/chummer5/engine/qualities.py`: `apply_quality_improvements` signature widened (see Design
  decisions); new `resolve_metatype_qualities(metatype, catalog) -> tuple[Quality, ...]` (raises
  `ValueError` for an unresolvable name — a data-integrity guard, not an expected runtime case);
  new `offerable_quality_catalog(character, catalog) -> tuple[Quality, ...]`. Module docstring
  updated for the first-ever offerable Negative qualities note carried over from WP22 (unchanged
  content, just confirmed still accurate).
- `src/chummer5/engine/character.py`: `Character` gains `metatype_qualities: tuple[Quality,
  ...] = ()`; `Quality` imported directly (not under `TYPE_CHECKING`, unlike `QualitySelection` —
  `chummer5.data.qualities` has no engine imports, so it isn't circular).
  (`ImprovementSource.METATYPE`, reserved since WP5/WP6, now has a real producer -- its docstring
  in `chummer5.engine.improvements` already anticipated this and needed no further edit).
- `src/chummer5/web/app.py`: new `_relink_metatype_qualities(character)` helper, called from both
  branches of `submit_priorities` and from `submit_attributes`; `_quality_selection_context`/
  `submit_qualities` use `offerable_quality_catalog(character, QUALITIES)` instead of the raw
  `MVP_QUALITIES` module constant; `_character_sheet_context` gains `metatype_quality_names`,
  reported separately from `quality_names` (not folded into `quality_karma_cost`).
- `src/chummer5/web/templates/_quality_selection.html`: a "Free from metatype: ..." line when
  `metatype_qualities` is non-empty.
- `src/chummer5/web/templates/_character_sheet.html`: same line, under the Qualities section.
- `src/chummer5/io/save_format.py`: `build_character` resolves and applies `metatype_qualities`
  the same way it already does `quality_selection`, including it in the final `replace(...)` — not
  a new `CharacterSave` field (see Design decisions).
- `src/chummer5/io/legacy_chum5.py`: `LegacyQuality` gains `quality_source: str` (parsed from
  `<qualitysource>`).
- `src/chummer5/io/legacy_import.py`: looks up the imported character's real `Metatype` (via the
  already-existing `sr5_metatypes` filter) to get its racial-quality name set; excludes a
  `qualitysource=Metatype` legacy quality from the candidate list only when its name is in that
  set (see Design decisions for why not a blanket skip).
- `spec/Project Overview.md`: new 2026-07-19 Open Questions entry documenting the discovery (added
  before implementation started, per this project's "raised... before being acted on" convention).

## Outcome

WP23 complete. `chummer5.data.metatypes.Metatype` now parses the base `<metatype><qualities>`
block, and `chummer5.engine.qualities.resolve_metatype_qualities` turns Elf/Ork's Low-Light Vision,
Dwarf's Thermographic Vision + Resistance to Pathogens/Toxins, and Troll's Thermographic Vision
into real, automatically-granted `Quality` objects on `Character.metatype_qualities` — free (never
counted toward karma or the 25-karma cap), correctly excluded from what a player can additionally
buy (`offerable_quality_catalog`, enforced both in the picker and in `create_quality_selection`
itself), correctly re-resolved if the metatype changes mid-chargen (verified live: Elf → Dwarf
swaps the granted set cleanly), correctly re-derived (not persisted) across save/load, and
correctly separated from a genuinely player-chosen `qualitysource=Metatype` quality during legacy
import (Yeti's Technomancer still reports as dropped, exactly as before this WP). `pytest`/`ruff`/
`mypy` are all green (323 tests, 19 more than before this WP), and a real-HTTP manual walkthrough
confirms the fix end to end: an Elf's Low-Light Vision shows as free on both the quality picker and
the character sheet, cannot be purchased even via a direct tampered form submission, and correctly
swaps out when the metatype is reconfirmed to something else.
