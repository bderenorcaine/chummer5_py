# WP24 — Talent as a real 5th priority category (plumbing only; still Mundane-only)

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase I, WP24.

## Goal

Retire "Talent forced to E" as a hardcoded assumption threaded through the web layer — with
**zero new player-visible capability**: the priority form gains a real 5th letter selector
(Talent, alongside Heritage/Attributes/Skills/Resources), `submit_priorities` validates a 5-way
A-E permutation instead of a 4-way A-D one, but Talent's chosen *option* still resolves
unconditionally to Mundane. A pure restructuring WP in the same spirit as WP18, proving the
letter-assignment plumbing before WP25 builds real archetype/tradition/free-skill selection on
top of it.

## Log

### 2026-07-19 — Confirming which letters actually offer "Mundane" before touching anything

The Implementation Plan's Phase I intro already flagged that Talent's real archetype options vary
per letter (`priorities.xml`'s Talent lists differ by letter — A grants "6 Magic/10 Spells"
Magician, D grants Aware/Adept, etc.). Checked directly rather than assumed: parsed every Talent
priority row's option names —

```
A ['Magician', 'Mystic Adept', 'Technomancer', 'A.I.']
B ['Adept', 'Magician', 'Mystic Adept', 'Aspected Magician', 'Apprentice', 'Technomancer', 'A.I.']
C ['Adept', 'Magician', 'Mystic Adept', 'Aspected Magician', 'Explorer', 'Enchanter', 'Apprentice',
   'Technomancer', 'A.I.']
D ['Adept', 'Aspected Magician', 'Aware', 'Apprentice', 'A.I.']
E ['Mundane', 'A.I.']
```

**Only letter E's list contains a "Mundane" option at all.** This is the one fact that shapes this
WP's whole design: a player can now assign Talent *any* of the 5 letters (real, validated,
session-held state), but the character built from that submission still has to resolve Talent's
*option* to `priorities.mundane_talent()` (literally letter E's own entry) regardless of which
letter was picked — there is no other Mundane-compatible option to resolve to yet, since offering
real per-letter archetype selection is WP25's job, not this one's. Recorded this directly in
`_priority_form_context`'s docstring (the natural place a future WP25 agent will look first) so
nobody mistakes "Talent letter is now free-form" for "Talent's letter now changes what a Mundane
character gets" — it deliberately doesn't, yet.

No rulebook PDF consultation needed this WP — the letter-assignment shape (assign each of 5
categories a distinct A-E letter) is a data/plumbing fact fully readable from `priorities.xml`
itself, not a rules question needing p.xxx clarification. `spec/rulebooks/learnings.md` gets no
new entry from this WP.

## Design decisions

- **`Character` gains no `talent_letter` field in this WP.** The Implementation Plan explicitly
  asked this to be decided and documented, not defaulted into silently. `heritage_letter`/
  `attributes_letter` live on `Character` because `create_character`'s own budget/range validation
  needs them immediately at construction time. `skills_letter`/`resources_letter` never got an
  equivalent `Character` field, because nothing on `Character` itself ever needed to look them up —
  `create_skill_allocation`/`create_resources_selection` take the letter as a plain parameter
  instead. `talent_letter` follows the second precedent, not the first: nothing on `Character`
  reads it in this WP (Talent's option resolves unconditionally, independent of the letter), so
  there's nothing for a `Character`-side copy to serve yet. `chummer5.web.session.ChargenSession
  .talent_letter` is the only copy, exactly like `skills_letter`/`resources_letter`. WP25 adds a
  real `Character` field once `create_magic_selection` actually needs to look the chosen letter's
  option list up against `priorities.talent`.
- **`PRIORITY_LETTERS` itself widens from `("A","B","C","D")` to `("A","B","C","D","E")`, in
  place, rather than introducing a second `ALL_PRIORITY_LETTERS` constant.** Every one of its 3
  call sites (the template's `letters` iterable for all 5 `<select>`s, and the duplicate-letter
  permutation check) needs the full 5-letter range now that Talent is a real category using the
  same tuple the other four already do — a second, wider constant would just mean two names for
  the same list with no call site left needing the narrower one.
- **`DEFAULT_TALENT_LETTER = "E"`**, keeping `DEFAULT_HERITAGE_LETTER`/`DEFAULT_ATTRIBUTES_LETTER`/
  `DEFAULT_SKILLS_LETTER`/`DEFAULT_RESOURCES_LETTER` at their existing A/B/C/D values. This isn't
  an arbitrary "pick whatever's left over" choice — E is the *only* letter whose Talent list
  contains Mundane at all (see Log), so this default is what makes a freshly-created session (and
  every existing test's A/B/C/D submission, now with `talent_letter=E` added) reproduce
  byte-for-byte pre-WP24 behavior.
- **`_apply_built_character_to_session` (native save load + legacy `.chum5` import) resets
  `session.talent_letter` to `DEFAULT_TALENT_LETTER` rather than leaving it untouched.** Neither
  `CharacterSave` nor `LegacyCharacter` carries a Talent letter (a save/import always predates real
  Talent selection — WP25's job), so there's nothing meaningful to restore; resetting to the
  default matches this function's own stated contract ("every field this WP's chargen routes read
  is set here, none is merged with what came before") rather than silently leaving a stale value
  from whatever the session held pre-load.
- **`CharacterSave` gains no new field this WP.** Consistent with `chummer5.io.save_format`'s own
  "selections, not derived values" principle — persisting a Talent letter that (in this WP) never
  affects anything computed would just be inert data with no consumer, the same reasoning WP23 used
  for *not* persisting `metatype_qualities`. WP25 is the natural point to add it, once a save
  actually needs to remember which letter unlocked which real archetype.

## Implementation

- `src/chummer5/web/session.py`: `PRIORITY_LETTERS` widened to `("A", "B", "C", "D", "E")`;
  new `DEFAULT_TALENT_LETTER = "E"`; `ChargenSession` gains `talent_letter: str =
  DEFAULT_TALENT_LETTER`. Docstrings updated (module-level comment above `PRIORITY_LETTERS`,
  `ChargenSession`'s own docstring) to explain the WP24 letter-range widening and why
  `talent_letter` stays session-only.
- `src/chummer5/web/app.py`:
  - `_priority_form_context` gains a `talent_letter` parameter, folds it into `selected`, and adds
    `"talent_priorities": PRIORITIES.talent` to the returned context (mirroring the other 4
    categories' `*_priorities` keys). New docstring paragraph explains the letter/option split
    (see Log).
  - `submit_priorities` gains a `talent_letter: str = Form(...)` parameter; the permutation check
    now validates all 5 submitted letters against the widened `PRIORITY_LETTERS`; on success,
    `session.talent_letter` is stored alongside the other four (both the fresh-`Character` and
    `dataclasses.replace`-in-place branches are otherwise unchanged — `Character` itself takes no
    Talent-related argument).
  - `index()` and the error-echo path both pass `talent_letter` through to `_priority_form_context`
    (session's stored value on a clean `GET /`, the just-submitted value on an error re-render,
    matching every other letter's existing echo behavior).
  - `_apply_built_character_to_session` resets `session.talent_letter = DEFAULT_TALENT_LETTER`
    (see Design decisions); new import of `DEFAULT_TALENT_LETTER` from `chummer5.web.session`.
  - `_character_sheet_context`'s `priority_summary` dict gains a `"talent"` key (`"{letter} —
    {priorities.talent[letter].name}"`, same shape as the other four), so the character sheet shows
    it too.
  - Module docstring gains a WP24 paragraph.
- `src/chummer5/web/templates/_priority_form.html`: new Talent `<select name="talent_letter">`
  (same shape as the other 4, offering all 5 letters via `talent_priorities[letter].name`),
  inserted between Heritage and Attributes; the confirmed-selection summary gains a matching
  `<li>Talent ...</li>` line; the intro paragraph rewritten from "Talent is forced to E" to
  "assign Heritage, Talent, Attributes, Skills, and Resources... whichever letter you give Talent
  doesn't unlock anything yet."
- `src/chummer5/web/templates/_character_sheet.html`: matching `<li>Talent {{
  priority_summary.talent }}</li>` line.

  the new Talent selector renders; two new tests —
  `test_submitting_only_four_distinct_letters_is_rejected` (Talent duplicating Resources' letter
  instead of using E is still rejected, proving the permutation check actually covers the 5th
  category and not just "4 out of 5 happen to be distinct") and
  `test_submitting_talent_at_a_non_e_letter_still_resolves_to_mundane` (Heritage moved to E,
  Talent moved to A — a real non-default 5-way permutation — still produces exactly the Mundane
  character `create_character` would, confirming the letter/option split holds for an assignment
  other than the default one).
- `tests/unit/test_web_attribute_skill_allocation.py`, `test_web_lifestyle.py`,
  `test_web_quality_contacts_resources.py`, `test_web_character_sheet.py`: every existing
  `/ui/priorities` POST across all 4 files gains `"talent_letter": "E"` (15 call sites total) so
  the whole suite keeps exercising the real endpoint contract rather than an already-stale one.

## Outcome

WP24 complete. Talent is now a real 5th priority category: the web layer validates a genuine 5-way
A-E permutation across Heritage/Talent/Attributes/Skills/Resources instead of hardcoding Talent to
E, and a player can assign it any of the 5 letters through a real form control. Per this WP's own
explicit scope, that assignment currently changes nothing about the resulting character — Talent's
*option* still resolves unconditionally to `priorities.mundane_talent()` regardless of which letter
was picked, since `priorities.xml` only ever offers a Mundane option at letter E and no other
letter's option list is wired up yet. `pytest`/`ruff`/`mypy` are all green (325 tests, 2 more than
before this WP), and a real-HTTP manual walkthrough confirms both the new selector and a
non-default 5-way permutation (Heritage moved off A, Talent moved off E) still produce exactly a
Mundane character. `Character` deliberately gains no `talent_letter` field yet — WP25 is where that
becomes necessary, once real archetype/tradition/free-skill selection needs to look the chosen
letter's options up against `priorities.talent`.
