# WP27 — Adept power selection

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase I, WP27.

## Goal

Let an Adept spend Power Points on Adept Powers. Engine + data layer only, mirroring WP25/WP26's own
scope — WP29 is where this reaches the browser.

## Log

### 2026-07-19 — Reading every SR5 power's raw `<bonus>` node before classifying anything

Checked `legacy/Chummer/data/powers.xml` directly: 136 raw `<power>` entries, 28 with
`source == "SR5"` — matches the Implementation Plan's own count exactly. Dumped every SR5 power's
full XML and read all 28 by hand (not just the ones the plan pre-named) before writing the
classifier, per this WP's own stated caution about `<selectattribute>` not being a single shape.

### 2026-07-19 — The Attribute Boost trap, confirmed both in the XML and in the rulebook prose

`pdftotext -layout` against p.308-311 (see `spec/rulebooks/learnings.md`'s new WP27 entry for the
full citations). Confirmed exactly what the Implementation Plan's intro predicted: Improved Physical
Attribute's `<bonus>` is `<selectattribute><attribute>BOD</attribute>...<val>Rating</val>
</selectattribute>`; Attribute Boost's is the identical tag with the identical attribute list but
**no `<val>` child at all**. Reading the rulebook text (not just the XML) confirms *why*: Attribute
Boost's real effect is a Magic + Rating Test with a temporary, hit-scaled boost and Drain on
expiry — genuinely not a permanent bonus, not just a data-format quirk. `chummer5.data.powers
._is_select_attribute_flat_bonus` requires the `<val>` child specifically, so Attribute Boost
correctly falls through to `NOT_YET_SUPPORTED`; `tests/unit/test_powers.py::
test_attribute_boost_is_not_yet_supported_despite_sharing_selectattribute` is the regression test
this WP's own intro exists to prevent.

### 2026-07-19 — A 4th FLAT_BONUS candidate the Implementation Plan didn't name: Voice Control

The plan's WP27 entry names exactly 3 verified `FLAT_BONUS` candidates (Improved Physical Attribute,
the Improved Potential trio, Enhanced Perception). Reading every SR5 power's `<bonus>` node directly
(not just the pre-named ones) turned up a 4th: Voice Control's `<bonus>` is `<sociallimit>Rating
</sociallimit>` + `<specificskill><name>Impersonation</name><bonus>Rating</bonus></specificskill>`
— both children individually match shapes this WP's classifier already recognizes (the same
`sociallimit` tag as Improved Potential (Social); the same named-skill shape as Enhanced
Perception). Cross-checked against the rulebook text (p.311) to confirm this isn't a coincidental
shape match: "giving you +1 per level to your Social limit" and an Impersonation Opposed Test
"adding the level of this power as a bonus to your dice pool" — both real, computable, per-level
bonuses. Included as a 5th... no, 6th (with Enhanced Perception's own 2-bonus shape counted once)
`FLAT_BONUS` power. See `spec/rulebooks/learnings.md`'s WP27 entry for the full citation.

### 2026-07-19 — Improved Ability (skill): shape-recognizable, deliberately deferred

`<bonus><selectskill minimumrating="1"><val>Rating</val>...` is shape-recognizable as a flat skill
bonus by the same pattern Enhanced Perception uses, but the rulebook (p.309) attaches two real rules
neither this classifier nor anything else in this engine implements: the target skill must already
be known at rating >= 1, and the achievable improvement is capped at "your current skill level x
1.5, rounded up" — a formula with no precedent anywhere in this codebase (it needs to read the
character's *current* skill rating, not just a fixed catalog value). Per the Implementation Plan's
own explicit permission to defer this either way, documented here: **deferred**, classified
`NOT_YET_SUPPORTED`. A future WP that wants Improved Ability specifically would need to plumb
`chummer5.engine.skills.SkillAllocation` (or the granted-skill-rating mechanism WP25 already built)
into the power classifier/applier — real, self-contained follow-up work, not bundled here.

### 2026-07-19 — No `NO_EFFECT` case among the empty-`<bonus>` powers, unlike WP22's qualities

4 SR5 powers have an empty or absent `<bonus>` node: Light Body, Missile Parry, Traceless Walk, Wall
Running. Per this WP's own stated caution ("confirm this by reading its rulebook effect, don't
assume an empty `<bonus>` means inert" — WP22's own discipline for `NO_EFFECT` qualities extended
here), read each one's rulebook text individually (p.310-311) rather than assuming. All 4 turned out
to have a real, unmodeled in-play effect (jump distance/Gymnastics dice, a ranged-defense Interrupt
Action, a stealth/Perception-penalty effect, a Running+Strength wall-climb test) — none qualify as
verified-inert. Unlike `chummer5.data.qualities.BonusSupport`, `chummer5.data.powers.BonusSupport`
therefore has **no `NO_EFFECT` member at all** — an always-zero-count enum value would just be
unused scaffolding (Project Overview's own "add it when a WP actually needs one" principle). A
future WP that finds a genuinely inert power should add the member then, the way WP22 added it to
qualities only once it had a real member to put in it.

### 2026-07-19 — Improved Potential (Chaos Mentor): a 4th variant, correctly excluded without
special-casing

`powers.xml` actually has 4 "Improved Potential" entries, not 3 — a `(Chaos Mentor)` variant with
`<bonus><selectlimit><val>1</val></selectlimit></bonus>` (a player-selects-which-limit shape,
different from the other 3's fixed named tags) and a `<hide/>` marker (a legacy-internal variant,
not meant to be offered as a standalone power — likely surfaced only via a specific mentor-spirit
selection this project doesn't model). Falls through to `NOT_YET_SUPPORTED` via the ordinary
unrecognized-shape rule; no special-casing needed, and none added — see
`tests/unit/test_powers.py::test_improved_potential_chaos_mentor_variant_is_not_yet_supported`.

### 2026-07-19 — Wesson's fixture: a correction to the Implementation Plan's own acceptance text

Read Wesson's `<powers>` block directly (bare `xml.etree.ElementTree`, mirroring WP26's Miko-spells
precedent — `chummer5.io.legacy_chum5` has never parsed powers; WP28 is where that lands). He has 6
real power entries. Only 4 are `source == "SR5"` — **Motion Sense and Rapid Draw are both
`SG`-sourced** (confirmed directly in `powers.xml`), the same non-core-content situation his own
tradition (Christian Theurgy, `FA`) is already in. This directly contradicts the Implementation
Plan's own WP27 acceptance text, which says "his 6 real powers resolve against the catalog" — only
4 of 6 do.

Worse (or rather, more honest) than the plan anticipated: of those 4 SR5-sourced powers (Attribute
Boost, Combat Sense, Enhanced Accuracy (skill), Improved Ability (skill)), **all 4** are
`NOT_YET_SUPPORTED` under this WP's classifier — not just the 2 the plan's acceptance text names
("Combat Sense, and Attribute Boost"). Combat Sense's `<bonus>` is a `dodge` combat-pool bonus;
Enhanced Accuracy (skill)'s is a weapon-accuracy bonus; both are combat mechanics this engine's
scope doesn't model. Improved Ability (skill) is the power deliberately deferred above. So Wesson's
fixture, while real ground truth for the Power Point *budget* math, cannot exercise
`create_power_selection`'s `FLAT_BONUS`/`apply_power_improvements` path positively at all — the same
"partial ground truth, verify by hand where the fixture can't reach" honesty WP26 already
established for Miko's spells (6/10 resolve) and WP25 for tradition-specific mechanics.

The Power Point budget itself still checks out exactly by hand: reading each of his 6 real powers'
raw `points`/`levels`/`rating` fields (4 from the SR5 catalog, 2 — Motion Sense/Rapid Draw — read
directly from the raw XML since they're not in the SR5-scoped catalog) and summing
`points * rating` (or flat `points` for `levels=False`) gives exactly 4.0, matching his MAG-4 Power
Point budget precisely. `tests/integration/test_magic_fixtures.py::
test_wesson_adept_powers_hand_verified_against_the_raw_fixture_and_catalog` asserts the full 6/4/2
split and the exact budget sum, not just the parts that happen to resolve.

## Design decisions

- **`create_power_selection` takes `(power_id, rating, selected_attribute)` triples, not a plain
  list of ids like `create_quality_selection`/`create_spell_selection`.** Unlike a quality or spell,
  a power pick genuinely carries two more pieces of player input: how many levels were bought
  (ratings aren't uniform across powers the way a quality's karma cost is fixed), and, for exactly
  one power shape (`select_attribute`), which attribute it targets. No existing `create_*` function
  in this engine had a precedent for either, so this is a new (if small) shape rather than a forced
  fit onto the existing `Iterable[str]` pattern.
- **Only one pick per power id is supported** — buying the same power twice for two different
  targets (e.g. Improved Physical Attribute for both BOD and AGI, which SR5 plausibly allows) is
  explicitly out of scope for this WP. No real fixture exercises it, and nothing else in this WP's
  scope needs the composite-id machinery it would require. Documented in `create_power_selection`'s
  own docstring as a deliberate cut, mirroring WP32's future duplicate-purchase decision for
  cyberware.
- **`power_point_budget` does double duty**, capping both an individual power's rating (`rating <=
  min(power.limit, power_point_budget)`, per the rulebook's own "Magic Rating or power's own limit,
  whichever is less" rule) and the total spend across all picks. This is safe specifically because
  Power Points equal the Magic rating 1:1 in this project's scope (no Mystic Adept split to track
  separately) — a hypothetical future scope where PP and Magic rating diverge would need two
  separate parameters, but nothing in this phase's scope does.
- **`PowerFlatBonus` carries no `value` field**, unlike `chummer5.data.qualities.FlatBonus`. Every
  verified `FLAT_BONUS` power's `<bonus>` value is the literal token `"Rating"`, and every one of
  them (once individually checked against the rulebook text) has a per-level magnitude of exactly
  1 — so the purchased pick's own `rating` *is* the resolved value, computed at `apply_power_
  improvements` time rather than pre-resolved in the data layer the way a quality's fixed int bonus
  can be.
- **`PowerSelection.power_points_spent` is a `Decimal`**, this engine's first fractional value
  anywhere (SR5 Power Point costs are routinely 0.25/0.5). Scoped locally to this one selection's
  budget arithmetic — the *bonus* values `apply_power_improvements` feeds into `Improvement.value`
  are always plain ints (the purchased rating), so `Improvement` itself needed no change for this
  WP. This deliberately doesn't preempt the Implementation Plan's Phase J/WP30 decision about
  whether `Improvement.value` itself should ever go fractional (for Essence) — that's a genuinely
  different, engine-wide question this WP's narrowly-scoped `Decimal` usage doesn't answer either
  way.
- **No `NO_EFFECT` value in `chummer5.data.powers.BonusSupport`.** See the Log's "no NO_EFFECT case"
  entry above — this was checked, not assumed, and the honest answer is zero qualifying powers.

## Implementation

- `src/chummer5/data/powers.py` (new): `Power` (id, name, points: `Decimal`, levels: `bool`,
  limit: `int`, source, page, bonus_support, flat_bonuses, raw_bonus); `PowerFlatBonus` (target_kind,
  target_name, attribute_options — no `value`, see Design decisions); `BonusSupport` (`FLAT_BONUS`/
  `NOT_YET_SUPPORTED` only); `load_powers()` (28 of 136, `source == "SR5"`); `count_by_support()`.
  Classifier recognizes 3 shapes: named-skill (`specificskill` with a `"Rating"` bonus token),
  select-attribute (`selectattribute` with a `<val>Rating</val>` child — the Attribute Boost
  discriminator), and the 3 Inherent-Limit tags (bare leaf, text `"Rating"`).
- `src/chummer5/engine/improvements.py`: new `ImprovementSource.ADEPT_POWER`.
- `src/chummer5/engine/magic.py`:
  - `mvp_power_catalog(powers)` — restricts to `FLAT_BONUS`, mirrors `mvp_quality_catalog`.
  - `PowerPick` (power, rating, selected_attribute) / `PowerSelection` (picks,
    power_points_spent: `Decimal`, power_point_budget).
  - `create_power_selection(picks, catalog, power_point_budget)` — validates id/duplicate/rating-
    range/select-attribute/total-budget together, per the Design decisions above.
  - `apply_power_improvements(character, selection)` — adds one `Improvement` per `PowerFlatBonus`
    per pick, `value = pick.rating`, `source_type = ADEPT_POWER`, `source_id = power.id`.
- `src/chummer5/engine/character.py`: `Character` gains `power_selection: PowerSelection | None =
  None` (imported under `TYPE_CHECKING`, same pattern as every other selection field); class
  docstring gains a WP27 paragraph.

  member; one full-field hand-check (Danger Sense).
- `tests/unit/test_magic.py`: 18 new tests for `create_power_selection`/`apply_power_improvements`
  — within-budget selection, empty selection, unknown id, `NOT_YET_SUPPORTED`-power rejection,
  duplicate pick, per-pick over-limit rejection, total-spend-over-budget rejection (two individually
  valid picks whose sum exceeds budget), rating below 1, rating capped by the Power Point budget
  (not just the power's own `<limit>`), `levels=False` rejecting a non-1 rating, select-attribute
  requiring/validating its target, rejecting a selected attribute where none is needed, a successful
  select-attribute pick; `apply_power_improvements` tests for the select-attribute case, a limit
  bonus, Enhanced Perception's 2-skill case, Voice Control's combined limit+skill case, and that
  `source_id` is the power's own id.
- `tests/integration/test_magic_fixtures.py`: new
  `test_wesson_adept_powers_hand_verified_against_the_raw_fixture_and_catalog` — confirms the exact
  4 SR5-sourced / 2 non-SR5 split among his 6 real powers, confirms all 4 SR5-sourced ones are
  `NOT_YET_SUPPORTED` (a stronger, more honest assertion than the plan's own acceptance text
  anticipated — see Log), and hand-verifies the Power Point budget sum (4.0) against his MAG-4
  rating using every one of his 6 real powers' raw data.

## Outcome

WP27 complete. `chummer5.data.powers.load_powers()` loads the 28 SR5-core Adept Powers, classifying
6 as `FLAT_BONUS` (Enhanced Perception, Improved Physical Attribute, the Improved Potential trio,
and Voice Control — a 4th candidate this WP's own rulebook research found beyond the 3 the
Implementation Plan named) and 22 as `NOT_YET_SUPPORTED`, with zero `NO_EFFECT` cases (individually
checked, not assumed). `chummer5.engine.magic.create_power_selection`/`apply_power_improvements`
compose that catalog with a Power Point budget and this engine's Improvement mechanism, reusing the
exact `MENTAL_LIMIT`/`PHYSICAL_LIMIT`/`SOCIAL_LIMIT`/`SKILL`/`ATTRIBUTE` machinery WP22/WP23 already
proved out for qualities — no new derived-stat plumbing needed. The regression trap the Implementation
Plan's own intro was built around (Attribute Boost vs. Improved Physical Attribute sharing a raw XML
tag) is caught and pinned down by a named test. Wesson's real fixture turned out to exercise none of
the `FLAT_BONUS` path positively (all 4 of his SR5-sourced powers are `NOT_YET_SUPPORTED`, a stronger
finding than the plan's acceptance text anticipated) but does verify the Power Point budget math
exactly by hand. `pytest`/`ruff`/`mypy` are all green (400 tests, 32 more than before this WP). WP28
(Drain Resistance + magic-aware save/load + legacy import unblocking) is next.
