# WP28 — Drain Resistance + magic-aware save/load + legacy import unblocking

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase I, WP28.

## Goal

Finish the derived-stat surface magic chargen needs (Drain Resistance), thread Phase I's new
`Character` fields (`magic_type`/`tradition`/`spell_selection`/`power_selection`) through native
save/load, and replace the blanket "Magic is enabled" legacy-import rejection with real,
itemized support up to this phase's scope.

## Log

### 2026-07-19 — Confirming Drain Resistance's two formulas via the rulebook, not just WP27's

Implementation Plan's own text already flagged (from WP27's research) that Drain Resistance is not
Magician-only — an Adept's Drain Resistance uses a fixed Body + Willpower formula, distinct from a
Magician's tradition-dependent pair. Confirmed both halves directly via `pdftotext -layout`:
Hermetic/Shamanic's own stat blocks (p.278-279) list "Drain: Logic + Willpower" / "Drain: Charisma +
Willpower" respectively — matching `chummer5.data.traditions.Tradition.drain_attributes` exactly,
which was parsed from the XML but never before cross-checked against the actual rulebook prose for
this specific derived stat; and the Adept Drain paragraph (p.308, already located by WP27 for the
Attribute Boost trap) confirms "resisted with Body + Willpower" as a fixed rule independent of which
powers were bought. See `spec/rulebooks/learnings.md`'s new WP28 entry for both citations in full.

### 2026-07-19 — A real, previously-latent gap found while pursuing this WP's own Wesson acceptance
criterion: Karma-bought attribute points at chargen were never modeled

The Implementation Plan's own WP28 acceptance text expected both Miko and Wesson to be usable as
"integration test importing Miko and Wesson end to end" cases (with Miko specifically expected to
still fail, for her non-SR5 tradition). Building Wesson's import path surfaced a second, completely
unrelated failure: `chummer5.io.legacy_import.import_legacy_character`'s `attribute_points` formula
has read `legacy.attributes[code].base + legacy.attributes[code].karma` since WP12 — silently
combining priority-derived points with Karma-bought points beyond the priority budget into one
number, then validating that combined number against `create_character`'s priority-budget-only
check. This was never actually exercised with a nonzero `karma` value before now: Yeti (the sole
Priority-built fixture among the curated mundane 11) has `karma == 0` on every allocatable
attribute. Wesson does not — his real `<attribute name="EDG"><base>1</base><karma>1</karma>
</attribute>` against Heritage E's 1-point special-attribute-points budget for Human means he spent
1 Karma-bought EDG point *beyond* that budget, a real, valid, standard SR5 chargen choice
(spending Karma to buy an extra attribute point at character creation) this engine has simply never
modeled at all — not a magic-specific gap, just one that happened to only be exposed by this
phase's own new fixture.

Fixed by rejecting any nonzero-karma allocatable attribute as a new, itemized blocking reason
(`"character has Karma-bought attribute points beyond the priority budget on {codes}; ..."`),
mirroring the existing cyberware/metavariant treatment, and narrowing `attribute_points` to `.base`
only (safe once the new guard guarantees `karma == 0` for anything reaching that line). The
consequence: **neither of Phase I's 2 real magic fixtures can achieve a full round-trip
`import_chum5()` success** — Miko for her own tradition gap (as the Plan anticipated), Wesson for
this orthogonal, newly-discovered one (which the Plan did not anticipate). This is a stronger,
more honest finding than the Plan's own acceptance text, in the same "verify by hand, don't force
the plan's optimism through" spirit WP25/26/27 already established repeatedly for these same two
fixtures. WP28's actual deliverables (Drain Resistance, magic-aware save/load, itemized-not-blanket
rejection) are still fully proven — via `tests/integration/test_magic_fixtures.py::
test_wesson_adept_magic_and_drain_via_direct_engine_construction`, which composes the same engine
functions `import_legacy_character` would have, directly against Wesson's real data, bypassing only
the one broken step (see Design decisions).

### 2026-07-19 — A second, smaller correction: Yeti's own Talent codename ("Technomancer") broke
the naive "always trust the legacy save's talent_codename" assumption

Fixing the above surfaced a second bug in the same area, caught by the existing Yeti regression
suite rather than new research: `Yeti-#ffffff2.chum5` (`resonance_enabled == True`, `magic_enabled
== False`) carries a real, non-"Mundane" `<prioritytalent>Technomancer</prioritytalent>` at a
Talent letter (`B`) that doesn't even offer "Mundane" as an option — passing that raw codename
through to `create_magic_selection` unconditionally (which the first draft of this WP's import
code did) raised `ValueError: 'Technomancer' is not an offered Talent option at letter 'B'` for
every existing Yeti-based test. Fixed by only trusting `legacy.priorities.talent_letter`/
`talent_codename` (and the free-skill grant) when `legacy.magic_enabled` is `True`; forcing both to
their Mundane defaults (`DEFAULT_TALENT_LETTER`/`DEFAULT_TALENT_CODENAME`, imported from
`chummer5.io.save_format` rather than re-defined) otherwise. This is the same "ignore Resonance
content, don't half-model it" rule WP6-WP10 already established for Yeti's other fields
(Technomancer quality, RES attribute), just applied to this WP's new Talent fields instead of
silently working by never reading them.

## Design decisions

- **`drain_resistance` returns `int | None`**, `None` for Mundane (`magic_type is None`) — mirrors
  `BASE_ESSENCE`'s own "not meaningful" carve-out for a similarly not-applicable case, rather than
  returning `0` (which would read as "a real Drain Resistance of zero," not "not applicable").
- **New `ImprovementType.DRAIN_RESISTANCE`**, with no current producer (checked directly: no SR5
  core quality/power's `<bonus>` targets Drain) — threaded through anyway, for the same "the
  derived stat needs somewhere to resolve Σ improvements against" reason every other
  `ImprovementType` member here was added for, before any real producer existed.
- **`CharacterSave`'s 6 new WP28 fields (`talent_letter`/`talent_codename`/`tradition_id`/
  `granted_skill_ids`/`spell_ids`/`power_picks`) all default to Mundane**, unlike WP20's Lifestyle
  fields (which are unconditionally required, since SR5 makes Lifestyle mandatory for every
  character). Talent is different: WP29 (the web UI for magic chargen) hasn't landed, so every
  save `chummer5.web.app` currently produces *is* Mundane — defaulting these fields keeps every
  existing call site (`chummer5.web.app`'s save/load routes included) working completely unchanged,
  rather than a mechanical "pass Mundane explicitly everywhere" edit for a UI capability that
  doesn't exist yet. `build_character`'s new `traditions`/`spells`/`powers` parameters default to
  `()` for the identical reason. `FORMAT_VERSION` stays `1` — this is a purely additive,
  backward-compatible shape change (`_dict_to_save` reads the 6 new keys via `.get(..., default)`,
  not `data[...]`), not the kind of breaking change that field exists to gate.
- **`DEFAULT_TALENT_LETTER`/`DEFAULT_TALENT_CODENAME` are defined locally in
  `chummer5.io.save_format`**, duplicating (not importing) `chummer5.web.session`'s identically-
  valued constants — `io` must not depend on `web`. `chummer5.io.legacy_import` imports
  `save_format`'s copies rather than defining a third.
- **A non-magic-enabled legacy character's Talent letter/codename/free-skill-grant are always
  forced to Mundane defaults, never read from the raw save.** See the Log's Yeti finding above —
  this isn't just cosmetic; a Resonance character's real `talent_codename` can be genuinely
  unresolvable against this phase's Magic-only offered set.
- **Spell/power budgets in `build_character` are each `0` for whichever of Magician/Adept doesn't
  apply**, rather than a special case rejecting a mismatched save's picks directly — `create_spell_
  selection`/`create_power_selection`'s own existing budget checks already reject any nonzero pick
  against a `0` budget, so this reuses validation that already exists instead of adding a new one.
- **Karma-bought attribute points are a new blocking reason, not a formula fix.** See the Log entry
  above for the full reasoning — modeling actual Karma-for-attribute-points spend at chargen is a
  genuinely different, non-trivial feature (it would need a tracked starting-Karma budget this
  engine has no concept of at all) squarely out of this WP's scope, so rejecting cleanly (mirroring
  cyberware/metavariant) is the correct move, not a workaround.
- **`legacy_import.py`'s new spell/power resolution is unconditional (not gated on Magician/Adept
  specifically), unlike the Talent-letter/codename/tradition/free-skill-grant fields.** A
  non-magic-enabled character's `<spells>`/`<powers>` blocks are empty in every real fixture
  checked, so gating would be defensive-but-untested; leaving it unconditional is simpler and
  behaves identically (an empty `legacy.spells`/`legacy.powers` resolves to nothing either way).

## Implementation

- `src/chummer5/engine/improvements.py`: new `ImprovementType.DRAIN_RESISTANCE`.
- `src/chummer5/engine/derived.py`: `drain_resistance(character)` — dispatches on `magic_type`:
  `None` for Mundane; `character.tradition.drain_attributes` summed for Magician; fixed
  `BOD + WIL` for Adept; both add `Σ improvements`.
- `src/chummer5/io/legacy_chum5.py`: `LegacyCharacter` gains `tradition_name: str` (from the
  save's own `<tradition><name>`, always present even for non-Magicians, per the raw format),
  `spells: tuple[LegacySpell, ...]`, `powers: tuple[LegacyPower, ...]` (new `LegacySpell`/
  `LegacyPower` dataclasses — the latter carries `extra` for a `select_attribute`-shaped power's
  purchased target). `MAG`'s own resolved rating needed no new field at all — `attributes["MAG"]
  .total_value` already resolves generically, the same as every other attribute.
- `src/chummer5/io/save_format.py`: `CharacterSave`/`create_character_save` gain the 6 new fields
  (see Design decisions); `_save_to_dict`/`_dict_to_save` thread them through JSON (the latter via
  `.get(..., default)`); `build_character` gains `traditions`/`spells`/`powers` parameters and now
  also composes `create_magic_selection`/`apply_magic_skill_grant_improvements`/
  `create_spell_selection`/`create_power_selection`/`apply_power_improvements`, attaching
  `magic_type`/`magic_rating`/`tradition`/`magic_granted_skill_ids`/`spell_selection`/
  `power_selection` onto the final `replace(...)`.
- `src/chummer5/io/legacy_import.py`: `_blocking_reasons` replaces the blanket "Magic is enabled"
  check with two narrower ones fired only when `legacy.magic_enabled` (unsupported Talent codename;
  Magician-specific unresolvable tradition), plus the new, unrelated Karma-bought-attribute check.
  `import_legacy_character` resolves Talent letter/codename/tradition id (Mundane-forced when not
  `magic_enabled` — see Design decisions), the Talent free-skill grant (raises on an unresolvable
  name — a data-integrity guard, mirroring `resolve_metatype_qualities`'s identical reasoning),
  spells (excluded-and-reported via new `ImportResult.dropped_spells`), and powers (same treatment,
  `ImportResult.dropped_powers`, restricted to `mvp_power_catalog` and resolving a `select_attribute`
  power's target from the legacy `extra` field). `attribute_points` now reads `.base` only.
  `import_chum5` threads the 3 new catalog parameters through, all defaulting to `()`.

## Outcome

WP28 complete. `chummer5.engine.derived.drain_resistance` implements both of Phase I's Drain
Resistance formulas (tradition-pair for Magician, fixed BOD+WIL for Adept, `None` for Mundane),
each confirmed directly against the rulebook. Native save/load (`chummer5.io.save_format`) now
round-trips a full magic character — Talent type, tradition, the free-skill grant, spells, and
Adept powers — with every new field defaulting to Mundane so no existing caller needed updating.
`chummer5.io.legacy_import` replaces its blanket "Magic is enabled" rejection with real, itemized
support: an unsupported Talent codename or an unresolvable Magician tradition both block with a
specific reason, while unsupported spells/powers are excluded and reported like any other
unsupported quality/skill. Two real, previously-latent gaps were caught and fixed along the way,
neither of which is really about magic: a non-magic-enabled Resonance character's raw Talent
codename must never be trusted (Yeti), and Karma-bought attribute points at chargen were never
modeled at all (Wesson) — both are now correctly itemized blocking reasons rather than crashes or
silently-wrong values. The net, more honest result than the Implementation Plan's own acceptance
text anticipated: **neither of Phase I's 2 real magic fixtures achieves a full round-trip
`import_chum5()` success** — Miko for her own non-SR5 tradition (anticipated), Wesson for the
Karma-bought-attribute gap (not anticipated) — but WP28's actual deliverables are still fully
proven, against Wesson's real numbers, by composing the engine directly. `pytest`/`ruff`/`mypy` are
all green (415 tests, 15 more than before this WP). WP29 (Magic chargen UI + character sheet) is
next — the last WP in Phase I.
