# WP29 — Magic chargen UI + character sheet

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase I, WP29 (last WP in Phase I).

## Goal

Expose Talent/tradition/spell/power selection through the browser, and show Magic rating/spells/
powers/Drain Resistance on the character sheet — the UI-reaching WP for everything WP24-WP28 built
headlessly. Decide and document the chargen-flow branching this introduces (every screen before
this WP has been unconditionally shown).

## Log

### 2026-07-19 — Neither of the corpus's 2 real magic fixtures can be used for the manual
walkthrough, confirmed again rather than re-assumed

WP28's own worklog already established that neither Miko (non-SR5 tradition) nor Wesson
(Karma-bought-attribute-points gap) can reach a full round-trip `import_chum5()` success. Re-checked
directly before writing this WP's tests/walkthrough rather than trusting that finding secondhand —
both still fail for the same reasons (nothing in WP29 touches `legacy_import.py`'s validation).
Built a Magician and an Adept from scratch through the browser instead, using the same letter/
codename combinations those two fixtures use (`priorities.xml` letter B: Adept magic=6, Magician
magic=4) so the numbers are still grounded in real data, just not reproduced fixture-for-fixture.

### 2026-07-19 — A real, previously-latent gap this WP's own manual walkthrough caught: the
character sheet's skill table used `MUNDANE_SKILLS`, which silently excludes every Magical Active
skill — including a Magician's own Talent-granted ones

`_character_sheet_context`'s `skill_rows` was built from `MUNDANE_SKILLS` (deliberately excludes
MAG/RES-linked skills — WP2's original "MVP is mundane-only" curation, still correct for the
*buy* UI, since regular Skills-priority points still can't be spent on them). But a Magician's
Talent free-skill grant (`chummer5.engine.magic.apply_magic_skill_grant_improvements`) raises a
Magical Active skill's rating via a pure `Improvement`, entirely independent of that buy UI — so
before this fix, confirming Spellcasting/Counterspelling at rating 5 through `/ui/talent` would
never show up on the sheet at all, silently. Fixed by adding `ALL_SKILLS_SORTED` (every skill, not
just the mundane-offered subset) as the sheet's own iteration source — safe for Mundane too, since
no skill this widens back in can ever have nonzero `SkillAllocation` points or an Improvement for a
Mundane character (nothing offers points on them), so the existing `rating > 0` filter still
excludes them identically. `MUNDANE_SKILLS` itself is unchanged; only the read-only sheet's source
catalog changed.

### 2026-07-19 — Deliberately scoped out: widening the regular Skills-priority buy UI to Magical
Active skills for Magician/Adept characters

A Magician/Adept can, per SR5, spend *additional* regular Skills-priority points on Magical Active
skills beyond the Talent free grant (e.g. buying Spellcasting past its granted rating 5). This WP
does not implement that — `MUNDANE_SKILLS` still excludes them from `/ui/skills`'s picker entirely.
Not silently broken (the previous section's fix means the grant's own rating still displays
correctly), but a real, deliberate scope cut: correctly widening the picker needs to decide, per
character, which subset of the 12 Magical Active skills to offer (all of them? only the character's
own tradition-relevant ones? nothing in this phase's two real fixtures or its own Implementation
Plan text resolves that), which is new research this WP's own scope (UI plumbing for already-decided
mechanics) doesn't cover. Flagged here rather than defaulted into silently, mirroring this project's
established practice for every other deliberate cut.

## Design decisions

- **Chargen-flow branching: Talent is a new, always-visible section (mirrors WP14's metatype+
  priority screen shape); Spells/Powers are new sections that render nothing at all (not even a
  heading) unless `character.magic_type` is `"Magician"`/`"Adept"` respectively.** Every prior
  section (attributes, skills, qualities, contacts, lifestyle, resources) is unconditionally shown
  once a metatype+priorities are confirmed. Talent joins that group unconditionally too — every
  character, magic or not, has *a* Talent (even if it's Mundane), so hiding it would misrepresent
  chargen's own real Step Three. Spells/Powers are different: they're not "empty until spent," they
  are *inapplicable* for 2 of the 3 Talent types, so an empty `<div id="spell-selection"></div>`
  (no placeholder text, no heading) is more honest than a "not available" message that would need to
  appear on every single non-Magician page load. Section order in `_chargen_body.html`: Priority
  form → Talent → Attributes → Skills → Spells → Powers → Qualities → Contacts → Lifestyle →
  Resources — Talent placed right after the priority form (SR5's own "Step Three," ahead of
  Attributes/Skills) and Spells/Powers placed right after Skills (both draw on the same "what
  skills/attributes does the character have so far" context, and neither blocks anything after it).
- **The Talent-codename picker uses the same live-refresh pattern WP14 already established for
  metatype selection (`GET /ui/talent-options`, mirroring `GET /ui/metatypes`), not a full-body
  round trip.** Picking a different codename radio button refreshes just the tradition dropdown +
  free-skill-grant checkboxes (`_talent_options.html`, a fragment shared between the initial
  server-render — via `{% include %}` — and the live-refresh route) via `hx-get`, keeping the
  editing experience responsive the same way changing Heritage already refreshes the metatype list
  without a full `/ui/priorities` submission.
- **No live refresh between the Talent letter selector (in `_priority_form.html`) and the Talent
  section itself.** Mirrors WP20's own documented "no HTMX out-of-band swap between `#resources` and
  `#lifestyle`" scope boundary: changing the Talent letter in the still-open priority form doesn't
  live-update which codenames the Talent section below offers until the priority form is actually
  submitted. Validation is always correct regardless (the codename is re-validated against whatever
  letter is actually confirmed); only the *display* of the not-yet-submitted letter's own offered
  codenames can lag by one submission, the same cosmetic-only staleness window WP20 already accepted
  for gear/Lifestyle.
- **A (re)confirmed Talent selection resets `spell_selection`/`power_selection` to `None`** (new
  `_replace_committed_talent` helper), rather than trying to carry them forward and flag them stale
  the WP19 way. Attribute/skill/resources spend against a resized-but-still-comparable budget has an
  obvious "still fits or doesn't" question to re-ask; a changed Talent codename (Mundane → Magician,
  Magician → Adept, or even a changed tradition) doesn't — there is no partial carry-forward of "3 of
  my 10 spells" onto an Adept who has no spell budget at all. The player re-picks spells/powers after
  any Talent change, the same "start that stage over" behavior a metatype swap already gives
  `skill_allocation` et al. pre-WP19 (Talent is foundational in the same specific sense, just
  narrower in what it resets — quality/contact selections are untouched).
- **`submit_attributes` needed a new relink helper, `_relink_magic_selection`, mirroring
  `_relink_quality_improvements`/`_relink_metatype_qualities`.** `submit_attributes` still rebuilds
  via `create_character()` fresh (WP19 deliberately left it that way — see that WP's own worklog),
  which resets `magic_type`/`magic_rating`/`tradition`/`magic_granted_skill_ids`/`spell_selection`/
  `power_selection` to their Mundane/unset defaults and starts a brand-new, empty `ImprovementIndex`.
  Without this helper, a Magician/Adept's *entire* Talent selection — not just the free-skill grant's
  Improvements, the flat fields themselves — would silently reset to Mundane on the very next
  attribute-point edit. Re-derives the Talent selection via `create_magic_selection` (using the
  session's *current* `talent_letter`, not necessarily whatever letter was in effect when the
  previous `Character` was built) rather than trusting a stored snapshot, the same "recompute, don't
  just re-attach" reasoning `_relink_contact_selection` already established — `Character` has no
  field for the free-skill grant's *rating*, only the granted skill *ids*, so re-deriving is the only
  option regardless of style preference. `submit_priorities`, by contrast, needed **no equivalent
  change**: WP19's `dataclasses.replace`-in-place already carries every untouched field (including
  the 6 magic-related ones and `improvements`, already populated) forward *by reference* — the
  staleness re-validation that *does* apply there is handled entirely in `_talent_selection_context`
  (a render-time check, the same `_attribute_allocation_context`/`_skill_allocation_context`/
  `_resources_context` pattern WP19 established), not in `submit_priorities` itself.
- **`_talent_selection_context` re-validates a committed Talent selection against the *current*
  Talent letter on every clean render**, the same WP19-style `*_budget_warning` pattern (here,
  `talent_budget_warning`) — a priorities reconfirmation can move Talent to a letter that no longer
  offers the committed codename (or drops/changes the tradition list), and `character.magic_type`
  stays exactly as it was (per the point above) rather than being silently reset. Folded into the
  same `priority_stale_selections` aggregate `_chargen_body_context` already computes, so the
  priority form's existing "some selections no longer fit" banner covers Talent too, not just
  attributes/skills/resources/lifestyle (the banner's own wording was widened from "attribute, skill,
  or gear" to include Talent explicitly, so it stays accurate rather than just technically true).
- **`_character_save_from_session`/`_apply_built_character_to_session` now thread the character's
  real Talent selection instead of the Mundane-only defaults WP28 left them at.** WP28 explicitly
  deferred this ("every save `chummer5.web.app` currently produces *is* Mundane... a future WP29
  would simply stop relying on the default") — this WP is that stop. `session.talent_letter` (never
  folded onto `Character`, same as `skills_letter`/`resources_letter`) plus `character`'s own flat
  magic fields and `spell_selection`/`power_selection` are exactly the missing pieces; no new
  `CharacterSave`/`build_character` field was needed since WP28 already added all 6.
- **`import_chum5_route`/`load_save` now pass the real `TRADITIONS`/`SPELLS`/`POWERS` catalogs**
  (previously all defaulted to `()`, since nothing in the web layer consumed them before this WP) —
  mechanical, but load-bearing: without it, even a hypothetical successful Magician/Adept import
  would have every spell/power dropped as unresolvable regardless of catalog membership. Confirmed
  this doesn't change either currently-passing import test's assertions (Miko's rejection reason is
  unaffected — Shinto isn't in the real 2-entry catalog any more than it was in an empty one); added
  `dropped_spells`/`dropped_powers` reporting to `import_chum5_route`'s info message, mirroring the
  existing `dropped_qualities`/`dropped_skills` treatment (WP28 added these fields to `ImportResult`
  but nothing surfaced them to a player before this WP).
- **Widening the regular Skills-priority buy UI to Magical Active skills is deliberately out of
  scope** — see the Log entry above.

## Implementation

- `src/chummer5/web/app.py`:
  - New module-level catalogs: `TRADITIONS`, `SPELLS`, `POWERS`, `MVP_POWERS`, `ALL_SKILLS_SORTED`.
  - New context builders: `_default_talent_codename`, `_talent_selection_context`,
    `_spell_selection_context`, `_power_selection_context`.
  - New relink/replace helpers: `_remove_adept_power_improvements`, `_relink_magic_selection` (used
    by `submit_attributes`), `_replace_committed_talent` (used by `submit_talent` — resets spell/
    power selections), `_replace_committed_powers` (used by `submit_powers`).
  - New parser: `_parse_power_picks` (mirrors `_parse_gear`'s "absence/zero means not purchased"
    convention).
  - New routes: `GET /ui/talent-options` (live tradition/skill-grant fragment refresh, mirrors `GET
    /ui/metatypes`), `POST /ui/talent`, `POST /ui/spells`, `POST /ui/powers`.
  - `_chargen_body_context` folds in `_talent_selection_context`/`_spell_selection_context`/
    `_power_selection_context` and `talent_budget_warning` into `priority_stale_selections`.
  - `_character_sheet_context`: `skill_rows` now iterates `ALL_SKILLS_SORTED` (see Log); new keys
    `magic_type`/`magic_rating`/`tradition_name`/`power_points`/`drain_resistance`/`spell_names`/
    `power_rows`.
  - `_character_save_from_session`/`_apply_built_character_to_session`: real Talent selection
    threading (see Design decisions).
  - `load_save`/`import_chum5_route`: pass `traditions=TRADITIONS, spells=SPELLS, powers=POWERS`;
    the latter also surfaces `dropped_spells`/`dropped_powers`.
- `src/chummer5/web/templates/`:
  - `_talent_selection.html` (new): Talent-letter summary, codename radio group (live-refreshing
    `_talent_options.html` via `hx-get`), submit posts to `/ui/talent`.
  - `_talent_options.html` (new): tradition dropdown (Magician only) + free-skill-grant checkboxes,
    shared between the initial render and the live-refresh fragment.
  - `_spell_selection.html` (new): mirrors `_quality_selection.html`'s picker shape; renders nothing
    for a non-Magician.
  - `_power_selection.html` (new): rating inputs per `FLAT_BONUS` power, attribute dropdown for the
    one `select_attribute`-shaped power; renders nothing for a non-Adept.
  - `_chargen_body.html`: includes the 3 new templates in the order described above.
  - `_priority_form.html`: Talent copy updated (no longer claims Talent "always resolves to
    Mundane"); staleness banner wording widened to mention Talent.
  - `_character_sheet.html`: new "Magic" section (type, rating, tradition, Power Points for Adept,
    Drain Resistance, spell list, power list) — entirely absent (not shown as zeroes) when
    `magic_type` is unset.

## Correction (2026-07-20) — Magic/Resonance IS raisable with Special Attribute Points; WP25's
"not a point-buy" finding was wrong

A user question ("shouldn't Special Attribute Points be spendable on Magic?") caught a real error
introduced by WP25 and carried unfixed through WP26-WP29. WP25's docstring claimed the Magic rating
"is not a point-buy" — the chosen Talent option's `magic` field *is* the finished rating, full stop.
Confirmed independently against both the rulebook and the legacy engine that this is wrong: it's
correct that MAG isn't funded from the *Attributes*-priority budget the primary 8 attributes use,
but wrong that it can't be raised at all.

**Rulebook, p.65 ("Choose Metatype" → "Special Attributes"):** "[Special attribute points] may be
spent entirely on Edge if the player chooses not to play a magic user or a technomancer, or they may
split these points as they see fit between their Edge and Magic or Resonance attribute ratings if
the player so chooses." Confirmed again in the p.69-70 worked examples: Kyra's and James's finished
sheets both show a Magic/Resonance row with its own "Points Spent" column, right alongside Edge's,
and the prose says outright that the Talent-granted rating "is added to" whatever Special Attribute
Points were dedicated to it.

**Legacy C# (`SelectMetatypePriority.cs`'s "Set starting magic" block):** `MAG.AssignLimits(talentOption
.magic, magMax, magMax)` sets the Talent value as MAG's *minimum*, not its final value — `Attribute
.Core.cs`'s `Value` property then applies the exact same `RawMetatypeMinimum + Base + modifiers`
formula every other attribute (including EDG) uses, drawing `Base` from the same pool EDG's own
`Base` draws from. See `spec/rulebooks/learnings.md`'s "Post-WP29 correction" entry for the full
citations, including why neither Miko nor Wesson (Phase I's only 2 real fixtures) ever exercised
this — both happened to pick a letter/codename combo where the Talent-granted rating already equals
the metatype's Magic maximum (6), leaving zero headroom to spend into.

**Fix, without a new WP number** (this corrects already-shipped WP25/WP29 work rather than adding a
new capability, so it's recorded here rather than claiming its own Implementation Plan entry):
- `chummer5.engine.character.Character` gains `magic_attribute_points: int = 0`; `attribute_value
  ("MAG")` becomes `magic_rating + magic_attribute_points + Σ improvements`, capped at the
  metatype's own Magic maximum (unchanged: `0` outright for Mundane, `magic_type is None`). `power_
  points` now reads `attribute_value("MAG")` (the *finished* rating), not the raw `magic_rating`
  field — the rulebook's "Power Points equal to their Magic attribute" (p.278) means the finished
  one.
- `chummer5.engine.magic.create_magic_attribute_points(magic_type, points, magic_rating, magic_
  maximum, special_attribute_points_budget, other_special_attribute_points_spent)` (new): validates
  `points` against both MAG's own per-attribute maximum and the *shared* budget with EDG — mirrors
  `chummer5.engine.lifestyle`'s cross-selection shared-budget precedent (gear + Lifestyle) rather
  than folding MAG into `ALLOCATABLE_ATTRIBUTES`/`create_character` itself: MAG's allocatability is
  character-specific (only legal once `magic_type` is set), unlike EDG's fixed, unconditional one.
- `chummer5.web.app`: the Attributes section (`/ui/attributes`) is where MAG's points get spent —
  the same screen EDG already uses, matching how the legacy UI groups every attribute (primary +
  special) in one spend screen, not the Talent form. A new `"MAG"` row is appended to `attribute_
  rows` with the identical shape every other row has, so `_attribute_allocation.html` needed no
  template branching. A (re)confirmed Talent selection (`_replace_committed_talent`) resets `magic_
  attribute_points` to `0`, mirroring the existing spell/power reset — a changed `magic_rating`
  changes how much headroom is even left, so a prior spend can't be blindly carried forward.
- `chummer5.io.save_format`/`legacy_import`: `magic_attribute_points` threaded through `CharacterSave`
  (defaults to `0`, additive/backward-compatible like every other WP28 magic field) and imported
  from a real `.chum5`'s own `legacy.attributes["MAG"].base` when `magic_enabled` (the same field
  `attribute_points` already reads for EDG); the existing Karma-bought-attribute blocking check
  (WP28) now also covers MAG's `.karma` when magic-enabled.
- 26 new tests across `test_magic.py` (7, the validator in isolation), `test_character.py` (4,
  formula/cap/Mundane-immunity), `test_save_format.py` (3, round-trip + shared-budget rejection),
  `test_legacy_import.py` (3, karma-bought-MAG rejection + `.base` resolution), and
  `test_web_magic.py` (9, the full web flow: MAG row visibility, spend/cap/shared-budget
  enforcement through `/ui/attributes`, Talent-reset, carry-forward across an attribute edit,
