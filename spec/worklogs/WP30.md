# WP30 — Essence as a real, Improvement-driven `Character` value

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase J, WP30 (first WP in Phase J).

## Goal

Replace `chummer5.engine.derived.BASE_ESSENCE`'s role as a fixed, final constant with a real,
reducible value — `essence()`, resolved as `BASE_ESSENCE + Σ ESSENCE improvements` — proven with
synthetic Improvement data before any cyberware catalog exists to produce one for real, mirroring
WP5's own sequencing relative to WP6+. This is the Essence-tracking prerequisite the Project
Overview's 2026-07-18 Open Questions entry and the Implementation Plan's Phase J intro both flag as
blocking real cyberware content (WP31+).

## Log

### 2026-07-20 — Confirming the fractional-precision requirement before picking a representation

The Implementation Plan's own WP30 entry names three candidate representations for
`Improvement.value` and asks this WP to record the tradeoff, but doesn't say how much fractional
precision is actually needed — checked directly against `legacy/Chummer/data/cyberware.xml`'s raw
`<ess>` values (`grep -oP '(?<=<ess>)[^<]+' cyberware.xml | sort -u`) rather than assuming. Real
flat (non-formula) essence costs go to **3 decimal places** — `1.125`, `5.31`, `2.09`, `2.23`,
`3.06`, `1.69`, `1.44`, `1.08` all appear alongside the more common 1-2 place values (`0.75`, `0.3`,
...). This rules out a hundredths-based fixed-point encoding inside the existing `int value` field
(candidate (c) in the Plan's own framing) as lossy for a real subset of WP31's future catalog, not
just a theoretical edge case — confirming this before picking a representation, rather than
assuming "two decimal places is surely enough" the way a casual reading of `0.75`/`0.3`-style
examples might suggest, is what actually decided the choice below.

### 2026-07-20 — `essence()` needs to be a free function in `derived.py`, not a `Character` method

Considered adding an `essence` property to `Character` directly (mirroring `power_points`, WP25/
WP29's precedent for a computed-not-stored value). Rejected: every other derived stat in this
project's scope (`initiative_value`, the three Limits, both condition monitors, `drain_resistance`)
is a free function in `chummer5.engine.derived`, not a `Character` method — and `derived.py` already
imports `Character` from `character.py`, so a `Character.essence` property calling back into
`derived.essence()` would be circular. `power_points` is a `Character` property because it composes
two fields (`magic_type`, `attribute_value("MAG")`) that already live directly on `Character` with
no external module involved; `essence()` only reads `character.improvements`, so it fits the
existing free-function shape with zero friction. This also means, contrary to the Implementation
Plan's own "touches `engine/character.py` too" framing in WP30's `Depends on` line, **no change to
`character.py` was actually needed** — recorded here so a future reader doesn't go looking for one.

## Design decisions

- **Fractional Essence representation: a parallel `Improvement.essence_value: Decimal | None = None`
  field, consulted only when `improvement_type is ImprovementType.ESSENCE`** — the Implementation
  Plan's own candidate (b). Weighed against the other two named candidates:
  - **(a) Widen `Improvement.value` to `Decimal`/`float` engine-wide.** Rejected: `resolve()`'s
    `int` return type is relied on, directly or transitively, by every one of the other 8
    `ImprovementType` members and by every arithmetic expression in `chummer5.engine.derived`/
    `character.py` that adds a resolved value to an attribute/limit/CM total — none of those are
    ever fractional in real SR5 (an attribute point, a Limit bonus, a condition-monitor box are
    integers by construction). Widening the shared field would either quietly turn every one of
    those into `Decimal` arithmetic (a type ripple with zero payoff, since none of them can actually
    produce a fraction) or require every non-Essence call site to wrap its result back to `int`
    defensively. Essence is a genuinely different *kind* of quantity from the other 8, not just a
    finer-grained version of the same thing.
  - **(b) A parallel `essence_value: Decimal` field — chosen.** Keeps every existing
    `ImprovementType`'s `resolve()` path (and its `int` return type) completely untouched; only
    `ESSENCE`-typed improvements read/write the new field. `resolve()` itself now rejects
    `ImprovementType.ESSENCE` outright (raises `ValueError`) instead of silently resolving to 0 for
    every such improvement — a real "would have looked like it worked" trap this guard exists to
    catch, given `value` is unused/`0` by convention on those instances. `Decimal` specifically
    (not `float`) avoids the binary-float representation error that would corrupt exact values like
    `0.3`/`0.1` (both of which appear in the real catalog) under repeated summation.
  - **(c) Fixed-point hundredths inside the existing `int` field.** Rejected per the Log entry above
    — real flat essence costs go to 3 decimal places, one more than a hundredths encoding preserves.
  - `resolve_essence(target) -> Decimal` (new `ImprovementIndex` method, mirroring `resolve()`'s
    shape but summing `essence_value`) deliberately does **not** apply `unique_name` dedup, unlike
    `resolve()`. SR5's "highest bonus wins" stacking rule exists to stop a player double-dipping on
    *bonuses* granted by multiple sources; an Essence cost is a plain sum of whatever
    cyberware/bioware was actually bought — there is no "highest cost wins" equivalent rule, and the
    legacy engine's own `Character.Essence()` sums every cyberware/bioware item's essence cost
    unconditionally (confirmed by reading it). Documented explicitly on `resolve_essence` itself so
    a future reader doesn't assume dedup carries over by analogy with `resolve()`.
- **`essence()` returns the exact, unrounded `Decimal`; only `social_limit` rounds, and only because
  its own formula is documented to need it.** Confirmed via `spec/rulebooks/learnings.md`'s existing
  WP10 entry (rulebook p.100: "For Social limits, round up Essence to the nearest whole number prior
  to calculating the cost") plus a fresh legacy-C# read this WP did to make sure "round up" really
  means ceiling and not round-half-up (`DecimalExtensions.StandardRound` — see this WP's own
  `spec/rulebooks/learnings.md` entry for the exact method body). Keeping `essence()` unrounded
  matters beyond `social_limit`: WP35 (Essence-driven Magic-rating loss, deferred to Phase I×J's
  cross-phase WP) needs to detect *any* nonzero fractional Essence loss per the rulebook's "for every
  point (or fraction thereof)" wording already recorded in `learnings.md`'s WP25 entry — a
  pre-rounded `essence()` would have silently thrown that signal away before WP35 ever gets to use
  it.
- **`ImprovementSource.CYBERWARE` added now, with no real producer yet** — mirrors every prior
  `ImprovementType`/`ImprovementSource` member's own introduction (WP10's 7 derived-stat types, WP25's
  `TALENT`, WP27's `ADEPT_POWER`): threaded through ahead of its first real consumer so WP31/WP32 can
  construct real `ESSENCE`/`CYBERWARE` improvements without a second enum-widening WP first.

## Implementation

- `src/chummer5/engine/improvements.py`:
  - `ImprovementType.ESSENCE` (new, 9th member) and `ImprovementSource.CYBERWARE` (new, 6th member),
    each with a docstring paragraph explaining its role and why it exists ahead of a real producer.
  - `Improvement.essence_value: Decimal | None = None` (new field) — see Design decisions.
  - `ImprovementIndex.resolve()`: now raises `ValueError` if called with
    `ImprovementType.ESSENCE` (see Design decisions).
  - `ImprovementIndex.resolve_essence(target) -> Decimal` (new method): sums `essence_value` for
    every `(ESSENCE, target)`-indexed improvement, no dedup (see Design decisions).
- `src/chummer5/engine/derived.py`:
  - `essence(character) -> Decimal` (new function): `Decimal(BASE_ESSENCE) +
    character.improvements.resolve_essence(_GLOBAL_TARGET)`.
  - `social_limit`: Essence term is now `math.ceil(essence(character))` instead of the bare
    `BASE_ESSENCE` constant — same value (6) for every character built so far, since nothing
    produces an `ESSENCE` improvement yet.
  - `BASE_ESSENCE`'s own comment and the module docstring's Essence paragraph updated to describe it
    as a starting point reduced by improvements, not a hardcoded final answer; added a new paragraph
    citing the `StandardRound`-is-ceiling finding for `social_limit`'s explicit rounding step.
  - No change to `character.py` — see the Log entry explaining why.

## Tests

- `tests/unit/test_improvements.py` (5 new tests): `resolve_essence` returns 0 for an untargeted
  key; sums fractional `Decimal` values exactly (including a 3-decimal-place case, `1.125`);
  ignores `unique_name` dedup even when two essence-costing improvements share one; only sums
  `ESSENCE`-typed improvements, ignoring an `ATTRIBUTE`-typed one in the same index;
  `resolve(ImprovementType.ESSENCE, ...)` raises `ValueError` rather than silently returning 0.
- `tests/unit/test_derived.py` (4 new tests): `essence()` defaults to `Decimal(BASE_ESSENCE)` with
  no improvements (proving zero behavioral drift); `essence()` sums multiple fractional
  `ESSENCE` improvements correctly; `social_limit` rounds a fractional Essence loss (0.5, leaving
  5.5) *up* to 6 rather than down to 5, leaving the limit unchanged from the base-Essence case (the
  rulebook's own "round up" rule, not round-to-nearest); `social_limit` reflects a real whole-number
  Essence loss (3.0, leaving Essence 3) as an actual drop in the computed limit (7 -> 6).
- The pre-existing `test_social_limit_hand_computed`/
  `test_social_limit_uses_fixed_essence_not_ess_attribute_value` tests pass unchanged — zero
  behavioral drift for every character with no `ESSENCE` improvement, which is every character
  buildable through this engine as of this WP (no producer exists until WP31/WP32).

## Outcome

WP30 complete. `chummer5.engine.derived.essence()` replaces `BASE_ESSENCE`'s role as a hardcoded
final answer with a real `base + Σ ESSENCE improvements` computation, proven entirely with synthetic
`Improvement` data (no cyberware catalog exists yet to produce one for real — that starts with
WP31). `Improvement` gains a dedicated `essence_value: Decimal` field (not a widened `value`, not a
fixed-point encoding) to carry fractional Essence costs exactly, since real SR5 essence costs go to
3 decimal places; `ImprovementIndex.resolve()` now actively rejects `ImprovementType.ESSENCE` rather
than silently mishandling it, and `resolve_essence()` is the real (dedup-free) summation path.
`social_limit` explicitly rounds Essence up before its own division, matching both the rulebook's
literal instruction and a freshly-confirmed legacy-C# detail (`StandardRound` is ceiling, not
round-to-nearest). Zero behavioral drift for every character buildable today: `pytest`/`ruff`/`mypy`
are all green (462 tests, 9 more than before this WP), and every pre-existing Essence-adjacent test
passes unchanged. Phase J continues with WP31 (Cyberware data loader), which is the first WP to
actually produce a real `ESSENCE`/`CYBERWARE` improvement.
