# WP32 — Cyberware selection & Improvement application

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase J, WP32.

## Goal

Compose WP30's Essence mechanism (`chummer5.engine.derived.essence`/`BASE_ESSENCE`) with WP31's
flat-cost, flat-Essence, Standard-grade cyberware catalog (`chummer5.data.cyberware`) and WP6's
`Character` into an actual, buildable cyberware purchase — the first WP in Phase J that produces a
real `ESSENCE`/`CYBERWARE` Improvement, mirroring `chummer5.engine.qualities`'s
`create_*_selection`/`apply_*_improvements` shape.

## Log

### 2026-07-21 — Confirming the shared-nuyen-pool claim before writing the signature

The Plan's own WP32 entry asks this to be checked, not assumed. Read the core rulebook directly
(`pdftotext -layout`): "STEP SIX: SPEND YOUR RESOURCES" (p. 94) names "Cyberware and Bioware" as its
own first subsection, on the same page whose intro text WP20 already cited for gear/Lifestyle's own
shared-budget finding. Confirms cyberware draws from the identical Resources-priority nuyen figure
as gear/Lifestyle, not a separate pool — recorded in `spec/rulebooks/learnings.md`'s new WP32 entry.
Chose to mirror `chummer5.engine.magic.create_magic_attribute_points`'s pattern (take the *other*
selection's already-resolved spend/budget as a plain parameter) rather than
`chummer5.engine.resources.create_resources_selection`'s pattern (a dedicated `lifestyle_cost`
parameter baked into the joint check) — `create_cyberware_selection` takes `nuyen_budget` directly,
since this WP is engine-only (no web route exists yet to compute "gear + Lifestyle already spent" and
subtract it); WP34 is where that arithmetic actually gets threaded through the web layer.

### 2026-07-21 — Confirming duplicate cyberware purchases are real, not a hypothetical edge case

Dumped every real `<cyberware>` entry from the Phase J intro's 8 cyberware-bearing fixtures via a
one-off `xml.etree.ElementTree` read before deciding this. `Barrett.chum5` has two `Synthetic Full
Arm` and two `Synthetic Full Leg`; `Bastion.chum5` has two `Obvious Full Arm` and two `Obvious Full
Leg` — a matched pair of cyberlimbs is an entirely ordinary build, not a data-entry fluke. Decided
`create_cyberware_selection` allows repeats (mirrors `chummer5.engine.resources
.create_resources_selection`'s existing "repeats allowed" gear-name handling), unlike
`chummer5.engine.qualities.create_quality_selection`'s one-of-each rule.

### 2026-07-21 — The same one-off dump also settled a subtler question: are stored `<ess>`/`<cost>`
fields grade-adjusted?

Several real purchases across these fixtures were bought at `Used`/`Alphaware` grade (e.g. Bastion's
`Obvious Full Arm` is `grade=Used`), which per `cyberware.xml`'s own `<grades>` table should multiply
Essence by 1.25 and cost by 0.75. Checked the actual stored `<ess>`/`<cost>` values directly: they
match the *Standard*-grade catalog numbers exactly (Essence 1, cost 15000), not the grade-adjusted
ones. Confirms the legacy engine stores the flat, pre-grade-multiplier value per item and applies the
grade multiplier only in a separate computed property at read time — which means this WP31/32
Standard-grade-only catalog can be compared against these fixtures' raw fields directly, regardless
of which real grade the item was actually bought at. This made the integration test
(`test_confirmed_flat_items_essence_and_cost_match_the_catalog_exactly`) straightforward instead of
needing a grade-aware comparison this phase deliberately doesn't implement.

### 2026-07-21 — Essence floor: checked the legacy validity gate directly rather than assuming "just
don't go negative"

The Plan's own WP32 entry calls for a `pdftotext -layout` check here specifically, not an assumption.
The rulebook (p. 51) confirms Essence acts as a hard cap but doesn't pin down whether exactly 0 is
still a legal result. Grepped the legacy C# for its own character-creation validity check
(`CharacterCreate.cs`'s `CheckCharacterValidity`) and found a dedicated "Check if the character's
Essence is above 0" block, rejecting the build (`Message_InvalidEssenceExcess`) whenever resulting
Essence would be `<= 0` — strictly positive, not merely non-negative. `create_cyberware_selection`
enforces the equivalent floor (`essence_spent >= BASE_ESSENCE` rejected) at selection time, since
nothing else in this project's scope produces an `ESSENCE` improvement yet — see
`spec/rulebooks/learnings.md`'s new WP32 entry for the full citation and code excerpt.

## Design decisions

- **`create_cyberware_selection(item_ids, catalog, nuyen_budget)` takes `nuyen_budget` as a plain
  parameter, not a `lifestyle_cost`-style joint-check parameter baked into
  `chummer5.engine.resources.create_resources_selection`.** See Log entry above — this WP is
  engine-only (no web route computes a three-way gear+Lifestyle+cyberware split yet), so the
  caller's responsibility to resolve "how much of the shared pool is left for cyberware" is left to
  whatever calls this function (a test today; WP34's web layer eventually), mirroring
  `chummer5.engine.magic.create_magic_attribute_points`'s `other_special_attribute_points_spent`
  parameter for the same "two selections, one shared budget, resolved by the caller" shape.
- **Duplicate item ids are allowed**, unlike every prior `create_*_selection` in this engine except
  `chummer5.engine.resources.create_resources_selection`'s gear names. See Log entry above for the
  real-fixture confirmation (Barrett, Bastion both buy matched cyberlimb pairs).
- **Essence floor is `essence_spent >= BASE_ESSENCE` rejected (i.e. resulting Essence must stay
  strictly `> 0`)**, checked against the fixed `BASE_ESSENCE` constant directly rather than against
  `character.improvements.resolve_essence(...)` plus this selection's own spend. This is
  intentionally simpler than a fully general "check the character's *current* Essence before this
  purchase" formula: nothing else in this project's scope (mundane MVP, Phase I magic) produces an
  `ESSENCE` improvement, so `BASE_ESSENCE` alone *is* the character's current Essence for every
  character this engine can build today. A future WP that adds a second Essence-reducing source
  (bioware, if ever built) would need to widen this to take the character's pre-purchase Essence as
  an input instead — flagged here so a future reader doesn't assume this function already
  generalizes to that case.
- **`apply_cyberware_improvements` gives every purchased item's `ESSENCE` Improvement `source_id =
  item.id`, not a per-purchase-unique id.** This means two purchases of the same item (a matched
  cyberlimb pair) collapse to indistinguishable `source_id`s — `ImprovementIndex.remove_source`
  would retract both at once, not one at a time. Accepted deliberately (see the module's own
  docstring): this project has no chargen-time "remove one specific cyberware purchase, keep its
  twin" use case yet (unlike a quality/power, always bought at most once), so a more elaborate
  per-instance id scheme would be unused complexity today. Matches the Implementation Plan's own
  WP32 text verbatim (`Improvement(ESSENCE, value=-item.essence_cost, source_type=CYBERWARE,
  source_id=item.id)`).
- **Every purchased item grants an `ESSENCE` Improvement unconditionally, including
  `NOT_YET_SUPPORTED` ones (e.g. Smartlink).** Mirrors `chummer5.data.cyberware`'s own WP31 decision
  to keep `NOT_YET_SUPPORTED` items in the loaded catalog: an item's Essence/nuyen cost is real,
  correctly-modeled content even when its `<bonus>` isn't. `apply_cyberware_improvements` simply has
  an empty `flat_bonuses` tuple to iterate for those items, so no special case was needed — the same
  "naturally a no-op" shape `chummer5.engine.qualities.apply_quality_improvements` already
  established for a quality/metatype-grant with no recognized bonus.

## Implementation

- `src/chummer5/engine/cyberware.py` (new): `CyberwareSelection` (`items`, `nuyen_budget`,
  `nuyen_spent`, `essence_spent`); `create_cyberware_selection(item_ids, catalog, nuyen_budget)`
  validating unknown ids, nuyen budget, and the Essence floor (duplicates allowed);
  `apply_cyberware_improvements(character, selection)` adding one `ESSENCE` Improvement per
  purchased item (always) plus `PHYSICAL_CM` Improvements for `FLAT_BONUS` items (Cyberlimbs).
- `src/chummer5/engine/character.py`: `Character` gains `cyberware_selection: CyberwareSelection |
  None = None` (the same "`None` until committed" shape every selection field since WP18 has); a new
  `TYPE_CHECKING`-only import of `CyberwareSelection`; docstring paragraph documenting the addition.

## Tests

- `tests/unit/test_cyberware_selection.py` (new, 11 tests, synthetic data): nuyen/Essence totals;
  unknown-id rejection; over-budget rejection; budget need not be fully spent; duplicate purchases
  allowed and sum correctly; Essence-floor rejection at exactly `BASE_ESSENCE` spent; a
  just-under-the-floor case allowed; `apply_cyberware_improvements` reduces `essence()` correctly and
  records the right `Improvement` fields; a Cyberlimb purchase raises `physical_condition_monitor` by
  1 via the existing `PHYSICAL_CM` type; a duplicate Cyberlimb purchase raises it by 2 and doubles the
  Essence cost; `Character.cyberware_selection` defaults to `None` and round-trips via
  `dataclasses.replace`.
- `tests/integration/test_cyberware_fixtures.py` (new, 5 tests): reads 6 of the Phase J intro's 8
  real cyberware-bearing fixtures' raw `<cyberwares>` via a direct `xml.etree.ElementTree` parse
  (none is `buildmethod == Priority`, and `chummer5.io.legacy_chum5.LegacyCharacter` doesn't parse
  per-item cyberware fields yet — that's WP33's job — mirroring `test_magic_fixtures.py`'s identical
  "read the raw XML by hand" precedent for Miko's spells/Wesson's powers). Confirms every fixture has
  at least one item in the confirmed flat subset (Datajack, the 8 Cyberlimb variants, Smartlink, Bone
  Lacing (Titanium)); confirms every such item's raw `<ess>`/`<cost>` matches this WP31 catalog
  exactly, regardless of the real grade purchased (see Log entry); builds a hand-constructed
  `Character` and applies Bastion's real two-`Obvious-Full-Arm`-plus-two-`Obvious-Full-Leg` purchase,
  confirming `physical_condition_monitor` rises by 4 and `essence()` drops by exactly 4; confirms
  Datajack/Smartlink's hand-checked Essence/cost fields; confirms a `NOT_YET_SUPPORTED` purchase
  (Smartlink) still costs real Essence while contributing zero `FLAT_BONUS` Improvements.

## Outcome

WP32 complete. `chummer5.engine.cyberware.create_cyberware_selection`/`apply_cyberware_improvements`
compose WP30's Essence mechanism with WP31's 60-item flat catalog into an actual, validated cyberware
purchase: nuyen spend checked against a caller-supplied budget (confirmed, via a direct rulebook
read, to be the same shared Step Six pool gear/Lifestyle already draw from), Essence spend checked
against a strictly-positive floor (confirmed against both the rulebook and the legacy engine's own
character-creation validity gate — exactly `0` remaining Essence is invalid, not just negative), and
duplicate purchases explicitly allowed (confirmed against real fixture data — matched cyberlimb pairs
are an ordinary build, not an edge case). Every purchased item grants an unconditional `ESSENCE`
Improvement, plus a `PHYSICAL_CM` Improvement for the 8 Cyberlimb `FLAT_BONUS` items — reusing the
existing `ImprovementType.PHYSICAL_CM` `chummer5.engine.derived.physical_condition_monitor` already
consumes, with zero new derived-stat code needed. `pytest`/`ruff`/`mypy` are all green (491 tests, 16
more than before this WP). Phase J continues with WP33 (cyberware-aware save/load + legacy import
unblocking) and WP34 (cyberware chargen UI + character sheet).
