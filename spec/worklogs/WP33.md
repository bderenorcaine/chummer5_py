# WP33 — Cyberware-aware save/load + legacy import unblocking

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase J, WP33.

## Goal

Let a cyberware-bearing character round-trip through native save/load (`chummer5.io.save_format`)
and let the legacy `.chum5` import path (`chummer5.io.legacy_import`) stop hard-rejecting every
cyberware/bioware-bearing character outright, replacing that blanket rejection with a real,
itemized per-item check against WP31's flat, Standard-grade cyberware catalog and WP32's
`create_cyberware_selection`/`apply_cyberware_improvements`.

## Log

### 2026-07-21 — Confirming what "per-item data" actually needs to capture before touching the parser

`chummer5.io.legacy_chum5.LegacyCharacter.has_cyberware` (WP12) was a bare presence boolean. Dumped
every real `<cyberwares><cyberware>` entry (including nested `<children>`) across all 8 of the Phase
J intro's cyberware-bearing fixtures via a one-off `xml.etree.ElementTree` read before deciding the
new `LegacyCyberware` shape. Two things settled the design:

- **`<improvementsource>` ("Cyberware" or "Bioware"), not `<category>`, is the only reliable way to
  split the two content types sharing this one wrapper element** — confirmed directly: categories
  like "Basic"/"Cultured"/"Genemods" are Bioware-only in the real data, but "Headware"/"Bodyware"
  span both, so a category-based guess would misclassify real entries (e.g. Bastion's own
  `Cerebral Booster`/`Adapsin`/`Platelet Factories`, all Bioware, sit at top level alongside her real
  Cyberware purchases).
- **Nested `<children>` (cyberlimb enhancements/accessories bought onto a limb) stay unparsed,
  mirroring `tests/integration/test_cyberware_fixtures.py`'s own WP32-era "top-level only" precedent
  already recorded in that file's module docstring.** Checked what recursing would actually buy:
  every nested item across all 8 fixtures is either non-`SR5`-sourced (`CF`/`HT`/`KC`) or a rating
  formula (`Rating * N`, `(Rating - MinRating + 1) * N`) — none would ever resolve against WP31's
  flat catalog regardless, so parsing them would only add classification volume with zero payoff.
  `LegacyCyberware.cost`/`.essence` are kept as raw text (not `int`/`Decimal`) for the same "what the
  save says, not what it resolves to" reason `legacy_chum5.py`'s own module docstring already states
  — a real `<cost>`/`<ess>` is routinely a formula, and forcing it through `Decimal()` would raise.

### 2026-07-21 — Confirming non-Standard-grade rejection is correct, not overly conservative

Re-read `spec/worklogs/WP32.md`'s own finding before deciding whether a real `Used`/`Alphaware`
purchase whose *name* matches a WP31 catalog entry should just be accepted using the catalog's
Standard values (since the stored raw fields already numerically match them). Decided **no** —
WP32 already established that the legacy engine stores a Standard-grade-equivalent number in the
save file regardless of which grade was actually bought, applying the real grade multiplier only at
read time via a separate computed property. That means a `Used`-grade `Synthetic Full Arm`'s *real*
in-game Essence cost (1.25x higher) is never actually represented in the raw `<ess>` field at all —
silently accepting it as Standard grade would misrepresent the character's real cost, not just
approximate it, the same "blocking, not incomplete" standard this module's docstring already applies
to a Prime Runner gameplay option or a non-`SR5` tradition. Grade is offered as a real, itemized
rejection reason (`f"cannot import {name!r} ({grade} grade): ..."`) rather than silently accepted.

### 2026-07-21 — Confirming real fixture coverage for both the positive and negative cases before writing tests

Cross-referenced every real top-level cyberware entry across all 8 fixtures against WP31's loaded
60-item catalog by name+grade. Found genuine positive cases beyond the negative ones the phase intro
already flagged: `Bastion.chum5` really does buy both `Smartlink` and `Datajack` at Standard grade
(alongside her Used-grade Cyberlimbs and several Bioware items), and `Blindfire.chum5` buys `Datajack`
at Standard grade too. This gave real-fixture backing for the "importable, not itemized" branch of
the new check, not just the "itemized rejection" branch the Phase J intro already anticipated —
`tests/integration/test_cyberware_import_fixtures.py` asserts both per fixture.

## Design decisions

- **`LegacyCyberware` parses only top-level `<cyberwares><cyberware>` entries, not `<children>`.**
  See Log entry above. Documented explicitly in the class's own docstring so a future reader doesn't
  assume this is an oversight.
- **`cost`/`essence` stay raw `str` fields on `LegacyCyberware`, not `int`/`Decimal`.** A real
  purchase's `<cost>`/`<ess>` is routinely a rating formula; `chummer5.io.legacy_import` decides
  importability by matching `name`+`grade` against WP31's catalog instead of parsing these fields
  numerically at all — the catalog's own already-resolved `cost`/`essence_cost` is what actually
  gets used once an item is confirmed importable.
- **A non-Standard grade is rejected even when the item's name matches a catalog entry.** See Log
  entry above — this is the one place this WP's design deliberately diverges from "if the raw fields
  happen to match, just accept it."
- **Bioware entries are unconditionally blocking, regardless of shape** (`improvement_source ==
  "Bioware"` alone is sufficient) — no Bioware catalog exists at all yet (Phase J intro: bioware is
  explicitly out of this phase's scope), so there is no "resolve against a catalog" question to even
  ask for one.
- **Cyberware/bioware issues stay in the *blocking* tier, not "excluded and reported" like a dropped
  quality/skill/spell/power.** A cyberware item's Essence cost feeds a real, already-imported derived
  value (`social_limit`, via WP30's Essence mechanism) — silently dropping an unsupported item would
  leave a character with a numerically wrong (too-high) Essence, not just an incomplete quality list.
  This mirrors the module's own pre-existing metavariant/game-option precedent exactly; no new
  `ImportResult.dropped_cyberware` field was added, since nothing is ever excluded-and-continued here.
- **`_blocking_reasons` and `import_legacy_character` each rebuild their own `{name: Cyberware}`
  lookup dict from the same `cyberware` catalog parameter**, rather than threading one dict between
  them. A 60-item dict comprehension is cheap enough that sharing it would only add a parameter for
  no measurable benefit; this mirrors how `offered_qualities`/`skills_by_name`/etc. are each already
  rebuilt fresh at their own use site rather than threaded across this module's functions.
- **`build_character` computes cyberware's nuyen budget as `resources_selection.nuyen_remaining`**
  (gear + Lifestyle already subtracted), not a fresh three-way split — this is exactly the
  "caller resolves the shared budget" contract `create_cyberware_selection` was written against in
  WP32 (see that module's own docstring), and `resources_selection` is already computed earlier in
  `build_character` by the time cyberware needs it.
- **`chummer5.web.app` is untouched.** The Implementation Plan scopes this WP to
  `chummer5.io.save_format`/`chummer5.io.legacy_import` only; no chargen UI exists yet to let a
  player pick cyberware (`character.cyberware_selection` is always `None` coming out of the web
  session today), so `ChargenSession`/`_character_save_from_session` have nothing new to thread —
  that wiring is WP34's job, mirroring how WP18/WP20 sequenced their own web-layer follow-ups.

## Implementation

- `src/chummer5/io/legacy_chum5.py`: new `LegacyCyberware` dataclass (`name`, `category`, `grade`,
  `source`, `improvement_source`, `cost: str`, `essence: str`); `LegacyCharacter.has_cyberware: bool`
  replaced with `cyberware: tuple[LegacyCyberware, ...]`; new `_parse_cyberware_item`/
  `_parse_cyberwares` helpers (top-level `<cyberware>` children only); `load_chum5` updated;
  now-unused `_has_children` helper removed.
- `src/chummer5/io/legacy_import.py`: new `STANDARD_CYBERWARE_GRADE`/`BIOWARE_IMPROVEMENT_SOURCE`
  constants; `_blocking_reasons` gains a `cyberware: tuple[Cyberware, ...]` parameter and the new
  itemized per-item check (replacing the old blanket `if legacy.has_cyberware` rejection);
  `import_legacy_character`/`import_chum5` gain a `cyberware: tuple[Cyberware, ...] = ()` parameter
  (mirrors WP28's `traditions`/`spells`/`powers` defaults), resolve `cyberware_item_ids` from
  `legacy.cyberware` once `_blocking_reasons` confirms every entry is importable, and thread them
  through `create_character_save`/`build_character`. Module docstring's cyberware paragraph rewritten
  to describe the new itemized behavior.
- `src/chummer5/io/save_format.py`: `CharacterSave` gains `cyberware_item_ids: tuple[str, ...] = ()`
  (JSON round-tripped in `_save_to_dict`/`_dict_to_save`, `.get(..., ())` on read for backward
  compatibility with saves written before this WP); `create_character_save` gains the matching
  parameter; `build_character` gains a `cyberware: tuple[Cyberware, ...] = ()` parameter, builds a
  `CyberwareSelection` via WP32's `create_cyberware_selection` using
  `resources_selection.nuyen_remaining` as the shared budget, applies it via
  `apply_cyberware_improvements`, and attaches the result to the final `Character` via
  `cyberware_selection=cyberware_selection` in the closing `replace(...)`.

## Outcome

WP33 complete. A cyberware-bearing character can now be saved/loaded through the native format
(`cyberware_item_ids` round-trips through `CharacterSave`'s JSON and re-validates via WP32's
`create_cyberware_selection` on load), and `chummer5.io.legacy_import` no longer hard-rejects every
cyberware/bioware-bearing `.chum5` file outright — it itemizes each real purchase individually,
accepting a Standard-grade item that resolves against WP31's flat catalog and rejecting everything
else (rating-scaled formulas, non-Standard grades, non-`SR5` sources, and all Bioware) with a
specific, named reason. Per the Phase J intro, no fixture in the 34-file corpus is both
`Priority`-built and cyberware-bearing, so this WP cannot claim (and does not claim) a full
end-to-end successful cyberware import the way WP12/WP28 could for their own milestones — instead,
`tests/integration/test_cyberware_import_fixtures.py` confirms the itemization logic itself against
all 8 real cyberware-bearing fixtures, including genuine positive cases (Bastion's Standard-grade
Smartlink+Datajack, Blindfire's Standard-grade Datajack) alongside the negative ones the phase intro
anticipated. `pytest`/`ruff`/`mypy` are all green (507 tests, 16 more than before this WP). Phase J
continues with WP34 (cyberware chargen UI + character sheet) and WP35 (cross-phase Essence-driven
Magic-rating loss).
