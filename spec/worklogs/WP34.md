# WP34 — Cyberware chargen UI + character sheet

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase J, WP34.

## Goal

Expose WP31's flat, Standard-grade cyberware catalog and WP32's `create_cyberware_selection`/
`apply_cyberware_improvements` through the browser, and show current Essence and purchased
cyberware on the character sheet. Per the Implementation Plan: decide and document whether the
picker folds into the existing Resources/gear screen or gets its own section, given all three
(gear, Lifestyle, cyberware) now share one Resources-priority nuyen budget.

## Log

### 2026-07-21 — UI placement: a new peer section, mirroring WP20's own Lifestyle-vs-gear choice

WP32/WP33's own docstrings left this open ("WP34 is where an actual three-way gear+Lifestyle+
cyberware joint budget gets threaded through the web layer"). Considered folding cyberware into
`_resources.html`'s existing gear picker (both spend from the same budget, and `_resources.html`
already has a working category-grouped `<details>` picker from WP21 that a 60-item cyberware
catalog could reuse verbatim). Decided against it, for the same reason WP20 gave for Lifestyle:
SR5 frames "buy gear" and "install cyberware" as distinct chargen decisions, and cyberware has a
real validation rule gear doesn't (the Essence floor) — cramming a second, differently-validated
~60-row catalog into `_resources_context` would make that one context builder responsible for two
unrelated catalogs and two different failure modes. Went with a new peer section (`_cyberware.html`,
`POST /ui/cyberware`), reusing WP21's `<details>`-grouped-by-category picker shape directly (same
`itertools.groupby` pattern, same "buy a quantity of each row" form shape) rather than designing a
new one.

### 2026-07-21 — `load_cyberware()`'s XML-document order doesn't group cleanly by category

Tried reusing `STARTER_GEAR_CATALOG`'s exact pattern (`itertools.groupby` directly over the loader's
own output, relying on `build_starter_gear_catalog`'s explicit `(category, name)` sort). `chummer5
.data.cyberware.load_cyberware()` has no equivalent sort step (WP31 didn't need one — nothing before
this WP ever needed a UI grouping). Checked the real order: most categories *do* appear consecutively
(Headware, then Eyeware, then Earware, ...) purely because `cyberware.xml` happens to list them that
way, except the last stretch of the file, where "Cyber Implant Weapon" and "Cyber Implant Weapon
Accessory" entries interleave. A plain `itertools.groupby(CYBERWARE, key=...)` over the raw loader
output would have silently produced duplicate, broken-up groups for those two categories. Fixed by
sorting a module-level `_CYBERWARE_BY_CATEGORY` tuple by `(category, name)` once at import time
(mirroring `STARTER_GEAR_CATALOG`'s own sort, just computed in `chummer5.web.app` instead of the
data/engine layer, since nothing in `chummer5.engine.cyberware` needs a stable display order) rather
than resorting `CYBERWARE` itself, which other code (`create_cyberware_selection`'s `by_id` lookup,
save/import) has no ordering dependency on either way.

### 2026-07-21 — Extending the shared budget to three sections: `cyberware_cost` on
`create_resources_selection`, not a new validator inside `chummer5.engine.cyberware`

WP20 already established the pattern for a second selection sharing the Resources-priority nuyen
budget: `create_resources_selection` gained a `lifestyle_cost` keyword parameter that folds an
already-computed total into the one joint over-budget check, keeping `chummer5.engine.resources`
and `chummer5.engine.lifestyle` mutually decoupled (neither imports the other). Extended the exact
same shape to `cyberware_cost` rather than inventing a different mechanism for the third selection
— `ResourcesSelection`/`create_resources_selection` now fold `lifestyle_cost + cyberware_cost` into
`nuyen_remaining`/the over-budget check together, and the raised message lists whichever of
gear/lifestyle/cyberware are actually nonzero (`"gear (X) + lifestyle (Y) + cyberware (Z)"`), rather
than hardcoding a fixed two-or-three-term sentence. Verified this preserves the exact WP20-era
message string a real test depends on
(`tests/unit/test_web_lifestyle.py::test_lifestyle_and_gear_share_one_nuyen_budget` asserts
`"gear (43500) + lifestyle (10000)"` verbatim) — with `cyberware_cost == 0`, the new code path
produces the identical two-term string, confirmed by running the full suite unchanged before
writing any new cyberware-specific test.

`chummer5.engine.cyberware.create_cyberware_selection`'s own `nuyen_budget` parameter is unchanged
— it still just validates against whatever `int` its caller resolves as "how much is left for
cyberware specifically" (`chummer5.web.app.submit_cyberware` computes this the same way
`submit_lifestyle` already computes "how much is left for Lifestyle specifically": the Resources
letter's raw budget minus the *other* two sections' currently-committed spend). The two checks
work together, not redundantly: `create_cyberware_selection`'s own check is what a *cyberware*
submission itself is validated against (and is where the Essence floor lives); `create_resources_
selection`'s three-way fold is what makes the *other* two sections' own displayed "remaining" number
and staleness re-validation (`resources_budget_warning`/`lifestyle_budget_warning`) correctly account
for a cyberware purchase that already exists, mirroring exactly how gear's own check and Lifestyle's
own check already coexist without either being redundant.

### 2026-07-21 — `build_character` needed a second `create_resources_selection` call, not a field
patch, to fold the resolved cyberware cost back in

`build_character` (WP33) already computes `resources_selection` (gear+Lifestyle) *before* resolving
`cyberware_selection` from it (`cyberware_selection = create_cyberware_selection(..., resources_
selection.nuyen_remaining)` — the "whatever's left after gear/Lifestyle" pattern). That first
`resources_selection` object, though, was never updated afterward — so `character.resources_
selection.nuyen_remaining` (what `_character_sheet_context` and every other reader actually display)
never reflected cyberware's own cost, only gear+Lifestyle's. Fixed by calling `create_resources_
selection` a second time, once `cyberware_selection.nuyen_spent` is known, folding it in via the new
`cyberware_cost` parameter — guaranteed to succeed (the first call's `nuyen_remaining` was exactly
the ceiling `create_cyberware_selection` already validated the cyberware spend against), so this is
a pure re-derivation, not a new failure mode. Considered patching `resources_selection.cyberware_cost`
/`nuyen_remaining` directly via `dataclasses.replace` instead of a second `create_resources_selection`
call — rejected, since that would duplicate the exact arithmetic `create_resources_selection` already
encodes (`budget - gear_spent - lifestyle_cost - cyberware_cost`) in a second place that could drift
from it.

### 2026-07-21 — A test-writing trap caught before it became a false "bug": form quantities are
absolute per section, submitted as one whole `<form>`, not incremental per item

While manually verifying via `urllib` (this project's established `curl`-unavailable workaround),
submitting two separate `POST /ui/cyberware` requests — one buying a Datajack, a second buying a
Synthetic Full Arm — resulted in only the *second* item surviving on the character sheet. Traced
this to `_parse_cyberware` reading a quantity of `0` for any `cyberware_{id}` key absent from the
submitted form, exactly mirroring `_parse_gear`'s identical shape: `_cyberware.html`, like
`_resources.html`, wraps *every* catalog row's quantity input in one `<form>`, so a real browser
submission (triggered by `hx-trigger="change, input delay:400ms"` on the whole form) always includes
every row's current value together, not just the one row the player just edited. Two separate
`urllib` POSTs each carrying only one field is not something the real UI can ever produce — confirmed
this is a test-harness artifact, not an engine/route bug, by resubmitting both quantities in one
request (matching what a real form submission looks like) and confirming both items then coexist
correctly, with Essence/nuyen totals matching hand-computed values exactly. Recorded here so a future
reader doesn't rediscover the same "looks like data loss" scare from the same cause.

## Design decisions

- **A new peer section (`_cyberware.html`, `POST /ui/cyberware`), not folded into `_resources.html`**
  — see Log above. Mirrors WP20's own explicit choice for Lifestyle.
- **`create_resources_selection` gains `cyberware_cost` (default `0`), extending the existing
  `lifestyle_cost` shared-budget mechanism from two sections to three**, rather than `chummer5
  .engine.cyberware` growing its own second validator or importing `chummer5.engine.resources`.
  Keeps the two engine modules mutually decoupled, matching the Project Overview's stated
  Improvement-engine philosophy applied here to a second joint constraint (see `chummer5.engine
  .resources`'s own updated module docstring).
- **`_cyberware_context`/`submit_cyberware` resolve "how much is available for cyberware
  specifically" as `starting_nuyen(letter) - gear_cost - lifestyle_cost`**, the same shape
  `submit_lifestyle` already uses for Lifestyle's own budget resolution, rather than reusing
  `resources_selection.nuyen_remaining` directly (that field, once WP34's own second `create_
  resources_selection` call exists, already has cyberware's *own* cost subtracted out of it too —
  using it directly as cyberware's own budget would double-subtract whatever cyberware already
  spent).
- **`_replace_committed_cyberware` removes by distinct previously-purchased item id, not once per
  purchased unit** — `ImprovementIndex.remove_source` already retracts every Improvement one source
  id granted at once, and `chummer5.engine.cyberware`'s own docstring establishes that a repeated
  purchase of the same item shares one `source_id` (the item's own catalog id), so iterating
  `{item.id for item in character.cyberware_selection.items}` (a set, not the raw tuple) is
  sufficient and avoids redundant no-op `remove_source` calls for a duplicate id.
- **`_relink_cyberware_selection` (mirroring `_relink_quality_improvements`) is needed for
  `submit_attributes` only**, the one route still rebuilding via `create_character()` fresh (WP18/
  WP19's documented, deliberately-kept asymmetry) — `submit_priorities`'s `dataclasses.replace`-in-
  place carries a committed `cyberware_selection` forward automatically, the same "untouched field
  survives by reference" behavior every other post-WP19 selection already gets.
- **`_cyberware_context` shows a live Essence preview (`essence_spent`/`essence_remaining`) computed
  directly from the submitted `item_ids`**, not by reading `character.improvements`/`essence()` —
  mirrors `_resources_context`'s own "recompute display numbers directly from the raw name/id list,
  never trust a possibly-stale stored object" pattern, and lets the picker show a correct preview
  even for a rejected (over-budget or over-Essence) submission being echoed back.
- **`_character_sheet_context.essence` reads `chummer5.engine.derived.essence(character)`
  directly** (the character's real, Improvement-resolved Essence), not a recomputation from raw
  `item_ids` the way the picker context does — the sheet is read-only recap of committed state,
  the same distinction `_character_sheet_context`'s own docstring already draws for `contact_
  selection`/`resources_selection` (recomputed for *staleness* reasons) versus everything else
  (read straight off `character`).
- **No new `spec/rulebooks/learnings.md` entry.** Every rulebook-grounded finding this WP relies on
  (shared Step Six budget, Standard-grade-only scope, the strictly-positive Essence floor) was
  already confirmed and recorded during WP30-WP32; this WP is UI wiring over already-validated
  engine mechanics, the same "no new citation needed" note WP33's own worklog made for the identical
  reason.

## Implementation

- `src/chummer5/engine/resources.py`: `ResourcesSelection` gains `cyberware_cost: int = 0`;
  `create_resources_selection` gains a `cyberware_cost: int = 0` keyword parameter, folded into the
  over-budget check/`nuyen_remaining` alongside `lifestyle_cost`; the raised message now lists
  whichever of gear/lifestyle/cyberware are nonzero (`"gear (X)"`, or `"gear (X) + lifestyle (Y)"`,
  or all three), preserving the exact pre-WP34 two-term string when `cyberware_cost == 0`.
- `src/chummer5/io/save_format.py`: `build_character` calls `create_resources_selection` a second
  time once `cyberware_selection.nuyen_spent` is known, folding it into the final `Character`'s
  `resources_selection` (see Log above for why this needed a second call, not a field patch).
- `src/chummer5/engine/cyberware.py`: module docstring updated to describe the now-real
  `cyberware_cost` wiring (previously described as "not yet threaded through the web layer").
- `src/chummer5/web/app.py`:
  - `CYBERWARE = load_cyberware()` (module-level, parsed once, mirroring every other `chummer5.data`
    catalog); `_CYBERWARE_BY_CATEGORY` (sorted by `(category, name)` for the picker — see Log above).
  - New `_parse_cyberware(form, catalog)` (mirrors `_parse_gear`, keyed by catalog id).
  - New `_relink_cyberware_selection`/`_replace_committed_cyberware` (mirror `_relink_quality_
    improvements`/`_replace_committed_qualities`'s identical shapes).
  - New `_cyberware_context(character, resources_letter, item_ids, gear_cost, lifestyle_cost, *,
    error=None)`: category-grouped picker rows (mirrors `_resources_context`'s WP21 shape), nuyen
    available/spent/remaining, Essence spent/remaining, and the WP19-style `cyberware_budget_
    warning` re-validation.
  - `_resources_context`/`_resources_selection_for_display`/`_lifestyle_context` each gain a
    `cyberware_cost` parameter, folded into their own displayed remaining budget and re-validation
    call — extends the existing gear↔lifestyle cross-section wiring to all three sections.
  - `_character_sheet_context` gains `essence`/`cyberware_rows` (tallied the same way `gear_rows`
    already is, since duplicate cyberware purchases are legal).
  - `_character_save_from_session` gains `cyberware_item_ids`, threaded into `create_character_save`.
  - `_chargen_body_context` computes `cyberware_ctx` and the cross-section `gear_cost`/
    `lifestyle_cost`/`cyberware_cost` numbers each of the three sections needs from the other two;
    folds `cyberware_budget_warning` into the existing `priority_stale_selections` aggregate.
  - `submit_attributes`: one new line, `_relink_cyberware_selection(character, previous.cyberware_
    selection)`, alongside the existing quality/metatype/contact/magic relink calls.
  - `submit_resources`/`submit_lifestyle`: both now resolve and pass `cyberware_cost` into their own
    `create_resources_selection` validation call and their own context builder.
  - New `POST /ui/cyberware` route (`submit_cyberware`), mirroring `submit_resources`/
    `submit_lifestyle`'s shape: resolves "available for cyberware" as the Resources letter's raw
    budget minus gear/Lifestyle's current spend, validates via `create_cyberware_selection`, then
    folds the result into a fresh `create_resources_selection` call for display/staleness purposes.
  - `download_save`/`load_save`/`import_chum5_route`: all three now pass `cyberware=CYBERWARE` into
    `build_character`/`import_chum5` (mechanical — those functions already accepted the parameter
    since WP33, but nothing in the web layer had ever passed it before this WP).
- `src/chummer5/web/templates/_cyberware.html` (new): category-grouped `<details>` picker (mirrors
  `_resources.html`'s WP21 shape), with an added Essence column per row and a combined nuyen/Essence
  summary line.
- `src/chummer5/web/templates/_chargen_body.html`: includes `_cyberware.html` after `_resources.html`.
- `src/chummer5/web/templates/_character_sheet.html`: new "Cyberware" section (purchased items +
  quantities, or "None installed") and an Essence line, placed alongside the existing Gear section.

## Outcome

WP34 complete. A player can now purchase Standard-grade cyberware through the browser (`POST
/ui/cyberware`, a new peer section alongside Resources/Lifestyle, per the same "distinct decision,
shared budget" precedent WP20 established for Lifestyle), with the three sections' nuyen budgets
genuinely joint — `chummer5.engine.resources.create_resources_selection`'s `cyberware_cost`
parameter extends the existing `lifestyle_cost` mechanism from a two-way to a three-way shared
check, and each section's own display/staleness-warning logic accounts for the other two. The
character sheet shows real, reducible Essence (`chummer5.engine.derived.essence`, no longer an
implicit fixed "6" no character before this WP could move away from) and the purchased-cyberware
list, with a Cyberlimb purchase's `PHYSICAL_CM` bonus visibly raising the physical condition monitor
end to end through the real HTTP layer. Native save/load and legacy `.chum5` import both thread the
cyberware catalog through correctly (mechanical — `build_character`/`import_chum5` already accepted
it since WP33; this WP is what finally passes it in from the web layer). `pytest`/`ruff`/`mypy` are
all green (524 tests, 17 more than before this WP), and a real-HTTP manual walkthrough (confirm →
buy cyberware → save → reload into a fresh session; separately, import a cyberware-free mundane
fixture to confirm zero regression) reproduces the correct combined nuyen/Essence numbers throughout.
Phase J continues with WP35 (cross-phase Essence-driven Magic-rating loss), the phase's final WP.
