# WP35 — Cross-phase: Essence-driven Magic-rating loss

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase J, WP35 (final WP in Phase J).

## Goal

Implement the one real rules interaction between Phase I (Magicians & physical Adepts) and Phase J
(Cyberware): SR5 reduces a magically active character's Magic rating as Essence is lost to
cyberware. Deliberately the last WP in either phase, since it depends on both phases' engine layers
already existing (Phase I's `magic_type`/MAG resolution from WP25/post-WP29's correction, Phase J's
Essence mechanism from WP30/WP32) and neither phase's own fixture corpus can exercise it (no fixture
in the 34-file corpus is simultaneously Priority-built, magic-enabled, and cyberware-bearing).

## Log

### 2026-07-21 — The rulebook citation was already banked during WP25, not a fresh extraction

The Implementation Plan's own WP35 entry instructs confirming the exact formula via `pdftotext
-layout` before implementing anything, warning not to assume a linear "1 Essence lost = 1 Magic
lost" rule. That extraction already happened, ahead of need, during WP25's own research (recorded
in `spec/rulebooks/learnings.md`'s WP25 entry, under "Not needed for WP25, but extracted... for
WP35's future benefit") — re-read it here rather than re-running `pdftotext` from scratch, and
confirmed it's still exactly what this WP needs: p.278, "For every point (or fraction thereof) of
Essence lost, both your current Magic Attribute and your maximum Magic Rating are reduced by one."
Added a short new `learnings.md` entry (this WP's own) recording that no new extraction was needed,
plus one real implementation-time finding not visible from the citation alone (see Design decisions
below) — matching this project's established practice of writing down what a rulebook check
confirmed, even when the check itself was "re-read a citation already on file."

### 2026-07-21 — A circular-import constraint decided *where* the reduction lives, not just *how*

`chummer5.engine.derived.essence()` (WP30) is the obvious-looking place to compute Essence loss,
since it already does `BASE_ESSENCE + Σ ESSENCE improvements`. But `derived.py` imports `Character`
from `chummer5.engine.character`, so `character.py` importing anything back from `derived.py` (the
`BASE_ESSENCE` constant, or a helper function) would be circular. Resolved by computing Essence loss
directly against `self.attribute_range("ESS").maximum` (parsed by WP2/WP23's metatype loader from
`metatypes.xml`'s `<essmax>` tag) instead of importing `BASE_ESSENCE` — confirmed equivalent by
`derived.py`'s own docstring, which already establishes `BASE_ESSENCE` (6) *is* "the SR5 core
metatypes' shared Essence maximum," not an independent number. This keeps the reduction logic inside
`Character.attribute_value("MAG")` itself, matching the Implementation Plan's own instruction to
"wire the result into `Character`'s MAG resolution path from Phase I's WP25" and the class
docstring's own forward-reference ("WP35, later, changes this further to also account for
Essence-driven Magic loss").

Also found, while wiring this in: `ImprovementIndex.resolve_essence()` returns each `ESSENCE`
improvement's `essence_value` summed directly — already a *negative* delta relative to the
metatype's Essence maximum (that's what `essence() = BASE_ESSENCE + Σ` means). So "Essence lost" is
simply the negation of that sum, not `essence_max - resolve_essence(...)` (a first draft of this
code did that subtraction, double-counting the maximum, and every synthetic test caught it
immediately — see Tests below).

## Design decisions

- **No new `Character` field.** WP35 changes `attribute_value("MAG")`'s own formula and adds two
  read-only properties (`magic_rating_before_essence_loss`, `magic_essence_loss`); nothing is
  stored, since both are fully determined by existing fields (`magic_rating`,
  `magic_attribute_points`, `improvements`) — the same "computed, not stored" reasoning
  `Character.power_points`'s own docstring already uses for an identical case.
- **The rulebook's two separately-named quantities ("current Magic Attribute," "maximum Magic
  Rating") collapse to one computation.** `magic_rating_before_essence_loss` is already capped at
  the metatype's raw MAG maximum (the pre-WP35 formula did this), so subtracting the same
  `magic_essence_loss` from both an already-capped current value and the metatype maximum can never
  let the current value exceed the reduced maximum — the "reduced maximum" cap is mathematically
  redundant here. `attribute_value("MAG")` is therefore just
  `max(magic_rating_before_essence_loss - magic_essence_loss, 0)`, with no second cap computed or
  applied. See the new `learnings.md` entry for the fuller reasoning, including why the rulebook's
  separate "current 0 is recoverable, maximum 0 is permanent burnout" distinction has zero
  observable effect in a chargen-only engine with no Karma-based advancement.
- **`magic_essence_loss` is `math.ceil` of the negated `resolve_essence()` sum**, not a subtraction
  from `attribute_range("ESS").maximum` — see the Log entry above for the sign-error draft this
  correctly avoids in the shipped version.
- **`magic_rating_before_essence_loss`/`magic_essence_loss` are exposed as public properties**
  purely so the character sheet can show *why* a reduced rating is reduced (mirrors WP28's own
  `drain_resistance` "shown regardless of build specifics" precedent for a *different* kind of
  always-visible derived value) — nothing else in this engine reads either property; every other
  computation (dice pools via `chummer5.engine.skills.dice_pool`, `power_points`) reads
  `attribute_value("MAG")` itself, which is already the real, reduced value.
- **Character-sheet display: a single conditional line, not a separate warning block.** `_character_
  sheet_context` adds `magic_essence_loss`/`magic_rating_before_essence_loss`; `_character_sheet.html`
  shows `"Magic rating: N (reduced from M by Essence loss)"` when `magic_essence_loss > 0`, otherwise
  the plain `"Magic rating: N"` line unchanged from before this WP — matching the Implementation
  Plan's own suggested wording and this project's existing "don't show a diagnostic unless there's
  something to diagnose" pattern (e.g. WP19's staleness warnings).

## Implementation

- `src/chummer5/engine/character.py`:
  - New module-level `_ESSENCE_TARGET = ""` (mirrors `chummer5.engine.derived`'s own
    `_GLOBAL_TARGET` sentinel — there is only one Essence pool per character).
  - `Character.attribute_value("MAG")`: now `max(magic_rating_before_essence_loss -
    magic_essence_loss, 0)` instead of the pre-WP35 `min(magic_rating + magic_attribute_points +
    bonus, metatype_max)` inline formula (that formula moved into the new
    `magic_rating_before_essence_loss` property, unchanged).
  - New `Character.magic_rating_before_essence_loss` property (the pre-WP35 MAG formula, exposed for
    display).
  - New `Character.magic_essence_loss` property (`math.ceil(-improvements.resolve_essence(
    _ESSENCE_TARGET))`).
  - Class docstring gains a WP35 paragraph; `import math` added (no `Decimal` import needed — see
    Design decisions, the sign-corrected formula never constructs one directly here).
- `src/chummer5/web/app.py`: `_character_sheet_context` gains `magic_essence_loss`/`magic_rating_
  before_essence_loss` keys, both read straight off the new `Character` properties.
- `src/chummer5/web/templates/_character_sheet.html`: the Magic rating `<li>` is now conditional on
  `magic_essence_loss > 0` (see Design decisions for the exact wording).

## Tests

- `tests/unit/test_character.py` (+4 tests): `test_magic_essence_loss_is_zero_with_no_essence_
  improvements` (zero-drift baseline); `test_mundane_character_is_unaffected_by_any_amount_of_
  essence_loss` (a stray `ESSENCE` improvement never leaks into a Mundane character's MAG);
  `test_essence_loss_reduces_mag_by_the_ceiling_of_essence_lost` (a 1.1-Essence synthetic loss knocks
  Magic down by 2, not a proportional/rounded-differently amount); `test_essence_loss_floors_mag_at_
  zero_rather_than_going_negative` (a 5.9-Essence loss against MAG 2 floors at 0, not -4).
- `tests/unit/test_web_magic.py` (+3 tests, new "WP35" section): `test_cyberware_essence_loss_
  reduces_adept_magic_rating_and_power_points_on_the_sheet` (a real Submachine Gun purchase, Essence
  1, through the full HTTP layer — Adept MAG 6 -> 5, Power Points follow); `test_fractional_essence_
  loss_still_knocks_off_a_full_magic_point` (two Datajacks, Essence 0.1 each = 0.2 total, still costs
  a full Magic point — the rulebook's "per point or fraction thereof" wording exercised through the
  real HTTP layer, not just synthetically); `test_mundane_character_with_cyberware_shows_no_magic_
  section_at_all` (a Mundane character with real cyberware still shows no Magic section at all,
  while Essence itself still displays correctly) — the two explicit boundary-case regressions the
  Implementation Plan's own acceptance criteria call out (Mundane totally unaffected; a magic
  character with zero cyberware sees no reduction, covered by every pre-existing WP29 test in the
  same file, all of which pass unchanged).

## Outcome

WP35 complete — **Phase J (Cyberware) is now fully shipped, WP30 through WP35.** A magically active
character's Magic rating now correctly falls as Essence is lost to cyberware, per the core
rulebook's p.278 "per point (or fraction thereof)" rule: `Character.attribute_value("MAG")` folds in
`magic_essence_loss` (ceiling of Essence lost, derived from the same `ESSENCE` improvements Phase J's
cyberware purchases already produce), and the character sheet shows *why* a reduced rating is
reduced (`"N (reduced from M by Essence loss)"`) rather than silently displaying the lowered number
unexplained. Every other computation that reads MAG (dice pools, Adept Power Points) automatically
sees the reduced value with no changes of its own, since they all go through `attribute_value("MAG")`
already. Zero behavioral drift for every character built before this WP (no `ESSENCE` improvement
producer existed before Phase J, and Mundane characters never read any of this new logic at all):
`pytest`/`ruff`/`mypy` are all green (531 tests, 7 more than before this WP), with explicit tests for
both boundary cases the Implementation Plan's acceptance criteria call out. With Phase J complete,
the codebase's only remaining scoped-but-unstarted work is Phase K (cyberware modifications/Capacity/
subsystems), which is explicitly on hold as of 2026-07-21 per that phase's own intro.
