# WP36 — Cyberware rating-formula resolver

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase K, WP36.

## Goal

A whitelisted, tested evaluator for the rating-scaled `<cost>`/`<ess>`/`<capacity>` formula shapes
SR5-sourced `cyberware.xml` entries actually use — proven in isolation before any real catalog data
touches it (WP5/WP30's "prove the mechanism first" precedent). This is the first of Phase K's four
separable primitives, and the one with no dependencies at all.

Phase K was **on hold** (scoped 2026-07-21, deliberately unstarted). Taken off hold this session at
the user's direction; the hold text stays in the phase file for the record, and the phase table row
now reads "in progress (WP36 done)".

## Log

### 2026-07-29 — Re-confirming the shape survey first: the Plan's "6 distinct formula shapes" is 8

WP36's entry explicitly requires re-confirming the Phase K intro's exploratory survey against the
*complete* 87-entry SR5 set before finalizing which shapes to support, so that came first — a one-off
`xml.etree` pass dumping every distinct `<cost>`, `<ess>`, `<capacity>`, `<rating>` and `<minrating>`
value with the items using it (44 distinct `<cost>` strings, 20 `<ess>`, 25 `<capacity>`).

The intro's counts survived almost intact, which is worth stating plainly: `Rating * N` really is 19
`<cost>` occurrences, `FixedValues(...)` really is 2, `(Rating - MinRating + N) * N` really is 2, the
two one-off `<cost>` expressions really are unique to Cybereyes Basic System and Cyberears, and the
"plain literal that failed only the *other* field's flatness check (2)" really is Essence Hole and
Essence Antihole (both `<cost>0</cost>`, both with a `Rating * ±0.01` `<ess>`). Two things it missed,
both because it looked at the 27 WP31-excluded entries rather than all 87, and mostly at `<cost>`:

- **`(Rating * A) + B`** — the `<ess>` of Cybereyes Basic System *and* Cyberears (`(Rating * 0.1) +
  0.1`, identical on both). The intro classified those two items wholesale as "one-off named
  formulas"; only their `<cost>` is genuinely one-off. Their Essence is a shape they share, and
  hardcoding it twice by item name would have been the wrong call.
- **A bare `Rating`** — never seen unbracketed, but it's what `[Rating]` (Vision Enhancement, Audio
  Enhancement, Select Sound Filter, Armor, Hydraulic Jacks) reduces to once the caller strips
  brackets, so the resolver needs it as a real shape.

Also recorded because WP37/38 will want it: **exactly the 60 entries with a flat `<cost>` and `<ess>`
are the 60 with no `<rating>` tag at all, and exactly the 27 rating-scaled ones all carry one.** WP31's
docstring asserted the first half of that ("None of the 60 flat items carry a `<rating>` tag"); the
complement holds too, which makes "is this item rating-scaled?" and "does this item have a rating
dimension?" the same question in this data set. `tests/unit/test_cyberware_formula.py`'s
`test_scales_with_rating_splits_the_sr5_set_the_way_wp31s_filter_did` pins that down, so a future data
update that breaks the correspondence fails loudly instead of quietly needing a new code path.

### 2026-07-29 — Hand-checking against the printed tables, and the PDF page-offset trap

The acceptance criteria demand each shape be checked "against a real rulebook-table value," not just
against the XML string it was parsed from — a formula that reproduces its own source string proves
nothing. So every shape got a `pdftotext -layout` lookup: Headware, Eyeware, Earware, Bodyware,
Cyberlimbs/Enhancements/Accessories. All 8 shapes reproduce their printed columns exactly, including
both one-offs (Cybereyes 4,000/6,000/10,000/14,000¥ — deliberately *not* linear, which is what the
`- 2000 * number(Rating > 1)` term encodes; Cyberears 3,000/4,500/7,500/11,000¥). Full transcriptions
in `spec/rulebooks/learnings/phase-k.md`'s new WP36 entry.

**The trap, and the thing most worth carrying forward:** I first wrote the learnings entry citing
"book page N is physical PDF page N + 3" after locating the Eyeware table on PDF page 456 and taking
the XML's own `<page>453</page>` at face value. Both halves of that were wrong. Reading each page's
printed folio out of its own footer gives **physical = book + 2**, and PDF 456 is therefore book
p. **454** — the Eyeware/Earware *tables*. Book p. 453 (PDF 455) holds the Headware table plus the
eyeware *narrative*, which is what Chummer's `<page>` tag points at. So: a Chummer `<page>` tag names
where an item's prose section starts, routinely one page before the table its numbers live in. Caught
it only because the footer check contradicted the offset I'd already written down; corrected the
learnings entry, the module docstring, every test comment, and the pre-Phase-K entry's own "p. 453
(Eyeware/Earware tables)" attribution (via a note in the new entry, not by editing the old one —
`learnings.md`'s standing rule is to correct in a new entry, not rewrite history). Logged in
`spec/decisions-log.md` since it applies to every future citation from this PDF, not just this WP.

The same pass settled two readings the pre-Phase-K entry had flagged as "confirm before relying on":
`[*]` (Image Link / Sound Link) is confirmed to be exactly the footnoted "included in the basic
cybereyes system" case, and `MinRating` in `(Rating - MinRating + 1) * 5000` is confirmed to be the
item's *lowest purchasable* rating, making the expression an **inclusive** count of purchased points
(printed row: "Each STR or AGI point above 3 → +5,000¥"; a limb's base STR/AGI is 3, so MinRating is
4 and rating 6 costs 3 × 5,000¥). Getting that wrong by one would have overcharged or undercharged
every customized cyberlimb by 5,000¥ — precisely the plausible-but-wrong-number failure mode this
project's testing discipline exists for.

### 2026-07-29 — `FixedValues` semantics read out of the legacy C#, not guessed

`FixedValues(39000,149000,217000)` is obviously "one value per rating," but the edge behaviour isn't
obvious, so I read `legacy/Chummer/Backend/Static/Extensions/StringExtensions.cs`'s
`ProcessFixedValuesStringCore` directly: 1-based on rating, **clamped at both ends** (`intRating <= 1`
returns the first segment; the per-entry walk returns the last segment as soon as it runs out of
commas). Unreachable in practice — no item can be bought past its `<rating>` cap — but the resolver
matches it anyway so this engine stays diff-clean against the legacy oracle. That function also
handles nested parentheses and multiple `FixedValues()` per string; neither occurs in any SR5
cyberware entry (both real uses are a flat comma list wrapping the whole field), so neither is
supported here.

### 2026-07-29 — The six "decide & document" calls

WP36's entry asks for four explicit decisions; two more fell out of the work. All six live in the
module docstring, since that's where the next reader will be:

1. **Location: a new `chummer5.data.cyberware_formula` module**, not a private helper inside
   `chummer5.data.cyberware`. That module is already 240 lines of dense filter/classifier
   documentation, and WP37 has to widen it substantially; keeping the formula whitelist separate
   means WP37's diff doesn't sit on top of WP36's.
2. **Bracketed values are rejected, not stripped.** `[2]`/`[Rating]`/`[Rating * 1]` return `None`
   from `parse_cyberware_formula`. WP36's entry left this open but insisted the resolver stay
   agnostic to budget-vs-cost — rejecting is the stronger form of that: brackets *are* the
   budget-vs-cost distinction, so the module that can't see them can't get them wrong. WP37 strips,
   then resolves.
3. **`[*]` is not a resolver concern at all** — confirming the pre-Phase-K read. It's a marker, not
   an expression; WP37/38 model it as a `bundled_free` flag.
4. **The two one-off formulas are keyed by verbatim (whitespace-normalized) formula text, not by item
   name.** This is a documented deviation from WP36's own suggested wording ("hardcode ... by item
   name"). Same one-off-per-item outcome, two advantages: the resolver stays a pure function of the
   formula string (no item identity threaded through WP37/38 call sites), and a future `cyberware.xml`
   update that edits either expression fails loudly as an unsupported formula instead of silently
   resolving with stale arithmetic. Tested both ways (a near-miss variant returns `None`; whitespace
   differences still resolve).
5. **`min_rating` defaults to `None`, not `0`** — another deliberate departure from the signature
   sketched in the plan. `(Rating - MinRating + 1) * 5000` with an implicit `min_rating=0` would
   silently overcharge by `MinRating * 5000` nuyen rather than raising, and "plausible but wrong" is
   this project's stated primary risk. `CyberwareFormula.requires_min_rating` lets a caller check
   ahead of time.
6. **A two-function API**: `parse_cyberware_formula(text) -> CyberwareFormula | None` (parse once,
   resolve many, `None` usable directly as WP37's inclusion filter) plus the
   `resolve_cyberware_formula(...)` one-shot the plan named, which raises
   `UnsupportedCyberwareFormulaError`. This deliberately leaves WP37's own open question — resolve
   eagerly at load time or keep raw strings and resolve per-purchase — genuinely open, since a parsed
   `CyberwareFormula` is a frozen, storable value either way.

`CyberwareFormula` itself is a frozen dataclass carrying a `FormulaKind` enum plus a
`params: tuple[Decimal, ...]`, with `resolve()` dispatching on the kind via `match`. Chose that over
storing a closure (uninspectable, and the whole point of "compile once" here is that the compiled
form stays readable/testable) and over eight per-shape dataclasses (verbose for arithmetic this
small). Everything returns `Decimal`, including `<cost>`/`<capacity>` values that are always integral
in practice: one signature for all three fields, and `<ess>` genuinely needs exactness —
`chummer5.engine.derived`'s Essence math is already `Decimal`-based, and a float `3 * 0.1` would drift
Essence (and through it Magic loss) by construction. There's an explicit test for that.

## Verification

The 35 tests split into two deliberate layers: hand-checked rulebook-table values per `FormulaKind`
(layer 1), and whole-data-set coverage (layer 2) — every `<cost>`/`<ess>`/`<capacity>` string on all 87
SR5 entries parses, and every `FormulaKind` is exercised by real data (`seen == set(FormulaKind)`, so
no dead branch exists and no new XML shape can reach WP37's loader unnoticed). Layer 2's bracket-
stripping helper deliberately lives in the test file, not in `chummer5.data`, precisely because WP36
decided not to ship it.

## Follow-up

- **WP37 is the natural next package** and now has everything it needs from this one: a parsed-formula
  value type, the confirmed shape list, and explicit ownership of bracket-stripping and `[*]`. Its own
  re-confirmation duty is the *parent/plugin* half of the intro's survey (the "29 parents = 16
  Cyberlimbs + 2 Cybereyes/Cyberears + 11 Cyber Implant Weapons" split), untouched by this WP.
- **Nothing consumes this module yet** — by design, but worth stating: WP36 adds no behaviour to any
  character this engine builds today, and no existing module imports it. `chummer5.data.cyberware`'s
  60-item flat catalog is byte-for-byte unchanged.
- The `{AGIMinimum}+1`/`{AGIMaximum}` bound placeholders on Customized Strength/Agility are still
  unresolved by anything — WP37/38 own them, and they're the one place a cyberware formula needs
  *character* state (an attribute's min/max) rather than just a chosen rating.
