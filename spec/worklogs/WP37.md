# WP37 — Cyberware Capacity/subsystem data loader

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase K, WP37.

## Goal

Widen what the cyberware data layer captures — parent Capacity budgets, plugin Capacity costs,
subsystem-category eligibility, bundled-free items — over the *complete* 87-entry SR5 set, not just
the 60 flat rows WP31 loads. Data layer only: no purchase logic, no Improvements, no UI (WP38+).
This is Phase K's second of four primitives, consuming WP36's formula resolver and feeding WP38's
purchase tree.

## Log

### 2026-07-29 — Re-confirming the parent/plugin split first (the intro's numbers hold exactly)

WP37's entry, like WP36's, requires re-deriving the Phase K intro's exploratory survey against the
full data set before building on it. WP36 found the intro's formula-shape count was off by two, so
I expected the same here. It isn't: **29 parents = 16 Cyberlimb + 2 Cybereyes/Cyberears + 11 Cyber
Implant Weapon** is exact, all three numbers, and the 7 `<capacity>` shapes are exactly as listed.
Worth stating plainly so a later reader doesn't re-do the pass a third time.

What the intro didn't have, and the full pass added: **50 rows carry a bracketed `<capacity>`** (i.e.
are installable as plugins), **19 are standalone-only** (bare `<capacity>0</capacity>`, no
`<allowsubsystems>`), and the 11 cyber implant weapons are the only rows that are *both* parent and
plugin. 50 + 19 + 29 − 11 = 87 checks out. Also dumped every distinct child tag across the 87 rows,
which is where the two findings below came from — neither was reachable by looking only at
`<capacity>`, which is what the WP entry's deliverable list literally asks for.

### 2026-07-29 — The two-level-nesting question, settled against a third level

WP37's entry required settling, before WP38 gets to it, whether the Cyber Implant Weapon →
Cyber Implant Weapon Accessory layer needs a third nesting level. Two independent lines of evidence,
both pointing the same way:

1. **No fixture exercises it.** Walked `<children>` recursively across all 34 `.chum5` fixtures:
   135 depth-1, 9 depth-2, 2 depth-3 nested items. Every depth-2/3 chain is a Chrome Flesh (`CF`)
   modular-limb chain (`Modular Connector, Wrist` → `Obvious Hand, Modular` → `Armor`;
   `Modular Connector, Shoulder` → `Obvious Full Arm, Modular` → …), all out of SR5 scope. The two
   cyber implant weapons that appear at all (`Spurs` in `Ghile Mear.chum5`, `Custom Submachine Gun`
   in `SCSi.chum5`) are childless depth-1 plugins into a limb.
2. **The data gives a weapon no budget to spend.** Its `<capacity>` is bracketed (`Hand Blade` `[2]`,
   `Grenade Launcher` `[15]`) — a cost. Read `Cyberware.CapacityRemaining` in the legacy C# rather
   than assuming what that implies: the method branches on `Capacity.Contains("/[")` and then
   `!Capacity.Contains('[')`, and a `[N]`-only value matches **neither**, so it falls through and
   returns `0`. The 3 SR5 accessories instead carry `<addtoparentcapacity>`/`<addtoparentess>`
   (empty flag tags) — their cost folds into the *weapon's* cost against the *grandparent limb*.

So the recommendation recorded for WP38 is: **cut the third level explicitly**, the same way WP31
cut rating-scaled items rather than half-supporting them. Both flags are captured anyway so WP38
makes that call from data, not from a docstring.

That same C# read incidentally confirmed two more things for free: `[*]` really is cost-0
(`if (strCapacity == "*") strCapacity = "0"`), and the combined `budget/[cost]` form the first
branch handles occurs in **no** SR5 row (no `<capacity>` contains `/`). The loader raises on that
form rather than guessing which half is which.

### 2026-07-29 — The finding I'd have missed by implementing the deliverable list literally

The WP entry's deliverables name four new fields: Capacity budget, Capacity cost,
`allowed_subsystem_categories`, `bundled_free`. Dumping *all* child tags instead of just the four
I'd been sent for turned up three more that are load-bearing for WP38 and cheap to capture:

- **`<subsystems>` — the actual auto-inclusion list, and the pre-Phase-K entry's reading of it was
  incomplete.** That entry read the p. 454 footnote plus Cybereyes' `<subsystems>` and concluded the
  bundled case was "`[*]` on Image Link and Sound Link," flagging it as needing confirmation.
  Confirming it turned up a **third** instance: **Control Rig → Datajack**. It breaks a `[*]`-only
  reading twice — `Control Rig` has no `<allowsubsystems>` at all, and `Datajack`'s `<capacity>` is
  a bare `0`, not `[*]` — and it is real fixture content (`Mittens Chargen.chum5`). So `[*]` and
  `<subsystems>` are two different signals ("costs no Capacity when plugged in" vs. "comes with this
  parent automatically") and WP38 needs both. Storing only `bundled_free` would have silently
  dropped the Control Rig case, which is exactly the plausible-but-wrong-number failure this
  project's discipline exists for.
- **`<requireparent>` (9 rows) answers half of WP38's dual-costing question before it's asked.**
  Ocular Drone, Armor, Customized/Enhanced Strength/Agility, Cyber Holster, Cyberarm Slide, Large
  Smuggling Compartment have no standalone mode at all — for them there is no Essence-vs-Capacity
  *choice*, only Capacity.
- **`<addtoparentess>`/`<addtoparentcapacity>`** — the fold-into-parent mechanic above.

Deliberately *not* captured, and listed in the module docstring so the omission reads as a decision:
`<limbslot>`/`<blocksmounts>`/`<limit>` (limb-count mechanic, not a Capacity one), `<allowgear>` (25
rows can hold gear children — a gear-in-cyberware mechanic no phase has scoped), `<selectside>`,
`<pairbonus>`/`<pairinclude>`, `<required>`/`<forbidden>`, `<addweapon>`/`<addvehicle>`, `<avail>`
(Availability cap ruled out project-wide).

### 2026-07-29 — The decisions the WP entry left open

1. **A sibling type (`CyberwareEntry`), not a widened `Cyberware`** — and this turned out to be
   forced rather than preferred. `Cyberware.cost` is an `int` and `essence_cost` a `Decimal`;
   Cybereyes Basic System's cost is `4000 * Rating - 2000 * number(Rating > 1)`, which has no single
   value until a rating is chosen. There is no way to widen in place without breaking WP31's
   contract, which the acceptance criteria explicitly forbid.
2. **Parsed at load, resolved per purchase** (the other open question). Resolving at load is
   impossible — no rating yet — and keeping raw strings would make WP38 re-parse. Parsing at load
   also puts data drift where it belongs: an unrecognized formula raises
   `UnsupportedCyberwareFormulaError` from the loader instead of surfacing deep inside a purchase.
   WP36's two-function API was shaped for exactly this.
3. **Its own module, `chummer5.data.cyberware_subsystems`**, following WP36's precedent and for the
   same reason: `chummer5.data.cyberware`'s docstring is 75 lines all about the flat-only catalog,
   and interleaving a second, wider catalog's rules would make both harder to read. The one edit to
   that module is `_classify_bonus` → public `classify_bonus`: the `<bonus>` grammar is identical
   (same file, same rows), so unlike `chummer5.data.bioware` — which reuses `BonusSupport` but had to
   re-implement the classifier for a different bonus grammar — there was nothing to re-implement.
4. **All 87 rows, not just the 27 WP31 excludes.** The alternative (a "subsystems-only" catalog)
   would have been 68 rows overlapping 60 already-loaded ones, i.e. two partial catalogs disagreeing
   about the same purchase. One wider catalog plus a frozen legacy one is the cleaner transitional
   state; migrating WP32/33/34's call sites onto `CyberwareEntry` is a later WP's call, deliberately
   not this one's.
5. **Absent `<minrating>` stores `None`, not `0`.** The legacy engine parses the empty string to 0
   (`Cyberware.GetMinRating`), but keeping "not stated" and "stated as zero" distinguishable costs
   nothing here — no SR5 row states zero — and mirrors WP36's own refusal to default `min_rating`.

## Follow-up

- **WP38 is the natural next package** and has everything from this one: a parsed-formula catalog,
  the confirmed parent/plugin split, an explicit recommendation on the third nesting level, and
  `requires_parent` narrowing the dual-costing question to the rows where a choice actually exists.
  Note WP39 (conditional Improvements) has no data dependency on this WP either way and can be taken
  first if that suits.
- **Nothing consumes this module yet**, by design — WP37 adds no behaviour to any character this
  engine builds today, exactly as WP36 added none.
- The one thing WP38 will still have to solve that neither WP36 nor WP37 touched: resolving
  `{AGIMaximum}`/`{AGIMinimum}+1` against a character's attribute range. That's the only cyberware
  formula input that needs *character* state rather than a chosen rating.
