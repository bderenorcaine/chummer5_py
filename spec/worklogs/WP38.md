# WP38 — Purchase tree & Capacity budget validation

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase K, WP38.

## Goal

Let a cyberware purchase actually nest: a limb/cybereye/cyberear holding plugins, validated against
the parent's resolved Capacity budget, with the Essence-vs-Capacity dual-costing choice applied at
purchase time. Phase K's third of four primitives — it consumes WP36's formula resolver and WP37's
Capacity/subsystem catalog, and feeds WP40 (conditional bonuses on real items) and WP41 (save/load +
legacy import).

Engine only. No Improvements, no `Character` field, no UI — the same "prove the mechanism, wire it
later" posture WP36 and WP37 each held.

## Log

### 2026-07-30 — The compatibility decision, which is most of what this WP is about

WP38's entry flags the replace-vs-alongside question as "a real compatibility decision, not a
mechanical rename," and it is the biggest call here. Both options are genuinely defensible:

- **Replace**: retype `CyberwareSelection.items` from `tuple[Cyberware, ...]` to
  `tuple[PurchasedCyberware, ...]`, every existing purchase becoming a zero-plugin leaf. One shape,
  no transitional duplication.
- **Alongside**: a sibling module/type, migrate call sites later.

I went with alongside, and the deciding factor was counting the call sites rather than reasoning
about it abstractly. A tree node necessarily holds WP37's `CyberwareEntry` (WP31's `Cyberware.cost`
is an `int`; a rating-scaled row has no single value for it), so "replace" is not a retype of one
field — it is a retype of `create_cyberware_selection`'s catalog parameter, which propagates into
`io.save_format`, `io.legacy_import`, `web.routes.cyberware`, `web.routes.character`,
`engine.resources`, `engine.bioware`, `tests/fixtures/synthetic.py` and five test modules. That is a
mechanical migration bundled into a rules change, and it is exactly the split WP37 already declined
to make ("migrating WP32/33/34's call sites onto `CyberwareEntry` is a later WP's call, deliberately
not this one's"). **WP41 is the natural owner** — it has to touch save/load and legacy import
anyway, which is precisely where the flat-vs-tree shape becomes visible outside the engine.

Two things I did to keep "alongside" from being a trap for WP41:
`CyberwareTreeSelection` reuses `nuyen_budget`/`nuyen_spent`/`essence_spent` verbatim (so the swap is
mechanical, not a re-derivation of what the totals mean), and **no `Character` field was added at
all** — so the obvious hazard of a character carrying two selections that both charge Essence cannot
arise today, rather than being guarded by a convention someone has to remember.

Module naming followed the data layer exactly: `data.cyberware`↔`engine.cyberware` is the WP31/32
flat pair, `data.cyberware_subsystems`↔`engine.cyberware_subsystems` the WP37/38 tree pair. WP38's
entry literally says "`chummer5.engine.cyberware`: a purchase-tree type," but appending to that
module would have interleaved a second catalog's rules into 60 lines of dense WP32-era flat-only
documentation — the same reasoning WP36 and WP37 each used to justify their own new module.

### 2026-07-30 — The PDF pass the WP entry said wasn't needed, and why it was worth doing anyway

WP38's entry says of dual costing: "confirm this reading against `learnings.md`'s own p. 29103
citation before implementing (already recorded, no new PDF pass needed for this part)." The recorded
citation is the equipment-table *legend* — correct, but a generic gloss. Reading the actual Bodyware
and Cyberlimb narrative on book p. 456 found the rule stated outright:

> Bodyware cannot be installed into cyberlimbs unless it has a Capacity cost [in brackets]. Bodyware
> with a Capacity cost can be installed in cyberlimbs, costing capacity rather than Essence.

That sharpens two things the legend leaves implicit — a plugin's Essence contribution is **zero**
(not reduced, not player's choice), and an item with no bracketed Capacity is not installable into a
parent at all, which is what makes WP37's `is_plugin` the correct eligibility test rather than a
convenience. The legacy engine says the same unambiguously:
`GetCalculatedESSPrototypeInvariantCoreAsync`'s first line is `if (Parent != null && !AddToParentESS)
return 0;`. Nuyen is deliberately *not* symmetric — `CalculatedTotalCostWithoutModifiers` in the same
file explicitly does "Add in the cost of all child components."

The same page also yielded **two constraints nothing in this project had recorded**, both real
chargen-time rules rather than in-play ones, so both are enforced:

1. "Each limb can have only one enhancement of each type (you can't stack two Strength 3
   enhancements in the same cyberarm)." Enforced narrowly, for the `Cyberlimb Enhancement` category
   that sentence is about. SR5 states no *general* one-plugin-per-parent rule, so none was invented
   — nothing forbids two Vision Enhancements in one cybereye, and the Capacity budget bounds that
   already.
2. "If either of your limb's attributes are increased beyond your natural maximum for that
   attribute, you can't use the cyberlimb (so don't overdo it)." This is what
   `<rating>{AGIMaximum}</rating>` means, which answers half of WP37's hand-off question.

Lesson worth generalizing: "no new PDF pass needed" was true for the number this WP had to compute,
and wrong about the *rules* it had to enforce. Reading the narrative page around a table has paid off
in both WPs that did it (WP36's page-offset finding came the same way).

### 2026-07-30 — `{AGIMinimum}+1` and `{AGIMaximum}` are asymmetric, which is the real trap here

WP37 handed this over as "the only cyberware formula input that needs *character* state." Half of it
doesn't, and reading them as one mechanism would produce a wrong-but-plausible purchasable range on
exactly the two items whose *price* depends on `MinRating`:

- `{AGIMinimum}`/`{STRMinimum}` is the **limb's** floor: p. 456, "All standard cyberlimbs come with
  Strength and Agility attributes of 3." Legacy agrees literally —
  `Cyberware.ProcessAttributesInXPath` overrides these two keys with the *parent cyberlimb's*
  `MinAgility`/`MinStrength`, backing fields initialised to `3` and overridden by no SR5 row. So
  `{AGIMinimum}+1` is the constant **4**, matching the "lowest purchasable point" reading WP36
  already derived from p. 457's "Each STR or AGI point above 3 … +5,000¥."
- `{AGIMaximum}`/`{STRMaximum}` is the **character's** natural maximum. That same override
  deliberately supplies only the `*Minimum` keys for a non-vehicle limb, so `*Maximum` falls through
  to `AttributeSection.ProcessAttributesInXPath` → the attribute's `TotalMaximum`, i.e.
  `Character.attribute_range(code).maximum` here. Human AGI 6, Troll STR 10 — both tested.

API shape: `create_cyberware_tree_selection` takes `attribute_maximums: Mapping[str, int] | None`
rather than a `Character`, with `cyberlimb_attribute_maximums(character)` as the adapter. Keeps the
validation testable against synthetic entries, and mirrors WP36's `min_rating=None` decision exactly:
omitting a bound a purchase actually needs **raises** rather than defaulting, because a silent
default here is a plausible-but-wrong rating cap.

### 2026-07-30 — Bundled subsystems: the fixture check settled it, and then broke my first
implementation

WP38's entry asked to confirm from fixture data whether a bundled item is ever skipped before
choosing between always-auto-attached and a skippable choice. Answer: **8 of 8** `<subsystems>`-
bearing purchases across all 34 fixtures carry their bundled child (5 Cybereyes Basic System, 2
Cyberears, 1 Control Rig). Never skipped, so always-attached — the simpler model, chosen on evidence
rather than on being simpler.

The trap: I first implemented bundling as "a normal plugin that happens to cost nothing," which
rejects `Control Rig` → `Datajack` outright. That pairing fails **all three** plugin eligibility
tests — Control Rig has no `<allowsubsystems>` (so it isn't a parent by the category test), Datajack
is `Headware` rather than a listed category, and Datajack's `<capacity>` is a bare `0` rather than a
bracketed cost — and it is real fixture content (`Mittens Chargen.chum5`). So a bundled subsystem
bypasses eligibility entirely: it is named by the parent's own `<subsystems>` list, which *is* the
parent saying "this one comes with me." WP37's worklog predicted the shape of this failure ("storing
only `bundled_free` would have silently dropped the Control Rig case"); it turned out to bite one
layer up from where it was predicted.

"Free" also needed pinning rather than assuming, because p. 454's Image link row prints real Essence
and cost numbers (`0.1 | * | 4 | 1,000¥`) — the `*` scopes to the **Capacity column only**. What
makes a bundled item free is the auto-inclusion, not the marker: legacy `Cyberware.Create` sets
`objSubsystem.Cost = "0"`, and every fixture stores `<cost>0` for its bundled item. Essence needs no
special case (a child contributes zero anyway).

Last bundling decision, made with WP41 in mind: an **explicit** request for a bundled name resolves
to the same free node rather than erroring or double-adding. Legacy `<children>` does list `Image
Link` explicitly, so this is the difference between WP41 needing a special case and not.

### 2026-07-30 — The third nesting level, and a mechanically-inert purchase

The 2026-07-29 ruling (cut the Cyber Implant Weapon → Accessory level) is implemented as an explicit
raise naming the reason, not a silent acceptance — a purchase whose Capacity charge would land
nowhere is exactly the plausible-but-wrong outcome this project's discipline exists to avoid. A cyber
implant weapon still installs into a limb normally (`Hand Blade` `[2]`, tested).

Separately: `Customized`/`Enhanced Agility`/`Strength` carry **no `<bonus>` at all**. Their real
effect is a *per-limb* STR/AGI attribute (p. 456) — a parallel attribute system the legacy engine
models per limb and this project has no representation of anywhere. Under the 2026-07-24 policy they
are still offered, priced correctly in nuyen and Capacity, with the gap recorded in the Project
Overview's "Unmodeled real effects" registry. Noting while there: WP31/34's `NOT_YET_SUPPORTED`
cyberware (Smartlink and friends) is **not** in that registry, which looks like a gap predating this
WP rather than one it introduced.

The 36 tests split the same two ways every Phase J/K WP's have:

- **30 unit tests** (`tests/unit/test_cyberware_tree.py`). Layer 1 proves each validation rule
  against hand-built synthetic `CyberwareEntry` rows, so no rule can pass by accident because a real
  catalog row happens to satisfy it: over-capacity rejection, wrong-category rejection, no-Capacity-
  price rejection, `<requireparent>` standalone rejection, third-level rejection, stacked-enhancement
  rejection, out-of-range rating, and the dual-costing pair (same row standalone vs. installed).
  Layer 2 re-runs the same rules on real rows against printed-table numbers (Cybereyes Rating 3 →
  0.4 Essence / Capacity 12 / 10,000¥ with a Rating 2 Vision Enhancement at Capacity 2 / 8,000¥ /
  zero Essence; Customized Agility rating 6 → 15,000¥ with bounds 4-6 for a Human and 4-10 for a
  Troll's Strength).
- **6 integration tests** (`tests/integration/test_cyberware_tree_fixtures.py`), replaying real
  nested purchases: Barrett's `Synthetic Full Arm` (the combination the acceptance criteria name —
  SR5 subset spends 3 of 8 Capacity, both enhancements contributing zero Essence), his
  `Synthetic Full Leg` + `Hydraulic Jacks`, his matched pair of arms, BLUE's Rating 3 Cybereyes
  (whose *full* child list spends exactly its budget of 12 — an independent confirmation that this
  engine resolves the same budget the legacy app did), prime's Rating 1 Cyberears (SR5-only children
  summing to exactly 4, the tightest real boundary in the corpus), and Mittens' Control Rig +
  Datajack.
