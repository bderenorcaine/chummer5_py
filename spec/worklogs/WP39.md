# WP39 — Conditional Improvements: a new engine primitive

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase K, WP39.

## Goal

Give `Improvement` (WP5) a real, typed condition mechanism — the Project Overview's long-stated
design intent for the Improvement engine ("conditions compile to typed predicates once, at
construction"), never implemented until now because nothing needed it. Proven with synthetic data
before any cyberware content uses it, which is WP5's own methodology applied to itself.

Taken **out of the phase's stated order** (WP38 is nominally next): the phase intro explicitly
scopes WP39 as having no data dependency either way "so it can be picked up first if that turns out
to be the more useful order," and WP38's purchase-tree compatibility work is the larger of the two.
Doing the self-contained one with the context budget that was left beat starting the big one badly.

## Log

### 2026-07-29 — There are four conditional bonuses, not three

WP39's and WP40's entries both name three items (Vision Enhancement, Audio Enhancement, Spatial
Recognizer). Enumerating every `<condition>`-bearing `<bonus>` in the SR5 cyberware set found a
**fourth**: **Hydraulic Jacks** (`<limitmodifier><limit>Physical</limit><value>Rating</value>
<condition>LimitCondition_CyberwareHydraulicJacks</condition>`), English text "Only for Gymnastics
(Jumping) and Running (Sprinting)".

That one wasn't a completeness footnote, it changed the design. The other three are each "only
during activity X"; Hydraulic Jacks is "only during activity X **or** Y", two unrelated activities
under a single condition. So a condition maps to a **set** of contexts, not to one — otherwise one
bonus would need two `Improvement` records, which would then also stack wrongly if a future
resolution ever matched both. It is also real fixture content (`Barrett.chum5` carries two, plugged
into Synthetic Full Legs), so WP40 should wire four items, and its own entry has been annotated to
say so.

The English strings all come from `legacy/Chummer/lang/en-us.xml` keyed by the `<condition>` value;
transcribed into `spec/rulebooks/learnings/phase-k.md` so WP40/42 don't have to re-look them up.

### 2026-07-29 — The legacy engine never actually applies these, which removes the oracle

Worth stating because it changes what "correct" means here: legacy Chummer does **not** evaluate a
`<condition>` at all. It builds a `LimitModifier` carrying the condition *string* and shows it on the
character sheet as a note for the player to apply by hand; the limit total is never adjusted. So
this engine evaluating conditions for real is a deliberate improvement on the legacy behaviour, not
a port of it — and, more importantly, **there is no legacy oracle for any judgment call about how
conditions interact.**

The one such call this WP had to make: Spatial Recognizer's "Perception to find the source of a
sound" is arguably a special case of Audio Enhancement's "Perception (Hearing)". Should a
hearing-Perception resolution pick up a Spatial Recognizer bonus too? **No subsumption is modeled**
— matching is plain set membership. Nothing establishes the containment as a rule rather than a
reading, and with no oracle to check against, inventing a hierarchy would be exactly the
plausible-but-wrong-number risk this project's discipline exists for. Documented in the module
docstring and pinned by `test_no_subsumption_between_related_conditions`, so if WP40 wants to
reverse it, it does so knowingly.

### 2026-07-29 — The three "decide & document" calls, and one the entry got wrong

1. **A `Condition` is an `Enum`** — of the three options the entry offered (closure, tagged union,
   Enum + parameters), the closure is disqualified outright: `Improvement` is `frozen=True` and
   relies on value equality and hashability, both of which a closure field destroys, and the whole
   point of "compile once" here is that the compiled form stays *readable and testable*, which a
   closure isn't. A tagged union buys parameterization that nothing needs — every confirmed shape is
   the unparameterized statement "only during these tests." So: a plain `ImprovementCondition` enum,
   with a module-private `_CONDITION_CONTEXTS` mapping each member to its `frozenset` of contexts.
2. **The context is one optional `ResolutionContext`** — the smallest shape covering all four rows.
   Not a dataclass of game state, not a predicate over the character: literally "which test is this."
3. **The entry's premise that this is "a real signature change to `resolve()`'s call sites, not just
   an additive field" turned out to be wrong**, and I'm recording that rather than quietly
   benefiting from it. A keyword-only `context: ResolutionContext | None = None` is purely additive:
   `context=None` means "no condition is satisfied," which resolves to exactly the pre-WP39 total.
   **Zero call sites changed**, and the zero-drift guarantee the acceptance criteria demand is
   structural rather than something the tests have to hunt for.

Two details that only show up once you write it:

- **Condition filtering runs before the `unique_name` dedup pass.** Otherwise an inapplicable
  conditional bonus could win a "highest bonus wins" group it isn't competing in, suppressing a
  smaller bonus that *does* apply. Own test.
- **`resolve_essence()` raises on a conditional `ESSENCE` improvement** rather than counting or
  skipping it. Nothing produces one (Essence cost is not a per-test thing), and both quiet ways of
  handling it are wrong — this is the same "fail loud, never fail quiet" posture WP36's resolver
  took.

### 2026-07-29 — A naming trap worth one line in the next reader's head

The obvious name for the context enum is `TestContext` — SR5 calls these "tests." pytest collects
any importable class whose name begins with `Test`, so every test module importing it emitted a
`PytestCollectionWarning`. Renamed to `ResolutionContext` with a docstring note saying why, so
nobody "fixes" it back.

## Verification

- `uv run python -m pytest -q` → **1055 passed** (1043 pre-existing + 12 new), and the only warning
  is the pre-existing Starlette/httpx deprecation.
- `uv run python -m mypy src` → clean, 58 files. `uv run python -m ruff check src/ tests/` → clean;
  `ruff format --check` clean on the two touched files.

The zero-drift requirement is covered three ways rather than one: structurally (the default argument
means no call site can behave differently), by `test_condition_defaults_to_none_and_is_a_true_no_op`
(an unconditional Improvement resolves identically under *every* context, iterating the enum so a
new member can't quietly break it), and by the other 1043 tests — every character this engine builds
goes through `resolve()`, and all of them are unchanged.

## Follow-up

- **WP38 is now the only unstarted prerequisite for WP40/41**, and is the biggest remaining piece of
  this phase: it has to decide whether `CyberwareSelection.items` (a flat `tuple[Cyberware, ...]`
  read by `chummer5.engine.derived`, three web route modules and the save format) becomes a tree or
  gains a sibling field. Worth a fresh conversation with room for that.
- **WP40 should wire four items, not three** — see above. Its Mental-limit trio all target
  `ImprovementType.MENTAL_LIMIT`; Hydraulic Jacks targets `PHYSICAL_LIMIT`, which
  `chummer5.engine.derived` already resolves against the same `""` sentinel target.
- **Nothing produces a conditional Improvement yet.** WP39 adds no behaviour to any character this
  engine builds today — the same "primitive first, content later" state WP36 and WP37 both left.
- WP42's "show the condition text alongside its value" needs a condition → display-string mapping.
  Deliberately not added here: that is i18n-key territory and belongs in the web layer, not the
  engine. The English strings are already transcribed in the learnings entry.
