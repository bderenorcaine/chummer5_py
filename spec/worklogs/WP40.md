# WP40 — Wire real conditional-bonus subsystem items

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase K, WP40.

## Goal

Turn WP39's conditional-Improvement primitive into real content: reclassify the four SR5 cyberware
items whose `<bonus>` is a condition-gated `<limitmodifier>` from `NOT_YET_SUPPORTED` to modeled
bonuses, and make them actually reach a `Character`. Phase K's first WP that adds player-visible
behaviour rather than a primitive — WP36/37/38/39 each deliberately added none.

The four (WP39's own correction to two earlier plan entries that named only three): Vision
Enhancement, Audio Enhancement, Spatial Recognizer (all Mental limit) and Hydraulic Jacks (Physical
limit).

## Log

### 2026-07-30 — Which module gains `CONDITIONAL_BONUS`, the one open call WP38 handed over

WP40's plan entry says to extend `chummer5.data.cyberware`'s classifier. WP38's follow-up flagged
the problem with taking that literally: that module is WP31's flat catalog, and three of the four
items are rating-scaled and therefore live only in WP37's wider `cyberware_subsystems` catalog.

The two catalogs share **one** classifier (`classify_bonus`, made public in WP37 precisely so the
wider loader could reuse it verbatim), so this isn't really a choice between two modules — it is a
choice between extending the shared classifier or forking it. Forking would mean two copies of the
same `<bonus>` grammar reading the same rows of the same file, which is a copy dressed up as a
separation. So: extend the shared one, and accept the visible consequence.

That consequence is the interesting part. **Spatial Recognizer is flat**, so it lives in WP31's
catalog, which is wired into the shipped UI today — reclassifying it means a purchase a player can
already make starts granting a real bonus. That is squarely what this WP is for, but it does dent
WP37's "WP31's loader is completely unchanged" acceptance pin, which I updated with a note rather
than deleting: same 60 rows, same costs, same call sites; one row's `<bonus>` classification and one
new field. Worth being explicit that the pin was *narrowed by a decision*, not quietly broken.

Second decision in the same area: `CyberwareConditionalBonus.condition` carries the **verbatim
legacy `<condition>` string**, not an `ImprovementCondition`. The data layer doesn't import from the
engine anywhere in this project, and `CyberwareFlatBonus.target_kind` already established the
string→enum split with `chummer5.engine.cyberware` owning the map. That leaves two whitelists in two
modules that must stay in step, so there's a test asserting exactly that (and that the engine map's
values cover every `ImprovementCondition` member).

### 2026-07-30 — The PDF pass the entry asked for, and the rule it found

WP40's entry says to confirm each item's condition semantics via `pdftotext` before hardcoding a
predicate, and WP39's landed note says the transcription is already done, "re-confirm rather than
re-derive." Both are right about the condition *strings*. Re-confirming still paid for itself twice.

**First: the numbers aren't where the `<page>` tags point.** All three Eyeware/Earware items are
"an implanted version of" the corresponding gear accessory, and the actual mechanical text is in the
Vision/Audio Enhancements block of the Gear chapter, **p. 444**, a chapter away from the p. 453/454
cyberware rows. This is a second instance of WP36's finding that a Chummer `<page>` tag names where
an item's narrative starts. The p. 444 text also confirms each bonus is to a *limit* rather than a
dice pool, which is what makes `<limitmodifier>` → `MENTAL_LIMIT`/`PHYSICAL_LIMIT` the right target
rather than a plausible guess.

**Second, and this one changed the implementation: Hydraulic Jacks is a matched pair.** p. 457:

> Hydraulic jacks: This implant requires you to have two cyberlegs with a hydraulic jack of
> identical Ratings in each leg. Each Rating point adds a +1 to your Physical limit for jumping and
> sprinting …

So one jack grants **nothing**, and a pair grants `+Rating` **once**. Nothing in the data says so —
the row carries no `<pairbonus>`/`<pairinclude>` (both tags exist in the legacy schema and WP37
deliberately captures neither), and the legacy engine never evaluates a conditional limit modifier at
all, so there is no oracle to have caught it either. The obvious per-node application would have
produced `+2 × Rating` for `Barrett.chum5`, which owns exactly two, one per Synthetic Full Leg. That
is precisely the plausible-but-wrong number this project's discipline exists to prevent, and it would
have shipped looking correct.

Modeled as a named rule (`_PAIRED_BONUS_ITEM_NAMES`), with two sub-decisions:

- The pair test is "two jacks of **equal Rating** in **distinct parents**," not "in two legs." The
  jacks' `<required><parentdetails>` does restrict the parent to a leg, but WP37 loads no
  `<required>` data at all, so leg-ness isn't something this engine can check. Recorded in the
  learnings entry so a later `<required>` WP knows to tighten it rather than assuming it's tight.
- The granted Improvement carries a `unique_name`, so two qualifying Ratings collapse to the highest
  under SR5's existing "highest bonus wins" dedup instead of stacking. Unreachable with two legs, but
  this engine counts no limbs, so the outcome is pinned by a test rather than left to chance.

### 2026-07-30 — Where the Improvements get applied, and the `context` parameter

WP38's module docstring explicitly deferred "a purchased plugin's `<bonus>` lands on a `Character`"
to this WP, so `apply_cyberware_tree_improvements` is WP40's, not scope creep — and it is the only
way to satisfy the acceptance criteria at all, since Vision Enhancement is reachable *only* through
the tree. It mirrors WP32's flat applier node-for-node and reuses a shared
`cyberware_bonus_improvements` builder, the engine-layer mirror of the data layer's single shared
classifier. Nothing consumes it yet: there is still no `Character` field for a tree selection (WP41).

The acceptance criteria are phrased as "applies when resolving a visual-Perception-flagged dice
pool," which needed an actual way to ask for one. `derived.physical_limit`/`mental_limit` gained a
keyword-only `context`, purely additive on top of WP39's `resolve(context=None)`. `social_limit`
deliberately did **not** — nothing this engine offers carries a conditional Social limit bonus, and
WP39's stated rule is to add a context only where a real bonus needs one. Asymmetric on purpose;
documented in `mental_limit`'s own docstring so it doesn't read as an oversight.

Small thing worth flagging for WP42: this is the first API in the project that distinguishes "the
character sheet's headline figure" from "the figure for one specific test." A Memory test is Mental-
limited and has no conditional bonus of its own, so it resolves with `context=None` — the same
number the sheet shows. That's what makes "the headline figure never moves" a structural property
rather than something the tests have to chase, and it's the shape WP42's "show the condition text
alongside its value" has to render.

## Follow-up

- **WP41 is the natural next package**, and both its dependencies (WP38, WP40) are now done. It
  inherits the call-site migration WP38 described *and* now has one more reason to do it: a
  character can carry a conditional bonus, so the save format has to round-trip the rating that
  bonus is computed from, not just the item id.
- **A pairing mechanic now exists in this engine, for one item, by name.** Other SR5 items use
  `<pairbonus>`/`<pairinclude>` for the same shape (WP37 captures neither tag). Whoever scopes those
  should generalize `_PAIRED_BONUS_ITEM_NAMES` rather than adding a second special case beside it.
- **The pair check can't see leg-ness**, because no `<required>` data is loaded. A future WP that
  loads `<required>` should tighten it — the current check would accept two jacks in two cyberarms.
- **Still open from WP38, untouched here**: WP31/34's `NOT_YET_SUPPORTED` cyberware (Smartlink,
  Damper, the Bone Lacing trio) is offered with unmodeled bonuses and is absent from the "Unmodeled
  real effects" registry. WP40 added rows only for the items it actually wired. Also unbuilt: no
  cyberware catalog dataclass populates the `unmodeled_effect_note` field
  `chummer5.engine.derived.unmodeled_effect_notes` reads, so none of these gaps surfaces on the
  character sheet yet — a cheap win for whoever wants it.
