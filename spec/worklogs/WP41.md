# WP41 — Cyberware modification save/load + legacy import

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase K, WP41.

## Goal

Thread WP38's purchase tree through native save/load (`chummer5.io.save_format`) and legacy import
(`chummer5.io.legacy_chum5` + `chummer5.io.legacy_import`), which through WP40 discarded
`<children>` entirely — a deliberate, documented WP31/33 scope cut, not an oversight.

In practice this WP is two jobs, and the second one is bigger than its entry lets on: the io work
proper, and **WP38's deferred call-site migration**, which WP38's own worklog assigned here ("WP41
inherits the call-site migration … It is the WP that decides whether `CyberwareSelection` survives
at all"). You cannot persist a tree without a `Character` field to load it back into, and a
`Character` may hold exactly one cyberware shape.

## Log

### 2026-07-31 — Sizing the migration before choosing how much of it to do

The first real decision was scope: does `Character.cyberware_selection` become the tree in this WP,
or does the tree stay a parallel structure the io layer alone knows about? The second option
collapses immediately — `build_character` has to attach what it built, and WP38 deliberately left
`Character` with no tree field specifically so that "a character carrying both selections, each
charging Essence" couldn't arise. So the retype is forced, and with it every read site.

Counting them first (rather than reasoning about the migration abstractly) is what made it tractable
— there are only six, and five are one-liners:

| Site | What it read | What it reads now |
|---|---|---|
| `engine/derived.py` | `.items` (unmodeled-effect notes) | `.walk()` — a plugin's unmodeled effect is as real as a standalone item's |
| `web/routes/priorities.py` | `.items` → ids for the picker | `.purchases` — top-level only, since the picker has no plugin row |
| `web/routes/character.py` (sheet) | `.items` → name×qty recap | `.walk()`, so imported plugins appear instead of hiding behind their parent |
| `web/routes/character.py` (save) | `.items` → flat id list | `.to_requests()` (new) |
| `web/routes/cyberware.py` | `.items` → distinct source ids to retract | `.walk()` — **a real bug if missed**: a plugin's Improvements are sourced by its *own* id, so retracting the parent's id alone would leave them behind |
| `io/save_format.py` | the whole flat call | `create_cyberware_tree_selection` |

`to_requests()` is the one genuinely new engine API, and it is the inverse of what
`create_cyberware_tree_selection` consumes. It deliberately **omits bundled nodes**: they aren't
picks, and `create_cyberware_tree_selection` re-attaches them on the way back in, so persisting them
would either double them or lean on the "an explicit request for a bundled name resolves to the same
free node" behaviour to paper over a real modelling error. Round-tripping is asserted directly
(`selection.to_requests() == save.cyberware_purchases`).

### 2026-07-31 — Retiring the flat selection, and why deleting tests was the right call anyway

WP38 handed over the survives-or-not question. I deleted `CyberwareSelection`,
`create_cyberware_selection` and `apply_cyberware_improvements`, and the honest argument for it is
short: after the retype they have no constructor path and no consumer, and a selection builder whose
output cannot be attached to a `Character` is a trap rather than a convenience. The tree engine
enforces a strict superset of their rules.

The reason I hesitated is that it costs ~19 passing tests, and "deleting tests" deserves more
suspicion than "deleting code." What settled it was checking the tree module's own test file
name-by-name rather than assuming: every one of the flat file's selection/apply tests (unknown id,
over-budget, Essence floor with and without `other_essence_spent`, duplicates summing, flat bonus
reaching a `Character`, conditional bonus gated by context) has a direct counterpart in
`tests/unit/test_cyberware_tree.py`. What did *not* have a counterpart is the translation step
itself — `cyberware_bonus_improvements` was only ever tested through a selection — so that file
became `tests/unit/test_cyberware_bonus.py`, testing it directly with no `Character` at all (7
tests, including the `value=None → rating` case and the unmapped-condition-key raise, neither of
which had a direct test before). Net: the module that survives is better covered than it was.

`chummer5.data.cyberware.load_cyberware()` is **not** retired, which is worth stating because "the
flat catalog" and "the flat selection engine" sound like one thing. The web picker still lists its
60 rows, `classify_bonus`/`BonusSupport`/`CyberwareFlatBonus` all live there, and WP37's loader
imports from it.

### 2026-07-31 — The save format's one non-default backward-compatibility path

Every optional field this format has ever gained defaults to empty on read (`.get(key, ())`), which
is enough because "absent" and "empty" mean the same thing for a field that didn't exist yet. WP41
is the first field to be *replaced* rather than added, so a pre-WP41 save has real data under the old
key. `_dict_to_save` reads `cyberware_purchases` when present and otherwise falls back to
`cyberware_item_ids`, mapping each id to a zero-plugin rating-1 request.

That mapping is exact, not approximate, and I checked both halves rather than assuming:

- **The ids match.** Both loaders read `<id>` from the same `cyberware.xml` rows, and
  `{i.id for i in load_cyberware()} <= {e.id for e in load_cyberware_entries()}` holds (60 ⊂ 87).
- **Rating 1 is right.** No WP31 row carries a `<rating>` tag at all (that filter is exactly what
  defines the flat 60), so 1 is every such row's only legal rating — the same fact
  `apply_cyberware_improvements` relied on when it passed `rating=1` unconditionally.

`FORMAT_VERSION` stays 1: a reader that understands both keys is not a schema break, and the field's
own docstring says so, so a future reader doesn't have to re-derive that judgement.

`CharacterSave.cyberware_purchases` holds `CyberwarePurchaseRequest` objects directly rather than a
save-format-local mirror type. The precedent is exactly `Contact`'s: a plain, frozen, JSON-shaped
dataclass with no engine state, which is *already* the shape the `create_*` function takes. A mirror
would mean translating twice for nothing. `CyberwarePurchaseRequest`'s own WP38 docstring
anticipated this ("plain data a UI/save file can hold with no catalog resolved, which is the shape
WP41/WP42 need"), which is a nice example of a prior WP's documented intent actually paying off.

### 2026-07-31 — Widening the import catalog, which the WP entry does not literally ask for

WP41's entry asks for nested items to resolve "against WP37's subsystem catalog" and says nothing
about top-level ones. Keeping top-level on WP31's flat 60 doesn't work, though: `Cybereyes Basic
System` is rating-scaled, so it would be unimportable, and its children would be unreachable — the
exact content this WP exists to import. So `import_legacy_character`/`import_chum5` take
`tuple[CyberwareEntry, ...]` and resolve every level against it.

Two consequences, both deliberate:

1. **"Rating-scaled" stops being a rejection reason anywhere.** That is Phase K's whole point (WP36
   built the resolver precisely so this filter could go), but it does invalidate a message and two
   test names WP33 wrote. `test_rejects_unsupported_cyberware_item` (Wired Reflexes, rejected for
   being rating-scaled) became `test_rejects_non_sr5_cyberware_item` (`Cyberlimb Optimization`,
   `CF`-sourced, real `Barrett.chum5` content), and a new
   `test_accepts_a_rating_scaled_cyberware_item_at_its_stored_rating` asserts the *opposite* of what
   the old one did — Wired Reflexes Rating 1 now imports at 39,000¥ / 2 Essence.
2. **A pre-existing gap gets bigger.** WP38's worklog already flagged that `NOT_YET_SUPPORTED`
   cyberware is offered with its bonus unmodeled and is missing from the Project Overview's
   "Unmodeled real effects" registry. Widening the catalog extends that to rating-scaled rows too
   (Wired Reflexes' Initiative/Reaction bonus is not modeled). I did not backfill the registry —
   that is WP31/34's content, not this WP's — but it is now a larger gap than when it was first
   noticed, and it is recorded in the decisions log as something to close before WP42 puts a wider
   catalog in front of a player.

### 2026-07-31 — Where structural validation lives, and the one case the data forced a decision on

`_augmentation_reasons` (the new recursive check) covers what can be decided **per item, with no
character**: name resolution, source, grade, and nested-Bioware. It deliberately does *not*
re-implement category eligibility, the parent's Capacity budget, or rating bounds — those surface
from `create_cyberware_tree_selection` during `build_character` as a plain `ValueError`, which is
exactly where an over-budget nuyen spend has surfaced from since WP33. Duplicating them here would
be a second copy of rules that can drift out of sync with the engine's.

The one thing I had to actually decide rather than defer was **nested Bioware**. Real SR5 allows it
— p. 456's "Bodyware with a Capacity cost can be installed in cyberlimbs, costing capacity rather
than Essence" is the same sentence WP38 cited for dual costing — but `chummer5.data.bioware` carries
no Capacity data, so there is nothing to charge the parent, and half-costing it (Essence as if
standalone) would produce a plausible-but-wrong Essence total. Before refusing it I checked whether
refusing would block real content: **zero** nested entries across all 34 fixtures carry
`improvementsource == "Bioware"`. So this refuses a case the corpus never exercises, which is the
cheap kind of refusal.

### 2026-07-31 — The fixture data turned out to be better than expected

WP41's acceptance criteria name `Barrett.chum5`'s `Synthetic Full Arm` + its 6 children. Barrett is
entirely `Used` grade, so every one of those 7 nodes is blocking — good for the "itemized, not
silently dropped" half (WP33 would have produced **one** reason for that limb; WP41 produces
**seven**, each naming its parent), but it proves nothing about the Capacity/Essence math the
criteria also ask for.

Dumping every nested entry across the corpus by (source, grade) found the case that does:
**`Fuzzy-chargen.chum5`'s Rating 1 `Cybereyes Basic System`** is Standard grade with three children —
`Image Link`, `Smartlink`, `Flare Compensation` — **all** SR5-sourced and Standard grade. It is the
only subtree in the corpus where nothing at all is itemized, and its numbers are a genuinely tight
check against p. 454: 4,000¥ / 0.2 Essence / Capacity **4** for the eyes, `Image Link` bundled and
free, `Smartlink` `[3]` and `Flare Compensation` `[1]` charging Capacity and **zero** Essence —
4 of 4 Capacity, exactly full, and a total spend of 9,000¥.

`BLUE.chum5`'s `Obvious Full Leg` gives the sharpest negative case: the limb and 3 of its 4 children
are clean Standard-grade SR5 content, and only `Retractable Climbing Claws (Feet)` (`CF`) is out of
scope — so the test asserts the reason list is *exactly one entry long*, which a
silently-dropping implementation would also satisfy with zero. That's the pairing that makes it
meaningful: the same fixture's resolvable siblings are asserted not to appear.

### 2026-07-31 — Why the web picker was left alone

The web layer is retyped (`_purchase_requests` wraps the form's flat ids into zero-plugin requests;
`apply_cyberware_tree_improvements` replaces the flat applier) but the **picker itself is untouched**,
because rating selection and plugin installation are WP42 and a picker built against a half-migrated
engine is throwaway work — this phase's own stated sequencing rationale.

That only holds if the flat picker can't accidentally trigger tree-only behaviour, which I verified
rather than assumed, and both facts are now in the route's docstring:

- No `CYBERWARE` row carries a `<rating>` tag, so rating 1 is exact for every offered item.
- **None of the three `<subsystems>`-bearing parents** (`Cybereyes Basic System`, `Cyberears`,
  `Control Rig`) is in `CYBERWARE` — all three are rating-scaled or otherwise WP31-excluded. So
  bundled auto-attach cannot fire from the picker, and `_cyberware_context`'s flat cost/Essence
  arithmetic stays exact.

`priorities.py` re-renders the picker from `.purchases` (top-level) rather than `.walk()`, since a
plugin has no row to be shown in. A tree with plugins can only reach the session via a loaded save or
a legacy import; its plugins stay committed on the character and simply aren't re-rendered in the
picker until WP42 gives them somewhere to go. Noted in the code, since it is the one place this WP
knowingly leaves a display gap.

## Follow-up

- **WP42 is unblocked and is the last of Phase K.** Everything it needs is in place:
  `CyberwarePurchaseRequest` is the shape a form should produce, `PurchasedCyberware
  .capacity_remaining` is the live figure a plugin picker shows, `to_requests()` is what the save
  route already calls, and `derived.physical_limit`/`mental_limit`'s `context` parameter (WP40) is
  how the sheet can show a conditional bonus as conditional. The two UI gaps this WP knowingly left
  are rating selection and plugin rows in the picker.
- **The "Unmodeled real effects" registry backfill is now overdue** — see the decisions-log entry.
  It predates WP41 but WP41 made it bigger, and WP42 is the WP that will surface those items to a
  player most prominently.
- **A structural rejection during a legacy import still surfaces as a bare `ValueError`**, not an
  itemized `UnsupportedLegacyCharacterError` (see the log above for why that split is deliberate).
  No corpus fixture reaches it today — all 34 are blocked earlier — but a future WP that imports a
  Priority-built cyberware character with a genuinely over-Capacity limb would want a nicer failure.
