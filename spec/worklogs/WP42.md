# WP42 — Cyberware modification/subsystem UI

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase K, WP42. **Closes Phase K.**

## Goal

Expose Phase K's purchase tree through the browser: install a plugin into a limb/cybereye/cyberear
with the parent's remaining Capacity visible live, and show the result on the character sheet nested
under its parent, with each conditional bonus's condition text beside its value.

Deliberately last in the phase, and deliberately blocked on WP36-41 (and, per Phase K's own
re-sequencing note, on WP77-80): a picker written against a half-migrated engine would have been
thrown away, and this is the WP that puts the widest augmentation catalog this project has ever
offered in front of a player.

## Log

### 2026-08-01 — Reading the state, and finding the deliverable was bigger than "add a checkbox"

The picker as WP41 left it: one quantity box per row over `chummer5.data.cyberware.load_cyberware()`'s
60 flat-cost rows, adapted to the tree engine by a one-line `_purchase_requests` that wrapped each id
in a zero-plugin, rating-1 `CyberwarePurchaseRequest`. WP41's own docstring called out the two facts
that made that exact: no row in the flat 60 carries `<rating>`, and none of the three
`<subsystems>`-bearing parents is in it either.

The second of those is what forces this WP's scope. The acceptance criterion is "install a Cybereyes
system, buy a Vision Enhancement plugin into it" — and `Cybereyes Basic System` is rating-scaled
(`4000 * Rating - 2000 * number(Rating > 1)`), so it is one of the 27 rows WP31's flatness filter
excludes. There was no way to satisfy the deliverable without widening the offered catalog and adding
a rating control; "just add a plugin checklist to the existing picker" would have left the only
reachable parent a cyberlimb.

### 2026-08-01 — Auditing all 87 rows for what a picker should actually offer

Dumping the full `load_cyberware_entries()` set grouped by category turned up four decisions, only
one of which the WP entry anticipated:

1. **`Essence Hole` / `Essence Antihole`** — `<category>Bodyware</category>`, `<rating>600</rating>`,
   `<page>0</page>`, `<cost>0</cost>`. `pdftotext` over the *whole* PDF finds the phrase "essence
   hole" **zero** times, and `legacy/Chummer/Backend/Characters/Character.cs` creates them from code
   (`IncreaseEssenceHole`) as career-mode bookkeeping for removed cyberware. Excluded by name. WP31's
   flatness filter had been excluding them by accident; once flatness stops being the picker's
   filter, that accident has to become a decision or these two silently become purchasable. Recorded
   in `spec/rulebooks/learnings/phase-k.md` because it is a negative rulebook finding — the kind that
   is expensive to re-derive and easy to doubt.
2. **The 9 `<requireparent>` rows** — and this turned up a live bug rather than a design question.
   `create_cyberware_tree_selection` raises for any of them bought standalone, and **four**
   (`Ocular Drone`, `Cyber Holster`, `Cyberarm Slide`, `Large Smuggling Compartment`) are in WP34's
   flat 60. So the shipped picker had four quantity boxes whose only possible outcome was an error
   message. They move into their parents' plugin lists; nothing is lost and a real (if quiet) bug is
   fixed.
3. **`Image Link` / `Sound Link`** (`<capacity>[*]</capacity>`) — auto-attached by their parent and
   free, so a checkbox for one would offer a choice that is not one. Filtered out of the plugin list,
   shown as an "Included free:" line instead. Left in the standalone list, because WP34 offered them
   and the engine prices a standalone purchase normally; removing them would be an unrelated
   narrowing.
4. **The 11 `Cyber Implant Weapon` rows are parents with a zero budget.** They carry
   `<allowsubsystems>Cyber Implant Weapon Accessory</allowsubsystems>` and a purely bracketed
   `<capacity>`, which per WP37's legacy reading means a budget of 0 — and the third nesting level is
   cut anyway (2026-07-29). Handled by a display-level guard: a subsystem block is rendered only when
   the unit's *resolved* Capacity budget is > 0, so no control is ever offered that could only fail.

Final offered catalog: **76 standalone rows** (87 − 9 − 2), plus a per-parent plugin list computed
once at import time in `chummer5.web.catalogs.CYBERWARE_PLUGIN_CHOICES` (29 parents; 32 choices for a
full cyberlimb, 8 for cybereyes, 5 for cyberears, 3 for each weapon).

### 2026-08-01 — The form shape: index per bought unit, and one deliberate narrowing

The hard part of a tree in an HTML form is identity: two cyberarms need two independent plugin sets.
WP80 had already solved the same problem one level shallower for `Reflex Recorder`'s per-unit skill
pick (`bioware_skill_{id}_{n}`), so this follows it exactly:

- `cyberware_{item_id}` — quantity, **unchanged from WP34**, which is why every one of that WP's
  tests passes untouched. That was a design goal, not a happy accident: keeping the field name
  stable means "additive, not breaking" is checkable rather than asserted.
- `cyberware_rating_{item_id}_{n}` — the n-th bought unit's rating.
- `plugin_{item_id}_{n}_{plugin_id}` / `plugin_rating_{item_id}_{n}_{plugin_id}` — that unit's
  plugin picks.

**A plugin is a checkbox, not a quantity box.** The engine would accept two of the same row in one
parent outside the `Cyberlimb Enhancement` category (where p. 456 forbids it and WP38 enforces it),
so this is genuinely narrower than the engine. Chosen because a quantity box would need a fourth
index level — a rating per copy — to stay coherent, and nothing in the SR5 core set gains from a
second copy in one limb. Its one consequence is recorded rather than hidden: a legacy-imported
character with two identical plugins in one parent renders as one ticked box, so re-submitting drops
the duplicate. No fixture in the corpus does this.

**Ratings default to the item's minimum, not to 1.** `Customized Agility`'s floor is
`{AGIMinimum}+1` = 4 (the *limb's* base 3 plus one, p. 456/457), so a blank field defaulting to 1
would have been an instant rejection presented as a default. This is the reason `_parse_cyberware`
needs `attribute_maximums` at all, and it is also why the route now passes
`cyberlimb_attribute_maximums(character)` into `create_cyberware_tree_selection` — it never did
before, because the picker could not reach either `{AGIMaximum}` row.

### 2026-08-01 — Two engine symbols made public, and the rule about which one the UI may restate

`_rating_bounds` became `cyberware_rating_bounds`. The rating control has to offer exactly the range
`_build_purchase` validates against; a control that can produce a rejection is the one thing a rating
picker must not be, and reimplementing the `{AGIMinimum}`/`{AGIMaximum}` resolution in the web layer
would have been two copies of a rule with a known asymmetry (limb floor vs. character maximum).
`_PAIRED_BONUS_ITEM_NAMES` became `PAIRED_BONUS_ITEM_NAMES` for the sheet's matched-pair caveat.

The one rule the web layer *does* restate is dual costing (a plugin charges Capacity, a standalone
purchase charges Essence) — one conditional inside `_cyberware_unit_row`. That is deliberate:
`_cyberware_groups` resolves each node's `CyberwareFormula` itself rather than reading numbers off a
validated `CyberwareTreeSelection`, because the picker has to render the **rejected** state (over
budget, over capacity) and that is exactly when no selection exists. WP34's own subtotal column
already had this independent-tally shape; this keeps it and widens it.

"Live Capacity" needed no JavaScript at all. The section's form already carries
`hx-trigger="change, …"` with `hx-swap="outerHTML"` on `#cyberware`, so ticking a plugin re-posts and
re-renders the parent's `Capacity N of M remaining` line — the same mechanism WP15's remaining-points
display uses. Worth stating because the entry's word "live" could easily have been read as asking for
a client-side budget calculation, which would have been a second implementation of the Capacity rule.

### 2026-08-01 — The sheet: nesting, condition text, and the first use of WP40's `context=`

WP34 tallied cyberware as a flat `name → quantity` dict; WP41 widened that over `walk()`, which made
an imported limb's plugins visible but as siblings of the limb. `_cyberware_sheet_rows` replaces both:
one row per *distinct top-level purchase* (same catalog row, same rating, same subsystems at the same
ratings), with its plugins nested beneath it.

Grouping rather than listing every purchase is what preserves `Datajack × 1` — four existing tests assert
that exact string, and more importantly "two bare Datajacks" really is one line of two while "two
cyberarms with different plugins" really is two lines. The key is a recursive
`(item id, rating, sorted plugin keys)` tuple.

Conditional bonuses print as `+2 Mental limit — Only for Perception (Visual)`, from a new
`chummer5.data.cyberware.CONDITION_DESCRIPTIONS`. That constant sits in the data layer next to
`UNMODELED_EFFECT_NOTES` for the same reason WP79 put those there: it is rulebook display text about
a catalog row, keyed by the same verbatim legacy `<condition>` string the classifier already carries,
and a test pins its key set to `_SUPPORTED_BONUS_CONDITIONS` so it cannot drift from the engine's own
key → `ImprovementCondition` map.

`Hydraulic Jacks` gets an explicit "(granted once for a matched pair, not per implant)" suffix.
Without it, a player reading two jacks' rows would count the printed +Rating twice — the exact
mistake WP40's engine-side pair rule exists to prevent, reintroduced at the display layer.

The derived-stats table gained conditional limit rows (`Mental limit, visual Perception tests`),
emitted **only when they differ** from the headline figure — this is the first consumer of the
`context=` parameter WP40 added to `derived.physical_limit`/`mental_limit` for exactly this and left
unused. Suppressing equal rows matters: without it, every character would carry five rows restating
two numbers, and the one row that means something would be invisible among them.

## Follow-up

- **`chummer5.data.cyberware.load_cyberware()` is now unused by `src/` outside its own module.** WP41
  kept it explicitly because "the UI picker still lists its 60 flat rows"; that reason is gone. A
  retirement would touch `tests/unit/test_cyberware.py`,
  `tests/integration/test_cyberware_fixtures.py`, `tests/unit/test_augmentation_unmodeled_registry.py`
  and `tests/unit/test_web_cyberware.py` — mechanical but wide, and deliberately not bundled into a UI
  WP. Note `chummer5.data.cyberware` the *module* is not retirable regardless: it owns
  `classify_bonus`, `UNMODELED_EFFECT_NOTES`, `CONDITION_DESCRIPTIONS` and both bonus dataclasses.
- **A cyberlimb's plugin list is 32 checkboxes.** Correct, and collapsed inside a `<details>`, but it
  is the largest single control group this UI has. If it becomes unpleasant in practice, grouping it
  by the plugin's own category (the same `<details>`-per-category shape the catalog above it already
  uses) is the obvious next step; not done here because it adds a nesting level for a problem nobody
  has hit yet.
- **The Availability gap is now wider, not new.** The 2026-07-21 ruling says new catalogs should
  exclude Availability > 12 items, and WP31's catalog never did; this WP widened the offered set from
  60 rows to 76 without adding that filter either, because doing so would have changed what WP34
  already ships and belongs in the backfill WP the Project Overview already flags as unclaimed.
- **The two-level cut is now visible to players, not just to the engine.** A cyber implant weapon
  bought into a limb shows no subsystem block, because its budget is 0. That reads as "this can't
  hold anything," which is true of this engine but not of SR5 (the accessories fold into the parent's
  cost instead). If the fold-into-parent mechanic is ever modeled, the display guard is where it
  surfaces.
