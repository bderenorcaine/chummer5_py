# WP43 — Karma-to-Nuyen conversion

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase L, WP43.

## Goal

Let a player convert up to 10 Karma into nuyen during Step Six (core rulebook p. 94: "up to 10
Karma at 2,000¥ per Karma point"), folding the resulting nuyen into the same Resources-priority
budget gear/Lifestyle/cyberware already share, rather than a separate pool.

## Log

### 2026-07-21 — Confirming the mechanism before writing any code: which `.chum5` field, and does
it really share the gear budget

The WP's own acceptance criteria said to confirm rather than assume both of these. Checked the
legacy C# directly (`Character.cs`): `TotalStartingNuyen` computes `CalculateStartingNuyenFromKarma
(Math.Min(NuyenBP, TotalNuyenMaximumBP), StartingNuyen)`, which evaluates `CharacterSettings
.ChargenKarmaToNuyenExpression` — default (every `settings.xml` block) `"{Karma} * 2000 +
{PriorityNuyen}"`. `{PriorityNuyen}` is literally `StartingNuyen`, the Resources-priority-letter
budget itself — confirms the converted amount is *added* to the same pool, not tracked separately.
`<nuyenbp>` (not `<nuyenmaxbp>`, which is the *setting's* cap) is the per-character amount actually
converted — read directly off `Character._decNuyenBP`. Cross-checked against the full 34-file
corpus: 25 of 34 files have a nonzero `<nuyenbp>`, including 6 of the 11 curated mundane fixtures
(BLUE=9, Barrett=10, Bastion=10, Blindfire=2, Gentle Earthquake=10, Rez0luti0n2.0=10) — real fixture
coverage no other Phase L candidate has this cleanly. Full citations recorded in `spec/rulebooks
/learnings.md`'s new WP43 entry, including the provenance check on the 10-Karma cap itself (real
rulebook prose, p. 94, specific to the "experienced runner" default level this project implements —
Street-Level/Prime Runner use different caps this project doesn't model, the same "hardcode the one
supported default" precedent `QUALITY_KARMA_LIMIT` already set).

### 2026-07-21 — Design: a `create_resources_selection` parameter that enlarges the budget, not a
new selection type

`lifestyle_cost`/`cyberware_cost` already established the "fold into the one joint budget check"
shape for anything sharing this pool — Karma-to-Nuyen is the same shape, just on the other side of
the ledger (it *enlarges* the available budget instead of spending from it). Added `karma_converted`
as a `create_resources_selection` parameter and a `ResourcesSelection.karma_converted` field, plus a
`karma_to_nuyen(karma_spent) -> int` helper (validates 0-10, raises otherwise) and an `available_nuyen`
composition helper (`starting_nuyen + karma_to_nuyen`) factored out since `chummer5.web.app` needed
the same sum independently at several call sites. Deliberately kept `ResourcesSelection.nuyen_budget`
meaning unchanged (pure priority-derived number, still `== legacy.starting_nuyen` for every fixture,
per existing test assertions) — only `nuyen_remaining` reflects the karma-derived top-up. Confirmed
this doesn't break `nuyen_budget`'s existing fixture cross-checks before proceeding.

### 2026-07-21 — Not wiring a double-spend check against qualities/contacts' own karma costs

The WP's own deliverables list flagged this as something to wire "if Phase O ships first" but not a
blocking dependency otherwise. Confirmed Phase O (the unified Karma ledger) hasn't landed — no code
anywhere sums `quality_selection.karma_cost`/`contact_selection.karma_cost` into one running total
today, so there is nothing yet for this conversion to double-spend against. `karma_to_nuyen` only
enforces the flat 0-10 range; documented this explicitly in `chummer5.engine.resources`'s module
docstring as a known, deliberate gap rather than leaving it ambiguous whether it was considered.

### 2026-07-21 — Threading `karma_converted` through the web layer touches more call sites than
`lifestyle_cost` did, because three sections (not just two) independently compute the available
budget

`_resources_context`, `_lifestyle_context`, and `_cyberware_context` (plus `_resources_selection_for
_display` and `submit_cyberware`'s own inline `nuyen_available` calc) each call `starting_nuyen`
directly rather than through one shared helper — `available_nuyen` didn't exist before this WP, so
each site previously computed the budget as `starting_nuyen(letter, PRIORITIES)` alone. Added
`karma_converted` as a parameter to all three context builders (mirroring `lifestyle_cost`/
`cyberware_cost`'s existing cross-section threading pattern) and to `submit_resources`/
`submit_lifestyle`/`submit_cyberware`, sourcing it from `character.resources_selection
.karma_converted` (0 if uncommitted) at every read site the way `gear_cost`/`lifestyle_cost`/
`cyberware_cost` already are. The Karma-conversion control itself lives on the Resources form
(`_resources.html`, submitted together with gear in one `<form>`) — Lifestyle/Cyberware only ever
*read* the committed amount to compute their own share of the budget, they don't let the player edit
it, so `submit_lifestyle`/`submit_cyberware` both carry the existing `resources_selection
.karma_converted` forward unchanged rather than defaulting it to 0 (which would have silently reset
any committed conversion on an unrelated Lifestyle/cyberware edit — checked this against the existing
`new_resources_selection` re-derivation in both routes before landing the fix).

### 2026-07-21 — A rejected submission's `karma_converted` value must never crash the redisplay

`create_resources_selection`'s `karma_to_nuyen` call raises for an out-of-range value (e.g. a player
typing "15") — correct for the *validating* call, but `_resources_context`'s own return dict also
computes a display `nuyen_remaining`/`karma_to_nuyen_amount` unconditionally, including on the
error-redisplay path where `karma_converted` is exactly the rejected, out-of-range value. Fixed by
adding `_display_karma_to_nuyen` (clamps to [0, 10] before calling the real `karma_to_nuyen`) for
every *display-only* computation, while the real validating calls (`create_resources_selection`
itself, inside the `if error is None` re-validation blocks) keep using the strict, raising version —
confirmed via a dedicated test (`test_converting_more_than_ten_karma_is_rejected`) that this path
renders the specific "between 0 and 10" message instead of crashing.

### 2026-07-21 — Character sheet display: kept `nuyen_budget` unchanged, added the karma top-up as a
separate, explicit line rather than baking it silently into one number

Initially considered just changing what `nuyen_budget` displays on the character sheet. Rejected:
`resources_selection.nuyen_budget` is asserted `== legacy.starting_nuyen` by several existing fixture
tests, and conflating "priority budget" with "priority budget + Karma top-up" under the same label
would make a player's own converted amount invisible on the one screen meant to show the finished
character. Added `karma_to_nuyen_amount`/`karma_converted` to `_character_sheet_context` and extended
the nuyen line to show `"{remaining} / {budget + karma_nuyen} ({budget} priority + {karma_nuyen} from
converting {karma_converted} Karma)"` when nonzero, collapsed onto one line (no internal newlines) so
`tests/integration/test_web_character_sheet_fixtures.py`'s existing exact-substring assertion for a
zero-karma character (Yeti) still matches byte-for-byte.

## Outcome

WP43 complete. A player can now convert up to 10 Karma into nuyen at Step Six (2,000¥/point, core
rulebook p. 94) through the Resources screen, with the converted amount folded into the same shared
Resources-priority nuyen budget gear/Lifestyle/cyberware already draw from — not a separate pool —
via `chummer5.engine.resources.create_resources_selection`'s new `karma_converted` parameter. All
three peer sections (`_resources.html`/`_lifestyle.html`/`_cyberware.html`) and the character sheet
correctly reflect the topped-up budget; an above-cap submission is rejected with a specific message
rather than crashing or silently clamping. Native save/load and legacy `.chum5` import both thread
the conversion through (a real, itemized `<nuyenbp>` field this project's own 11-fixture corpus
exercises on 6 of 11 files — the best real fixture coverage of any Phase L candidate). One deliberate,
documented gap: nothing yet stops the converted Karma from being "spent" a second time on qualities
or contacts, since no unified Karma ledger exists until Phase O — flagged in `chummer5.engine
.resources`'s module docstring rather than silently assumed away. `pytest`/`ruff`/`mypy` are all
green (560 tests, 29 more than before this WP), and a real-HTTP manual walkthrough (confirm → buy
gear + convert Karma → reject an above-cap resubmission → character sheet → save → reload into a
fresh session) reproduces the correct combined nuyen numbers throughout. Phase L continues with WP44
(Sum-to-Ten build method).
