# WP44 — Sum-to-Ten build method

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase L, WP44.

## Goal

Let a player choose Sum-to-Ten instead of Priority for assigning the 5 priority-table letters
(Heritage/Talent/Attributes/Skills/Resources) — same `priorities.xml` data, same per-letter
meaning, a different validity rule: letters may repeat, and their point values (A=4/B=3/C=2/D=1/
E=0) must sum to a target (10 by default) instead of forming a bijection.

## Log

### 2026-07-21 — Confirming the actual rule before writing any code: the Implementation Plan's own
"must not exceed 10" phrasing is wrong

The WP's own text (written before this research pass) said the letters' point values "must not
exceed a target that defaults to 10." Checked directly against the legacy C#
(`SelectMetatypePriority.cs`): `MetatypeSelected()` compares the current total against
`CharacterSettings.SumtoTen` with `!=`, not `>`, and on a mismatch shows `Message_SumtoTen`
(`legacy/Chummer/lang/en-us.xml`): **"Your Priority selection must equal {0}. It is currently
{1}."** — explicit equality, both directions. Cross-checked against 5 real curated `.chum5`
fixtures with a complete 5-letter assignment (the other 6 of the 11 mundane fixtures are missing a
Skills letter — see below): `Yeti-#ffffff2.chum5` (Priority-built, D/A/B/C/E = 10) and 4
`SumtoTen`-built Technomancer-Talent fixtures — `Bastion.chum5` (E/C/A/E/A = 10, repeats E and A),
`Rez0luti0n2.0.chum5` (B/A/B/E/E = 10, repeats B and E), `SCSi.chum5` (E/C/D/B/A = 10, no repeats),
`Serpent.chum5` (E/C/C/B/B = 10, repeats C and B). All 5 total *exactly* 10, including the repeated-
letter cases — real, independent confirmation beyond the C#/language string. Also confirmed via
`pdftotext -layout` over the full rulebook PDF: zero hits for "sum to ten"/"sum-to-ten"/"sumtoten" —
this is legacy-Chummer/errata content, not a rulebook citation, matching the Implementation Plan's
own claim on that point (the "must equal" correction is the only thing wrong with the plan's
research). Full detail, including the point table's provenance and the settings.xml cross-check for
the target defaulting to 10, recorded in `spec/rulebooks/learnings.md`'s new WP44 entry.

### 2026-07-21 — A second, unrelated real gap the same research surfaced: 6 of the 11 mundane
fixtures have no Skills priority letter recorded at all

While cross-checking the 5 fixtures above, found the other 6 curated mundane fixtures (`BLUE`,
`Barrett`, `Blindfire`, `Fuzzy-chargen`, `Gentle Earthquake`, `Monomax (approved) 3`) all have a
blank `<priorityskills>` scalar — not a `"<letter>,<n>"` value. What actually predicts this across
all 11 turns out to be `<prioritytalent>`, not build method: every one of the 6 gaps has
`talent_codename == "Mundane"`; every fixture with a real Skills letter (the 4 Technomancer-Talent
ones above, plus Yeti) has a real Talent archetype. A genuine legacy save-format/UI quirk (a
Mundane-Talent Sum-to-Ten character's Skills combo box apparently never persists), not a parser bug
— confirmed via a direct `ElementTree` read of the raw XML. This had been invisible until now because
the pre-WP44 build-method gate rejected every `SumtoTen` character outright before reaching this
field at all. Once that gate widens, importing any of these 6 would crash
`chummer5.engine.skills.create_skill_allocation` with `priorities.skills[""]` — a `KeyError`, not a
clean rejection — unless guarded against. Added a new itemized `_blocking_reasons` check: every one
of the 5 `<priority*>` categories must resolve to a real A-E letter via `chummer5.io.legacy_chum5
.priority_letter`, or the import is rejected with a specific reason rather than reaching that crash.

Re-ran `_blocking_reasons` against all 8 real cyberware-bearing fixtures (and separately the 6
blank-Skills ones) with the build-method check stripped out, to see what widening the gate would
actually unblock. Answer: nothing. Every one of the 10 curated `SumtoTen` mundane fixtures still
hits at least one other, already-itemized blocker (cyberware, Bioware, a karma-bought attribute, or
a metavariant) — so this WP's real import success remains synthetic/hand-verified, same honesty
caveat the plan's own acceptance text anticipated, just for a more specific reason than "no fixture
uses this build method" (several separate pre-existing blockers, confirmed by name, do).

### 2026-07-21 — Design: no new `Character` field, no new validation in `create_character`/
`build_character`

Confirmed neither `create_character` nor `build_character` has ever validated the letter
*assignment*'s shape (bijection vs. Sum-to-Ten) to begin with — only `chummer5.web.app
.submit_priorities` does, at the point of interactive submission. That means `build_method` is pure
session-side UI state (which validity rule to apply on the *next* reconfirmation), the same shape
`talent_letter`/`skills_letter`/`resources_letter` already have on `ChargenSession` — `Character`
gains no field for it. `CharacterSave` does gain a `build_method` field (defaulting to
`PRIORITY_BUILD_METHOD` for every pre-WP44 save), purely so a reloaded Sum-to-Ten character's next
priorities reconfirmation applies the right rule instead of silently defaulting back to Priority's
bijection — which its own letters might not even satisfy if they repeat. `build_character` does
*not* re-validate this field against the letters (proven by a dedicated test:
`test_build_character_does_not_validate_build_method_against_the_letters`), matching the "nothing
downstream needs it to be correct" finding above.

New module, `chummer5.engine.build_method`: `PRIORITY_BUILD_METHOD`/`SUM_TO_TEN_BUILD_METHOD`
(matching `<buildmethod>`'s literal legacy strings, so `chummer5.io.legacy_import` needs no
translation layer), `SUM_TO_TEN_POINT_VALUES`, `SUM_TO_TEN_TARGET`, `sum_to_ten_total()` (never
raises on an off-target total — used for a live "X/10" display), and `validate_sum_to_ten_total()`
(raises on anything other than exactly `SUM_TO_TEN_TARGET`).

### 2026-07-21 — UI: no new controls needed, just a build-method radio + a live total

`_priority_form.html`'s 5 `<select>` dropdowns already offer the full A-E range per category (WP24)
with no client-side distinctness constraint — Sum-to-Ten needs no new picker, only a build-method
radio selector (`_priority_form_context` gains `build_method`/`build_methods`/`sum_to_ten_total`/
`sum_to_ten_target`) and a conditionally-shown "current total: X/Y" line. Deliberately *not* wired
for true per-keystroke live recompute (which would need a dedicated fragment endpoint, unlike the
attribute/skill sections' "submit-on-change against the real route" pattern) — the priority form
already requires an explicit "Confirm" click for a good reason (a metatype/letter change invalidates
already-spent points elsewhere; see WP19), so the total simply recomputes on every real submission,
success or rejection, the same way the existing `error`/`priority_stale_selections` messages already
do.

`submit_priorities` gained a `build_method: str = Form(PRIORITY_BUILD_METHOD)` parameter — defaulted,
not required, so every pre-WP44 test/caller that never sends the field keeps today's bijection
behavior unchanged. Branches on it: Priority keeps the existing bijection check; Sum-to-Ten calls
`validate_sum_to_ten_total`; anything else is its own itemized error.

### 2026-07-21 — Legacy import: widened the gate, added the missing-letter guard, updated the tests
that assumed the old all-SumtoTen-rejected behavior

`_blocking_reasons`'s build-method check widened from `!= "Priority"` to `not in
SUPPORTED_BUILD_METHODS` (still rejecting `Karma`/`LifeModule` per the Project Overview's explicit
2026-07-21 ruling). Several existing tests baked in the old "every SumtoTen fixture/character is
rejected on build-method grounds alone" assumption and needed updating to match the new, more
specific reality:
- `tests/integration/test_cyberware_import_fixtures.py`'s parametrized test no longer asserts a
  build-method reason — just that the real itemized cyberware/Bioware reason still appears (which it
  does, for all 8).
- `tests/integration/test_legacy_import_fixtures.py`'s `test_rejects_sumtoten_mundane_fixture`
  (`Barrett.chum5`) now asserts the two real reasons that actually fire post-WP44: her blank Skills
  letter, and her real cyberware/Bioware content.
- `tests/unit/test_legacy_import.py`'s `test_rejects_sumtoten_build_method` became
  `test_sumtoten_build_method_with_all_priority_letters_present_imports_successfully` (a
  synthetic, letter-complete SumtoTen character now imports cleanly) plus a new
  `test_rejects_karma_build_method` (an actually-unsupported method still rejects) and
  `test_rejects_missing_priority_letter` (the blank-Skills crash guard, proven directly since no
  otherwise-clean real fixture exercises it in isolation).
- `test_itemizes_every_blocking_reason_in_one_pass` switched its build method from `SumtoTen` to
  `Karma` to keep exercising a genuine 3-reason case (SumtoTen alone would only leave 2, now that
  it's accepted).

## Outcome

WP44 complete. A player can now choose Sum-to-Ten instead of Priority for assigning the 5
priority-table letters, via a build-method radio selector on the existing priority form — no new
letter-picker controls were needed, since Sum-to-Ten only relaxes an existing constraint (distinct
letters) rather than needing a different input shape. The validity rule implemented is **exact
equality to 10** (`chummer5.engine.build_method.validate_sum_to_ten_total`), correcting the
Implementation Plan's own "must not exceed 10" phrasing — confirmed via the legacy C#'s literal
`!=` comparison and its `Message_SumtoTen` string, and independently via 5 real curated fixtures
(including two with repeated letters) that all total exactly 10. A second, unrelated real gap
surfaced by the same research — 6 of the 11 mundane fixtures have no Skills priority letter
recorded at all, a genuine Mundane-Talent-Sum-to-Ten legacy save-format quirk — is now guarded
against in `chummer5.io.legacy_import` with an itemized rejection reason rather than an unhandled
`KeyError`, though (confirmed) no fixture in the current corpus reaches that guard in isolation
today, since each already hits a separate, pre-existing blocker. `Character`/`build_character`
gained no new validation at all: neither ever checked the letter-assignment's shape to begin with,
so `build_method` is carried through purely as descriptive session/save state (`ChargenSession
.build_method`/`CharacterSave.build_method`) so a reloaded Sum-to-Ten character's next
reconfirmation applies the right rule instead of silently reverting to Priority's bijection.
`pytest`/`ruff`/`mypy` are all green (586 tests, 14 more than before this WP), and a real-HTTP
manual walkthrough (confirm via Sum-to-Ten with repeats → reject an over-target resubmission →
save → reload into a fresh session → reconfirm the same repeated-letter assignment → confirm
Priority's own behavior is unaffected) reproduces every one of the above end to end. Phase L
continues with WP45 (Bioware).
