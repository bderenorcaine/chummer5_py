# WP45 — Bioware (data loader, selection, save/load, and legacy import)

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase L, WP45.

## Goal

Add the SR5-core, flat-cost/flat-essence, Standard-grade bioware catalog, reusing Phase J's
Essence/nuyen-budget machinery directly. Scoped as one WP (not split loader/selection/save-load
like cyberware's WP31/32/33), per the Implementation Plan's own call — confirmed correct: the
catalog is tiny (6 items after this WP's own research, see below), so cyberware's reviewability
rationale for a 3-way split doesn't apply.

## Log

### 2026-07-21 — Re-deriving the Plan's pre-stated count directly from the XML: 8 flat items
becomes 6 once the Availability filter (a second filter the Plan's own WP45 text didn't fully
anticipate) is applied

Parsed `legacy/Chummer/data/bioware.xml` directly before writing any loader code, the same
"verify, don't assume" habit every prior data-loader WP established. Confirmed: 213 total
`<bioware>` entries, 23 `source == "SR5"`. Applying the identical flat-cost-and-Essence filter
`chummer5.data.cyberware` already uses gives exactly 8, matching the Plan's own pre-stated count —
but the Plan also calls for a 2026-07-21-ruling Availability filter (`Availability > 12` excluded)
that its own WP45 entry mentions applying but doesn't re-derive the resulting count for. Checked
directly: 2 of the 8 (Pain Editor at `18F`, Suprathyroid Gland at `20R`) exceed 12 and are excluded,
leaving **6**: Cat's Eyes, Enhanced Articulation, Platelet Factories, Reflex Recorder, Skin Pocket,
Sleep Regulator. Recorded in `spec/rulebooks/learnings.md`'s new WP45 entry, including a `grep` of
the legacy C# confirming none of the 4 bonus-less items (Cat's Eyes/Platelet Factories/Skin Pocket/
Sleep Regulator) has a hidden by-name special case — the same verification `chummer5.data.cyberware`
did for its own bonus-less items, applied here since this project's "never silently drop a real
effect" discipline doesn't get to skip a step just because the shape looks obviously inert.

### 2026-07-21 — `BonusSupport` reused directly from `chummer5.data.cyberware`, confirmed to
generalize cleanly (per the Plan's own explicit instruction to check before adding a new one)

Read every one of the 6 items' raw `<bonus>` node directly. 4 have no `<bonus>` at all (`NO_EFFECT`,
unconditionally — mirrors cyberware's own "no name-gate needed" reasoning, verified per the grep
above rather than assumed to transfer). Enhanced Articulation's `<bonus>` combines
`<physicallimit>1</physicallimit>` with `<specificskill><name>Escape Artist</name>
<bonus>1</bonus></specificskill>` — two *different* flat shapes in one node, both already
recognized by `chummer5.data.qualities`'s identical grammar (not cyberware's — cyberware only ever
produces a `<conditionmonitor>` shape). Reflex Recorder's `<bonus>` is
`<selectskill limittoattribute="BOD,AGI,REA,STR"><val>1</val></selectskill>` — a *player-selected*
skill bonus, structurally different from `<specificskill>`'s fixed-name shape and from anything
this engine's Talent-free-skill-grant mechanism (Phase I) already resolves (that mechanism turns a
category/xpath *filter* into a caller-supplied list at chargen time via a different code path
entirely, not a single-item purchase-time picker) — correctly falls through to `NOT_YET_SUPPORTED`.
`chummer5.data.cyberware.BonusSupport`'s existing 3-way scheme (`FLAT_BONUS`/`NO_EFFECT`/
`NOT_YET_SUPPORTED`) describes all 6 shapes with no gap, so `chummer5.data.bioware` imports and
reuses it directly rather than defining an equivalent duplicate — unlike WP31's own choice to give
cyberware a fresh Enum instead of reusing qualities'/powers', where the two modules' real membership
differed in a documented way. `BiowareFlatBonus`, by contrast, mirrors `chummer5.data.qualities
.FlatBonus`'s shape (a `target_name` field), not `chummer5.data.cyberware.CyberwareFlatBonus`'s
narrower one (no `target_name`) — cyberware's only flat shape (the Cyberlimb condition-monitor
bonus) never needed one; bioware's `specificskill`/`specificattribute` shapes do.

### 2026-07-21 — Deciding the shared-pool composition order: cyberware first (unaware of bioware),
bioware second (aware of cyberware) — a fixed, documented convention, not an arbitrary choice

`chummer5.engine.cyberware`'s own WP32-era docstring already flagged this exact gap ahead of time:
"a future WP that adds a second Essence-reducing source (bioware, if ever built) would need to
widen this to take the character's pre-purchase Essence as an input instead." Widened
`create_cyberware_selection` with an `other_essence_spent: Decimal = Decimal(0)` keyword parameter
(default preserves every pre-WP45 call site unchanged), and gave `create_bioware_selection` the
mirror-image parameter. Every real call site in this project (`build_character`, the combined
`_cyberware_context`/`submit_cyberware` web route) resolves cyberware first with the parameter at
its default, then bioware second, passing cyberware's own `essence_spent`/leftover nuyen budget in
— so a combination that's only invalid once *both* are counted together is always caught, on the
bioware call, never silently missed by either call passing independently. Verified this composes
correctly with a dedicated cross-module test
(`test_bioware_selection.py::test_shared_floor_matches_a_real_combined_cyberware_and_bioware_check`)
and, at the web layer, `test_web_bioware.py::test_bioware_essence_floor_rejects_when_combined_
with_cyberware_exceeds_it` (confirmed live over real HTTP too, see Verification).

### 2026-07-21 — UI: fold bioware into the existing cyberware section/route, not a new peer section

The Plan's own WP45 entry asks to decide & document this, mirroring WP34's identical "does this
share a screen with cyberware" call. Considered a new peer section (WP20's Lifestyle precedent) —
rejected: unlike Lifestyle (its own distinct rulebook chargen step), the rulebook's own Step Six
groups "Cyberware and Bioware" as one combined subsection, both catalogs are tiny/near-identical in
shape (nuyen + Essence, no other validation rule), and they share one Essence pool that has to be
checked jointly regardless — a second, near-duplicate section would only fragment one shared
decision the two catalogs already are content-wise. `_cyberware_context`/`POST /ui/cyberware`
widened to build both catalogs' picker rows and validate both selections together (fixed order, see
above); `_cyberware.html` gained a second `<h3>Bioware</h3>` sub-section inside the same `<form>`,
submitting `bioware_{id}` fields alongside the existing `cyberware_{id}` ones in one request.

A real trap caught while writing the manual-verification script (mirroring WP34's own documented
"two separate submissions lose each other's item" finding, just rediscovered independently here):
buying cyberware and bioware in the *same* `POST /ui/cyberware` request works correctly (both
persist), confirming the combined form's single-submission contract holds for the new bioware
fields exactly the way it already did for cyberware's own.

## Design decisions

- **One new module, `chummer5.engine.bioware`, not folded into `chummer5.engine.cyberware`.** Each
  is its own SR5 chargen decision with its own catalog/dataclass (mirrors `chummer5.engine
  .lifestyle`'s own precedent for staying separate from `chummer5.engine.resources`), even though
  both share the nuyen budget and (uniquely here) the Essence pool. See module docstring.
- **`chummer5.data.bioware` reuses `chummer5.data.cyberware.BonusSupport` directly** (confirmed to
  generalize cleanly, per the Plan's own instruction) but defines its own `BiowareFlatBonus`
  (mirroring `chummer5.data.qualities.FlatBonus`'s shape instead of cyberware's narrower one) — see
  Log above.
- **`create_cyberware_selection`/`create_bioware_selection` both gain an `other_essence_spent`
  keyword parameter, defaulting to `Decimal(0)`** — the fixed cyberware-first/bioware-second
  composition order is a documented convention (both modules' docstrings state it), not something
  either function enforces on its own; every real call site in this project follows it consistently.
- **Bioware folds into the existing `_cyberware.html`/`POST /ui/cyberware` UI section**, not a new
  peer section — see Log above for the reasoning, a deliberate divergence from WP20's Lifestyle
  precedent for a documented reason (shared Essence pool + near-identical shape + a rulebook
  subsection that already groups the two).
- **Duplicate bioware purchases are allowed**, mirroring cyberware's shape for consistency — unlike
  cyberware's own duplicate-cyberlimb-pair finding, no real fixture confirms this is an ordinary
  bioware purchase pattern specifically (none of the 6 real-bioware-bearing fixtures buy the same
  item twice); recorded as a consistency choice, not a separately-verified rule, in the module
  docstring.
- **`ImprovementSource.BIOWARE` is a new, distinct source from `CYBERWARE`**, even though both only
  ever grant an `ESSENCE`/`FLAT_BONUS`-shaped Improvement — keeps `ImprovementIndex.remove_source`
  able to retract one without touching the other.
- **No new `spec/rulebooks/learnings.md` rulebook-PDF citation was needed** — every rulebook-
  grounded fact this WP relies on (shared Step Six pool, Essence floor, the Availability ruling)
  was already confirmed and cited during WP30-32/the Project Overview's own ruling. The new
  `learnings.md` entry records this WP's own *data*/*fixture* research instead (the Availability-
  filtered count, and the real-fixture-bioware correction — see Log above).

## Implementation

- `src/chummer5/data/bioware.py` (new): `Bioware` frozen dataclass (`id`, `name`, `category`,
  `cost: int`, `essence_cost: Decimal`, `availability: int`, `source`, `page`, `bonus_support`,
  `flat_bonuses`, `raw_bonus`); `BiowareFlatBonus` (`target_kind`, `target_name`, `value`);
  `load_bioware()` filtering to `source == "SR5"` AND flat `<cost>` AND flat `<ess>` AND
  `Availability <= 12` (6 of 213 total, 6 of 23 SR5 entries); `_classify_bonus` (reuses qualities'
  skill/attribute/limit-tag grammar); `count_by_support()` mirroring every other `chummer5.data`
  loader's identical helper.
- `src/chummer5/engine/bioware.py` (new): `BiowareSelection`, `create_bioware_selection`
  (validates nuyen + the shared Essence floor via `other_essence_spent`), `apply_bioware_
  improvements` (grants `ESSENCE` unconditionally + `FLAT_BONUS`es under `ImprovementSource
  .BIOWARE`) — mirrors `chummer5.engine.cyberware`'s shape exactly.
- `src/chummer5/engine/cyberware.py`: `create_cyberware_selection` gains `other_essence_spent:
  Decimal = Decimal(0)`, folded into the Essence-floor check.
- `src/chummer5/engine/improvements.py`: `ImprovementSource.BIOWARE` (7th member).
- `src/chummer5/engine/character.py`: `Character` gains `bioware_selection: BiowareSelection |
  None = None` (the same "`None` until committed" shape every selection field since WP18 has); a
  new `TYPE_CHECKING`-only import.
- `src/chummer5/engine/resources.py`: `ResourcesSelection`/`create_resources_selection` gain
  `bioware_cost: int = 0`, extending the existing `lifestyle_cost`/`cyberware_cost` shared-budget
  mechanism from three terms to four (including the raised over-budget message's `parts` list).
- `src/chummer5/io/save_format.py`: `CharacterSave` gains `bioware_item_ids: tuple[str, ...] = ()`
  (JSON round-tripped); `create_character_save` gains the matching parameter; `build_character`
  gains a `bioware: tuple[Bioware, ...] = ()` parameter, resolves `bioware_selection` *after*
  `cyberware_selection` (fixed order — nuyen: whatever cyberware left over; Essence:
  `other_essence_spent=cyberware_selection.essence_spent`), applies it via `apply_bioware_
  improvements`, folds its cost into a final `create_resources_selection` call (alongside
  cyberware's), and attaches it to the returned `Character`.
- `src/chummer5/io/legacy_chum5.py`: **no changes needed** — `LegacyCyberware` already parsed both
  Cyberware and Bioware entries (distinguished via `<improvementsource>`) since WP33, including the
  `grade` field this WP's Standard-grade check needs.
- `src/chummer5/io/legacy_import.py`: the previously-unconditional "every Bioware entry is
  blocking" check is replaced with the identical itemized name+Standard-grade resolution cyberware
  entries already get, against the new `bioware` catalog parameter; `import_legacy_character`/
  `import_chum5` gain a `bioware: tuple[Bioware, ...] = ()` parameter, resolve `bioware_item_ids`
  the same way `cyberware_item_ids` already is, and thread it through `create_character_save`.
- `src/chummer5/web/app.py`: `BIOWARE = load_bioware()` (module-level); `_BIOWARE_BY_CATEGORY`
  (sorted, mirrors `_CYBERWARE_BY_CATEGORY`); new `_catalog_groups` helper (shared by the
  cyberware/bioware halves of `_cyberware_context`, factored out since both need the identical
  category-grouped-picker-row shape); `_parse_bioware` (mirrors `_parse_cyberware`); `_relink_
  bioware_selection`/`_replace_committed_bioware` (mirror the cyberware pair exactly); `_resources_
  context`/`_lifestyle_context`/`_resources_selection_for_display` gain `bioware_cost`; `_cyberware_
  context` widened to build both catalogs' rows and validate both selections together (fixed
  order); `_character_sheet_context` gains `bioware_rows`; `_character_save_from_session` gains
  `bioware_item_ids`; `_chargen_body_context` computes the new cross-section `bioware_cost`/
  `bioware_item_ids` numbers; `submit_attributes` gains one `_relink_bioware_selection` call;
  `submit_resources`/`submit_lifestyle`/`submit_cyberware` all resolve and pass `bioware_cost`
  (the latter also parses/validates/applies the actual bioware selection); `download_save`/
  `load_save`/`import_chum5_route` pass `bioware=BIOWARE` into `build_character`/`import_chum5`.
- `src/chummer5/web/templates/_cyberware.html`: renamed header to "Cyberware & Bioware"; added a
  second `<h3>Bioware</h3>` category-grouped picker inside the same `<form>`; combined nuyen/Essence
  summary line covers both catalogs together.
- `src/chummer5/web/templates/_character_sheet.html`: new "Bioware" section alongside the existing
  "Cyberware" one, sharing the one Essence line.

## Outcome

WP45 complete. `chummer5.data.bioware`/`chummer5.engine.bioware` add the SR5-core, flat-cost,
flat-Essence, low-Availability, Standard-grade bioware catalog (6 items — Cat's Eyes, Enhanced
Articulation, Platelet Factories, Reflex Recorder, Skin Pocket, Sleep Regulator), reusing Phase J's
Essence/nuyen-budget/Improvement-application machinery directly: `chummer5.data.cyberware
.BonusSupport` is reused unchanged, `create_bioware_selection`/`apply_bioware_improvements` mirror
their cyberware counterparts' shape exactly, and both cyberware's and bioware's own Essence-floor
checks now compose correctly via a fixed, documented evaluation order (cyberware first, bioware
second, aware of cyberware's spend) so a combination invalid only once both are counted together is
always caught. Bioware purchases fold into the existing cyberware chargen UI section rather than
getting a new peer one, a deliberate divergence from Lifestyle's own WP20 precedent justified by the
rulebook's own "Cyberware and Bioware" combined Step Six subsection and the two catalogs' shared
Essence pool. Native save/load and legacy `.chum5` import both thread bioware through the normal
mechanical path; `chummer5.io.legacy_import` no longer blanket-rejects every Bioware-bearing
character, itemizing each real purchase the identical way cyberware's own WP33 already does. A data-
research finding worth flagging: `Barrett.chum5` turns out to carry 3 real Standard-grade,
flat-cost-and-Essence Bioware purchases that resolve cleanly against this catalog — correcting the
Implementation Plan's own "no fixture carries real bioware" claim and giving this WP's itemized
import logic real positive-case fixture coverage neither the Plan nor cyberware's own WP31 had
anticipated. `pytest`/`ruff`/`mypy` are all green (640 tests, 51 more than before this WP), and a
real-HTTP manual walkthrough (confirm → buy cyberware+bioware together → save → reload into a fresh
session; separately, trigger and confirm the shared-Essence-floor rejection; separately, import a
cyberware/bioware-free mundane fixture to confirm zero regression) reproduces the correct combined
nuyen/Essence numbers throughout. Phase L is now complete (WP43 Karma-to-Nuyen, WP44 Sum-to-Ten,
WP45 Bioware) — Phase M (Magic expansion: Bound Spirits, Foci, Mentor Spirits) is next.
