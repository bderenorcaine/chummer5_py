# WP46 — Bound Spirits (roster + Karma budget only)

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase M, WP46.

## Goal

Let a Magician spend leftover Karma binding spirits, modeled as roster entries plus a budget check
only — no spirit stat block, skills, or powers (per the Implementation Plan's Phase M intro). A
spirit's Force is always exactly the caster's Magic rating, not player-chosen; the only two things a
player picks are which spirit type and how many services, which sets the Karma cost 1:1. Deliberately
the smallest of Phase M's three WPs, sequenced first so it isn't blocked behind the much larger Mentor
Spirits (WP48).

## Log

### 2026-07-21 — Rulebook research first: Step Seven's table, the Spirits section's 6 core types,
and confirming the offered spirit-type list is tradition-dependent

Read the Additional Purchases & Restrictions table (Step Seven, p. 98) directly via `pdftotext
-layout` before writing any code: "1 Karma per service (Force of spirit is equal to Character's Magic
Attribute rating)... Can only have a number of bound spirits equal to Charisma" — confirms Force is
always the *live* Magic rating (never a fixed snapshot) and the only chargen-time cap is a count cap,
not a Force cap the way Foci's own chargen bonding cap will be (WP47, not this one).

Cross-read the Magic chapter's own "Spirits" section (pp. 303-306, confirming 6 core types: Air,
Beasts, Earth, Fire, Man, Water) against `legacy/Chummer/data/traditions.xml`'s `<spirits>` block,
which the loader (`chummer5.data.traditions`) had never parsed before this WP. Confirmed directly,
not assumed: each SR5-core tradition's 5-role affinity table (Combat/Detection/Health/Illusion/
Manipulation) names a *different* 5 of the 6 types — Hermetic never offers Beasts, Shamanic never
offers Fire — so which spirit types a Magician may bind is tradition-dependent, not a single
universal list. A classifier that assumed otherwise would have been wrong in both directions. Full
citations recorded in `spec/rulebooks/learnings.md`'s new WP46 entry.

Also confirmed, via the rulebook's own "Adepts" section (p. 308: "adepts still need the appropriate
licenses to... cast spells if they are that rare hybrid, the mystic adept"), that only a Magician
(never a pure Adept, Mystic Adept being out of this project's scope entirely) can ever have bound
spirits — `create_bound_spirit_selection` gates on `character.tradition is None` rather than a
separate `magic_type` check for this reason, tying the check to the actual data dependency (which
spirit types are offered comes from the tradition) instead of duplicating a redundant test.

### 2026-07-21 — No unified Karma ledger exists yet (Phase O), so this WP adds its own provisional,
deliberately-temporary stand-in rather than waiting

Confirmed by reading `chummer5.engine.resources`'s own module docstring and Phase O's WP51 intro:
qualities (WP8) and contacts (WP9) each compute their own `karma_cost` today with nothing that sums
them into a running total, and Phase O (not yet built) is what will eventually do that properly.
Per the Implementation Plan's own WP46 text ("no technical dependency on Phase O's unified ledger,
but wire into it if that phase ships first"), added `chummer5.engine.spirits.provisional_karma_
budget(quality_karma_cost, contact_karma_cost) -> int` — `STARTING_KARMA` (25, core rulebook p. 64,
cross-checked against the Step Four worked example) minus whatever the two existing Karma-spending
selections have already cost. Deliberately shaped to match Phase O's own WP51 intro's sketch
(`starting_karma - Σ every known Karma-spending selection's cost`) so retrofitting once WP51 lands
is a rename, not a redesign — documented explicitly in the function's own docstring as a stand-in to
be retired then, not a permanent second Karma-tracking mechanism.

### 2026-07-21 — `Character` gains a wrapping `bound_spirit_selection` field, not the Plan's own bare
`tuple[BoundSpirit, ...]` sketch

The Implementation Plan's own WP46 text sketches `Character` gaining `bound_spirits: tuple[
BoundSpirit, ...]` directly. Deviated from that in favor of a wrapping `BoundSpiritSelection`
(`spirits`, `karma_cost`, `karma_budget`), mirroring `SpellSelection`'s identical shape — the karma
totals need to be re-displayed (picker screen, character sheet) without recomputing them from the
raw list every time, the same reason `SpellSelection` wraps `spells` with its own `budget` field
instead of being a bare tuple.

### 2026-07-21 — `force` is never persisted (save format or `Character`'s stored `BoundSpirit`
values are the only place it appears, and even those can go stale)

Since Force is always the *live* Magic rating rather than a value fixed at binding time, storing it
in `CharacterSave` would just be redundant, staleness-prone data (the same "don't persist a derived
value" precedent `metatype_qualities` already set in WP23) — `CharacterSave.bound_spirit_picks` only
carries `(spirit_type, services)` pairs; `build_character` resolves `force` fresh against the fully-
built `Character` at load time. The one place a stale `force` snapshot *can* still appear is a live,
uncommitted browser session: `BoundSpirit.force` is captured at selection-submission time and isn't
automatically recomputed if a later, separate attribute edit changes Magic without resubmitting the
Bound Spirits form. Decided this was an acceptable, explicitly-documented limitation rather than
building a full `_relink_bound_spirit_selection` recompute-on-every-carry-forward mechanism (unlike
Contacts, which *does* recompute on every carry-forward since its karma cost has no hard cap to
violate) — the WP19-style staleness warning (`spirit_budget_warning`) already surfaces a "no longer
fits" message if a later edit invalidates the *count*/*budget*, and the character sheet template
deliberately reads `character.attribute_value("MAG")` live for its own `force` display rather than
trusting the stored snapshot, so the one visible place a player actually looks always shows the
correct number regardless.

### 2026-07-21 — Bound Spirits gets its own chargen section, not folded into Contacts

The Implementation Plan's own text floats folding into "the existing contacts UI" as one option.
Rejected in favor of a new peer section (`_spirit_selection.html`, `/ui/spirits`), placed directly
after Spells/Powers in `_chargen_body.html` — Bound Spirits is a Magician-only chargen extra with
the identical "gate on `magic_type`" shape Spells/Powers already have, not a mundane-universal step
the way Contacts is; grouping it with the other two magic-specific sections keeps the page's section
order matching the rulebook's own chargen step order (Talent → Spells/Powers → Bound Spirits →
Qualities → Contacts → ...) better than wedging it into an unrelated, always-present section would.

### 2026-07-21 — A real bug caught by the web-level round-trip test, not the engine-level ones:
`_character_save_from_session` never threaded `bound_spirit_picks` through at all

The engine-level (`chummer5.engine.spirits`) and `save_format.py`-level (`build_character`) tests
all passed on the first try. The save/load *web* test (`test_save_load_round_trip_preserves_bound_
spirits`) initially failed with an empty `bound_spirit_picks` in the downloaded save — traced to
`chummer5.web.app._character_save_from_session` (the function that turns a live `ChargenSession`
into a `CharacterSave` for `GET /character/save`), which I had correctly wired for `build_character`'s
*read* path but forgotten on this, its *write* path. A reminder that this project's "selections, not
derived values" save format has two independent threading sites per new field (`build_character`
reads a `CharacterSave` back into a `Character`; `_character_save_from_session` does the reverse),
and only exercising one in isolation doesn't prove the other — the same class of gap a save/load
*round-trip* test (not two one-directional tests) exists specifically to catch.

## Design decisions

- **New module, `chummer5.engine.spirits`, not folded into `chummer5.engine.magic`.** `magic.py` is
  already ~500 lines covering Magic type/rating/tradition, the Talent free-skill grant, spells, and
  powers; Bound Spirits is its own self-contained SR5 chargen decision with no shared state beyond
  reading `character.tradition`/`attribute_value`, the same "own module" precedent `chummer5.engine
  .lifestyle` set relative to `chummer5.engine.resources`.
- **`provisional_karma_budget` takes the two raw `karma_cost` ints, not a `Character`.** Mirrors
  `create_resources_selection`'s `lifestyle_cost`/`cyberware_cost` parameters (each caller resolves
  the *other* selection's own already-computed cost) rather than this function reaching into
  `character.quality_selection`/`.contact_selection` itself — keeps it composable and trivially
  testable in isolation.
- **`create_bound_spirit_selection` takes `character` directly** (unlike `create_spell_selection`/
  `create_power_selection`, which take plain budgets), because it needs two character-derived reads
  (`attribute_value("CHA")` for the count cap, `attribute_value("MAG")` for Force, and `.tradition`
  for the offered-types gate) that have no sensible single-number stand-in the way a spell/power
  budget does — matches the Implementation Plan's own sketched signature.
- **Binding two spirits of the same type is allowed** (no dedup check) — confirmed as a real,
  legal SR5 purchase (distinct individual spirits), unlike a quality or skill pick.
- **`<spirits>` (bound spirits) is deliberately not imported from legacy `.chum5` at all** —
  `LegacyCharacter` gained no new parsing for this WP. Flagged in `chummer5.io.legacy_import`'s
  module docstring as a documented, deliberate gap (mirroring the Availability-cap precedent:
  "flagged, not scheduled") rather than upgraded to the excluded-and-reported tier WP28 gave
  spells/powers, since no currently-importable fixture is affected either way (Miko is rejected
  before reaching this point for an unrelated reason; Wesson is an Adept and never has any).

## Implementation

- `src/chummer5/data/traditions.py`: `Tradition` gains `spirits: SpiritAffinities` (`combat`,
  `detection`, `health`, `illusion`, `manipulation`, plus an `offered_types` property), parsed from
  `<spirits>`'s 5 children via a new `_parse_spirits` helper.
- `src/chummer5/engine/spirits.py` (new): `STARTING_KARMA` (25), `KARMA_PER_SERVICE` (1),
  `provisional_karma_budget`, `offered_spirit_types`, `BoundSpirit` (`spirit_type`, `force`,
  `services`), `BoundSpiritSelection` (`spirits`, `karma_cost`, `karma_budget`), `create_bound_
  spirit_selection` (validates: empty picks always fine; non-empty requires `character.tradition`;
  count ≤ CHA; each type ∈ offered types; each `services ≥ 1`; total Karma ≤ budget).
- `src/chummer5/engine/character.py`: `Character` gains `bound_spirit_selection: BoundSpiritSelection
  | None = None`; a new `TYPE_CHECKING`-only import.
- `src/chummer5/io/save_format.py`: `CharacterSave` gains `bound_spirit_picks: tuple[BoundSpiritPickPair,
  ...] = ()` (JSON round-tripped, `force` never persisted — see Log); `create_character_save` gains
  the matching parameter; `build_character` resolves `bound_spirit_selection` last, against the
  now-fully-populated `Character` (needs `magic_type`/`tradition`/`magic_rating`/`magic_attribute_
  points` already attached for `attribute_value("CHA"/"MAG")` to resolve correctly), via one extra
  `replace()` after the main selection-attaching one.
- `src/chummer5/io/legacy_import.py`: new module-docstring paragraph documenting the deliberate
  non-import of `<spirits>` — no code changes (default `()` already means "not imported").
- `src/chummer5/web/app.py`: `MAX_BOUND_SPIRIT_ROWS` (10, mirrors `MAX_CONTACT_ROWS`'s fixed-row
  precedent); `_parse_bound_spirits` (mirrors `_parse_contacts`); `_spirit_selection_context`
  (mirrors `_spell_selection_context`, gated to Magician only, plus a WP19-style `spirit_budget_
  warning`); `POST /ui/spirits` route; `_replace_committed_talent` resets `bound_spirit_selection`
  to `None` on any Talent change (mirroring `spell_selection`/`power_selection`); `submit_attributes`
  carries `bound_spirit_selection` forward by plain reference (no relink helper needed — a bound
  spirit produces no Improvement); `_chargen_body_context` folds in `spirit_ctx` and its own staleness
  flag; `_character_sheet_context` gains `bound_spirit_rows` (Force shown *live*, not the stored
  snapshot — see Log) and `bound_spirit_karma_cost`; `_character_save_from_session` gains `bound_
  spirit_picks` (the bug caught by the round-trip test — see Log).
- `src/chummer5/web/templates/_spirit_selection.html` (new): mirrors `_spell_selection.html`'s
  shape — gated `{% if character.magic_type == "Magician" %}`, a fixed-row spirit-type/services
  table, a Karma-spent/budget line.
- `src/chummer5/web/templates/_chargen_body.html`: includes `_spirit_selection.html` after
  `_power_selection.html`.
- `src/chummer5/web/templates/_character_sheet.html`: new "Bound Spirits" list + Karma-cost line
  inside the existing Magic section.

## Outcome

WP46 complete. `chummer5.engine.spirits` adds Bound Spirits as roster entries plus a Karma-budget
check, exactly per the Implementation Plan's own scope cut (no spirit stat block/skills/powers):
Force is always the caster's live Magic rating, count is capped by Charisma, cost is 1 Karma per
service, and which spirit types are even offered is read fresh off the character's tradition's
`<spirits>` affinity mapping (now parsed for the first time by `chummer5.data.traditions`) — Hermetic
and Shamanic each offer a different 5 of the rulebook's 6 core types. No unified Karma ledger exists
yet (Phase O), so this WP adds its own small, explicitly-provisional `provisional_karma_budget`
stand-in (`25 - quality_karma_cost - contact_karma_cost`) shaped to match Phase O's own anticipated
formula, rather than either blocking on that phase or inventing a second, competing mechanism.
Native save/load threads `(spirit_type, services)` pairs through the normal mechanical path without
ever persisting Force (always re-resolved live); legacy `.chum5` import deliberately doesn't parse
`<spirits>` at all yet, documented as a flagged-not-scheduled gap with no live fixture impact. As
this WP's own acceptance criteria anticipated, no real fixture in the corpus exercises Bound Spirits
at all (neither of Phase I's two magic fixtures has any) — every test here is synthetic/hand-verified
against the rulebook table and traditions.xml directly, the same honesty standard WP25's own
two-fixture limitation set. `pytest`/`ruff`/`mypy` are all green (672 tests, 37 more than before this
WP). Phase M continues with WP47 (Foci) next, sequenced before the much larger WP48 (Mentor Spirits)
per the Plan's own ordering.
