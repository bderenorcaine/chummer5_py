# WP49 — Knowledge & Language skills

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase N, WP49 (first WP in the phase).

## Goal

Let a player spend the free Knowledge/Language point budget — `(Intuition + Logic) x 2` per the
rulebook (Step Five, p. 89) — on freeform-named Knowledge skills and Language skills, including the
one free native language every character gets (plus a second if Bilingual is taken).

## Log

### 2026-07-23 — Rulebook research: the free-point formula, native-language rule, and the max
rating cap, all confirmed via `pdftotext -layout` before writing any code

Extracted "Purchase Skills"/"Knowledge and Language Skills" (p. 88-90). Confirmed exactly what the
Implementation Plan's own WP49 entry already claimed: `(INT + LOG) * 2` free points, one native
language free (a second with Bilingual), max rating 6 at chargen (the same cap
`chummer5.engine.skills.MAX_SKILL_RATING_CREATE` already defines for Active skills — reused
directly, not redefined), Language skills linked to Intuition. Full citations in
`spec/rulebooks/learnings.md`'s new WP49 entry.

### 2026-07-23 — Category naming: `legacy/Chummer/data/skills.xml` says "Interest" (singular), the
rulebook prose says "Interests" (plural) — followed the data file

`skills.xml`'s own `<categories type="knowledge">` list has exactly 5 entries: Academic, Interest,
Language, Professional, Street. Every real `.chum5` fixture's `<skillcategory>` field agrees with
this spelling. `chummer5.data.knowledge.KNOWLEDGE_CATEGORIES` uses "Interest" (singular), matching
this project's established "match the data over rulebook prose" precedent rather than the table
header's plural. Language is deliberately not one of the 4 `KnowledgeCategory` entries — it's its
own `LanguageSkillPick` shape (native-language handling has no analogue in the other 4 categories),
mirroring the data file's own even split (4 Knowledge categories + Language as a distinct 5th).

### 2026-07-23 — A real correction to the Implementation Plan's own text: Bilingual was
`NOT_YET_SUPPORTED`, not "already offered"

The Plan's WP49 entry says "`chummer5_py`'s existing Bilingual quality already grants a second free
[native language]... confirm this quality's Improvement actually feeds into this budget once it
exists, since it was inert with respect to Knowledge/Language points before this WP" — phrasing that
assumes Bilingual was already a real, offerable, `FLAT_BONUS` quality with an inert *effect*, just
missing a consumer. Checked directly: `chummer5.data.qualities.load_qualities()` classified
Bilingual's own `<bonus><nativelanguagelimit>1</nativelanguagelimit></bonus>` as
`NOT_YET_SUPPORTED` — it was never in WP22's 14-quality offered catalog at all, the same "unsupported
shape, excluded entirely" treatment every other not-yet-classified quality gets. The bonus shape
itself is the identical bare-numeric-leaf pattern the Indomitable trio (WP22) already established,
so classifying it was a small, mechanical addition — but a real, previously-missing one, not a
pre-existing capability this WP merely had to wire up. Fixed by:
- Renaming `chummer5.data.qualities._LIMIT_BONUS_TAGS` to `_GLOBAL_BONUS_TAGS` and adding
  `"nativelanguagelimit": "native_language_limit"` alongside the 3 existing Limit tags (same
  bare-numeric-leaf, global-target shape).
- Adding `ImprovementType.NATIVE_LANGUAGE_LIMIT` (11th member) and
  `"native_language_limit": ImprovementType.NATIVE_LANGUAGE_LIMIT` to
  `chummer5.engine.qualities._TARGET_KIND_TO_IMPROVEMENT_TYPE`.

This makes Bilingual `FLAT_BONUS` and therefore automatically offerable through the existing
`mvp_quality_catalog` filter — no special-casing needed, unlike Mentor Spirit (WP48). Raised the
MVP-offered quality catalog from 14 to 15; `tests/unit/test_qualities.py`'s
`test_supported_vs_unsupported_counts_are_visible` and `tests/unit/test_quality_selection.py`'s
`test_mvp_quality_catalog_is_exactly_the_fourteen_offerable_qualities` both had their hardcoded
counts corrected (7 `FLAT_BONUS` not 6, 81 `NOT_YET_SUPPORTED` not 82; 15-quality set not 14).

### 2026-07-23 — A real fixture-provenance finding: no Priority-built fixture in the corpus marks a
native language at all

While cross-checking the design against real data (Miko/Wesson/Yeti's own `<knoskills>`), found that
none of the three carries a single `<isnativelanguage>` tag anywhere. Traced this in the legacy C#:
`SkillsSection.cs` has a "Legacy sweep for native language skills" migration, gated on
`LastSavedVersion <= 5.212.72`, that synthesizes a native-English entry at *load* time for any older
save with none marked — an in-memory fixup this project's read-only `.chum5` parser never runs (all
three fixtures save at 5.202.x, well under that threshold). Concretely: Yeti's own "English" entry
is recorded at `<base>0</base>` with no native marker at all (clearly her native language by cost,
but unrecoverable as such from the raw file); Wesson has no "English" entry whatsoever. This isn't a
parsing gap to fix — it's what the file actually contains. `chummer5.io.legacy_chum5
.LegacyKnowledgeSkill.native` still parses `<isnativelanguage>` faithfully (default `False` when
absent), matching this parser's established "what the save literally says" contract. Full trace in
`spec/rulebooks/learnings.md`'s WP49 entry.

This also caught a real bug during test-writing: an early version of `chummer5.io.legacy_import`'s
`base <= 0` skip (borrowed from the Active-skill import precedent, where `base <= 0` always means
"nothing to import") dropped a *marked*-native Language entry too, since a real native pick
legitimately has `base == 0` by design (see `LanguageSkillPick`'s own docstring: native fluency
isn't a numeric rating). Fixed by keeping any `native=True` entry regardless of `base`, and only
applying the `base <= 0` skip to non-native entries and to Knowledge-category entries (which are
never native). Caught by `test_native_language_flag_reaches_the_built_character`
(`tests/unit/test_legacy_import.py`) before it ever reached a real fixture.

### 2026-07-23 — Yeti achieves full round-trip import success, the best fixture coverage this WP
gets; Miko/Wesson cross-checked directly instead

`Yeti-#ffffff2.chum5` (this project's sole mundane Priority-built fixture) has 5 real `<knoskills>`
entries and imports end-to-end through `import_chum5()` unchanged by this WP's new code, spending
her entire 22-point `(INT 5 + LOG 6) * 2` budget exactly (4 real Language/Professional entries,
after her own unmarked "English" native entry is excluded per the finding above) —
`tests/integration/test_legacy_import_fixtures.py`'s `test_imports_yeti_end_to_end` extended with

Shinto; Wesson: a karma-bought EDG point, WP28's own finding), so their own `<knoskills>` data is
cross-checked directly against `create_knowledge_selection` in a new
`tests/integration/test_knowledge_fixtures.py` instead — the same "read the raw fixture, build a
`Character` by hand, verify the formula" pattern WP26/WP29 already established when the full import
path can't be exercised end to end.

### 2026-07-23 — Design decision: `chummer5.engine.knowledge` is a new sibling module, not folded
into `chummer5.engine.skills`

Knowledge/Language skills are freeform (no catalog to validate names against) and funded from a
wholly separate budget (`(INT+LOG)*2`, not a Skills-priority-letter pool) — a genuinely different
mechanism from Active-skill allocation, not a variant of it. Mirrors `chummer5.data.mentors`/
`chummer5.engine.foci`'s own "fresh module when the shape is genuinely different" precedent rather
than widening an existing one. `KnowledgeSkillPick`/`LanguageSkillPick` mirror
`chummer5.engine.resources.Contact` exactly: a player-authored pick, not a catalog selection, since
a Knowledge/Language skill's name is the player's own invention.

### 2026-07-23 — Web layer: `knowledge_selection` is a plain carried-forward field, no relink
helper needed

Unlike quality/metatype/Talent/cyberware/bioware/foci selections, Knowledge/Language grants no
`Improvement` of its own — it only *consumes* Bilingual's `NATIVE_LANGUAGE_LIMIT` bonus (already
re-landed by the existing `_relink_quality_improvements` call). So it belongs in the same "plain
`dataclasses.replace` carry, no relink" bucket as `skill_allocation`/`resources_selection`/
`lifestyle_selection`/`bound_spirit_selection` in `submit_attributes`'s final `replace(...)` call —
confirmed by reading those functions' own docstrings before adding the new keyword, not by guessing
at the pattern. `_knowledge_selection_context` re-runs `create_knowledge_selection` fresh on every
render (when no fresh submission error) to surface a WP19-style "no longer fits" warning if an
attribute edit shrinks INT/LOG below what's already spent — the identical precedent
`_skill_allocation_context`/`_spirit_selection_context` already established, verified against a real
test (`test_reconfirming_a_lower_attributes_budget_flags_the_existing_knowledge_spend`) rather than
assumed to work by analogy alone.

## Design decisions

- **`chummer5.data.knowledge` is a new module, not part of `chummer5.data.skills`** — parses no XML
  catalog at all (Knowledge/Language skills are freeform by rulebook design), so it holds only
  reference data (category names/linked attributes/suggested examples) for the picker UI, not a
  loader.
- **Category names match `skills.xml`'s own spelling** (`Interest`, singular), not the rulebook
  prose's plural — see Log.
- **`KnowledgeSkillPick`/`LanguageSkillPick` mirror `Contact`'s "player-authored, no catalog" shape**
  exactly, including reusing `chummer5.engine.skills.MAX_SKILL_RATING_CREATE` directly rather than
  redefining a duplicate constant.
- **A native language's `rating` must be exactly `0`, enforced by `create_knowledge_selection`** —
  native fluency isn't a numeric rating (the character sheet marks it "N"), so forcing `0` keeps
  `points_spent`'s sum correct with no separate "ignore this field for native picks" special case.
- **Bilingual's `NATIVE_LANGUAGE_LIMIT` Improvement gets its own `ImprovementType` member (11th)**,
  resolved against the same `_GLOBAL_TARGET` sentinel the Limit trio/Drain Resistance/Essence
  already use — one native-language cap per character, the same "character-wide total" shape as
  those.
- **Active-skill points funding Knowledge/Language spend (rulebook p. 88) is deliberately not
  modeled** — this WP only implements the separate, unconditional `(INT+LOG)*2` pool, mirroring
  `chummer5.engine.skills`'s own "Karma-bought skill points are out of scope" precedent for a
  similar cross-funding gap.
- **Cyberware/bioware-boosted INT/LOG are read via the ordinary `attribute_value(...)` call**, same
  as `chummer5.engine.resources` already does for CHA/contact points — the rulebook says augmented
  attributes shouldn't affect this budget (p. 90), but nothing in this engine's current scope ever
  produces an `ATTRIBUTE` bonus targeting INT/LOG, so the distinction has no observable effect yet
  (verified directly, not assumed) — same "real rule, currently unobservable" note `resources.py`
  already carries for CHA.
- **`_knowledge_selection_context`/`knowledge_selection` participate in the WP19-style staleness
  aggregate** (`priority_stale_selections`) alongside every other carried-forward selection.

## Outcome

WP49 complete. `chummer5.data.knowledge`/`chummer5.engine.knowledge` add Knowledge & Language skill
selection — the `(INT+LOG)*2` free-point budget, freeform Knowledge/Language picks, and native-
language handling (1 free, +1 with Bilingual) — as a genuinely new mechanism (freeform names, a
separate budget) rather than a variant of Active-skill allocation. Along the way, this WP corrected
a real error in its own Implementation Plan entry (Bilingual was `NOT_YET_SUPPORTED`, not already
offered — now fixed and offered, raising the MVP quality catalog from 14 to 15) and surfaced a real
fixture-provenance finding (no Priority-built fixture in the 34-file corpus ever marks a native
language, since all three predate the legacy engine's own `<isnativelanguage>` field) that a test
caught as a real bug before it reached any fixture (a native pick's legitimate `base == 0` was
briefly indistinguishable from "nothing to import"). `Yeti-#ffffff2.chum5` achieves full
`import_chum5()` round-trip success spending her entire 22-point budget exactly — the strongest
fixture coverage available for this WP — while Miko/Wesson's own data is cross-checked directly
against the engine formula since neither achieves a full round-trip import for reasons unrelated to
this WP. `pytest`/`ruff`/`mypy` are all green (816 tests total, up from 770: 20 in
`test_knowledge.py`, 8 in `test_knowledge_data.py`, 7 in `test_web_knowledge.py`, 3 in
`test_knowledge_fixtures.py`, plus new/updated cases across `test_save_format.py`,
`test_legacy_import.py`, `test_legacy_chum5.py`, `test_legacy_import_fixtures.py`,
`test_qualities.py`, and `test_quality_selection.py`). Phase N's other WP (WP50, skill
specializations) is next.
