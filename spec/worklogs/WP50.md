# WP50 — Skill specializations (Step Five: skill-point-funded)

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase N, WP50 (second and final WP in
the phase).

## Goal

Let a player spend 1 skill point (from the same Skills-priority budget WP7 already tracks) to add
one specialization to an individually-purchased skill, wiring up the `+2` dice-pool bonus that
already existed in the engine (`chummer5.engine.skills.dice_pool`'s `specialized` parameter) but had
no purchase mechanism, budget accounting, or UI before this WP.

## Log

### 2026-07-23 — Rulebook research: cost, one-per-skill cap, and the group-breaking restriction,
confirmed via `pdftotext -layout` before writing any code

Extracted both "Purchase Skills" (Step Five, p. 88) and the Skills chapter's own "SPECIALIZATIONS"
section (p. 129). Confirmed exactly what the Implementation Plan's own WP50 entry already claimed: 1
skill point per specialization, at most one per skill at creation, and — the restriction worth
double-checking rather than assuming — a skill group cannot be specialized in Step Five at all
("buying a specialization for a skill within a skill group... breaks that group... this cannot
happen in Step Five of character creation — you can only break up a skill group... in Step Seven").
The Skills chapter adds the other half: "If you want a specialization in a skill, you have to have
it first (meaning a Rating of at least 1)." Full citations in `spec/rulebooks/learnings.md`'s new
WP50 entry.

### 2026-07-23 — Both real fixtures spend their entire Skills budget once specializations are
counted in, not approximately — an unusually strong data point

Cross-checked `create_skill_allocation`'s new budget math (`skill_points` spend + 1 per
specialization) against `Yeti-#ffffff2.chum5` and `Miko.chum5`, this project's only two real
skill-allocation fixtures. Both land exactly on their Skills-C budget of 28: Yeti at 23 individual
points + 5 specializations, Miko at 25 individual points + 3 specializations. Neither is a
coincidence produced by this WP's own math — both totals come straight from the raw `.chum5` data —
so this is real (if circumstantial) confirmation that the legacy engine really does charge 1 skill
point per specialization from the same pool, not a separate budget this project might otherwise have
missed.

### 2026-07-23 — A real specialization-drop case, found in Yeti's own data: a specialization
recorded for a skill this engine never actually imports

While building the Yeti fixture cross-check, found her Computer skill carries a real "Matrix
Perception" specialization (`<spec>Matrix Perception</spec>`) — but Computer's own `<base>` is 0,
only `<karma>` is nonzero, so Computer itself never reaches `skill_points` at all (this project's
pre-existing "karma-bought skill points are out of scope" cut, from WP7, unrelated to this WP).
A specialization can't be imported for a skill this engine never actually granted her, so it's
excluded and reported via a new `ImportResult.dropped_specializations` (mirroring the
`dropped_skills`/`dropped_qualities` precedent) rather than either crashing or silently vanishing.
5 of Yeti's 6 recorded specializations (Compiling/Cybercombat/Hacking/Registering/Software) import
cleanly; only Computer's is dropped.

### 2026-07-23 — A near-miss: `WP49.md`'s own citation of a Miko "specialization" turned out to be a
weapon's `<spec>`, not a skill's

While hunting for a specialization to test against, `grep`-ing `Miko.chum5` for `<spec>` initially
turned up `<spec>Staves</spec>` — the exact string WP49's own worklog cited as "a real specialization
(`<spec>Staves</spec>`)". Checked directly: that `<spec>` sits inside a `<weapon>` element (a Staff's
own weapon-category tag, unrelated to skill specialization), not inside `<newskills><skills><skill>`.
Miko's *real* skill specializations are a different 3 entries entirely (Etiquette/Tea Ceremonies,
Spellcasting/Manipulation, Summoning/Plant Spirit) — confirmed by resolving each entry's `<suid>`
against the skill catalog. WP49's citation was therefore a false positive that happened not to matter
for that WP (WP49 never actually used the `<spec>` data), but is worth correcting here since this WP
is the one that actually reads it. No code was affected — this was caught before any test was
written against the wrong data.

### 2026-07-23 — `dice_pool`'s `specialized` parameter changed from a plain `bool` default to an
auto-detecting `bool | None`, not left as a manual per-call-site lookup

The Implementation Plan's own text says to "wire the existing `dice_pool(..., specialized=...)`
parameter to read from this new selection instead of always defaulting to `False`" — read literally,
that could mean either changing every call site to compute `skill.id in allocation.specializations`
itself, or changing `dice_pool`'s own default to do that lookup once. Chose the latter:
`specialized: bool | None = None`, and when unset, `dice_pool` reads `skill.id in
allocation.specializations` itself. This is a stricter reading of "wire the parameter to read from
the selection" (the function does the reading, not each caller), removes a repeated lookup from three
different call sites (`_skill_allocation_context`, `_character_sheet_context`, and any future one),
and stays fully backward compatible — every existing test that passed an explicit `True`/`False`
(`test_dice_pool_specialization_adds_bonus_only_at_positive_rating`,
`test_dice_pool_specialization_ignored_for_exotic_skills`) is untouched, since an explicit value still
overrides the default.

### 2026-07-23 — Import: specializations resolved as a second pass over `legacy.skills`, not folded
into the existing `skill_points`-building loop

The existing loop (`chummer5.io.legacy_import.import_legacy_character`) does `if legacy_skill.base <=
0: continue` early, before a skill is known to have reached `skill_points`. Folding specialization
resolution into that same loop would mean checking a not-yet-fully-known `skill_points` dict mid-
build. A second pass, run after `skill_points` is finalized, is simpler and matches exactly what the
drop condition actually needs to check ("is this skill's id already in the finished `skill_points`
dict"). Also handles, defensively (no fixture in the 34-file corpus needs it, confirmed by grepping
every `.chum5` for a skill with more than one recorded `<spec>`): a second-or-later specialization on
one skill is dropped and reported the same way, since this project — like the rulebook's own Step
Five rule — only models one specialization per skill.

## Design decisions

- **`SkillAllocation.specializations` is `dict[skill_id, name]`**, mirroring `skill_points`/
  `group_points`'s own keying — encodes "at most one specialization per skill" for free (a dict can't
  have two values for one key), with no separate uniqueness check needed.
- **Validation lives entirely in `create_skill_allocation`, not a separate function** — a
  specialization's only two preconditions (nonblank name; `skill_points.get(skill_id, 0) >= 1`) both
  reduce to checks already natural to make alongside the existing `skill_points`/`group_points`
  validation, and the budget math (`skills_spent = sum(skill_points.values()) +
  len(specializations)`) is one line added to the existing check rather than a parallel budget.
- **`dice_pool`'s `specialized` parameter auto-detects from the allocation** (see Log) — `None` means
  "look it up," an explicit `True`/`False` still overrides.
- **The specialization's name is freeform player-authored text, not a catalog entry** — SR5 doesn't
  enumerate valid specialization names (only example ones, e.g. "Axes" for Blades), mirroring
  `chummer5.engine.knowledge.KnowledgeSkillPick`'s identical "no catalog, the player invents it"
  shape from WP49.
- **`CharacterSave.specializations` is a plain `{skill_id: name}` mapping, not a flattened tuple of
  triples** — unlike WP49's `KnowledgeSkillPickTriple`/`LanguageSkillPickTriple` (which need a third
  field per entry), a specialization is already exactly a `str -> str` mapping with nothing else to
  carry, so the extra flattening step WP49 needed for JSON-safety isn't needed here.
- **A dropped specialization is reported via a new `ImportResult.dropped_specializations`**, not
  folded into `dropped_skills` — a specialization can be unimportable for a reason that has nothing
  to do with its host skill being unresolvable (group-purchased, karma-only), so conflating the two
  would lose the distinction between "this skill doesn't exist" and "this skill exists but wasn't
  imported."
- **Step Seven's Karma-funded specialization / group-breaking case is explicitly out of this WP's
  scope** — the rulebook itself frames it as a different step's mechanic (see Log), and it depends on
  Phase O's unified Karma ledger (WP51), which doesn't exist yet. Scoped as WP53 per the Implementation
  Plan.

## Implementation

- `src/chummer5/engine/skills.py`: `SkillAllocation.specializations: MappingProxyType[str, str] =
  MappingProxyType({})` (new field); `create_skill_allocation` gains a `specializations` parameter
  (default `{}`), validating each entry (known skill id, nonblank name, `skill_points.get(id, 0) >=
  1`) and folding `len(specializations)` into the existing skill-point budget check; `dice_pool`'s
  `specialized` parameter changed from `bool = False` to `bool | None = None`, auto-detecting from
  `allocation.specializations` when unset.
- `src/chummer5/web/app.py`: `_parse_specializations` (new, mirrors `_parse_points`); `_skill_
  allocation_context` gains a `specializations` parameter, threading it into the throwaway preview
  `SkillAllocation`, the re-validation call, and `skills_remaining`'s count; `submit_skills` parses
  and passes `specializations` through; `_character_sheet_context`'s `skill_rows` gain a
  `specialization` key; `_character_save_from_session` threads `allocation.specializations` through.
- `src/chummer5/web/templates/_skill_allocation.html`: new "Specialization" column (free-text input
  per individually-purchased skill).
- `src/chummer5/web/templates/_character_sheet.html`: new "Specialization" column on the skills
  table.
- `src/chummer5/io/save_format.py`: `CharacterSave.specializations` (new field, defaults `{}`);
  `create_character_save`/`_save_to_dict`/`_dict_to_save` threading; `build_character` passes
  `save.specializations` into `create_skill_allocation`.
- `src/chummer5/io/legacy_import.py`: a new second pass over `legacy.skills` (after `skill_points` is
  finalized) resolving `specializations`/`dropped_specializations`; `ImportResult.dropped_
  specializations` (new field); both threaded through `create_character_save`/`ImportResult(...)`.
  `chummer5.io.legacy_chum5.LegacySkill.specializations` already existed (parsed, unused before this
  WP) — no changes needed there.

## Outcome

WP50 complete — the last WP in Phase N. `chummer5.engine.skills` now models Step Five's skill-point-
funded specialization end to end: 1 skill point per specialization, capped at one per skill, forbidden
on a skill whose rating comes from a purchased group (the rulebook's own "this cannot happen in Step
Five" restriction, enforced for free by the pre-existing "strict skill groups" rule rather than a new
check), wired straight into the `+2` dice-pool bonus that already existed in the engine but had no
purchase mechanism before this WP. Both real skill-allocation fixtures in the corpus (`Yeti-
#ffffff2.chum5`, `Miko.chum5`) land exactly on their Skills-C budget once specializations are counted
in — strong, if circumstantial, confirmation of the cost model — and Yeti's own data additionally
exercises a real drop case (a specialization recorded for a karma-only skill this engine never
imports), caught and reported via a new `ImportResult.dropped_specializations` rather than silently
dropped or mis-applied. Along the way, corrected a small provenance error in WP49's own worklog (a
cited "specialization" was actually an unrelated weapon field). `pytest`/`ruff`/`mypy` are all green
(832 tests total, up from 816). Phase N (expanded skill support) is now complete — both WP49
(Knowledge/Language skills) and WP50 (specializations) are done. Phase O (unified Karma ledger and
Karma-funded chargen spend, WP51-54) is next on the Implementation Plan.
