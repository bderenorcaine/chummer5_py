# WP51 — Unified Karma ledger

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase O, WP51 (first WP in the phase,
foundational for WP52-54).

## Goal

Give `Character` a single running "Karma remaining" value that every Karma-spending selection
(qualities, contacts, Bound Spirits, Foci today; attribute/skill/spell purchases in WP52-54) reads
from together, replacing the several independent one-shot checks that existed before this WP —
most concretely, `chummer5.engine.spirits.provisional_karma_budget`, a deliberately-temporary
stand-in WP46/WP47 built and explicitly flagged for retirement once this WP landed.

needed by this WP, but recorded in `spec/rulebooks/learnings.md`'s new WP51 entry so WP53 doesn't

recomputing the raw `positive_karma - negative_karma` arithmetic behind them directly against the
"Worked example — Choosing Qualities" passage, rather than trusting the already-transcribed totals
in `character_creation_chapter.md` alone.

### 2026-07-23 — The real shape was already half-built: `chummer5.engine.spirits.provisional_karma_
budget` and its 4-term sum

Reading WP46/WP47 before writing any code: both had already anticipated this WP directly.
`provisional_karma_budget(quality_karma_cost, contact_karma_cost, bound_spirit_karma_cost=0,
foci_karma_cost=0)` was explicitly documented as "a minimal, deliberately-temporary stand-in... at
which point this function should be retired in favor of the real one" — and its shape (sum of every
known selection's own already-computed `karma_cost`, subtracted from `STARTING_KARMA`) was already
exactly the WP51 intro's own suggested design. This made the actual design decision easy: promote
that same sum to a computed property directly on `Character` (`karma_spent`/`karma_remaining`),
since every summand is already a validated, frozen selection's own resolved cost — nothing to
incrementally track, cheap to recompute character-sized on every read, matching the Project
Overview's "reconstruct wholesale to validate" principle for jointly-constrained values. `STARTING_
KARMA` moved from `chummer5.engine.spirits` to `chummer5.engine.character` (its new one home) and is
re-exported from `chummer5.engine.spirits` for backward compatibility — nothing outside this WP's own
diff needed to change its import.

### 2026-07-23 — Retiring `provisional_karma_budget` simplified more call sites than expected: two
web-layer parameters turned out to be redundant with `character` itself

`_spirit_selection_context`'s `foci_karma_cost` parameter and `_foci_selection_context`'s
`bound_spirit_karma_cost` parameter were, at every call site, always exactly `character.foci_
selection.karma_cost`/`character.bound_spirit_selection.karma_cost` (or `0` if uncommitted) for the
same `character` already being passed as the first argument — the caller was manually re-deriving a
value the ledger now makes redundant. Removed both parameters; each function now reads the *other*
section's current commitment directly off `character` itself. This dropped ~25 lines of
caller-side plumbing across `_character_context`, `submit_spirits`, and `submit_foci` with no
behavior change (verified by an end-to-end manual walkthrough, see Manual verification below).

### 2026-07-23 — The re-validation budget still needs "add back this section's own current cost",
not a bare `character.karma_remaining`

`karma_remaining` sums *every* committed selection, including the one about to be re-validated. Using
it bare as the budget for, say, a new Bound Spirit submission would double-subtract the old Bound
Spirit spend (once already inside `karma_remaining`, again when the new pick is checked against it).
Both `_spirit_selection_context`/`_foci_selection_context` and both `submit_spirits`/`submit_foci`
handlers therefore compute `character.karma_remaining + <this section's own currently-committed
cost>` as the budget passed to `create_bound_spirit_selection`/`create_foci_selection` — the same
"exclude this section's own prior commitment" shape the pre-WP51 `provisional_karma_budget` calls
already had, just expressed as an addition back onto the unified sum instead of an omitted term.
`chummer5.io.save_format.build_character`'s one-shot reconstruction needed no such adjustment: its
fixed evaluation order (Bound Spirits resolved before `bound_spirit_selection` is attached to
`character`, Foci resolved after) means `character.karma_remaining` at each point already excludes
the not-yet-attached section by construction — a straight swap for the old `provisional_karma_
budget(...)` calls, no arithmetic change needed.

## Design decisions

- **`karma_spent`/`karma_remaining` are computed properties on `Character`, not stored fields or a
  separate `chummer5.engine.karma` module function.** Matches the Implementation Plan's own
  recommendation and the same "reconstruct wholesale to validate" principle every other
  jointly-derived `Character` value already follows (`attribute_value`, `power_points`,
  `magic_essence_loss`). No circular-import cost: the property only reads `.karma_cost` off
  already-declared (TYPE_CHECKING-only-imported) selection fields, never imports their classes at
  runtime.
- **`STARTING_KARMA` moved from `chummer5.engine.spirits` to `chummer5.engine.character`**, its new
  canonical home, re-exported from `spirits` (`__all__`) so `tests/unit/test_spirits.py`'s existing
  `from chummer5.engine.spirits import STARTING_KARMA` needed no change.
- **`provisional_karma_budget` is fully removed, not deprecated in place** — its own docstring
  already called out this exact retirement as the point of its existence; keeping a redundant
  wrapper around `Character.karma_remaining` would just be dead code with no caller left needing it.
  Its own 3 direct unit tests (`test_provisional_karma_budget_*` in `test_spirits.py`) are removed
  rather than ported, since they tested the retired function's own arithmetic, not a still-existing
  behavior — the equivalent (and, for the "exceeds starting Karma" case, expanded to all three
  James/Rob/Kyra worked examples rather than just James) coverage now lives in
  `tests/unit/test_character.py`'s new karma-ledger section.
- **Both `_spirit_selection_context`/`_foci_selection_context` lost a parameter each** (`foci_karma_
  cost`/`bound_spirit_karma_cost`) rather than keeping them for backward compatibility — both were
  private, module-internal helpers (not part of any public API), and every call site's argument was
  already exactly what the function can now derive from its own `character` parameter. WP18-style
  pure restructuring: no test needed a behavior change, only fewer lines threading an already-derivable
  value through.
- **The "add back this section's own committed cost" idiom is inlined at 4 call sites, not factored
  into a shared helper.** Each site's exact "which section" differs (Bound Spirits reads its own
  `bound_spirit_selection`, Foci reads its own `foci_selection`), and the resulting one-liner
  (`character.karma_remaining + own_committed_cost`) is short enough that a 3-line helper function
  would be more machinery than the thing it replaces — consistent with this project's "don't
  introduce an abstraction below the size where it pays for itself" default.

## Implementation

- `src/chummer5/engine/character.py`: `STARTING_KARMA = 25` (moved from `spirits.py`, cited to
  rulebook p. 64 and the Step Four worked examples); `Character.karma_spent`/`karma_remaining`
  (new computed properties, summing `quality_selection`/`contact_selection`/`bound_spirit_
  selection`/`foci_selection`'s own `karma_cost` fields); new class-docstring paragraph explaining
  the design and citing the James/Rob/Kyra cross-check.
- `src/chummer5/engine/spirits.py`: `provisional_karma_budget` removed; `STARTING_KARMA` now
  imported from `chummer5.engine.character` and re-exported via `__all__`; module docstring updated.
- `src/chummer5/engine/foci.py`: module docstring's Karma paragraph updated to reference `Character
  .karma_remaining` instead of the retired stand-in.
- `src/chummer5/io/save_format.py`: `build_character`'s two `provisional_karma_budget(...)` calls
  replaced with `character.karma_remaining` (the fixed evaluation order already in place needed no
  other change); docstring/comment updates.
- `src/chummer5/web/app.py`: `provisional_karma_budget` import removed; `_spirit_selection_context`
  loses its `foci_karma_cost` parameter (reads `character.foci_selection` directly), `_foci_
  selection_context` loses its `bound_spirit_karma_cost` parameter (reads `character.bound_spirit_
  selection` directly); both now compute their re-validation `karma_budget` as `character.karma_
  remaining + <own section's currently-committed cost>`; `_character_context`, `submit_spirits`,
  `submit_foci` updated to match (net removal of the now-redundant `bound_spirit_karma_cost`/`foci_
  karma_cost_committed` local variables and their threading).

  now-slimmer context functions produce identical HTML for every scenario those suites already cover.

Manual end-to-end walkthrough via `TestClient` (this project's established proxy for a browser):
confirmed Human/Magician, bound a Spirit of Fire for 20 services (20 Karma of 25), then confirmed a
Force-2 Alchemical Focus (6 Karma) is correctly rejected ("exceeds the Karma budget" — 20+6=26 > 25)
while a Force-1 Alchemical Focus (3 Karma) is accepted (20+3=23 <= 25); re-opened the Bound Spirits
form afterward and confirmed its shown budget correctly excludes its *own* prior 20-Karma commitment

other's" cross-validation logic this WP's retrofit depends on, through the real HTTP flow rather than
only unit-level.
