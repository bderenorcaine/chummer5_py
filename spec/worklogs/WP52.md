# WP52 — Karma-funded attribute increases

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase O, WP52 (depends on WP51's
unified Karma ledger).

## Goal

Let leftover Karma raise a Mental/Physical/Special (EDG) attribute beyond its priority-derived
budget, using the rulebook's `new Rating x 5` formula (Step Seven / Character Advancement). Also
the fix for the specific, previously-flagged gap in Project Overview's 2026-07-19 entry
("Karma-bought attribute points... never modeled... Wesson's own `<attribute name="EDG"><base>1
</base><karma>1</karma></attribute>`").

## Log

### 2026-07-23 — Rulebook research: the Karma Advancement Table formula (already confirmed by
WP51) plus the "only one at natural maximum" restriction, re-extracted directly

WP51's own research pass (previous WP, same session range) already confirmed the `new Rating x 5`
attribute formula against the "KARMA ADVANCEMENT TABLE FOR ATTRIBUTES" (p.106-107) — reused
directly here rather than re-extracting. What WP51 didn't need and this WP does: Step Seven's own
text (`pdftotext -f 100 -l 101 -layout`), which restates a restriction from Step Two specifically
for Karma spend: "Only one attribute can be at the natural attribute limit... These rules still
apply to when you are spending Karma." Step Two's fuller statement (p.99, already in
`character_creation_chapter.md`): "Characters at character creation may only have 1 Mental or
Physical attribute at its natural maximum limit — Magic, Edge, and Resonance are not included in
this limitation." Recorded in `spec/rulebooks/learnings.md`'s new WP52 entry, along with a
cross-check of the legacy engine's own `Attribute.Core.cs`'s `UpgradeKarmaCost` property (confirms
`(current_rating + 1) x KarmaAttribute`, i.e. exactly `new_rating x 5` under Standard settings,
with the `AlternateMetatypeAttributeKarma` discount house rule off by default).

### 2026-07-23 — The "only one at natural maximum" rule was never implemented anywhere, contradicting
the Implementation Plan's own phrasing

The Plan's own WP52 entry reads as though this restriction already applied elsewhere in the engine
("confirmed this restriction explicitly still applies to Karma-funded increases too"). `grep` across
`src/` found zero hits for anything resembling it — `chummer5.engine.character.create_character`
(WP6) has never validated it for the ordinary priority-point path. Checked whether this is a live,
exploitable gap against the one priority-build fixture that could exercise it
(`Yeti-#ffffff2.chum5`): her highest primary attribute (LOG) is 5 against a metatype maximum of 6 —
never reaches it, so the gap has been silently harmless throughout WP6-WP51. Decision: enforce the
rule inside WP52's own new `create_karma_attribute_points`, but do not retrofit `create_character`
itself — a different function's job, not in scope for an attribute-*Karma*-spend WP, flagged
explicitly in `create_karma_attribute_points`'s own docstring "Scope note" rather than silently
assumed away.

### 2026-07-23 — Enforcing the rule unconditionally broke an existing, legal WP19 regression test —
caught before commit, not after

First implementation checked "at most one `PRIMARY_ATTRIBUTES` code at its natural maximum" across
the *entire* candidate character on every call, including calls with an empty or EDG-only
`karma_points`. `chummer5.web.app.submit_attributes` calls `create_karma_attribute_points` on
*every* attribute-form submission (not just Karma-spending ones), purely to re-validate whatever
Karma spend is already committed against the newly-submitted priority-point spend. This meant a
perfectly legal pure-priority submission that happens to raise more than one Mental/Physical
attribute to its metatype cap — a real, existing test case
(`tests/unit/test_web_attribute_skill_allocation.py::test_reconfirming_priorities_with_a_lower_
attributes_budget_flags_the_existing_spend`, which spends BOD/AGI/REA all up to Human's natural
maximum of 6 via priority points alone) — started failing the moment attributes were resubmitted
with no Karma involved at all. Fixed by only running the natural-maximum check when the *submitted*
`karma_points` itself contains a nonzero `PRIMARY_ATTRIBUTES` entry (an empty or EDG-only
`karma_points` skips it entirely) — this also matches the Scope-note decision above: a character
that already has two-plus Mental/Physical attributes at maximum from priority spend alone is left
alone unless *this* Karma spend is what would add a second one. Pinned down as a permanent
regression test (`test_create_karma_attribute_points_does_not_retroactively_check_pure_priority_
spend`), not just fixed and forgotten.

### 2026-07-23 — Attempting Wesson.chum5's end-to-end import: still blocked, but by a new, unrelated
gap this WP's own research uncovered

The Implementation Plan's WP52 acceptance text expected `Wesson.chum5` (this project's one real
Adept fixture, previously blocked by WP28's blanket karma-bought-attribute check) to finally reach a
clean `import_chum5()` round-trip once this WP landed. It doesn't. His real EDG Karma-buy (rating
3 → 4) legitimately costs 20 Karma (`(3 + 1) x 5`, confirmed against the legacy engine's own formula
above) — his real character could afford it because his real `<qualities>` block includes `SINner
(Corporate Limited)`, a Negative quality worth Karma value -15 (a +15 Karma credit). SINner isn't,
and per WP22's own scoping ruling never will be, one of this project's MVP-offered qualities
(background-check/social-consequence narrative weight, not a chargen-time computed value). Every
unsupported quality a legacy import drops was already silently losing its Karma-cost side effect
before this WP (WP8's "excluded, not silently mis-applied" rule already implied this for the
*selection itself*, just not obviously for its Karma arithmetic) — nothing was Karma-budget-sensitive
enough for the loss to actually block an import until this WP added a Karma-spending consumer
expensive enough to need it. Confirmed by direct calculation: without SINner, Wesson's reconstructed
`character.karma_remaining` before the EDG purchase is 15 (`25 - 10` for the one MVP-offered quality
he keeps, Guts); the purchase itself costs 20; with SINner's real -15 Karma value included it would
be 30, comfortably enough.

This is the same situation WP28 hit for Miko one WP earlier (Implementation Plan's own acceptance
text expecting a clean import, corrected by that WP's own research) — followed the identical
pattern: corrected the module docstring and the fixture test to assert the new, honest failure mode
(a plain `ValueError` bubbling out of `build_character`'s own `create_karma_attribute_points` call,
not the itemized `UnsupportedLegacyCharacterError` WP28's now-retired check used to raise), and added
a "direct engine construction" test
(`test_wesson_karma_funded_edg_increase_via_direct_engine_construction`) proving this WP's actual
deliverable against his real numbers in isolation, the same precedent WP28 established for his Drain
Resistance/`power_points`. Fixing SINner's exclusion is out of this WP's scope — flagged in Project
Overview's Open Questions rather than silently worked around or silently left undocumented.

## Design decisions

- **`KarmaAttributeSelection` is a new wrapping-selection field
  (`Character.karma_attribute_selection`), not a bare mapping folded into `attribute_points`.**
  Mirrors `BoundSpiritSelection`/`FociSelection`'s shape (wraps the picks alongside an
  already-resolved `karma_cost`, so a render never has to recompute it) rather than
  `magic_attribute_points`' flat-int shape — this selection needs to report its own cost into
  `Character.karma_spent`, which a bare `MappingProxyType` field couldn't do without a parallel
  cost-tracking field anyway.
- **`karma_advancement_cost(start_rating, points, karma_per_rating)` is a small, shared,
  parameterized helper in `chummer5.engine.character`**, not attribute-specific — its
  `karma_per_rating` parameter is what lets WP53 (Karma-funded skills, 2/rating; skill groups,
  5/rating; Knowledge/Language, 1/rating) reuse it directly rather than re-deriving the same
  cumulative-sum shape three more times.
- **MAG/RES are deliberately excluded from `create_karma_attribute_points`**, even though
  `ALLOCATABLE_ATTRIBUTES` is the only set it validates against and the rulebook's own Karma
  Advancement Table nominally covers Magic/Resonance under the identical formula. MAG already has
  its own, separately-built mechanism for post-Talent growth (`create_magic_attribute_points`,
  spending Special Attribute Points, not Karma) and extending Karma-funded growth to it would need
  to interact with WP35's Essence-driven Magic-loss formula in a way no current fixture exercises —
  deliberately not attempted, per this project's "don't build past what's asked or verified"
  discipline. See `KarmaAttributeSelection`'s own docstring.
- **The "only one at natural maximum" check only fires when the submitted `karma_points` itself
  touches a `PRIMARY_ATTRIBUTES` code** — not whenever the finished character happens to have two
  maxed Mental/Physical attributes regardless of source. See the Log's own "caught before commit"
  entry above for why this isn't just a theoretical nicety.
- **Resolved in `build_character`/`submit_attributes` right after quality/contact selections are
  attached, before Bound Spirits** — Bound Spirits' own budget (`character.attribute_value("CHA")`)
  is one of `PRIMARY_ATTRIBUTES`, so it must see any Karma-funded CHA increase already applied, the
  same fixed-evaluation-order discipline WP46/WP47 already established for their own shared-budget
  interactions.
- **`legacy_import.py`'s `_blocking_reasons` keeps a narrower, MAG-only version of WP28's old
  blocking check**, rather than removing it outright — MAG's own `<karma>` field still can't be
  represented (see the MAG/RES exclusion above), so it still needs to block, just under a more
  specific message than before.

## Implementation

- `src/chummer5/engine/character.py`: `ATTRIBUTE_KARMA_PER_RATING = 5`;
  `karma_advancement_cost(start_rating, points, karma_per_rating)` (new, shared helper);
  `KarmaAttributeSelection` (new frozen dataclass: `points`, `karma_cost`);
  `create_karma_attribute_points(character, karma_points, karma_budget)` (new — validates
  allocatability, non-negative spend, metatype maximum, the natural-maximum rule, and the Karma
  budget); `Character.karma_attribute_selection: KarmaAttributeSelection | None = None` (new
  field); `Character.attribute_value` widened to add `karma_attribute_selection.points.get(code,
  0)`; `Character.karma_spent` widened with a matching `karma_attribute_selection.karma_cost` term.
- `src/chummer5/io/save_format.py`: `CharacterSave.karma_attribute_points: MappingProxyType[str,
  int]` (new field, defaults to `{}`); threaded through `create_character_save`/`_save_to_dict`/
  `_dict_to_save`; `build_character` resolves `karma_attribute_selection` via `create_karma_
  attribute_points` right after quality/contact selections are attached (before Bound Spirits — see
  Design decisions).
- `src/chummer5/io/legacy_import.py`: `_blocking_reasons`'s old blanket karma-bought-attribute
  check narrowed to MAG only; `import_legacy_character` now reads `legacy.attributes[code].karma`
  for `ALLOCATABLE_ATTRIBUTES` into a new `karma_attribute_points` dict, threaded into `create_
  character_save`.
- `src/chummer5/web/app.py`: `_attribute_allocation_context` gains a `karma_points` parameter (plus
  `karma_budget`/`karma_remaining` in its returned context) and re-validates a committed Karma
  spend via `create_karma_attribute_points` in its existing WP19-style re-validation block;
  `submit_attributes` parses `karma_attr_{code}` form fields, validates them, and attaches the
  resulting `karma_attribute_selection` to the committed `Character`; `_character_context`/
  `_character_save_from_session` thread `karma_attribute_selection.points` through for rendering
  and for save/download respectively.
- `src/chummer5/web/templates/_attribute_allocation.html`: a second "Karma points" input column
  (`karma_attr_{code}`) alongside the existing priority-point one, plus a "Karma remaining for
  attribute increases" line.

## Outcome

WP52 complete. Leftover Karma can now raise a Mental/Physical/Edge attribute beyond its
priority-derived budget, validated against the unified Karma ledger (WP51), the metatype maximum,
and SR5's "only one Mental/Physical attribute at natural maximum" rule — reachable through the web
UI (a new Karma-points column on the attribute allocation screen), the save format, and legacy
import. The specific `Wesson.chum5` karma-bought-EDG blocking reason this WP set out to fix (Project
Overview's 2026-07-19 entry) is gone, but the fixture still can't reach a full end-to-end import —
a second, unrelated Karma-ledger gap (his real `SINner` quality's Karma credit, lost because that
quality isn't MVP-offered) this WP's own research surfaced and documented rather than silently
worked around. `pytest`/`ruff`/`mypy` are all green (849 tests total, +15 net from WP51's 834).
WP53 (Karma-funded skill/skill-group increases, including the group-breaking specialization case)
is next on the Implementation Plan.
