# WP53 — Karma-funded skill/skill-group increases (including group-breaking)

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase O, WP53 (depends on WP51's
unified Karma ledger and WP50's skill-point-funded specialization mechanism).

## Goal

Let leftover Karma raise an Active skill (`new Rating x 2`), Active skill group (`new Rating x 5`),
or Knowledge/Language skill (`new Rating x 1`) beyond its priority-derived budget, and implement the
rulebook's Step Seven rule that a skill group can be "broken" — one member raised or specialized
individually, the rest staying at the group's own rating — a transition WP50 explicitly excluded
from Step Five.

## Log

### 2026-07-24 — Rulebook research: the group-breaking rule has two independent triggers, not one

WP50's own worklog (and WP51's research pass) had already banked the flat 7-Karma specialization
cost and the `new Rating x 2`/`x 5`/`x 1` formulas from the "KARMA ADVANCEMENT TABLE FOR SKILLS"/
"CHARACTER IMPROVEMENT TABLE" (p.106-107). What was still open: WP50's own citation (p.88) frames
group-breaking purely as a consequence of buying a specialization — re-reading the same passage in
full (`pdftotext -layout`) surfaced a second sentence WP50 hadn't quoted: "If the character wishes
to break up the skill group during game play and raise only one of the skills, he is free to do so,
but may not raise those skills as a skill group again until all skills possess the same rating." A
plain Karma-funded rating raise on one group member — no specialization at all — breaks the group
exactly the same way. `create_karma_skill_selection` treats *both* `karma_skill_points` and
`karma_specializations` entries targeting a group member as breaking that member's group, not
specialization alone. Also chased the passage's own "see p.98 for details" cross-reference and
confirmed (via `pdftotext -f 98/-f 100 -l 98/100`) that raw PDF page numbers run exactly 2 ahead of
the book's own printed footers in this range — printed p.98 is raw page 100, the same "STEP SEVEN"
opening WP51/WP52 already extracted, with no further group-breaking detail beyond what the two Step
Five citations (WP50's and this WP's) already say. Full citations in `spec/rulebooks/learnings.md`'s
new WP53 entry.

### 2026-07-24 — No fixture in the 34-file corpus exercises any of this — confirmed, not assumed

Re-checked directly: neither `Yeti-#ffffff2.chum5` nor `Miko.chum5` (this project's only two real
skill-allocation fixtures) has a skill/group `<karma>` value representing genuine Step-Seven Karma
spend — Yeti's own nonzero `<karma>` entries (Compiling, Computer) are the pre-existing "karma-bought
skill points are out of scope" cut WP7's own docstring already flags, not new territory this WP
unblocks. The whole mechanism — including the group-breaking transition specifically — is
hand-verified against the rulebook text directly, per this phase's own honesty standard (the
Implementation Plan's own WP53 acceptance text anticipated this).

### 2026-07-24 — Two selections, not one: Knowledge/Language Karma spend can't live in
`chummer5.engine.skills` without a circular import, and shouldn't share a `Character` field with
Active skills anyway

`chummer5.engine.knowledge` already imports `MAX_SKILL_RATING_CREATE` from `chummer5.engine.skills`
(a real, pre-existing one-directional dependency) — `skills.py` importing back from `knowledge.py`
to build one consolidated Karma-spend selection would make that circular. More importantly, Active
skill/group/specialization Karma spend and Knowledge/Language Karma spend are submitted through two
different web forms/routes (`POST /ui/skills` vs. `POST /ui/knowledge`) — a single shared `Character`
field that either route replaced wholesale would let one route's submission silently clobber the
other's already-committed Karma spend. Split into two independent selections instead:
`chummer5.engine.skills.KarmaSkillSelection` (Active skills/groups/specializations, including
`broken_groups`) and `chummer5.engine.knowledge.KarmaKnowledgeSelection` (Knowledge/Language, keyed
by pick name since those have no catalog id — see that module's own opening paragraph). Both are new
`Character` fields (`karma_skill_selection`, `karma_knowledge_selection`), both feed
`Character.karma_spent` with one more additive term each.

### 2026-07-24 — `skill_rating`/`dice_pool` read `character.karma_skill_selection` directly, not as
a parameter — and the broken-group rating math turned out to be one clean three-way branch

Mirrors how `skill_rating` already reads `character.improvements` directly rather than taking an
`ImprovementIndex` parameter. The three cases (group intact and Karma-topped-up; group broken, this
skill's own frozen-group-rating-plus-individual-Karma; plain individually-tracked skill) all reduce
to "compute a combined group rating if the group isn't broken, else 0" followed by "group rating if
positive, else the broken-group member's own math, else the ordinary individual math" — no separate
code path was needed per case beyond that one `if`/`elif`/`else`.

## Design decisions

- **`KarmaSkillSelection.broken_groups` is derived, not player-submitted** — computed inside
  `create_karma_skill_selection` from whichever `karma_skill_points`/`karma_specializations` keys
  target a skill whose group already has `character.skill_allocation.group_points` spent. A group
  referenced by *both* `karma_group_points` (funding it as a whole) and one of the two breaking
  inputs in the same submission is rejected outright as a real conflict, not silently resolved
  either way.
- **`KARMA_SPECIALIZATION_COST` (7, flat) applies uniformly** — to both the group-breaking case and
  an ordinary specialization on an already-individually-tracked skill (the Character Improvement
  Table doesn't distinguish the two; only the group-breaking *consequence* differs, not the price).
- **A fresh Karma-funded skill group (0 priority points, entirely Karma-funded) is validated against
  the same "strict skill groups" rule priority spend already has** — rejected if any member already
  carries individually-spent points (priority or Karma), mirroring `create_skill_allocation`'s own
  check rather than leaving a new, Karma-specific gap.
- **The web layer's live preview calls the real `create_karma_skill_selection`/
  `create_karma_knowledge_selection` against a deliberately huge budget (`10**9`)**, not a
  hand-rolled parallel cost calculation — unlike `_attribute_allocation_context`'s simpler per-
  attribute formula, the group-breaking logic is genuinely stateful (which groups are broken depends
  on which skills are targeted), so re-deriving it by hand in the web layer risked drifting from the
  engine's own logic. Only a genuine structural failure (unknown id, breaking/funding conflict,
  already-specialized, unbought skill) suppresses the preview overlay; "over budget" never does,
  since the huge budget absorbs it — the real budget re-validation (with the real budget) runs
  separately in the existing WP19-style `if error is None` block.
- **`_parse_karma_points_by_name` is a fresh pass over the raw form, not reused output from
  `_parse_knowledge_skills`/`_parse_languages`** — those two compact out blank-named rows, so pairing
  a Karma field with the compacted list by index would misalign the moment an earlier row is blank.
  Reading `{prefix}{i}`/`{karma_prefix}{i}` together, keyed by name, sidesteps the whole problem.
- **`karma_skill_selection`/`karma_knowledge_selection` carry forward by plain reference wherever
  `skill_allocation`/`knowledge_selection` already do** (`submit_attributes`'s fresh-`Character`
  rebuild) — neither Karma-funded selection produces its own `Improvement` (a Karma-funded rating
  increase is a pure number, not something the Improvement engine resolves), and neither depends on
  an attribute value, only on the sibling selection it extends, which is already carried forward.

## Implementation

- `src/chummer5/engine/skills.py`: `KARMA_SKILL_PER_RATING` (2), `KARMA_SKILL_GROUP_PER_RATING` (5),
  `KARMA_SPECIALIZATION_COST` (7, flat); `KarmaSkillSelection` (new frozen dataclass:
  `skill_points`, `group_points`, `specializations`, `broken_groups`, `karma_cost`);
  `create_karma_skill_selection(character, skills, karma_skill_points, karma_group_points,
  karma_specializations, karma_budget)` (new — full validation per the module's own docstring);
  `skill_rating`/`dice_pool` updated to read `character.karma_skill_selection` directly.
- `src/chummer5/engine/knowledge.py`: `KARMA_KNOWLEDGE_PER_RATING` (1); `KarmaKnowledgeSelection`
  (new frozen dataclass: `points`, `karma_cost`); `create_karma_knowledge_selection(character,
  karma_points, karma_budget)` (new — resolves a name against `character.knowledge_selection`,
  rejecting an unknown/ambiguous/native name).
- `src/chummer5/engine/character.py`: `Character.karma_skill_selection`/`karma_knowledge_selection`
  (new fields, `None` until committed); `karma_spent` widened with both terms; new TYPE_CHECKING
  imports.
- `src/chummer5/web/app.py`: `_skill_allocation_context`/`submit_skills` gain
  `karma_skill_points`/`karma_group_points`/`karma_specializations` parameters/parsing
  (`karma_skill_{id}`/`karma_group_{name}`/`karma_spec_{id}` form fields, submitted alongside the
  existing ones); `_knowledge_selection_context`/`submit_knowledge` gain `karma_points` (parsed via
  new `_parse_karma_points_by_name` from `knowledge_karma_{i}`/`language_karma_{i}`); both context
  builders gain `karma_budget`/`karma_remaining`; `_chargen_body_context`'s initial-render wiring and
  `submit_attributes`'s carried-forward-selection block updated to match;
  `_character_sheet_context`'s skill-row `specialization` falls back to a Karma-funded one, and its
  knowledge/language rows add `karma_knowledge_points` on top of the free-point-funded base;
  `_character_save_from_session` threads all four new fields into `create_character_save`.
- `src/chummer5/io/save_format.py`: `CharacterSave` gains `karma_skill_points`/`karma_group_points`/
  `karma_specializations`/`karma_knowledge_points` (all default `{}`); threaded through
  `create_character_save`/`_save_to_dict`/`_dict_to_save`; `build_character` resolves both new
  selections right after `karma_attribute_selection` (same Step Seven ledger) and before Bound
  Spirits.
- `src/chummer5/web/templates/_skill_allocation.html`: new "Karma pts" column (groups + individual
  skills) and "Karma spec" column (individual skills), plus a "Karma remaining for skills" summary
  line.
- `src/chummer5/web/templates/_knowledge_skills.html`: new "Karma pts" column (both tables), plus a
  "Karma remaining for knowledge/language" summary line.
- `src/chummer5/web/templates/_character_sheet.html`: new "Skill/skill-group karma cost"/
  "Knowledge/language karma cost"/"Karma remaining" lines in the existing Karma section.

## Outcome

WP53 complete. Leftover Karma can now raise an Active skill, Active skill group, or Knowledge/
Language skill beyond its priority-derived budget, and — the phase's own distinguishing mechanic —
either an individual Karma-funded raise or a Karma-funded specialization on a group-purchased skill
permanently breaks that group from that point forward, exactly matching the rulebook's own two-
trigger framing (confirmed by a closer reading of the same Step Five passage WP50 already cited,
which turned out to describe a second, independent trigger WP50 itself never needed). Knowledge/
Language Karma spend is a separate, sibling selection (`KarmaKnowledgeSelection`) rather than folded
into the Active-skill one, both for import-graph reasons (`chummer5.engine.knowledge` already depends
on `chummer5.engine.skills`, not the reverse) and because the two are submitted through different web
forms. No fixture in the corpus exercises any of this Step Seven mechanic — every number is
hand-verified against the rulebook directly, consistent with this phase's own honesty standard.
`pytest`/`ruff`/`mypy` are all green (893 tests total, +44 net from WP52's 849). WP54 (Karma-funded
extra spells/complex forms) is next on the Implementation Plan.
