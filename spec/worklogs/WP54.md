# WP54 — Karma-funded extra spells/complex forms

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase O, WP54 (depends on WP51's
unified Karma ledger and WP26's `create_spell_selection`).

## Goal

Let a Magician spend leftover Karma (5 Karma/spell, per the Additional Purchases table) on spells
beyond their Talent option's free grant, up to the rulebook's combined "Magic Rating x 2" known-
spells cap. Complex Forms are Technomancer-only content, permanently out of scope per the Project
Overview, so this WP is Magician-only, exactly as the Implementation Plan's own entry flags.

## Log

### 2026-07-24 — Rulebook research: the Additional Purchases table's "Spells" row, re-extracted
directly

Extracted via `pdftotext -f 100 -l 100 -layout` (raw PDF page 100 = printed p. 98, per WP53's own
footer-offset finding): "Spells — Karma Cost (at character creation): 5 Karma per spell —
Restriction: Maximum number of spells/rituals/preparations known at Character Creation equals
Magic Rating x 2." Confirms both numbers the Implementation Plan's own entry already claimed
exactly — no correction needed, unlike WP52/WP53's own research passes. Full citation in
`spec/rulebooks/learnings.md`'s new WP54 entry, including the one real trap the table's wording
exposes: the x2 cap governs the *total* known spells (`len(spell_ids)`), not the Karma-funded
portion alone — capping only the overflow would let a high-free-budget Talent option (Miko's 10 at
letter A) exceed her own Magic-6-derived cap of 12 if some other, hypothetical option ever granted
more than 12 for free. Confirmed neither of this phase's two real fixtures (Miko, Wesson) exercises
Karma-funded spells at all — both already match their free grant exactly (Miko: 6 of her 10-budget
spells resolve at all, the rest non-SR5; Wesson is an Adept, no spell budget) — so, like WP53's
group-breaking case, this mechanism is hand-verified against the rulebook text directly.

### 2026-07-24 — Design: overflow-based Karma funding, not an explicit per-item flag

`create_spell_selection` already took a flat `spell_ids` list with no per-item metadata (unlike
`chummer5.engine.skills.create_karma_skill_selection`'s explicit `karma_skill_points` mapping,
needed there because skills have *ratings* to fund incrementally). A spell has no rating — it's
either known or not, and every spell costs the identical 5 Karma once bought — so there's nothing
for a per-item "is this one Karma-funded" flag to usefully distinguish; only the *count* beyond
`budget` matters for cost/cap purposes. Widened the function to derive `karma_spell_count = max(0,
len(spell_ids) - budget)` from the pick list itself, rather than asking the caller (or the web
form) to partition picks into two separate lists. This also means `CharacterSave`/the save format
need no new field at all — `spell_ids` alone, unchanged in shape, already round-trips a Karma-
funded pick correctly.

### 2026-07-24 — A real correctness trap caught before commit: an Adept's own nonzero Magic rating
must not reach the new cap check

First pass wired `create_spell_selection`'s new `magic_rating` parameter to whatever the caller's
"finished Magic rating" was, unconditionally. This is wrong for an Adept: non-mystic Adepts never
cast spells at all (confirmed via WP46's own citation, p. 308: "adepts still need the appropriate
licenses to purchase magical goods or cast spells if they are that rare hybrid, the mystic adept"),
but an Adept's own `attribute_value("MAG")` is very much nonzero (Wesson's is 4) — passing it
through would have let an Adept "know" up to `magic_rating * 2` spells via Karma, with nothing to
stop them, exactly the gap `budget=0`'s old bare rejection used to close for free. Fixed by treating
`magic_rating` the same as `budget` in every non-Magician call site: 0 unless `magic_type ==
"Magician"`, not the character's real rating. `chummer5.io.save_format.build_character`'s own
`spell_magic_rating` local variable makes this explicit (`0` unless `magic_selection.magic_type ==
"Magician"`, mirroring `spell_budget`'s existing identical gating) rather than leaving it implicit
in caller behavior.

### 2026-07-24 — `build_character`'s fixed evaluation order: `spell_selection` has to move, not just
widen in place

`create_spell_selection`'s new `karma_budget` parameter needs `character.karma_remaining` to
already reflect every other committed Karma spend so far, the same "next Step Seven spend sees the
prior ones' cost already reflected" rule WP52/WP53 established. But `spell_selection` was originally
resolved (WP26/WP28) in the Magic-selection block, *before* `build_character`'s one big
`dataclasses.replace()` call that attaches `quality_selection`/`contact_selection`/etc. to
`character` — at that point in the function, `character.karma_remaining` would still read as the
full, un-decremented `STARTING_KARMA`, silently over-crediting the budget. Moved the actual `create_
spell_selection` call to right after `karma_knowledge_selection` is resolved and attached (the same
zone WP52/WP53's own Karma spends already occupy) — `spell_budget`/`spell_magic_rating` themselves
stay computed in their original location, since neither depends on the Karma ledger. Caught by
reasoning through the evaluation order directly (mirroring the same trap WP52/WP53's own worklogs
flagged for their own call sites) rather than by a failing test — no fixture exercises this path,
so a silent over-credit here would not have been caught by the existing suite at all.

### 2026-07-24 — Web layer: no new form field, but a genuinely new staleness source WP54 itself
introduces

`_spell_selection_context`/`submit_spells` needed no new form input (the existing `spell_id`
checkbox list already carries whatever's Karma-funded, per the overflow design above) — just a
wider `create_spell_selection` call and new Karma-cost/remaining display fields, mirroring
`_skill_allocation_context`'s "Karma pts" column precedent but without a new column, since there's
nothing per-row to input. One thing this WP does newly introduce: `spell_selection` is carried
forward unchanged across an attribute-form resubmission (`_relink_magic_selection`, pre-existing),
but an attribute edit can now genuinely invalidate it two new ways — lowering Special-Attribute-
Point-funded MAG shrinks the Magic-Rating-x2 cap, and spending more Karma elsewhere shrinks `karma_
remaining` out from under an already-committed Karma-funded spell. Added the same WP19-style
`spell_budget_warning` re-validation `_spirit_selection_context`/`_foci_selection_context` already
carry for their own analogous Karma-budget dependency, rather than leaving this newly-possible
staleness silently unsurfaced.

## Design decisions

- **Overflow-based Karma funding** (`karma_spell_count = max(0, len(spell_ids) - budget)`), not an
  explicit per-item Karma flag — see the Log's own reasoning; a spell has no rating to fund
  incrementally, only a count.
- **`magic_rating` is caller-resolved, explicitly 0 for non-Magician**, mirroring `budget`'s
  existing identical convention — `create_spell_selection` still has no `magic_type` parameter of
  its own (WP26's original design choice, unchanged), so correctness here depends on every caller
  passing 0 for both `budget` and `magic_rating` together for Adept/Mundane, not on the function
  detecting the mismatch itself. Documented explicitly in the function's own docstring and in
  `build_character`'s inline comment, not left implicit.
- **No new `CharacterSave` field.** `spell_ids` alone already round-trips a Karma-funded pick
  correctly, since which spells are "free" vs. "Karma-funded" is never tracked past the count used
  to compute cost — re-deriving `karma_spell_count`/`karma_cost` from `len(spell_ids)` and the
  current `budget` on every load produces the identical split every time.
- **`spell_selection`'s resolution moves in `build_character`**, from the Magic-selection block to
  right after `karma_knowledge_selection` — a real, if narrow, evaluation-order fix this WP's own
  Karma-budget dependency required; see the Log's own entry for why the original placement would
  have silently over-credited the budget.
- **The web-layer preview computes Karma cost directly (`max(0, len(ids) - budget) *
  KARMA_PER_SPELL`)**, not by calling `create_spell_selection` — unlike `_skill_allocation_
  context`'s group-breaking logic, spells have no stateful cross-pick interaction to get wrong by
  hand-deriving the formula, so the extra indirection of calling the real function for the preview
  buys nothing (mirrors `_attribute_allocation_context`'s identical choice for the simpler
  attribute-Karma formula).
- **A new WP19-style `spell_budget_warning`** on `_spell_selection_context`, calling the real
  `create_spell_selection` against the character's current state when a selection is already
  committed — added because WP54 itself is what makes `spell_selection` newly dependent on
  mutable state (`karma_remaining`, Special-Attribute-Point-funded MAG) that an attribute-form
  resubmission can change without resetting it, mirroring `_spirit_selection_context`'s identical
  pattern for the same underlying reason.

## Implementation

- `src/chummer5/engine/magic.py`: `KARMA_PER_SPELL` (5, new); `SpellSelection` widened with
  `karma_spell_count`/`karma_cost` fields; `create_spell_selection` widened with `magic_rating`/
  `karma_budget` parameters — replaces the old flat "total picked <= budget" rejection with a
  "Magic Rating x2" known-spells cap plus a Karma-budget check on whatever's picked beyond `budget`.
- `src/chummer5/engine/character.py`: `Character.karma_spent` gains a `spell_selection.karma_cost`
  term; class docstring's WP54 paragraph (no new field — widens the existing `spell_selection`).
- `src/chummer5/io/save_format.py`: `spell_selection`'s resolution moves from the Magic-selection
  block to right after `karma_knowledge_selection` (see Design decisions); `spell_magic_rating`
  local variable (0 unless Magician, mirroring `spell_budget`'s existing gating); `build_character`'s
  own docstring gains a WP54 paragraph explaining the move.
- `src/chummer5/web/app.py`: `_spell_selection_context` gains `magic_rating`/`karma_budget`-derived
  fields (`spell_max_known`, `spell_karma_cost`, `spell_karma_budget`, `spell_karma_remaining`) and
  a new `spell_budget_warning` (WP19-style re-validation); `submit_spells` computes and passes
  `karma_budget`/`character.attribute_value("MAG")` into the widened `create_spell_selection`;
  `_character_sheet_context` gains `spell_karma_cost`.
- `src/chummer5/web/templates/_spell_selection.html`: shows the free/Karma split, the known cap, and
  a Karma-remaining line; renders `spell_budget_warning` alongside the existing `spell_error`.
- `src/chummer5/web/templates/_character_sheet.html`: new "Spell karma cost" line in the existing
  Karma section.

## Outcome

WP54 complete. A Magician can now spend leftover Karma (5 Karma/spell) on spells beyond their
Talent option's free grant, up to the rulebook's combined "Magic Rating x 2" known-spells cap —
reachable through the web UI (the existing spell picker, now showing free/Karma-funded counts and a
Karma-remaining line), the save format (no schema change needed), and legacy-import-adjacent code
paths (`build_character`, used by both). Complex Forms stay out of scope (Technomancer, permanently
excluded). No fixture in the corpus exercises Karma-funded spells specifically — both real magic
fixtures already match their free grant exactly — so, consistent with WP53's own precedent, the
mechanism is hand-verified against the rulebook text directly. A real, evaluation-order bug (Karma
budget under-accounting) and a real correctness trap (an Adept's own nonzero Magic rating leaking
into the spell cap) were both caught during implementation, before either reached a test failure —
recorded in this worklog and `spec/rulebooks/learnings.md`'s new WP54 entry so a future WP touching
`build_character` or `create_spell_selection` again doesn't rediscover either from scratch.
`pytest`/`ruff`/`mypy` are all green (896 tests total, +3 net from WP53's 893 — 5 new engine tests, 1
new integration assertion, 2 web tests replacing 1). WP55 (SINner and the other selecttext-blocked
qualities) is next on the Implementation Plan.
