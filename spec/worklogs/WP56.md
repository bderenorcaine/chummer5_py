# WP56 — Character sheet: unmodeled-effects disclosure section

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase O, WP56 (sequenced after WP55 so
its own manual walkthrough could exercise a SINner-holding character too).

## Goal

Give Project Overview's "Unmodeled real effects" registry a player-facing home: a collapsible
character-sheet section listing, for whichever unmodeled-effect aspects the *current* character
actually has, the specific note from that registry — built generically across every aspect kind
`Character` can hold, not scoped to qualities and widened later, even though qualities are the only
kind with registry entries today.

## Log

### 2026-07-24 — Source-of-truth decision: per-dataclass field, not a standalone mapping module

The Plan's own "decide and document" instruction offered two shapes: (a) a field on each aspect's
own catalog dataclass (`Quality.unmodeled_effect_note`, mirroring how `BonusSupport` is already
classified in `chummer5.data.qualities`), or (b) one standalone `{aspect_name: note}` mapping every
catalog loader consults. Chose (a) — it's the identical pattern this project has already used twice
for exactly this kind of "verified property of a named catalog entry" fact (`NO_EFFECT`/
`SELECT_TEXT`'s own name-gated classification in WP22/WP55, `forbidden_names`'s general parse in
WP55), so there's no new mechanism to learn, and it keeps each catalog module self-contained (a
future WP adding this to `Power`/`Cyberware`/etc. touches only that module, not a shared file every
catalog has to import). Project Overview's own markdown table is confirmed, explicitly, to **not**
be read at runtime by either shape — this WP's `_UNMODELED_EFFECT_NOTES` dict in
`chummer5.data.qualities` is a hand-kept mirror of it, transcribed directly from the table (no new
`pdftotext` pass needed — every citation was already extracted and verified by WP22/WP23/WP55's own
research; this WP performs no new rulebook research, so no new `spec/rulebooks/learnings.md` entry
was added).

### 2026-07-24 — `unmodeled_effect_note` is independent of `bonus_support`/offerability

Resistance to Pathogens/Toxins (metatype-granted only, never player-purchasable, and
`NOT_YET_SUPPORTED` — its `<bonus>` block is a full resistance-test dice-pool grid this project
doesn't parse) still needs a note: WP23 grants it for free to Dwarf regardless of its
`bonus_support` classification, and its real effect (a Resistance Test bonus) is exactly the kind of
gap this registry exists to disclose. Confirmed this by checking its raw XML directly — a
`<hide/>` tag (legacy-UI-only, doesn't affect this loader) plus 8 sibling resist-type tags, none of
which `_classify_bonus` recognizes. `_UNMODELED_EFFECT_NOTES` is looked up by name independently of
`_classify_bonus`'s own verdict, so this "grantable-but-not-purchasable-and-not-even-classified"
case gets a note with no special-casing needed.

### 2026-07-24 — Generic walk via `getattr` duck-typing, not per-kind branching

The function (`chummer5.engine.derived.unmodeled_effect_notes`) still has to enumerate
`Character`'s own selection fields one by one (there's no way around that — the fields are what they
are), but the *classification* step — "does this aspect have a note" — is a plain
`getattr(item, "unmodeled_effect_note", None)` against whatever catalog object each field yields,
never an `isinstance`/kind check. This is what makes the function genuinely aspect-kind-agnostic per
the Plan's own requirement: when a future WP adds the identical field to `Power`/`Cyberware`/
`Bioware`/`Focus`/`LifestyleTier`/`StarterGearItem`/`Spell`, this function picks the new notes up
automatically with zero changes — proven by
`test_unmodeled_effect_notes_walks_other_selection_kinds_without_crashing`, which populates one real
item from each of those catalogs today (none of which carry the field yet) and confirms the walk
completes cleanly and contributes nothing.

Covered fields, beyond the Plan's own explicit list (`quality_selection`/`metatype_qualities`/
`power_selection`/`cyberware_selection`/`bioware_selection`/`foci_selection`/
`lifestyle_selection`): also walked `resources_selection.gear` (real, catalog-backed SR5 items),
`spell_selection.spells`, `bound_spirit_selection.spirits` (a bare `spirit_type: str` — `getattr` on
a plain string just returns `None`, so this costs nothing extra), and `quality_selection
.mentor_spirit.archetype` (also catalog-backed, also nameable). `skill_allocation`/
`contact_selection`/`knowledge_selection`/the Karma-spend selections (WP52-54) were deliberately
left out — a skill/contact/Knowledge pick isn't a *catalog* entry with its own SR5-rules identity
the way a Quality/Power/Cyberware item is (a contact's name is player-invented free text; a skill is
already a fully-modeled mechanic with nothing unmodeled to disclose), so walking them would only add
dead branches with no possible future payoff.

### 2026-07-24 — Empty-state: hide the section entirely

Decided (per the Plan's own "be explicit" instruction) that a character with zero unmodeled-effect
aspects (a plain Human with none of the 8 `NO_EFFECT`/9 `SELECT_TEXT` qualities) hides the `<details>`
block entirely, rather than rendering it collapsed-and-empty with placeholder text. Reasoning: the
section exists to flag gaps the player might otherwise not know about; an empty section adds visual
clutter for the common case (most builds) without informing anyone of anything. Confirmed via
`test_unmodeled_effects_section_hidden_for_plain_human`.

## Design decisions

- **`Quality.unmodeled_effect_note: str | None = None`** (new field, `chummer5.data.qualities`),
  populated via a new name-gated `_UNMODELED_EFFECT_NOTES` dict at parse time — the same mechanism
  `_VERIFIED_NO_EFFECT_NAMES`/`_VERIFIED_SELECT_TEXT_NAMES` already use, but independent of
  `bonus_support` (see Log). Covers all 17 of WP22/WP23/WP55's already-registered qualities
  (8 `NO_EFFECT` + 9 `SELECT_TEXT`) plus Resistance to Pathogens/Toxins (`NOT_YET_SUPPORTED`,
  metatype-granted only) = 18 entries, transcribed directly from Project Overview's table text.
- **`chummer5.engine.derived.unmodeled_effect_notes(character) -> tuple[tuple[str, str], ...]`** —
  a plain function alongside `initiative_value`/`physical_limit`/etc. (same "pure function of a
  finalized `Character`, meant for the character sheet" shape), not a `Character` property and not
  its own module — see Log for the `getattr` duck-typing design that makes it aspect-kind-agnostic.
  Dedup by name, insertion order preserved (no sort — the template needs no ordering guarantee
  beyond "stable within one render").
- **Web layer**: `_character_sheet_context` gains one new key, `unmodeled_effect_rows`
  (`unmodeled_effect_notes(character)` directly — no session-specific wrapping needed, unlike
  `contact_selection`/`resources_selection`, since this reads straight off the committed
  `character`). `_character_sheet.html` gains one `<details>` block (closed by default, no `open`
  attribute — unlike `_resources.html`/`_cyberware.html`/`_foci_selection.html`'s picker sections,
  which open when they have contents, this one starts collapsed regardless, since it's supplementary
  disclosure rather than something the player is actively editing), guarded by
  `{% if unmodeled_effect_rows %}` for the hide-when-empty decision above.

## Implementation

- `src/chummer5/data/qualities.py`: `_UNMODELED_EFFECT_NOTES` (new, 18 entries); `Quality
  .unmodeled_effect_note: str | None = None` (new field); `_parse_quality` populates it via
  `_UNMODELED_EFFECT_NOTES.get(name)`.
- `src/chummer5/engine/derived.py`: `unmodeled_effect_notes` (new function, see Design decisions).
- `src/chummer5/web/app.py`: import `unmodeled_effect_notes`; `_character_sheet_context` gains
  `"unmodeled_effect_rows"`.
- `src/chummer5/web/templates/_character_sheet.html`: new `<details>` section before the "Save"
  heading.
