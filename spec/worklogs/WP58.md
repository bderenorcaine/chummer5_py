# WP58 — Architecture audit: confirm/extend Phase R's candidate list before splitting into cleanup WPs

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase R, WP58.

## Goal

Phase R's own intro (raised 2026-07-24, same session as Phase Q) flagged two findings incidentally
while scoping something else — `web/app.py`'s 4,499 lines with no phase ever owning a split, and the
`submit_attributes`/`submit_priorities` `replace()` asymmetry `Project Overview.md` already names —
but explicitly said neither candidate list was built from a systematic read. WP58 is that read: a
real structural pass over `web/app.py`, a verdict on the asymmetry, a second pass over
`io/save_format.py`/`io/legacy_import.py` for the same accretion pattern, and the resulting WP
breakdown. Audit only — no source changes, `pytest`/`ruff`/`mypy` untouched.

## Log

### 2026-07-27 — `web/app.py`'s structure confirms the per-chargen-step split hypothesis

Read every `def`/`@app.` line in the file (not a sample) rather than guessing from its size alone.
Confirmed shape: for nearly every chargen step, the same four pieces already exist and sit
grep-adjacent to each other — form-parsing helper(s), Improvement-relink/carry-forward helper(s), one
`_*_context` builder, and that step's own route (all 21 routes are closures inside one `create_app()`
factory, lines 3319-4499). The only two genuinely cross-cutting pieces are `_character_sheet_context`
(spans every committed selection, for the read-only summary page) and `_chargen_body_context` (spans
every step's own context builder, for the two routes — `index`, `submit_priorities` — that re-render
the whole page instead of one section's fragment).

Two facts made the split verdict "mechanically low-risk," not just "structurally plausible," which is
the bar this audit was trying to clear rather than a size-based guess:
- `templates` (`Jinja2Templates`) and `resolve_session` are both defined *inside* `create_app()`
  today but don't actually close over anything local to it — `resolve_session` only reads
  `request.app.state.sessions`; `templates` only needs the already-module-level `TEMPLATES_DIR`. Both
  can become plain module-level definitions with zero behavior change, which is what actually makes
  route functions extractable into separate router modules at all (checked this directly rather than
  assuming FastAPI's `APIRouter` pattern would "just work" without confirming no closure dependency).
- `grep -rl "chummer5.web.app" tests/` → 15 files, but the actual per-name import list is small and
  enumerable: 14 of 15 import only `create_app`; the remainder is 7 catalog-constant names
  (`LIFESTYLES`, `CYBERWARE`, `BIOWARE`, `MAX_CONTACT_ROWS`, `MVP_QUALITIES`, `MUNDANE_SKILL_GROUPS`,
  `MUNDANE_SKILLS`) across 6 files. Cheapest fix for WP62: re-export those 7 names from the shrunk
  `web/app.py` rather than editing 6 test files' imports.

Verdict: confirmed, scoped as WP62. Target shape (module boundaries, which aggregator lives where,
the re-export plan) written into `spec/plan/phase-r-architecture-cleanup.md`'s new "Audit results"
section rather than repeated here.

### 2026-07-27 — `submit_attributes`/`submit_priorities` asymmetry: read both routes side by side
instead of trusting the docstring's own framing

`Project Overview.md`'s "Character as the single aggregate" section already documents this as "a
real, intentional asymmetry... left for a future WP to unify if it's ever worth it, not an
oversight" — WP58's job was to actually make that call, not just repeat the framing. Read
`submit_priorities` (3403-3535) and `submit_attributes` (3536-3670) in full.

`submit_priorities`, on its post-WP19 `dataclasses.replace(previous, ...)` shape, needs exactly two
relink calls afterward: `_relink_metatype_qualities` (metatype may have changed) and `_relink_contact_
selection` (CHA may have changed) — both substantive, not asymmetry artifacts, since both really can
change on this route.

`submit_attributes`, still on its pre-WP19 `create_character()`-fresh shape, needs **seven**:
`_relink_quality_improvements`, `_relink_metatype_qualities`, `_relink_contact_selection`,
`_relink_magic_selection`, `_relink_cyberware_selection`, `_relink_bioware_selection`, `_relink_foci_
selection` — plus an explicit 8-field carry-forward inside its own closing `replace()` call
(`skill_allocation`, `resources_selection`, `lifestyle_selection`, `bound_spirit_selection`,
`knowledge_selection`, `karma_skill_selection`, `karma_knowledge_selection`, plus the magic/Karma
points this same route computes). Cross-referencing which WP added each: WP23 (metatype qualities),
WP29 (magic), WP34 (cyberware), WP45 (bioware), WP47 (foci), WP49 (knowledge), WP53 (karma skill/
knowledge) each had to add a line to this one function as their own new Character-level selection
shipped, a repeating "remember this one function too" tax `submit_priorities` never pays because
`replace()` carries an untouched field forward for free.

No live bug traced back to this today — every WP so far remembered its line. That's exactly the
shape of risk worth naming rather than waiting on: the failure mode is silent (a forgotten relink line
means that selection's Improvements vanish on the next attribute edit, with no test failure unless
that exact combination is covered), and it's the identical bug class WP18/19 already found and fixed
once for `submit_priorities` itself before the `replace()` switch. Verdict: worth fixing, scoped as
WP63. One caveat recorded for whoever implements it: attribute edits genuinely can move CHA and (for
a magic-active character) MAG, so `_relink_contact_selection`'s CHA-recompute and the route's own
separate MAG-points handling both survive the fix — only the sheer count of pure Improvement-relink
calls collapses, not every piece of this route's post-processing.

### 2026-07-27 — `io/save_format.py`'s `build_character`: read in full, retired as a split candidate

962 lines total, but `build_character` alone is 355 of them (607-962) — the single largest function
in the repo. Read start to finish rather than assuming its size alone meant it needed splitting.
Unlike `web/app.py`'s independent per-step chunks, this is one genuinely sequential 9-stage pipeline
(metatype/quality → knowledge → skills/contacts/lifestyle/resources → cyberware → bioware →
magic/spells/powers → karma-attribute → karma-skill/knowledge → spells(Karma) → bound spirits →
foci), where each stage's `create_*` call reads `character.karma_remaining` or an attribute value
that's only correct because every earlier stage already ran and got folded back in via `replace()`.
The function's own inline comments already cite, stage by stage, *why* each one sits where it does
(a fixed evaluation order, not an arbitrary one). Splitting this into per-stage helpers would trade
one linear, already-well-commented read for several smaller functions each needing a wide,
already-computed-elsewhere parameter list, with no independent reuse to show for it. Verdict:
proportionate to its actual job, not a cleanup candidate — explicitly retired, not left unexamined.

### 2026-07-27 — `io/legacy_import.py`'s `import_legacy_character`: a genuine split candidate on
structure, retired anyway on the project's own abstraction-cost standard

795 lines total; `import_legacy_character` is 330 of them (435-765). Structurally this one *is*
different from `build_character`: its chunks (attributes, skills, specializations, knowledge,
qualities, contacts, talent/magic, spells, powers) are each independent — every chunk reads only
`legacy` plus a static catalog and writes a local variable, none reads another chunk's output, and
they only converge at the single closing `create_character_save(...)` call. On structure alone this
is more splittable than `build_character`. Retired anyway: each chunk runs exactly once, several
hundred words of existing per-field commentary explain a legacy-XML quirk specific to that exact call
site (the `qualitysource=Metatype` disambiguation, the native-language 0-cost carve-out, ...), and
extracting each into an adjacent private function would mean re-threading the same catalog parameters
into every one without eliminating any duplication or enabling any reuse — exactly the case Project
Overview's "don't add abstractions beyond what the task requires" / "three similar lines is better
than a premature abstraction" standard argues against. Both `io/save_format.py` and
`io/legacy_import.py` are left as-is; neither gets a cleanup WP.
