# WP59 — Fixture-strategy research pass

Phase S. Research only, no source/fixture changes. Settle *how* new regression fixtures get created
(legacy-engine-generated vs. hand-authored) and *what* they should cover, then emit the concrete
fixture-authoring WP list, before any engine-content WP commits to a path.

## Goal

Answer the three open questions the Phase S intro (2026-07-24) left hanging:
1. Can any environment available to this project build and run `Chummer.Tests` headlessly to *generate*
   a new golden `.chum5` for a synthetic character? (The intro guessed "very likely not," but flagged
   it needed confirming, not inferring.)
2. What are the concrete, currently-real coverage gaps — cross-checked against the "hand-verified, no
   fixture" call-outs already scattered across the phase files and `learnings.md`, not guessed from
   scratch?
3. What fixture-authoring mechanism + format wins, and what's the resulting WP list?

## Log

### Legacy toolchain: confirmed not viable, and one intro premise was wrong

`which dotnet mono msbuild nuget` → all absent. `curl`/`wget` also absent (used `python3 -m urllib`
for the one network probe). The `~/.dotnet` directory that existed on disk turned out to be a red
herring — it holds only `corefx/cryptography/crls/*.crl` (a TLS CRL cache), no runtime.

Network *is* reachable (`urllib.request.urlopen('https://download.mono-project.com')` returns OK), so
the blocker isn't isolation. But `apt-get install --dry-run mono-complete` → "Unable to locate
package": Mono isn't in the configured repos, so a build would first require hand-adding a third-party
repo + GPG key.

The Phase S intro asserted `Chummer.Tests.csproj` is "old-style `packages.config` (pre-SDK-style)."
**That's wrong** — the file opens `<Project Sdk="Microsoft.NET.Sdk">` (SDK-style; it *also* carries a
`packages.config`, which is what likely misled the intro). Correcting it doesn't change the verdict,
because the real blockers are downstream:
- `<TargetFramework>net48</TargetFramework>` + `<UseWindowsForms>true</UseWindowsForms>` +
  `Reference Include="WindowsBase"` — a net48 WinForms target the .NET SDK cannot build on Linux.
- `<ProjectReference Include="$(SolutionDir)Chummer\Chummer.csproj" />` — the test project pulls in
  the **entire WinForms Chummer application** (100+ forms). Building that headlessly under Mono, even
  with a runtime installed, is a long shot given Mono's incomplete `System.Windows.Forms`.

### The finding that closes the door regardless of toolchain

Read `ChummerTest.cs`. Its tests only **load and round-trip the existing `TestFiles/*.chum5`**:
`Test02_LoadCharacters` loads them, `Test03_SaveAsChum5lz` saves-as-lzma, `Test04_LoadThenSaveIsDeterministic`
checks load→save stability, `Test05_LoadThenPrint` prints. **None takes a synthetic chargen definition
and emits a computed character.** So even a working build would not generate a new golden fixture for a
hand-designed character — that requires driving the actual WinForms chargen forms interactively
(realistically Windows-only) or writing fresh C# harness code against the chargen engine, i.e.
reverse-engineering the WinForms codebase this project exists to avoid. Legacy-engine-generated
fixtures are off the table **on the merits**, not merely for want of a compiler.

### Gap inventory (from existing call-outs, not invented)

Grepped `no fixture` / `hand-verified` / `hand-derived` across `spec/plan/*` and
`spec/rulebooks/learnings/*` and read each hit in context. The pattern is consistent: the `.chum5`
corpus is structurally thin on *interactions* (3 of 34 Priority-built; only `Yeti-#ffffff2` is
mundane-Priority), so every case where two subsystems combine is "hand-verified against the rulebook,
no fixture." The unit tests already cover each mechanism in isolation (WP5/WP30 style) — what's missing
is whole-character fixtures combining them. Seven concrete gaps (G1-G7) are tabulated in the phase file
with their source call-outs (Phase J WP33/35, Phase L WP45, Phase J intro, Phase O WP52/53, Phase M
WP46-48, Phase L WP44). Phase K's two-level cyberware nesting is explicitly *excluded* from scheduling
— Phase K is on hold, so there's no engine code to test against yet.

### Format decision

Rejected hand-authored fake `.chum5` files: a `.chum5` whose derived values are hand-computed rather
than legacy-computed is strictly worse than an honest synthetic fixture — same hand-derivation, but
wearing the costume of legacy ground truth. Decided instead on a **synthetic whole-character harness**
that drives the *real* engine (`create_character()` + the existing selection APIs) from a small frozen
`SyntheticCharacter` input literal, paired with a hand-derived `expected` table whose every entry
carries an inline rulebook/`priorities.xml`/legacy-C# citation. This is the WP5/WP30 synthetic-primitive
pattern extended from "one mechanism" to "one whole character exercising an interaction" — precisely the
axis the real corpus can't grow along. It sits beside the 11-file `.chum5` registry, which remains the
ground truth for build-method-agnostic derived-stat formulas.

## Design decisions

- **Legacy-generated fixtures ruled out permanently**, not "deferred until a toolchain appears" — the
  decisive reason (the test harness only round-trips, never generates) is toolchain-independent.
- **Synthetic fixtures are native-format, never fake `.chum5`.** Documented in the phase file so a
  future WP doesn't reach for the "just hand-write the XML" shortcut.
- **Harness before fixtures** (WP72 is pure infrastructure closing no gap on its own), mirroring WP4.
