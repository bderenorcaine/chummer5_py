# WP60 — Fix karma-summary context-key collision

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase T, WP60.

## Goal

Fix a real bug reported after manual browser testing: buying a Karma-funded attribute point (e.g.
1 EDG), then reloading the page, showed a wrong "karma remaining" number in the Attributes section —
reported alongside a quality purchase, which made it look like quality-driven karma recomputation was
somehow dropping already-spent points.

## Log

### 2026-07-24 — Reproduced directly against the running app; qualities were a red herring, the real
trigger is any full-page render with more than one karma-consuming section populated

Used `TestClient` plus direct introspection of `app.state.sessions` (bypassing the HTTP/template
layer) to isolate the bug from the user's own repro steps. Confirmed the underlying `Character`
object's own `karma_attribute_selection`/`karma_remaining` were correct at every point — the bug is
not in the engine or the session's committed state at all, it's purely in how the *display* context is
assembled for a full-page render.

Root cause: `_chargen_body_context` (`src/chummer5/web/app.py`) builds `chargen.html`'s context by
spreading every section's own context dict together —
`{**priority_ctx, **talent_ctx, **attribute_ctx, **skill_ctx, **knowledge_ctx, ...}`. Three of those
dicts — `_attribute_allocation_context`, `_skill_allocation_context`, and
`_knowledge_selection_context` — all returned the **identically-named** `"karma_budget"`/
`"karma_remaining"` keys. Python dict-spread merge means whichever dict is applied last wins for that
key across the *entire* merged context — and since `chargen.html` renders all three sections' templates
against this one shared dict, `knowledge_ctx` (merged last among the three) silently overwrote both
`attribute_ctx`'s and `skill_ctx`'s own numbers on every `GET /` and `POST /ui/priorities`. Confirmed
by faking a scenario where all three sections had genuinely different own-budgets (1 EDG bought via
Karma, 1 skill point bought via Karma, nothing spent on Knowledge yet): both Attributes and Skills
displayed Knowledge's own (nothing-spent) numbers on `GET /`, even though each section's own isolated
`POST` response was correct.

This fully explains the user's report without needing quality purchases to be the cause at all: they
happened to reload the page (or navigate) right after touching qualities, but *any* full-page reload
after a Karma-funded attribute/skill spend triggers this. "Reverting looked correct" was coincidental —
with nothing committed anywhere, all three sections' numbers converge to the same value
(`character.karma_remaining`), so the collision becomes invisible.

Three other sections (`_spell_selection_context`, `_spirit_selection_context`,
`_foci_selection_context`) already avoid this by prefixing their keys (`spell_karma_budget`,
`spirit_karma_budget`, `foci_karma_budget`) — apparently established later than the attribute/skill/
knowledge sections, never retrofitted onto the earlier three. `_character_sheet.html`'s own "Karma
remaining" line was never affected — it reads `character.karma_remaining` directly off the model, not
the merged context dict.

### Fix

Renamed the three offending context builders' return keys to the same prefixed pattern the other
three sections already use: `attribute_karma_budget`/`attribute_karma_remaining`,
`skill_karma_budget`/`skill_karma_remaining`, `knowledge_karma_budget`/`knowledge_karma_remaining`.
Updated the three templates' Jinja references to match. No other call site needed changes —
`submit_attributes`/`submit_skills`/`submit_knowledge` each render their own dedicated template
directly from the same (now-correct) context dict.

Added a regression test
(`test_full_page_reload_shows_each_sections_own_karma_numbers_not_knowledges` in
`tests/unit/test_web_attribute_skill_allocation.py`) that commits a Karma-funded EDG point and a
Karma-funded skill point (chosen so their costs differ, so the two sections' budgets are provably
distinct), then asserts the full-page `GET /` response shows each section's own correct numbers — the
exact case that was previously untested, since existing tests only ever checked each `POST` route's
own isolated response.
