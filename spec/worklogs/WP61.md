# WP61 — Widen the Skills buy UI to Magical Active skills; skill-picker QoL; whole-page accordion

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase T, WP61.

## Goal

Fix a real, previously-documented-but-deferred gap: a Magician/Adept could not spend regular
Skill-priority points or leftover Karma on Spellcasting or any other Magical Active skill — only
their Talent free-grant ever raised one. Bundle in two QoL requests made in the same conversation:
collapsible skill categories with a name filter (mirroring the existing gear picker), and a
whole-page accordion so only one of the 14 chargen sections is expanded at a time.

## Log

### 2026-07-25 — Resolved WP29's open question by reusing an already-verified predicate, not new
research

`MUNDANE_SKILLS`/`MUNDANE_SKILL_GROUPS` were the only source the Skills-priority buy UI ever offered
— `chummer5.engine.magic.apply_magic_skill_grant_improvements` could still raise a Magical Active
skill via the Talent free-grant, entirely independent of this buy UI, but nothing let a player spend
*additional* points on one. WP29's own worklog (2026-07-19) flagged this explicitly and deferred it,
pending a decision on which subset of Magical Active skills to offer.

Resolved by reusing `chummer5.engine.magic._MAGICAL_SKILL_CATEGORIES` (renamed to the public
`MAGICAL_SKILL_CATEGORIES`) — the exact `{"Magical Active", "Pseudo-Magical Active"}` category filter
already verified against the legacy `GetMagicalSkillList()` for the free-grant itself (WP25). SR5
doesn't restrict regular skill-point spend by magic type or tradition (only the free grant is
restricted), and an Adept's MAG > 0 makes these skills just as functional as they are for a
Magician — so the widening applies identically to both, no new rules research needed.
`create_skill_allocation`/`create_karma_skill_selection` already took the full `SKILLS` catalog
generically; the restriction was purely `web/app.py`'s own UI curation. Added `_offered_skills`/
`_offered_skill_groups(character)` as the character-scoped equivalents, used by both the display
side (`_skill_allocation_context`) and the form-parsing side (`submit_skills`) — both needed the
same widened id set, or a magic-active character's submitted points on a newly-offered skill would
have been silently dropped by the parser even though the picker showed it.

### 2026-07-25 — A second, previously-undiscovered bug surfaced by the category-grouping work: the
original Mundane exclusion was attribute-based, not category-based, and let 3 skills through that
shouldn't have been offered to any Mundane character at all

While building WP61's own collapsible-category grouping (this session's QoL request), a Mundane
test character's skill picker showed its own "Magical Active" category header — a red flag, since
Mundane characters shouldn't see that category at all. Traced to `MUNDANE_SKILLS`'s original filter,
`s.attribute not in ("MAG", "RES")` — a plausible-looking proxy for "doesn't require being
Awakened/Emerged," but wrong: `chummer5.data.skills` confirms 3 of the 12 Magical/Pseudo-Magical
Active skills use a non-MAG linked attribute for their dice pool despite requiring Awakened status
to use at all — Assensing (INT), Astral Combat (WIL), Arcana (LOG, Pseudo-Magical Active). The old
attribute-only filter let *any* character, including a strictly Mundane one, already buy all three —
a real, latent gap dating back to WP2's original "MVP is mundane-only" curation, invisible until this
WP's own grouping made a Mundane character's "Magical Active" header visible at all.

Fixed alongside the main widening rather than deferred: switched the exclusion predicate to
`Skill.category not in (MAGICAL_SKILL_CATEGORIES | {"Resonance Active"})` — confirmed via the loaded
catalog that Resonance Active is its own clean, non-overlapping category (Compiling/Decompiling/
Registering, all RES-linked), so this is a strictly more correct predicate than the old one, not
just a different one. `MUNDANE_SKILLS` shrinks from 64 to 61 entries (3 previously-miscategorized
skills move from "always offered" to "offered only when magic-active"); `_MAGICAL_SKILLS` (WP61's
own new constant) and `MUNDANE_SKILLS` are now a clean, disjoint partition of all 76 SR5 skills minus
the 3 Resonance Active ones, confirmed via a direct overlap check.

### Design decisions

- **Collapsible skill categories**: mirrors `_resources_context`'s existing `gear_groups` pattern
  exactly — `itertools.groupby` on `(category, name)`-sorted skills, `<details>` open only if the
  category has an active row (points/karma/specialization). Kept `skill_rows` (flat) alongside the
  new `skill_row_groups` (grouped) in the context dict rather than replacing it, since nothing else
  reads the flat form but removing it wasn't necessary either.
- **Skill filter**: a small vanilla-JS `<script>` (no build step), per an explicit choice between
  that and an HTMX server round-trip — the project's only existing JS is vendored HTMX, but its
  stated principle is "no JS build pipeline," not "no JS at all," and an instant client-side filter
  avoids a network round-trip per keystroke. The filter `<input>` had to move *outside* the
  `<form>` element (a first draft placed it inside, which meant HTMX's own `hx-trigger="change,
  input delay:400ms"` on that form fired a real `POST` on every filter keystroke — the opposite of
  the intended "instant, no round-trip" behavior).
- **Whole-page accordion**: `<details name="chargen-section">` on all 14 sections — the shared
  `name` attribute gives native, zero-JS mutual exclusion. Wrapped *inside* each partial (around its
  own `<h2>`-turned-`<summary>` and content), not around the `{% include %}` in
  `_chargen_body.html`, so each partial's own conditional-render-nothing logic (Spells/Powers render
  nothing at all for the wrong magic type, per WP29's own design) stays intact — a section that
  renders nothing never has a `<details>` in the DOM, so it's never part of the accordion group.
  Dropped each section's own `<h2>` tag in favor of `<summary>Heading text</summary>` (matching
  `_resources.html`'s existing gear-category convention, which never used `<h2>` inside `<summary>`
  either) — this broke a few existing tests that asserted on `"X</h2>"` substrings (now vacuously
  true/false regardless of the section's real state, since the tag no longer exists at all);
  updated them to assert on `"<summary>X"` instead.
- **Open/closed state**: `ChargenSession.open_section: str = "priority-section"` — the same kind of
  pre-`Character` UI scratch state the priority letters already are. Every section's own `POST`
  handler sets `session.open_section` to its own id unconditionally (before the success/error
  branch), not just on success — a closed section's form can't realistically be the one a user just
  submitted, so the section being submitted was already open; keeping it open through a validation
  error means the error stays visible rather than the page reverting to whatever was open before.
- **Warning marker while collapsed**: each `<summary>` appends `⚠` when that section's own
  `*_error`/`*_budget_warning` context key is set — reuses keys that already existed per section
  (no new plumbing), verified against the exact WP19 acceptance scenario (lower an Attributes
  priority letter below already-spent points) with the Attributes section deliberately left
  collapsed on that render.
- **`open_section` threading**: added to the one shared dict `_chargen_body_context` returns (read
  automatically by every partial via Jinja's `{% include %}` context-sharing, no per-function
  signature change needed), and mutated onto each single-section `POST` route's own context dict
  right before rendering (`context["open_section"] = session.open_section`) rather than threading a
  new parameter through all 14 context-builder functions' signatures.

## Verification

`pytest`/`ruff`/`mypy` all green (938 tests, up from 930 before WP60/61). New tests: skill-widening
(`test_web_magic.py`, both the Ritual Spellcasting/Assensing purchase cases and the Mundane-still-
excluded cases), the accordion (`test_web_accordion.py`, 4 tests covering default state, moving the
open section, reopening on a validation error, and the collapsed-warning marker). Manual walkthrough
via a live `uvicorn` instance (using `httpx` directly against the running server, not just
`TestClient`) confirmed: a Human Shaman's picker shows Spellcasting/Ritual Spellcasting/Assensing
grouped under "Magical Active," purchasable with regular points; a Mundane character's picker has no
Magical/Pseudo-Magical/Resonance Active categories at all; the accordion opens exactly one section at
a time and correctly moves as different sections are submitted.
