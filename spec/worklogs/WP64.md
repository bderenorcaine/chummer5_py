# WP64 — Persist `<details>` open/closed state across htmx section swaps

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase U, WP64.

## Goal

Two reported defects with one root cause: htmx's `hx-swap="outerHTML"` rebuilds a chargen section's
DOM subtree on every submit, throwing away any *client-only* `<details>` open/closed state.
Concretely:

1. **"Accordion lets more than one section open at once."** WP61 removed the native
   `name="chargen-section"` grouping (it raced with htmx — see `ChargenSession`'s "Post-WP61 fix"
   docstring), leaving exclusivity re-established only server-side on the *next* full-page render.
   So manually clicking several `<summary>` bars open (no round trip) left them all open.
2. **"Changing a skill rating re-expands collapsed skill categories."** Each skill category's
   `<details open>` is a purely server-derived state (`selectattr` on active rows), re-evaluated on
   every `POST /ui/skills`. A player who manually collapsed a category with active skills saw it
   snap back open the instant any skill change swapped the section.

## What I did

A single shared vanilla-JS listener in `base.html` (consistent with WP61's no-build-step precedent),
covering both `<details>` levels:

- **Open-state store keyed by a stable key.** A `toggle` capture-phase listener (toggle doesn't
  bubble) records each `<details>`'s `open` state; an `htmx:afterSwap` listener restores the player's
  recorded choice over whatever the server just re-rendered. First sighting of a `<details>` seeds
  the store from the server default, so `ChargenSession.open_section` still governs the initial
  full-page-load state with nothing to restore.
- **Client-side exclusivity.** When a top-level section opens, the same `toggle` listener closes its
  sibling sections — restoring true one-at-a-time behavior *without* re-adding the racing `name=`
  grouping (the explicitly-decided shape in the WP).

### Key decisions / traps

- **Top-level sections detected structurally, not by a new attribute.** A top-level section
  `<details>` is the direct child of a `<div id>` that is itself a direct child of `#chargen-body`
  (see `_chargen_body.html`); its stable key is that section div's id. This deliberately avoids
  editing all 14 section templates — and, critically, keeps `test_web_accordion.py`'s exact
  `'<details open>'` / `'<details >'` / `count('<details open>') == 1` assertions valid, since the
  top-level tags are byte-for-byte unchanged. Only the **sub-category** `<details>` (skills,
  cyberware, bioware, resources, foci) gained an explicit `data-details-key` (`skillcat:`,
  `cyberware:`, `bioware:`, `gear:`, `focus:` namespaced by category) — the store keys off that when
  present, else falls back to the structural section key.
- **No new server-side logic.** `open_section` and the sub-category `selectattr`-derived server
  defaults are untouched; the fix is purely presentation/JS, matching the WP's "no engine or
  route-signature change" scope. The JS layers the player's choice *on top of* the server default,
  it doesn't replace it.
- **Why not `hx-preserve`:** `hx-preserve` keeps an element's *content* verbatim by id, but here the
  `<details>` content (the rows) must keep updating on each swap while only the `open` attribute is
  preserved — the opposite of what `hx-preserve` does. A capture/afterSwap listener is the right
  shape.
- **`toggle` fires async and only on real state change,** so restoring `d.open = stored` on an
  already-matching element is a no-op (no event, no loop); restoring a section to `open` may fire the
  exclusivity path, which only ever closes *already*-open siblings and terminates. Reasoned through
  for loop-freedom.

## Verification

- `pytest` green (940, up from 939 — one new wiring-guard test in `test_web_accordion.py`), `ruff`
  and `mypy` clean.
- New test `test_details_open_state_persistence_mechanism_is_wired` asserts the shared script ships
  on the page and skill sub-categories carry `data-details-key="skillcat:…"`. The restore/exclusivity
  behavior itself is pure JS (no headless browser in this environment), manual-walkthrough-verified
  per the WP's stated precedent — the existing server-side open-state tests already cover everything
  server-side, which this WP does not change.
- Rendered-HTML spot check (TestClient): confirmed top-level section `<details>` render unchanged
  (`<details >`/`<details open>`, no `data-details-key`), sub-categories carry namespaced keys, and
  the persistence/exclusivity script is present on every page.
