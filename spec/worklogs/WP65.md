# WP65 — Specialization pool "X (Y)" + text-input focus loss

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase U, WP65.

## Goal

Two unrelated-but-small reported skill-picker defects, bundled into one summary WP:

1. **Specialization pool shows only the higher number.** `_skill_allocation.html` rendered a single
   `{{ row.pool }}`, computed by `dice_pool` with the +2 specialization bonus already folded in
   (`SPECIALIZATION_BONUS = 2`). A specialized skill therefore showed only its specialized pool,
   never the base — expected format is `X (Y)`, X the base pool and Y = X + 2.
2. **Text inputs lose focus mid-typing.** Every section form carried
   `hx-trigger="change, input delay:400ms"` with `hx-swap="outerHTML"`. Typing in a *text* field
   (specialization, contact name, knowledge name, free-text quality detail, …) fired a `POST` ~400 ms
   after the last keystroke; the `outerHTML` swap destroyed and rebuilt the focused input, dropping
   focus. The `input delay` trigger exists for the *number* spinners' live responsiveness — text
   fields don't need it.

## What I did

### Pool "X (Y)"

- `chummer5.web.routes.skills._skill_allocation_context`: `skill_rows["pool"]` is now the
  *un-specialized* pool (`dice_pool(..., specialized=False)`) rather than `dice_pool`'s auto-detect
  default. A new `skill_rows["pool_specialized"]` carries `dice_pool(..., specialized=True)` **only
  when the skill actually has a specialization** — priority-point (`allocation.specializations`) or
  Karma-funded (`display.karma_skill_selection.specializations`) — else `None`.
- `_skill_allocation.html`: the Pool cell renders
  `{{ row.pool }}{% if row.pool_specialized is not none %} ({{ row.pool_specialized }}){% endif %}`.
  A plain skill keeps its single value; only a specialized skill gains the ` (Y)` parenthetical.

The `specialized=` override already existed (WP50), so no engine change was needed — this is purely
a context-builder/template presentation change.

### Text-input focus

- All 10 section forms carrying `hx-trigger="change, input delay:400ms"` changed to
  `hx-trigger="change, input[event.target.type=='number'] delay:400ms"`. The bracket is an htmx
  event filter: htmx compiles `[expr]` into `function(event){ return (expr) }` (verified in the
  vendored `htmx.min.js` — `nt()` builds exactly that, `pt()` calls it with the element as `this`
  and the triggering event as `event`). So `input` now only triggers a swap when the event's target
  is a `number` input; text inputs fall through to `change` (fires on blur), which no longer
  interrupts typing. Number spinners keep their live `input delay:400ms` updating unchanged.

## Key decisions / traps

- **`event.target`, not bare `target`.** htmx's filter function takes a single `event` parameter and
  `this` = the element — it does *not* wrap the expression in a `with(event)` scope. A bare `target`
  would resolve to `window.target` (undefined) and silently disable the filter (or worse). Confirmed
  against the actual minified source before committing to the syntax, since a malformed trigger would
  break form submission entirely rather than just failing the feature.
- **Two existing tests asserted the old single-value format** and had to move to `X (Y)`:
  `test_submitting_a_specialization_matches_engine_output` (now asserts
  `<td>{base} ({base+2})</td>`) and `test_submitting_karma_specialization_breaks_a_purchased_group`
  (the specialized Automatics row now `<td>{pool} ({pool+2})</td>`; the plain group-rated Longarms
  row still `<td>{pool}</td>`, which continues to match as a distinct substring since it's not
  followed by ` (`).
- **Number inputs still lose focus on swap** — unchanged, and out of scope. WP65 is specifically the
  text-field case; the number spinners' live-swap tradeoff (WP61) is intentional.

## Verification

- `pytest` green (942, up from 940 — two new tests), `ruff` and `mypy` clean.
- New tests:
  - `test_skill_allocation_context_exposes_base_and_specialized_pool` — a specialized row exposes

  - `test_section_forms_scope_input_trigger_to_number_inputs` — the rendered skills form carries the
    scoped `input[event.target.type=='number']` trigger and no longer the unscoped one.
- The focus-restore behavior itself is client-side JS (no headless browser here), manual-walkthrough
  verified per Phase U/WP61's stated precedent.
