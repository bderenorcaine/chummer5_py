# WP67 — Skill picker: filter to skills with a positive rating

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase V, WP67.

## Goal

Let a player narrow the active-skills picker to only the skills they've actually put points in
(rating > 0), on top of the existing by-name text filter. QoL request from the 2026-07-27
manual-testing pass; purely client-side, consistent with WP61's filter design.

## Log

### 2026-07-29 — Straightforward extension of WP61's vanilla-JS filter; only presentation touched

WP61 (`_skill_allocation.html:159-177`) already had a name filter that walks
`#skill-tables details`, hides non-matching `tr[data-skill-name]` rows, hides categories with no
visible rows, and auto-opens a category with matches. WP67 slots into that same loop rather than
adding a second, parallel one — the two filters combine (a row is shown only if it matches both the
name query *and*, when the checkbox is ticked, has rating > 0).

Three template edits, no engine/route change:

- Added an `<input type="checkbox" id="skill-rated-only">` "Only rated skills" control next to the
  existing `#skill-filter` text input — outside the `<form>`, same as the name filter, so HTMX's
  `hx-trigger="change, input …"` on the form doesn't fire a server round-trip when it's toggled
  (the same trap WP61 documented for the name input).
- Added `data-skill-rating="{{ row.rating }}"` to each skill `<tr>`. The rating was already rendered
  in a `<td>`, but reading it back out of cell text in JS is brittle (the Pool cell also holds
  numbers, DOM order isn't contractual); a dedicated data attribute is the clean read. `row.rating`
  comes from `skill_rating(...)` in `chummer5.web.routes.skills` and is already an int, so no
  formatting concern — group-driven ratings included, since `row.rating` is the effective displayed
  rating, which is exactly what "rated" should mean to the player.
- Generalized the filter callback (`applyFilter`) to read both controls and wired it to both
  `input` (text) and `change` (checkbox) events. The auto-open-on-match condition now triggers for
  either active filter (`(query || onlyRated) && anyVisible`).

### Testing

Added `test_skill_picker_offers_rated_only_filter_with_per_row_rating` to
`tests/unit/test_web_attribute_skill_allocation.py`. The filter itself is client-side JS that
pytest/TestClient can't exercise, so the test pins the *server contract* the JS depends on: the
checkbox renders, and every row carries its rating as `data-skill-rating` (asserting both a rated
`="3"` row and an unrated `="0"` row appear after buying one skill to rating 3).
