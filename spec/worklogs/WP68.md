# WP68 — Knowledge/Language skills: display a dice pool

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase V, WP68.

## Goal

The knowledge/language picker (`_knowledge_skills.html`) showed Name/Category/Rating/Karma-pts but no
dice **Pool** — the active-skills picker has one, this didn't. Add a Pool column to both the Knowledge
and Language tables, mirroring the active-skills picker.

## Rules

`pool = rating + linked attribute` (no citation dig needed — already documented in
`chummer5.data.knowledge`, cross-checked to core rulebook p. 89's "KNOWLEDGE CATEGORY EXAMPLES"
table by WP49):

- Knowledge categories: **Academic/Professional → LOG**, **Interest/Street → INT**
  (`KnowledgeCategory.linked_attribute`).
- Language skills: always **INT** (`LANGUAGE_LINKED_ATTRIBUTE`).

Knowledge/Language skills carry none of the active-skills machinery (no specialization, no
defaulting penalty, no skill-group rating), so the pool is a plain sum — no `dice_pool`-style
branching needed. WP68's note about giving specializations the WP65 `X (Y)` treatment is moot:
Knowledge/Language skills have no specialization support in this engine, so there's nothing to
parenthesize.

## What I did

### Engine (`chummer5.engine.knowledge`)

Two tiny helpers, so the "pool = rating + linked attribute" rule lives in the engine (testable) rather
than the route:

- `knowledge_dice_pool(character, category, rating)` — looks up the category's linked attribute via
  `chummer5.data.knowledge.knowledge_category` and returns `attribute_value + rating`.
- `language_dice_pool(character, rating)` — `attribute_value(INT) + rating`.

Both use the augmented `attribute_value` for parity with `chummer5.engine.skills.dice_pool`, though
(per the module's existing docstring) nothing in scope augments INT/LOG.

### Web (`chummer5.web.routes.knowledge`)

- Factored the two inline row-building dict comprehensions in `_knowledge_selection_context` into
  `_knowledge_row` / `_language_row` helpers, each of which now also computes a `pool`:
  - Knowledge: `None` (rendered blank) for a padding row, an unnamed/unrated row, or a row whose
    category isn't one of the 4 real Knowledge categories (linked attribute unknown until a valid
    category is chosen); otherwise `rating + karma_pts + linked attribute`.
  - Language: `None` for a padding/unrated row **and for a native pick** (fluency "N" — no numeric
    rating, so no meaningful dice pool); otherwise `rating + karma_pts + INT`.
- Pool is **Karma-inclusive** (`rating + karma_points`), matching the active-skills picker, which
  folds Karma-funded points into its displayed pool via `skill_rating`.

### Template (`_knowledge_skills.html`)

- Added `<th>Pool</th>` + a `<td>` to both tables.
- Knowledge cell: `{{ row.pool }}` when not `None`, else blank.
- Language cell: **`N`** when `row.native`, else `{{ row.pool }}` when not `None`, else blank.

## Key decisions / traps

- **Native language → "N", not a number.** A native language has no numeric rating (the sheet marks
  it "N"), so `_language_row` leaves `pool=None` and the template special-cases the native flag to
  render "N". Showing `INT + 0` would be misleading.
- **Blank category → blank pool, not a crash.** `knowledge_category` raises `ValueError` for an
  unknown/blank category, so `_knowledge_row` guards on `category in KNOWLEDGE_CATEGORY_NAMES`
  before computing — a half-filled row (name typed, category not yet chosen) shows no pool rather
  than erroring.
- **Engine helpers over inline math.** The sum is trivial, but keeping the linked-attribute lookup in
  the engine (rather than reaching into `KNOWLEDGE_CATEGORIES` from the route) keeps the rule
  testable headless and consistent with how active skills locate their pool logic.
