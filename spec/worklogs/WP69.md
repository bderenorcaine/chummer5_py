# WP69 — Spell picker: group spells by category/type and filter for known/unknown

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase V, WP69.

## Goal

The spell picker (`_spell_selection.html`) was one flat table. Make it (a) grouped by category into
collapsible `<details>` (Combat, Detection, Health, Illusion, Manipulation, Rituals) and (b)
filterable to show only known (selected) or unknown (unselected) spells. QoL request from the
2026-07-27 manual-testing pass; presentation-only, no engine change, mirroring WP61's
collapsible-`<details>`-per-category + client-side-filter pattern.

## Log

### 2026-07-29 — Template-only change; reused WP61's grouping/filter shape

Nothing in the route or engine needed touching. `_spell_selection_context`
(`chummer5.web.routes.spells`) already hands the template `spell_rows` as a flat list of
`{"spell": …, "selected": bool}` dicts, which carries everything both features need
(`spell.category` for grouping, `selected` for the filter).

Grouping is done with Jinja's `groupby` filter directly in the template
(`{% for category, rows in spell_rows | groupby("spell.category") %}`) rather than building groups
in Python like the skill picker's `skill_row_groups`. WP69 is explicitly presentation-only, and
`groupby` (which sorts by the grouping key) is the minimal-footprint way to get one
`<details data-details-key="spellcat:{{ category }}">` per category with no route change. Each
category's `<details>` opens by default when it contains a selected spell
(`{% if rows | selectattr("selected") | list %}open{% endif %}`), matching the skill picker's
"open the categories that have content" behavior.

The Category column was dropped from the per-spell table since the category is now the group
header; the remaining columns are Select / Spell / Type / Range / Duration / DV.

The known/unknown filter is a `<select id="spell-known-filter">` (All / Known only / Unknown only)
placed **outside** the `<form>` — same trap WP61/WP67 documented: the form's `hx-trigger="change"`
would otherwise fire a server round-trip when the control is toggled. The filter keys off each
row's server-rendered `data-spell-selected="true|false"` (derived from `row.selected`), not the
live checkbox state, so it stays correct across the full-`outerHTML` re-render every checkbox toggle
triggers. The vanilla-JS callback walks `#spell-tables details`, hides non-matching
`tr[data-spell-selected]` rows, hides categories left empty, and auto-opens a category with matches
when a non-"all" filter is active — structurally identical to `_skill_allocation.html`'s
`applyFilter`.

Like the skill picker, the filter `<select>` resets to "All" on each re-render (the whole
`#spell-selection` is swapped via `hx-swap="outerHTML"` on any checkbox change). Same accepted
tradeoff as WP61/WP67; not worth persisting client state for.

### Testing

Added `test_spell_picker_groups_by_category_and_offers_known_unknown_filter` to
`tests/unit/test_web_magic.py`. The filter is client-side JS that TestClient can't exercise, so the
test pins the server contract the JS depends on: the `#spell-known-filter` control renders, both
`data-spell-selected="true"` and `="false"` rows appear (after selecting exactly one spell), and
every spell category in the catalog gets its own `data-details-key="spellcat:…"` `<details>`.
