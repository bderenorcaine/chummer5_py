# WP70 — Bind spirits at a Force lower than the Magic rating

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase V, WP70.

## Goal

Let a Magician bind a spirit at a Force below their Magic rating. Through WP46-WP69 every bound
spirit's Force was pinned to exactly the caster's live Magic rating (never player-chosen, never
stored). WP70 makes Force a per-spirit player choice from 1 up to Magic. This is an engine + save
+ UI change, not presentation-only.

## Log

### 2026-07-29 — Rulebook check first: WP70's own note guessed the cost wrong

The WP note flagged uncertainty ("Check the exact SR5 Force cap and chargen binding-cost formula
against the rulebook before implementing") and guessed the cost "scales with Force (Force × Karma
per service)". Verified against the rulebook — the guess is wrong:

- **Cost is a flat 1 Karma per service, not Force-scaled.** Step Seven's "Additional Purchases &
  Restrictions" table (p. 98, already in `character_creation_chapter.md:798`) reads "1 Karma per
  service (Force = character's Magic rating)". The parenthetical is the *default* Force, not a
  multiplier. `KARMA_PER_SERVICE` stays `1`.
- **Chargen Force cap is Magic, not Magic × 2.** The general Summoning rule (p. 300) allows Force
  "up to twice your Magic rating," but Step Seven pins the reference at Magic and the WP scopes the
  request to Force ≤ Magic — the same "chargen number is the tighter one" pattern WP47 hit for
  Foci's x2-not-x5 bonding cap. So `1 ≤ force ≤ Magic`.

Full citation recorded in `spec/rulebooks/learnings/phase-m.md`'s new WP70 entry (placed in the
bound-spirits phase file for discoverability, labeled "(Phase V)"); the corrected-guess ruling is
in `spec/decisions-log.md` (2026-07-29 WP70 entry).

### Engine (`chummer5.engine.spirits`)

- `create_bound_spirit_selection`'s `picks` widened from `(spirit_type, services)` pairs to
  `(spirit_type, force, services)` triples, `force: int | None`. `None` means "default to the
  character's Magic rating" — both the UI default and how a pre-WP70 save (no stored Force) resolves.
- New validation: `1 ≤ resolved_force ≤ Magic`. Cost unchanged (`services * KARMA_PER_SERVICE`).
- `BoundSpirit.force` (already an `int`) now stores the resolved chosen value rather than always the
  Magic rating; module docstring rewritten to retire the "always Magic, never player-chosen" claim.

### Save format (`chummer5.io.save_format`)

- `BoundSpiritPickPair` → `BoundSpiritPickTriple = tuple[str, int | None, int]`.
- `_to_dict` writes `{"spirit_type", "force", "services"}`; `_from_dict` reads `p.get("force")` so a
  pre-WP70 save (entries with no `"force"` key) fills `None` and round-trips unchanged. `None`
  persists as JSON `null`.
- Force must now be persisted (it's a real choice), unlike WP46 which deliberately never stored it —
  the `None` default is what preserves WP46's "live Magic" behavior for the untouched default case.

### Web (`chummer5.web.routes.spirits` + `_spirit_selection.html`)

- `_parse_bound_spirits` reads a new `spirit_force_{i}` field per row; blank/malformed → `None`
  ("default to Magic"), mirroring how a blank services field is left for the engine to reject.
- `_spirit_selection_context` builds each row's `force` (a `None` pick displays as the Magic rating,
  matching what the engine would resolve), and threads Force through the staleness re-validation
  committed-picks list.
- Template gains a "Force" column: `<input type="number" min="1" max="{{ spirit_force }}">`
  (`spirit_force` = Magic rating) between the type dropdown and the services input. The intro line
  now explains cost is 1 Karma/service regardless of Force.
- Two carry-forward sites that rebuild spirit picks from a committed selection —
  `routes/priorities.py` (priority reconfirm) and `routes/character.py` (save building + the
  character-sheet `bound_spirit_rows`, which previously hardcoded `force = MAG`) — now read
  `spirit.force`.

### Traps hit

- The character sheet's `bound_spirit_rows` builder hardcoded `force = character.attribute_value
  ("MAG")` — a latent spot that would have shown the wrong Force once Force could differ from Magic.
  Fixed to `spirit.force`.
- `_spirit_selection_context`'s row builder indexed the pick tuple positionally (`entries[i][1]`
  was services); with triples that index is now Force, so the row/karma-spent builders and the
  `karma_spent = sum(services for ...)` unpack all had to shift to the 3-tuple shape.

### Testing

- `tests/unit/test_spirits.py`: all existing picks updated to triples (`None` Force where they
  previously relied on Force = Magic); added tests for None-defaults-to-Magic, explicit sub-Magic
  Force, cost-does-not-scale-with-Force, Force > Magic rejected, Force < 1 rejected.
- `tests/unit/test_save_format.py`: `_magician_save` signature widened; added explicit-Force
  round-trip and a pre-WP70 backward-compat test (strip the `"force"` key, confirm it reloads as
  `None`).
- `tests/unit/test_web_spirits.py`: existing save-JSON assertion updated to include `"force": 4`
  (Magic at letter B); added a web test binding at explicit Force 2 (shows on sheet, cost still 3)
  and one rejecting Force 5 > Magic 4.
