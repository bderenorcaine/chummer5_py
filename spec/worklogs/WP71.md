# WP71 — Gear picker: name/category filter

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase V, WP71.

## Goal

The starter-gear picker (`_resources.html`) had collapsible per-category `<details>` but no filter
over the ~380-item catalog. Add a by-name (and by-category) text filter mirroring the skill picker's
WP61 vanilla-JS pattern. QoL request from the 2026-07-27 manual-testing pass; presentation-only, no
engine change.

## Log

### 2026-07-29 — Template-only change; reused WP61/WP67/WP69's filter shape

Nothing in the route or engine needed touching. `_resources_context`
(`chummer5.web.routes.resources`) already hands the template `gear_groups` as
`[{"category": …, "rows": [{"item": GearItem, …}]}]`, which carries everything the filter needs
(`item.name` and `group.category`).

Changes to `_resources.html`:
- A `<input type="text" id="gear-filter">` placed **outside** the `<form>` — the same trap WP61/WP67/
  WP69 documented: the form's `hx-trigger="change, input…"` would otherwise fire a server round-trip
  on every keystroke. Placing the filter outside the form keeps it purely client-side.
- Wrapped the `{% for group in gear_groups %}` details loop in `<div id="gear-tables">` so the script
  can scope its `querySelectorAll` to just the gear tables.
- Added `data-gear-name="{{ row.item.name | lower }}"` and
  `data-gear-category="{{ group.category | lower }}"` to each `<tr>`. The category is per-group but
  stamping it per-row keeps the JS callback structurally identical to the skill picker's `applyFilter`
  (which walks `tr[data-*]` rows directly).
- An inline `<script>` mirroring `_skill_allocation.html`'s `applyFilter`: on `input`, walk
  `#gear-tables details`, hide `tr[data-gear-name]` rows whose name **or** category doesn't contain
  the lowercased query, hide categories left empty, and auto-open a category with matches when a query
  is active. A single text box thus covers both name and category ("by-name and optionally
  by-category" from the WP) without a second control.

Like the skill/spell pickers, the filter input isn't part of the swapped form state; the whole
`#resources` block is replaced via `hx-swap="outerHTML"` on any gear change, so the filter box resets
to empty on each re-render. Same accepted tradeoff as WP61/WP67/WP69 — not worth persisting client
state for.

### Testing

Added `test_gear_picker_offers_a_name_category_filter` to
`tests/unit/test_web_quality_contacts_resources.py`. The filter is client-side JS that TestClient
can't exercise, so the test pins the server contract the JS depends on: the `#gear-filter` control
renders, and a known catalog item (Meta Link) gets both its `data-gear-name` and `data-gear-category`
attributes.
