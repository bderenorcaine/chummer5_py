# WP72 — Synthetic whole-character fixture harness + one reference fixture

Phase S. First fixture-authoring WP after WP59's research pass. Establish the substrate the rest of
Phase S depends on (WP73-76), proven end to end by one reference fixture. Closes no §2 coverage gap
on its own — it's infrastructure, mirroring how WP4 established the `.chum5` harness before any test
consumed it.

## Goal

A synthetic whole-character fixture mechanism (decided in WP59 §3): a `SyntheticCharacter` input
literal fed through the *real* engine, paired with hand-derived `expected` values each carrying a
rulebook/`priorities.xml`/legacy-C# citation. Proven by one full mundane Human Priority build,
asserting attribute totals, skill ratings/dice pools, initiative, the three Limits, both condition
monitors, Essence, and the Karma ledger.

## Log

### Engine API surface used (no new engine code)

WP72 is a tests-only WP — it adds nothing under `src/`. `build_synthetic()` drives exactly the public
engine functions the web routes already call, confirmed by reading `engine/character.py`,
`engine/skills.py`, `engine/qualities.py`, `engine/derived.py` and `tests/integration/
test_character_fixtures.py`:
- `create_character(metatype_choice, heritage_letter, attributes_letter, priorities,
  attribute_points)` — with `metatype_choices(heritage, metatypes)` resolving the `MetatypeChoice`.
- `create_skill_allocation(letter, priorities, skills, skill_points, group_points, specializations)`
  — keyed by `Skill.id`; the harness resolves human-readable skill/group names to ids.
- `create_quality_selection(quality_ids, catalog)` + `apply_quality_improvements(character,
  qualities)` — the improvements land in the character's already-linked `ImprovementIndex`, same
  call order as `test_character_fixtures.py`.
- `derived.py`'s pure functions + `skills.dice_pool`/`skill_rating` for the asserted metrics.

`Character` carries `skill_allocation`/`quality_selection` as fields (WP18's fold), so
`build_synthetic()` returns a single finalized `Character` and `resolve_metric` reads every asserted
value off it (`dice_pool(character, character.skill_allocation, skill)`).

### Fixture-authoring ergonomics: name-keyed inputs

The engine's selection APIs key on GUIDs (`Skill.id`, `Quality.id`). A hand-authored fixture keyed
on GUIDs would be unreadable and un-auditable, defeating the "every number is cited and checkable"
point. So `SyntheticCharacter` is keyed by catalog *name* (Sneaking, Firearms, Catlike) and
`build_synthetic()` resolves names → ids, raising a clear `KeyError` on an unknown name rather than
letting it fall through to a confusing downstream error.

### Metric-key grammar

`resolve_metric(character, key)` maps a string key to a computed value (`attr:BOD`, `rating:Sneaking`,
`pool:Sneaking`, `initiative`, `limit:physical`, `cm:stun`, `essence`, `karma_remaining`, ...). This
lets a fixture's `expected`/`citations` dicts double as documentation of exactly what's asserted, and
keeps each `expected` value aligned 1:1 with a citation. `assert_fixture()` enforces the contract:
every `expected` key must both compute to its target *and* have a non-blank citation — a magic number
with no cited source is itself a test failure. `essence` compares via `Decimal` normalization so a
`6` authored in the fixture equals the engine's `Decimal("6")`.

### Reference fixture — hand-derived values

A mundane Human build, Talent forced to E (mundane). Priorities: Attributes A, Skills B, Heritage C,
Resources D. All figures cross-checked against `priorities.xml` (queried live), `metatypes.xml`
ranges, and `learnings/phase-d.md`'s derived formulas:

- Attributes (24 primary pts, all spent; +2 EDG from Heritage C/Human's 5 special pts): BOD 4, AGI 5,
  REA 4, STR 3, CHA 3, INT 5, LOG 4, WIL 4, EDG 4.
- Skills (Skills B = 36 skill + 5 group pts): Firearms group 5 → Automatics rating 5; Sneaking 3 pts
  → rating 3 + 2 Catlike = 5; Hacking 3 → rating 3; Perception 2 + "Visual" spec (1 pt).
- Dice pools: Automatics 10 (5+AGI5), Sneaking 10 (5+AGI5), Hacking 7 (3+LOG4), Perception 9
  (2+INT5+2 spec).
- Derived: initiative 9 (REA4+INT5), init dice 1, physical limit 5 (ceil14/3), mental limit 6
  (ceil17/3), social limit 6 (ceil16/3, Essence 6), physical CM 10 (8+2), stun CM 10 (8+2).
- Karma: Catlike +7, Simsense Vertigo −5 → net +2 spent, 23 remaining of the 25 starting.

## Design decisions

- **Name-keyed inputs, id-resolved in the builder** — legibility/auditability of a hand-authored
  fixture matters more than mirroring the engine's GUID API shape; the resolution is one dict lookup
  with a loud failure mode.
- **Harness declares only mundane-exercised fields; WP73-76 extend dataclass + builder together.**
  Deliberately *not* pre-adding speculative cyberware/bioware/magic/karma input fields whose exact
  shape no fixture yet pins down — the acceptance criteria explicitly warn against "speculative
  future-proofing," and WP4 likewise grew its parser one field at a time. The module/README docstrings
  spell out the extension pattern so a later WP doesn't reach for a fake `.chum5` shortcut.
- **`assert_fixture` makes "cited or it's a failure" executable**, not prose-only — the honesty
  standard the worklogs' scattered "hand-verified, no fixture" caveats already held themselves to,
  now regression-guarded.
- **Returns one finalized `Character`** (WP18's single-aggregate fold) rather than a tuple of
  `(character, allocation, selection)` — `skill_allocation`/`quality_selection` are already fields,
  so a single object is enough for every metric.

## Traps hit

- `ruff` line-length (100) on the prose-heavy module/fixture docstrings and the long citation
  strings — reflowed by hand (`ruff format` doesn't rewrap strings/comments). No logic impact.
- No PDF lookup was needed: every formula (derived stats) and budget (priority tables) this fixture
  asserts was already extracted in `learnings/phase-d.md` / lives in `priorities.xml`, so no new
  `learnings.md` entry and no `decisions-log.md` entry were warranted.
