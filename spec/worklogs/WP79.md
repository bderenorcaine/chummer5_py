# WP79 — Surface augmentation unmodeled-effect notes on the character sheet

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase K, WP79.

## Goal

Make WP77's registry rows visible where a player can act on them. WP77 wrote ten "Unmodeled real
effects" rows for cyberware content into `spec/Project Overview.md` and then discovered that a
player who buys Bone Lacing (Titanium) sees nothing at all on the character sheet — WP56's whole
disclosure mechanism exists, and no augmentation catalog populates the field it reads.

Scoped as a data-layer WP by WP77's own claim: populate `unmodeled_effect_note` on the two cyberware
catalogs and the bioware one, and the sheet lights up with no engine or template change.

## Log

### 2026-07-31 — The prediction was exactly right, which is worth recording as a result

WP77's entry asserts that `chummer5.engine.derived.unmodeled_effect_notes` "already walks
`cyberware_selection.walk()` and `bioware_selection.items`" with a kind-agnostic
`getattr(item, "unmodeled_effect_note", None)`, so populating the field is the entire change. That
held literally: `derived.py`'s only edit in this WP is a docstring correction (it claimed "today
only `Quality` does"), `_character_sheet.html` is untouched, and no route, engine, save-format or
import module changed. Three defaulted dataclass fields and one dict were the deliverable.

That is a real property of WP56's design, not luck — it wrote the collector kind-agnostically on
purpose and left a test pinning "walks cyberware/bioware/powers/foci, contributes nothing." Two
WPs later the pin turned into a working feature by deletion of nothing. Worth naming so the same
shape gets reused when `Power`/`Focus`/`Spell`/`StarterGearItem` eventually need their own notes:
the field name is the contract, and there is no registration step.

### 2026-07-31 — One dict or two: the entry's open question, and why the answer isn't symmetric

The entry asks whether the two cyberware catalogs share a constant, noting they "load the same rows
from the same file, and only the second reaches a `Character` today."

**Shared, and the sharing is the point.** `chummer5.data.cyberware.UNMODELED_EFFECT_NOTES` is
public and imported by `chummer5.data.cyberware_subsystems` in the same import block that already
brings over `classify_bonus`/`BonusSupport`/`CyberwareFlatBonus`. The registry table has one row per
item; two dicts would be two hand-kept mirrors of that one row, each looking maintained while
drifting from the other. The failure would be invisible: `Cyberware`'s copy is the one the browser
picker holds and `CyberwareEntry`'s is the one a `Character` holds, so a divergence would show up as
"the note is wrong on the sheet but right in the picker" — precisely the kind of thing nobody
checks. A test asserts the two are string-identical for every registered row that appears in both,
so even the shared-constant version is pinned rather than assumed.

**Bioware keeps its own, and it is empty.** Different file, independent name space, so there is
nothing to share. Empty is a fact about the registry rather than an omission: of the 6 offered SR5
bioware rows, five have their printed effect modeled or genuinely have none, and the sixth is
`Reflex Recorder`, which WP77 classified as **Bucket A** — computable by this engine and merely
unimplemented. Giving it a note would launder a live policy violation into an accepted gap, which
is the one distinction `tests/unit/test_augmentation_unmodeled_registry.py` exists to keep. So the
dict stays empty and a test asserts `Reflex Recorder` specifically has no note; WP80 removes the
question by modeling the row.

The temptation here was to skip bioware entirely, since an empty dict is inert code. Against that:
the entry asks for all three, the three augmentation catalogs are read as a set by anyone touching
this area, and an asymmetry with no explanation costs more than five lines do. The dict and the
field are documented as deliberately empty in the module docstring, so a future bioware registry row
is a one-line change rather than a re-derivation of this paragraph.

### 2026-07-31 — 16 names, not 10, and the wording problem in the six that predate WP77

The entry folds in "the 6 augmentation rows already in the registry from WP38/WP40," warning that
those have a *partly* modeled effect so "their note is the unmodeled remainder, not 'this does
nothing.' Check the wording carries that." Two things came out of taking that seriously:

- **Six registry rows are eight catalog names.** `Customized Agility / Customized Strength` and
  `Enhanced Agility / Enhanced Strength` are each one table row covering two real `cyberware.xml`
  entries (the registry groups them because they differ only in which attribute they name). Notes
  are keyed by catalog name, so the dict has 18 keys covering WP77's 10 rows and WP38/WP40's 8
  names.
- **The remainder wording needed a checkable form, not just care.** Each of the eight partly-modeled
  notes ends with a sentence naming what *is* applied ("The +Rating Mental limit on those same tests
  is modeled", "The purchase's nuyen and Capacity costs are modeled"), and a test asserts the word
  "modeled" appears in each of them. That is a proxy, and a weak one on its own — but it converts
  "somebody should check the tone" into something that fails when a future edit strips the clause,
  which is the difference between a convention and an invariant.

The wording of the ten absent-effect rows is compressed from
`spec/rulebooks/learnings/phase-k.md`'s WP77 entry rather than re-derived: the printed text of all
ten is already transcribed there with page citations, so **no PDF pass was needed for this WP** and
there is nothing new to add to the learnings file. The one place I deliberately kept WP77's
awkwardness is Smartlink, whose note says both the book's "+2 Accuracy" and legacy's dice-pool
reading — a player-facing note mentioning the legacy engine reads oddly, but dropping half of it
would re-introduce exactly the claim WP77 spent three page-hops correcting.

### 2026-07-31 — Pinning the correspondence in both directions

WP77's own follow-up called the missing piece "moving the notes into the catalogs and asserting
against them — which is WP79, and is the better version of this." The four new tests in
`tests/unit/test_augmentation_unmodeled_registry.py` are that, and the second direction is the
half that does real work:

1. Every `REGISTERED_UNMODELED` name resolves to a note in both cyberware catalogs, identically.
2. Every `PARTLY_MODELED_WITH_NOTES` name resolves to a note that says what is modeled.
3. **No row outside those two sets carries a note.** This is what keeps WP78's four newly-modeled
   rows out of the registry: if some future WP gives `Reaction Enhancers` a note instead of fixing
   something, this fails. It also means a WP that *models* a currently-registered row must delete
   its note in the same commit.
4. No bioware row carries a note, `Reflex Recorder` explicitly included.

`PARTLY_MODELED_WITH_NOTES` is a literal name-list because there is no `bonus_support` value that
identifies those eight — two are `NO_EFFECT` and four are `CONDITIONAL_BONUS`, i.e. "partly
modeled" is a fact about the registry, not about the classifier. Same posture as the file's existing
frozensets, and the same reason.

**What is still not pinned**, and this WP did not close it: the note *wording* against the markdown
table. Doing so means parsing `Project Overview.md` at test time, which WP56 rejected explicitly and
nothing here reopens. Instead the Project Overview's registry preamble now states the obligation
outright — edit a row there, edit the matching catalog dict in the same commit — and names the three
dicts, so the mirror is at least documented at the place where it can be broken.

### 2026-07-31 — What the web test can and can't reach

The acceptance criterion asks for a Bone Lacing (Titanium) web test, which covers the *offered* half
of WP77's split (5 of the 10 rows). The import-only half (Dermal Plating, Armor, Internal Air Tank,
Skillwires, Skilljack) is unreachable from the browser by construction, and — checked, not assumed —
**no `.chum5` fixture in the corpus owns any of the five**, so there is no integration path to them
either. They are covered at the data layer only, by test 1 above, which runs over
`load_cyberware_entries()`'s full 87 rows. Recorded because "why is there no end-to-end test for
half of these" is otherwise a reasonable question with a non-obvious answer.

The second web test is the negative case: a Datajack purchase must render *no* section at all.
Without it, "the sheet shows an unmodeled-effects row" would also pass for an implementation that
attached a note to every purchase indiscriminately.

## Follow-up

- **WP80 must delete nothing here, and that is the check.** `Reflex Recorder` has no note; when
  WP80 models it, it leaves `MODELED_BUT_UNCLASSIFIED` and the "no unregistered row carries a note"
  test keeps holding without any edit. If WP80 instead finds it *can't* model the row, adding a
  note is a policy change needing a decisions-log entry, not a quiet dict edit.
- **WP42 should consider showing notes in the picker, not only on the sheet.** Both catalogs carry
  the field now, including the flat one the browser renders, so "this item's armor bonus is not
  modeled" could appear at the moment of purchase rather than after it. Out of scope here (this WP
  changed no template deliberately), but the data is in place.
- **The markdown table and the catalog dicts can still drift in wording.** See the pinning section
  above; the preamble sentence is the mitigation, not a fix.
- **Non-augmentation catalogs still populate nothing** — `Power`, `Focus`, `Spell`,
  `LifestyleTier`, `StarterGearItem`, `SpiritType`. `derived.unmodeled_effect_notes` walks all of
  them already, so each is the same one-module change this WP made if a future audit finds rows for
  them (WP21's gear catalog is the likeliest candidate — it models no bonus for any gear item at
  all, and has never been audited against the registry).
