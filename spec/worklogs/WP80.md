# WP80 — `Reflex Recorder`: a purchase-time skill choice on an augmentation

Status: complete
Ref: [Implementation Plan.md](../Implementation%20Plan.md) — Phase K, WP80.

## Goal

Finish WP77's Bucket A. `Reflex Recorder` (bioware, SR5, in the shipped picker since WP45) carried
`<bonus><selectskill limittoattribute="BOD,AGI,REA,STR"><val>1</val></selectskill></bonus>` and
granted nothing — the last augmentation row that was offered, charged in full, and mechanically
silent, and a live departure from the Project Overview's 2026-07-24 "model it in full or exclude it"
policy for as long as it stayed that way. WP78 modeled the other four Bucket A rows and ruled this
one out of its own scope because it is a different kind of problem: the bonus's target is a *player
choice*, which needs persisting, re-validating on load, importing from a legacy `<extra>`, and
picking in the browser — WP55's four-layer shape.

## Log

### 2026-07-31 — The rulebook answered both of the entry's open questions, and corrected one of them

The entry named two decide-and-document deliverables. `pdftotext -layout -f 461 -l 463` (book
pp. 459-461) answered both from one paragraph, transcribed in full in
`spec/rulebooks/learnings/phase-k.md`:

**(a) Rating or dice pool?** "The reflex recorder adds 1 to the **Rating** of a specific skill
linked to a Physical attribute." So `ImprovementType.SKILL` — this engine's established route, which
folds into `skill_rating` — is right, and no new pool-modifier primitive was needed. This is worth
being precise about, because WP78's worklog raised the question in a much broader form (legacy reads
*every* `<specificskill>` without `<applytorating>` as a pool modifier, and `Barrett.chum5`'s own
copy of this bonus carries the comment `<!-- Hero Lab says this is not RAW <applytorating>True -->`).
The book settles it **for this row only**: Voice Modulator's printed wording (p. 452) is "Add the
Rating of the modulator to your *dice pool*." Two genuinely different bonuses that happen to share
one XML shape — so the broad question stays open and stays not-one-WP's-job, exactly as WP78 said.

**(b) Does a matched pair behave differently?** No, and the entry's premise was wrong. It claims
`Reflex Recorder` carries `<pairinclude><name>Reflex Recorder</name></pairinclude>`. It does not:
the catalog row in `bioware.xml` has no `<pairinclude>` and no `<pairbonus>` at all, and the file's
only two `<pairinclude>` elements belong to `Striking Callus (Hands)`/`(Feet)`, both `CF`-sourced.
The element the entry saw is in `Barrett.chum5`'s *saved character* node, where it sits beside an
empty `<pairbonus />` — a vestige of an older catalog revision that grants nothing. The printed
entry has no pair rule either; what it has is the opposite one, which turned out to matter more:

> Multiple recorders may be taken for multiple skills, but you can't implant two reflex recorders
> for the same skill.

That is the first SR5 rule this project has met that constrains *which* duplicate purchases are
legal rather than whether duplicates are legal at all. `cyberware.xml`'s LCD-sourced implant
packages corroborate the "multiple" half independently: one bundles two Reflex Recorders, `<forced>
Locksmith</forced>` and `<forced>Pistols</forced>`.

The same paragraph's last sentence — "Reflex recorder bioware is incompatible with skillwires
cyberware" — is real and deliberately unenforced. There is no cross-catalog incompatibility
mechanism in this engine, `bioware.xml` carries no `<forbidden>` node for the row (so legacy doesn't
enforce it either), and `Skillwires` grants nothing here at all (it is one of WP77's registry rows),
so allowing both changes no derived number. Recorded in `chummer5.data.bioware`'s docstring, *not*
in the Project Overview's "Unmodeled real effects" table — that table is for an offered aspect's own
uncomputed effects, `Reflex Recorder`'s are now all computed, and a row there would launder the fix
into an accepted gap (the exact thing WP77/WP79 built a test to prevent).

### 2026-07-31 — Why the pick can't live in a mapping, and what that forced

WP55's `QualitySelection.quality_text` is `{quality_id: free_text}`, which works because a quality
can only be taken once. Bioware can be bought repeatedly, and p. 460 explicitly contemplates buying
several recorders for several skills — so the pick has to belong to a *purchase*, one per bought
unit. That is the whole reason this WP is bigger than WP78's four rows put together: it changes the
shape of what a bioware selection *is*, and that shape is load-bearing in five layers.

Three shape decisions, all made to keep the change proportional to the feature:

- **`create_bioware_selection` takes `Iterable[str | BiowarePurchaseRequest]`.** A bare id keeps
  meaning "this item, no player choice." The alternative — WP41's hard retype of
  `cyberware_item_ids` → `cyberware_purchases` — would have rewritten ~20 call sites and test
  literals into `BiowarePurchaseRequest("ce")` noise, for 5 of 6 catalog rows that have nothing to
  choose. The union isn't a placeholder or a compatibility shim: "no player choice" is a total,
  well-defined state, and an id for the one row that *does* need a pick is rejected by exactly the
  same validation a `chosen_skill=None` request hits. (WP41's own retype was different in kind: a
  flat id genuinely *couldn't express* a tree, so there was no honest reading to keep.)
- **`BiowareSelection.purchases` is the new field; `items` survives as a property.** Every reader
  that only wants "what did this character buy" — `chummer5.engine.derived.unmodeled_effect_notes`,
  the web layer's Improvement swap, half a dozen tests — kept working untouched. Only the two places
  that genuinely need the pick (the character sheet's recap, the save) moved to `purchases`.
- **`CharacterSave.bioware_item_ids` → `bioware_purchases`, with WP41's fallback shape.** Here a
  retype *was* unavoidable, for WP41's own reason: a bare id can't carry the pick. The fallback is
  exact for every row except `Reflex Recorder` — see the next entry.

### 2026-07-31 — The one deliberate backward-compatibility break

A pre-WP80 save holding a `Reflex Recorder` now fails to build, with "Reflex Recorder requires a
chosen skill". This is the intended behaviour, not a regression to work around, and the reasoning is
worth stating because "old saves keep loading" has been an unbroken rule in this project so far:

- The pick was **never persisted** before this WP, so there is nothing to recover. Any default this
  code could invent (first eligible skill, none, drop the item) would be a fabricated player choice.
- The bonus was **never applied** before this WP either, so a save that fails here was already
  describing a character whose 14,000¥/0.1-Essence purchase did nothing.
- The failure is loud and specific rather than silent, which is the whole posture
  `chummer5.io.legacy_import`'s itemized reasons already take.

Every *other* pre-WP80 save round-trips exactly: `_bioware_purchases_from_dict` reads
`"bioware_purchases"` when present and otherwise maps each `"bioware_item_ids"` entry to a
pick-free request. `FORMAT_VERSION` is unchanged — a reader that understands both keys is not a
schema break (WP41 set that precedent).

### 2026-07-31 — Classified by shape, not by name — and why that's the opposite call from WP55

`chummer5.data.qualities` name-gates its `SELECT_TEXT` rows (`_VERIFIED_SELECT_TEXT_NAMES`) because
`<selecttext>` means something different in every quality that carries it (which SIN, which
protected group, which Matrix action) and only a per-row reading can confirm the engine models it.
`<selectskill limittoattribute="…"><val>N</val></selectskill>` has one reading, stated in the data
itself: "+N to one active skill whose linked attribute is in this list." So `_classify_bonus`
accepts it by shape, and a `<selectskill>` that is *missing* the filter, or carries any other child,
still falls through to `NOT_YET_SUPPORTED` — an unfiltered pick is a different mechanic, not this
one, and defaulting the filter to "any skill" would be exactly the silent widening the
never-partially-classify rule exists to prevent.

Verified by enumeration rather than assumed: `Reflex Recorder` is the only SR5-sourced row in either
augmentation catalog whose `<bonus>` contains a `<selectskill>` at all (no SR5 `cyberware.xml` row
does; the one cyberware row that carries the tag, `Cyberlimb Optimization`, is `CF`-sourced and
outside the loaded catalog). A test pins that, so the shape gate can't quietly start matching a
second row.

`SELECT_SKILL` went onto the shared `chummer5.data.cyberware.BonusSupport` rather than becoming a
bioware-local enum, following the precedent already in that type: `CONDITIONAL_BONUS` lives there
and no bioware row produces it. The asymmetry is fine; a second enum would be five duplicated names
plus one difference.

### 2026-07-31 — The UI shape the quantity picker forced

The bioware picker is a quantity box per catalog row, and the section already re-renders on every
`change` (WP15's live-totals pattern). So the skill picker is **per bought unit**:
`bioware_skill_{item_id}_{n}`, `n` counting from 0, rendered `quantity` times and only for a row
that has actually been bought — 28 `<option>`s for a row nobody owns would be noise on every render
of this section.

That falls out well for the interesting interaction. Bumping the quantity 1 → 2 submits only
`_0`, so the second purchase arrives with no pick: the route re-renders with the error, *two*
dropdowns, and the first pick still selected. Checked by hand, not just asserted — it's the one
flow where "the form regenerates itself" could plausibly have eaten a choice.

The `chosen_skills` list the template reads is in submission order, which is what makes the
re-selection work across both re-render paths (the section's own htmx swap, and
`chummer5.web.routes.priorities`' full-page rebuild — the latter needed `to_requests()` instead of a
bare id list, or re-submitting an untouched form would have dropped the pick).

### 2026-07-31 — Where each validation rule lives, and why they're not in one place

Three rules, three homes, following WP41's own split rather than inventing a new one:

| Rule | Enforced in | Why there |
|---|---|---|
| The pick resolves, and passes `limittoattribute` | `create_bioware_selection` | It's a property of the purchase, checked wherever a purchase is built (web, save load, import) |
| No two of the same item for the same skill (p. 460) | `create_bioware_selection` | Same — and it needs the *whole* selection, so it can't be a per-item check |
| A legacy `<extra>` that doesn't resolve | `legacy_import._blocking_reasons` | Itemized alongside every other unimportable augmentation detail, so a rejected file reports all of its problems at once |

The duplicate-skill rule is deliberately *not* re-implemented in the import path: like every other
structural rule (WP41's docstring paragraph makes this explicit for Capacity/category/rating), it
surfaces from `create_*` at build time. The `<extra>` check *is* there, because a pick that can't
resolve would otherwise import an item whose entire modeled effect is that pick.

## Follow-up

- **WP82** (new): `skill_rating`'s clamp to `MAX_SKILL_RATING_CREATE` swallows an augmented bonus, so
  a Reflex Recorder bought for a rating-6 skill does nothing. The skill-side twin of WP81, reachable
  from today's shipped UI, and shared by every skill Improvement this project grants (Enhanced
  Articulation, foci, Mentor Spirits, Voice Modulator, Voice Control). Smaller than WP81 in one
  specific way worth remembering: the purchase-side validators already read purchased points
  directly, so only `skill_rating` and the display are in scope.
- **Still open, still nobody's WP: rating vs. pool for the *other* skill bonuses.** p. 460 settled
  `Reflex Recorder` and p. 452 says the opposite for Voice Modulator, which means the project
  currently applies both through the same rating route. Whoever takes this needs a per-row reading
  of every skill bonus this engine grants, not a global switch.
- **`MODELED_BUT_UNCLASSIFIED` is empty and should stay a named, empty constant.** It is the thing a
  future `NOT_YET_SUPPORTED` row has to be added to, deliberately, to get
  `tests/unit/test_augmentation_unmodeled_registry.py` passing again — deleting it would remove the
  fork in the road that WP77 built the file to force.
- **The bioware catalog is 6 rows and one of them now needs a skill catalog to validate.** Any WP
  that widens `chummer5.data.bioware` past its flat-cost filter (Muscle Toner/Augmentation are the
  obvious candidates, and would give `unique="muscle"` its first real collision test — see WP78's
  own follow-up) inherits a `create_bioware_selection` that already takes `skills`.
