# WP87 — Harness: express the spend side of the budgets

Phase S. Closes the *harness half* of coverage gap **G12** — gear, Rating-priced gear, Lifestyle,
contacts, Knowledge/Language skills, and Karma-to-Nuyen conversion. Tests-only; every one of these
already had an engine function `build_synthetic()` simply never called.

## Goal

Before this WP a synthetic fixture could prove its dice pools were right and could not prove its
*budgets balanced*. `SyntheticCharacter` declared no field for anything a character buys outside
cyberware/bioware/foci, so no fixture ever committed a `resources_selection`, a `contact_selection`
or a `knowledge_selection` at all.

## Log

### Following `build_character`'s order rather than inventing one

The WP entry's own note — "a fixture that disagrees with the save path is a fixture that proves
nothing" — turned out to be the whole design. Every one of these selections has a *position* in
`chummer5.io.save_format.build_character`, and each position is load-bearing for a stated reason:

- **Knowledge/Language immediately after qualities.** Bilingual's `NATIVE_LANGUAGE_LIMIT` Improvement
  is applied by `apply_quality_improvements`, and `create_knowledge_selection` reads it. No current
  fixture takes Bilingual, so getting this wrong would have cost nothing today and broken the first
  fixture that did.
- **Contacts and Lifestyle before Resources.** Lifestyle's cost is an *input* to the Resources check,
  not a separate budget (`engine/lifestyle.py` deliberately doesn't validate against nuyen).
- **Resources before cyberware.** This is the one behavioural change to existing fixtures' code path:
  the cyberware block used to read `_PRIORITIES.resources[letter].nuyen` directly, and now reads
  `resources_selection.nuyen_remaining`. Identical for WP73-76 (they buy no gear), correct for
  anything that does.
- **`create_resources_selection` re-called as each later spender becomes known** — once up front,
  again after cyberware/bioware, again after foci. That's WP34/WP45/WP47's own pattern, not a new
  one, and the reason is that it *re-validates the combined total* rather than running a subtraction
  that could drift.

Both free-point budgets read **natural**, not augmented, attributes — `create_contact_selection`'s
`natural_attribute_value("CHA") * 3` and `free_knowledge_points`' `(natural INT + natural LOG) * 2`,
per p. 95 ("Attributes boosted by cyberware or bioware do not affect the calculation for things such
as points for Knowledge skills or Contacts"). Both were already correct in the engine (WP81); this WP
is the first thing that can *assert* them on a whole character, which is exactly what the WP entry
flagged as worth pinning down.

### Reusing engine dataclasses instead of mirroring them

`contacts`, `knowledge_skills` and `languages` take `Contact` / `KnowledgeSkillPick` /
`LanguageSkillPick` straight from the engine rather than a name-keyed authoring mirror. That looks
like a break from the harness's "fixtures are name-keyed, the engine is id-keyed" convention, but it
isn't: the convention exists to keep GUIDs out of fixture literals, and these three types have *no
catalog* to key against — the player invents the contact's name and the Knowledge skill's subject.
`chummer5.io.save_format` reuses `Contact` directly for the identical reason, already stated in its
own docstring.

### `karma_knowledge_points` — closing a hole §4 named by hand

Phase S §4's closing note recorded WP53's Knowledge/Language Karma spend as a deliberate gap, with an
explicit cause: *"no synthetic fixture declares a Knowledge roster, so the harness has no
`karma_knowledge_points` field."* This WP removes the cause, so the field went in with the rest,
wired third in Step Seven's order (attributes → Active skills → Knowledge) exactly as
`build_character` resolves them. WP88 spends 8 Karma through it.

One wrinkle worth recording: `KarmaKnowledgeSelection` records the *increase*, and does not rewrite
the committed `KnowledgeSkillPick`. So a Knowledge dice pool is the pick's own rating **plus** its
Karma points, which `_karma_knowledge_points()` adds back in — a metric key that read only
`pick.rating` would silently under-report every Karma-raised Knowledge skill.

### Proof: against the save's own rebuilt character, not transcribed constants

`test_spend_side_fields_reproduce_the_saves_nuyen_and_knowledge_budgets` builds `razorboy.json`
through `build_character` and the same inputs through `build_synthetic()`, then compares. If the
harness and the save path ever disagree about the evaluation order or which budget a cost lands in,
it fails — which is the entire reason for following that function's order instead of a plausible one.
Both reach ¥580 remaining of ¥283,000 and 12/12 Knowledge points.
