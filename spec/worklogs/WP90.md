# WP90 — Rigger-support research pass

Phase P. Research only, no `src/`/`tests/` changes. Answer the four questions Phase P's 2026-07-21
research-intro left open, extract the purchase-relevant rulebook material, and emit a concrete WP
breakdown — before any WP commits to a shape.

## Goal

The intro's four bullets, verbatim:
1. Confirm the exact `vehicles.xml` shape — flat vs. rating-scaled fields, how many SR5-core
   flat-cost entries exist across vehicles/drones/RCCs/cyberdecks, and whether Availability ≤ 12
   meaningfully shrinks the offerable list.
2. Confirm whether any curated `.chum5` fixture carries a vehicle/drone/RCC purchase at all.
3. Confirm the rulebook's page range for the Vehicles/Rigger chapter and extract the
   purchase-relevant subset.
4. Decide whether a stock RCC/cyberdeck's Matrix stat block needs any new `Character`-level concept.

## Log

### Question 3 first, because it reframed everything else

Started with the PDF rather than the XML, deliberately: the intro asked for "the rulebook's own page
range for the Vehicles/Rigger chapter," and I wanted the printed tables transcribed **before** seeing
the XML so the comparison would mean something.

There is no such single chapter. Three disjoint ranges, in three chapters — 198–208 (Combat: vehicle
stats, Vehicle Tests, Vehicle Combat), 264–271 (**Riggers**, its own chapter), 438–439 + 461–466
(Street Gear: commlink/cyberdeck tables, then Vehicles and Drones). Found via the TOC dump
(`pdftotext -layout -f 3 -l 8`) rather than by guessing; the page offset (book p. N = PDF p. N+2)
held throughout, as every entry since WP36 has found.

Then the finding that reshaped the phase. The intro's justification for excluding modifications
described "multiple separate per-category modification-slot pools (Cosmetic/Powertrain/Protection/
Weapons, each sized differently per vehicle)." I went looking for the printed sizing rule and
couldn't find one, so I dumped the whole PDF (`pdftotext -layout`, 489 pages) and grepped
case-insensitively for `powertrain`, `modification slot`, `mod slot`. **Zero hits.** The complete
SR5-core vehicle-modification system is four rows on p. 461 (Rigger interface, Standard/Heavy weapon
mount, Manual operation) plus "weapon mounts equal to unaugmented Body ÷ 3." The slot-pool system is
Rigger 5.0; `vehicles.xml` carries it because Chummer supports every book — 170 of its 197 `<mods>`
rows are `R5`, exactly 2 are `SR5`.

That doesn't argue for reopening the ruling, but it does mean the ruling was priced wrong. What it
*actually* costs turned up on p. 265: drones ship with the rigger interface built in, vehicles don't.
`vehicles.xml` agrees to the row — all 13 SR5 drone entries bundle a `Rigger Interface` mod, none of
the 29 vehicle entries do. So a no-mods rigger can buy a usable drone and an un-jumpable car. Filed
as a registry row (WP95) rather than a carve-out; reversing the ruling for one 1,000¥ flag that no
in-play subsystem reads would reopen the entire modification system.

### Question 1: the data is easier than expected, and mostly already loaded

`vehicles.xml`: 380 rows, **42 `source=SR5`** (29 vehicles + 13 drones). Every purchase-relevant
field is a **bare literal** — no `Rating * N`, no `FixedValues(...)`, no `Variable(...)` anywhere in
the SR5 set. The only non-integer shape is the printed `on-road/off-road` pair
(`<handling>4/3</handling>`, `<speed>3/4</speed>`), which the `.chum5` format splits into
`<handling>`/`<offroadhandling>`. So this phase needs nothing resembling
`chummer5.data.cyberware_formula` — it's the WP21 case, not the WP36 case.

Transcribing all four printed tables (Groundcraft/Watercraft/Aircraft/Drones) and comparing: **every
SR5 row agrees stat-for-stat**, including the `R`/`F` availability suffixes. Two XML rows aren't in
any printed table — `Horizon Flying Eye w/Flash-Pak and Grenade` (a 2,500¥ Chummer convenience
bundle) and `Ocular Drone` (`<page>453</page>`, cost 0 — the cyberware ocular drone, already a
`requires_parent` plugin in this project's cyberware catalog). Both should be excluded the way WP42
excluded `Essence Hole`/`Essence Antihole`.

Availability ≤ 12 removes 5 of 42 (Westwind 13, Nightsky 16, Cutlass 14R, Hound 13R, Banshee 24F).
Modest, and it removes exactly the rows a starting character has no business with. **35 offerable**
(24 + 11), all affordable within Resources A's ¥450,000, so no second cost filter is needed.

**Then the surprise.** The intro treats RCCs and cyberdecks as things this phase would need to add.
They're already there. `STARTER_GEAR_CATALOG` offers **11 RCCs, 9 cyberdecks, 7 commlinks, 6
autosofts and 26 programs** today, and has since WP21 — they're flat-cost `gear.xml` entries and the
loader takes any flat-cost SR5 row. What's missing is that `StarterGearItem` has no field for
`<devicerating>`, `<attack>`, `<sleaze>`, `<dataprocessing>`, `<firewall>`, `<programs>` or
`<attributearray>`, so the entire stat block is dropped at load time. Buy a Fairlight Excalibur and
the sheet shows a name and a price.

That collapses a whole imagined WP into a display job (WP94) and leaves vehicles/drones as the
phase's only genuinely new purchase flow.

It also surfaced a second thing I wasn't looking for: `build_starter_gear_catalog` applies the
Availability ≤ 12 cap **only** to WP66's Rating-priced half. Flat-cost gear is unfiltered, and so is
the entire cyberware catalog. Project Overview has flagged this since 2026-07-21 without numbers, so
I costed it: 3/11 RCCs, 2/9 cyberdecks, 1/7 commlinks, plus 7 flat cyberware rows over the cap and 17
rating-scaled rows whose top ratings exceed it (Wired Reflexes r3 = 20R being the worst). Sized in
`decisions-log.md`; WP94 closes only the three rigger-adjacent gear categories, the rest stays
unscheduled but is now costed rather than gestured at.

### The Control Rig, found while checking whether it was purchasable

I expected `Control Rig` to be excluded (rating-scaled `<ess>` and `FixedValues` `<cost>`, which
WP31's flat filter would drop). It isn't: WP37 widened the loader, and WP42's picker offers the full
87-row catalog, so it's been standalone-purchasable since that commit — the same commit that made
five of WP77's registry rows UI-reachable. It carries **no** `unmodeled_effect_note`.

Its entire printed effect (p. 266): "When you're jumped into a vehicle, drone, or other device, the
limits of that device are increased by the rating of your control rig. This includes vehicle and
drone Sensor, Speed, and Handling, and the Accuracy of mounted weapons when used by the rigger." No
character-level term at all. So a player can spend ¥43,000 and a **full point of Essence** on an
implant this engine models as pure cost. Under the 2026-07-24 policy that's fine to *offer* — with
the registry row that isn't there. WP95.

(Its rating-3 availability is `15R`, over the cap, which the cyberware picker doesn't enforce either
— same backfill as above.)

### Question 2: one usable fixture, and it can validate half of what you'd want

Checked all 34 corpus files for a `<vehicles>` node: 14 have one. Among the 13 curated fixtures:

- `Wesson.chum5` (Human Adept, **Priority**) — Harley-Davidson Scorpion (Chopper), `source=SR5`,
  ¥12,000. Its stat block matches both `vehicles.xml` and the printed p. 462 table exactly. **But it
  carries 7 mods, all `R5`** (Metahuman Adjustment, Anti-Theft System, Spoof Chips, GridLink,
  GridLink Override, Morphing License Plate, Off-Road Suspension), so his ¥3,965 remaining is not
  reproducible from a stock purchase.
- `Yeti-#ffffff2.chum5` — the one mundane Priority build — has **no** vehicles.
- `Miko.chum5` — vehicle is `R5`.
- `BLUE`, `Fuzzy-chargen`, `Serpent` carry SR5 drones but are all SumtoTen.

So: real legacy-computed corroboration exists for a stock vehicle *stat block*, and none at all for a
vehicle *ledger*. Moot for import in any case — `chummer5.io.legacy_import` passes `gear_names=()`
and imports no Step Six gear whatsoever, so vehicles were never arriving that way. Phase P gets the
same "hand-verified against the printed table" standard Phase M's WPs already anticipate, with
Wesson's Scorpion as the one real check and a synthetic fixture (WP96) as the regression guard.

### Question 4: no new Character-level concept, except one number

Every RCC/cyberdeck/commlink number is a printed constant read by nothing, because no Matrix rules
exist — so record and display, derive nothing. Same call WP27 made for Adept Powers. Two details
worth not getting wrong: the RCC's Noise Reduction/Sharing split is a **boot-time** choice bounded by
Device Rating (p. 267), not a purchase-time one, so chargen has nothing to record beyond the Device
Rating; and `<attributearray>` `"4,3,2,1"` is an *assignable* set of four Matrix attributes in
descending order (p. 439), not four labelled columns — rendering it as a fixed A/S/DP/FW assignment
would assert a rule the book doesn't make.

The one genuine derived value in the whole phase is p. 199's Condition Monitor: **vehicles
`12 + ⌈Body/2⌉`, drones `6 + ⌈Body/2⌉`**. Same `+ ⌈attribute/2⌉` shape as the character-level
monitors `engine.derived` already computes, different constant, plus a vehicle/drone split. Worth
deriving precisely because it's the one printed-page number a player can't read off the catalog row.

## Decisions made

- **The 2026-07-21 no-modifications ruling stands**, with its premise corrected and its one real cost
  (un-riggable vehicles) turned into a registry row rather than a carve-out.
- **Vehicles/drones are the phase's only new purchase flow**; RCC/cyberdeck/commlink work is display
  + Availability capping on gear already being sold.
- **Record-and-display for Matrix stat blocks; derive exactly one thing** (Condition Monitor).
- **Exclude 7 of 42 vehicle rows** — 5 by Availability, 2 as unprinted Chummer artifacts — for a
  35-row offerable catalog.
- **Hand-verified-against-printed-tables is this phase's standard**, with one real corroborating
  fixture and one synthetic fixture as the guard.
- Six implementation WPs, **WP91-96**, each tied to a finding above. Next unclaimed number is WP97.

## Traps hit (worth not re-hitting)

- **Don't take a phase intro's rules claims as rulebook-sourced.** Phase P's intro described the
  modification-slot system in enough mechanical detail to read as a citation; it was a description of
  `vehicles.xml`'s *fields*, which span every sourcebook. Grep the PDF.
- **Check whether the thing you're about to scope already exists in the catalog.** I nearly wrote a
  "load RCC/cyberdeck data" WP for content `STARTER_GEAR_CATALOG` has offered since WP21. The gear
  loader's filter is *cost shape*, not category, so it sweeps in whole subsystems nobody scoped.
- **`build_starter_gear_catalog(...)` takes its loaders as arguments and defaults to empty.** Calling
  it bare returns `()`, which reads like "the catalog is empty" rather than "you wanted the
  module-level `STARTER_GEAR_CATALOG` constant." Cost me one confused minute.
- Transcribe printed tables **before** looking at the XML if the point is to verify the XML. Doing it
  the other way round makes agreement unfalsifiable.
