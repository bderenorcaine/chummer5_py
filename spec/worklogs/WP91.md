# WP91 — `chummer5.data.vehicles`: the SR5 vehicle/drone catalog loader

Phase P's first implementation WP, and the substrate the rest of the phase stands on — mirroring how
WP21's gear loader preceded WP9's purchase flow. Closes no gap of its own.

## Goal

A literal `vehicles.xml` → frozen-dataclass pass restricted to `source == "SR5"`, returning all 42
rows so the count stays testable, with the two policy filters (Availability ≤ 12, the 2 unprintable
rows) deliberately left for the engine layer.

## Log

### The loader is the easy half; the interesting work was the acceptance test

WP90 had already answered every shape question — no formulas anywhere in the SR5 set, `handling`/
`speed` sometimes an `on-road/off-road` pair, `seats` absent on drones, availability a magnitude
plus an optional `R`/`F`. So `chummer5.data.vehicles` came out almost mechanical: 18 fields, one
`_pair_field` splitter, one `_availability` splitter, and a `_fail()` that raises a row-naming
`ValueError` for anything unrecognized.

**Fail-closed is the one design opinion in the module.** WP91's own brief says "if the loader ever
needs to parse a formula, something upstream changed and it should fail closed rather than guess."
Implemented literally: every field parser raises rather than defaulting, so a future data drop that
introduces `Rating * N` pricing produces a crash naming the row and the tag instead of a silently
zero-priced vehicle. Three tests drive synthetic XML through it (`Rating * 2500` cost,
`(Rating * 3)R` avail, `4/3/2` handling) to prove the guard rather than assert it in prose.

### Transcribing all four printed tables instead of one row per table

The acceptance criterion asked for "at least one row per printed table" checked against the chapter
extract. I transcribed all four **in full** (40 rows × 10 stats) into `tests/unit/test_vehicles.py`
instead, because a 40-row table is small enough to type out once and it buys two things a spot-check
can't:

1. **WP92's exclusion list becomes derived, not asserted.** The printed tables cover exactly 40 of
   the loader's 42 rows, and `test_the_printed_tables_cover_every_row_except_the_two_unprintable_ones`
   asserts the leftover set *is* `{Horizon Flying Eye w/Flash-Pak and Grenade, Ocular Drone}` — WP90
   §2's pair, arrived at from the book rather than trusted from the plan. If a future data drop adds
   a third Chummer-only row, that test names it.
2. **It found a real error** (below), which one-row-per-table would have had a 1-in-9 chance of
   catching.

The stats are compared *as printed* (`"4/3"`, `"14R"`) rather than pre-parsed, via an `_as_printed()`
helper that renders the loader's own fields back into the book's notation. That way the test asserts
the round trip through the loader's splitting, not just the halves in isolation.

### The finding: `vehicles.xml` gets the Tundra-9's Handling wrong

p. 465's AIRCRAFT table prints `R-F Fokker Tundra-9 | HANDL 3`. `vehicles.xml` says
`<handling>2</handling>`. Every other stat in the row matches the printed line exactly, and the row's
own `<page>464</page>` points at that very table.

Before calling it an error I checked the obvious alternative — that Chummer was encoding a Rigger 5.0
reprint's stat over the core one, which would make 2 correct-for-a-later-book. It isn't: there is
exactly **one** Tundra-9 row in the whole file across all sourcebooks. Nothing to prefer, so nothing
was preferred. It's a transcription slip on Chummer's side.

This also corrects WP90 §2's "All four printed tables agree with the XML stat-for-stat. No
corrections needed." — true for 39 of 40. Amended in place in `learnings/phase-p.md` with a pointer
forward rather than rewritten, since the claim's *derivation* (a spot-check) is worth keeping visible
next to what a full check found.

**Resolution (see `spec/decisions-log.md`'s 2026-08-01 entry):** the printed value wins, and the
correction goes in `chummer5.engine.vehicles`' catalog builder, not here. The loader stays what every
other `chummer5.data.*` module is. `KNOWN_XML_DIVERGENCES` pins the pair in both directions, so if a
data drop ever fixes the XML the test fails loudly instead of letting the catalog double-correct.

## Design decisions

- **`hidden` is carried even though the brief didn't list it.** `Ocular Drone` is the file's one
  `<hide/>` SR5 row, and the field mirrors `chummer5.data.gear.Gear.hidden` exactly. WP92 still
  excludes both unprintable rows *by name* as the phase file specifies — `hidden` would only catch
  one of the two, so it's data fidelity, not a shortcut.
- **`handling_offroad`/`speed_offroad` are `None`, not a repeat of the on-road value**, for rows that
  print a single number. That matches what the book prints (only the Yamaha Growler prints a Speed
  pair at all) and lets WP93 render `4/3` vs `4` off the data without a second flag. The legacy save
  format makes the opposite choice — `Wesson.chum5`'s Scorpion has `<speed>4</speed>` *and*
  `<offroadspeed>4</offroadspeed>` for an XML `<speed>4</speed>` — which the Wesson cross-check test
  asserts explicitly so the difference is recorded rather than discovered later.
- **`<mods>`, `<gears>`, `<weaponmounts>` and the `*modslots` counts are not read at all.** All
  modification-system surface, excluded by the 2026-07-21 ruling. The module docstring says so
  explicitly, including the one consequence worth knowing (drones bundle a Rigger Interface, vehicles
  don't — p. 265), so a later reader doesn't mistake the omission for an oversight. That gap is
  WP95's registry row, not something to work around here.

## Traps hit

- **`ruff format` destroys a transcription table.** Written as normal dict literals, the four printed
  tables got exploded to one value per line — 700 lines of unreadable column soup that defeats the
  entire point of transcribing a table. Fixed with `# fmt: off` / `# fmt: on` around the block and by
  dropping the printed-abbreviation column from each tuple (it lives in
  `vehicles_and_riggers_chapter.md` §6 already), which got every row under the 100-char limit as a
  single line.
- **`<id>` in a `.chum5` `<vehicle>` node *is* the catalog row's id.** I assumed it was a
  per-purchase instance id and asserted inequality; the test failed. `<guid>` is the instance id.
  Both are now asserted, which is the more useful check anyway — it proves this loader reads the same
  row the legacy engine resolved.
- **`uv run python -m mypy` with no arguments fails** in this checkout ("Package 'chummer5' cannot be
  type checked due to missing py.typed marker") because it resolves the *installed* package rather
  than `src/`. `MYPYPATH=src uv run python -m mypy -p chummer5` checks the source tree and is clean
  (64 files). Recorded here because Project Overview's stale-`.venv` note covers the console-script
  variant of this problem but not this one.
