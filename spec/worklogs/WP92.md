# WP92 — `VehicleSelection`, the Condition Monitor, and save/load

Phase P's second WP: turn WP91's catalog rows into something a `Character` can actually own. The
first (and, per the 2026-07-21 no-modifications ruling, only) genuinely new purchase flow this phase
adds.

## Goal

A stock vehicle/drone purchase as a real, budget-checked part of a `Character`: the 35-row offerable
catalog, a validated `VehicleSelection`, the one derived number (Condition Monitor), and save/load
round-tripping.

## Log

### This is the plainest selection type in the engine, and that's the interesting part

Every prior `create_*_selection` carries something extra: cyberware a purchase *tree* with Capacity,
bioware a per-purchase player choice, foci a Force and a Karma bond, qualities free text. A stock
vehicle has none of them. So `chummer5.engine.vehicles` came out as the minimal shape the
`create_*_selection` convention allows — a list of ids, a budget, a sum — and three things fall out
of that which are worth stating rather than leaving implicit:

- **No `apply_vehicle_improvements`.** Nothing about a vehicle changes a *character* number. Every
  printed vehicle stat feeds Vehicle Tests and Vehicle Combat, neither of which exists here, and the
  Condition Monitor is the vehicle's own, not the character's. Adding an empty applier "for
  symmetry" would imply there was something to apply.
- **No `karma_spent` term.** Vehicles cost nuyen only, so `Character.karma_spent`'s sum is
  untouched — the first selection field since WP32 that joins `Character` without appearing there.
- **`VehicleSelection.vehicle_ids` instead of a `to_requests()`.** The persistable inverse of the
  input is literally the ids, so it's a property, not a translation.

### Ids, not names

`create_resources_selection` takes gear by *name*; every other catalog since WP21 (cyberware,
bioware, foci, spells, powers) takes **ids**. The phase file's own note ("follow `gear_names`'
repeats-allowed precedent") is about multiplicity, not identity, so the two questions got answered
separately: repeats yes, name-keying no.

Names would have worked — `test_vehicles.test_names_are_unique_so_a_name_keyed_catalog_is_safe`
proves the 42 rows are uniquely named — but gear is name-keyed for a specific reason that doesn't
apply here: `StarterGearItem` is *synthesized* from three XML files (gear/armor/weapons) whose ids
live in different namespaces, so it has no single id to key on. `vehicles.xml` is one file with one
id per row. Ids it is.

### Where vehicles sit in `build_character`'s fixed sequence

WP87 was told to follow `build_character`'s own evaluation order rather than invent one; same
instruction here. The shared-nuyen-pool spenders now resolve cyberware → bioware → **vehicles**,
each against what the previous one left, and one `create_resources_selection` re-call folds all
three costs back in. That ordering isn't arbitrary: it means a combination that only overruns the
budget once all three are counted is always caught, on the last call, rather than being missed by
each call individually passing. Foci still resolve last of all, and their budget now correctly
reflects vehicles too, because they read the already-refolded `resources_selection.nuyen_remaining`.

### The Condition Monitor, and why it's the only computed number

p. 199: `12 + ceil(Body / 2)` for a vehicle, `6 + ceil(Body / 2)` for a drone. Implemented as
`(body + 1) // 2` rather than importing `chummer5.engine.derived._ceil_div` — the private helper of
another module is not an interface, and for the non-negative Body every catalog row has, the two are
identical. Cited in the docstring so the equivalence isn't left as folklore.

Everything else is a constant carried through from the catalog row, per WP90 §5's "record and
display, derive nothing." The tests pin the rounding case that actually distinguishes ceil from
floor (MCT Fly-Spy, Body 1 → 7, not 6) and the floor case (Kanmushi, Body 0 → 6).

## Design decisions

- **`build_character(vehicles=VEHICLE_CATALOG)` — the one optional catalog that doesn't default to
  `()`.** Every other catalog parameter defaults to empty because a save that never opted into that
  subsystem never consults it, and an empty default keeps pre-existing call sites honest. That
  reasoning inverts here: `VEHICLE_CATALOG` is a single fixed 35-row constant with no per-character
  variation and no filtering a caller would want to override, so `()` wouldn't mean "not needed", it
  would mean "silently reject every `vehicle_ids` entry as unknown." A test can still pass a stub.
- **The three policy filters live in the engine, not the loader** — same split `chummer5.data.gear`
  and `build_starter_gear_catalog` already use. That's what makes WP91's "42 rows, literally" and
  WP92's "35 rows, offerable" both testable as separate claims.
- **`_PRINTED_HANDLING_CORRECTIONS` is typed to the one stat that diverges**, not a general
  `{name: {field: value}}` map. mypy strict rejected the general form's `replace(obj, **kwargs)`
  anyway, which turned out to be the right nudge: a second correction, in a different field, should
  have to be written deliberately and argued for in the decisions log rather than dropped into an
  open-ended dict.
- **`create_vehicle_selection` validates against the *offerable* catalog**, so an
  over-Availability or unprinted row is rejected as an unknown id. There is no second "is this
  offerable?" check that a future caller could forget to run — the catalog *is* the filter. Tested
  from both directions (the GMC Banshee is in `load_vehicles()` and rejected by `build_character`).

## Traps hit

- **`dataclasses.replace(obj, **dict)` fails mypy strict** with a per-field `arg-type` error for
  every field the dict *isn't*. Restructuring the corrections map to a `dict[str, int]` keyed by
  name, applied as an explicit `replace(vehicle, handling=handling)`, fixed it and read better.
- **The final `resources_selection` re-call happens *before* foci resolve**, so adding `vehicle_cost`
  to only the cyberware/bioware fold would have left foci validating against a budget that hadn't
  paid for the vehicles. Both call sites needed the new kwarg; the second one is easy to miss
  because it's 150 lines further down and looks like a duplicate.

## Follow-up

- **WP93** reaches the player: nothing in the web layer knows about vehicles yet, so a purchase is
  currently only expressible through the engine API or a hand-edited save file.
- **WP95** owes the `Vehicle` dataclass an `unmodeled_effect_note` — both the "every printed stat
  feeds a subsystem that doesn't exist" note and the rigger-interface gap (a bought *vehicle* can't
  be jumped into; drones ship with the interface built in).
- `chummer5.io.legacy_import` was deliberately not touched — it imports no Step Six gear at all, so
  a legacy `<vehicles>` node was never going to arrive through it. Said so in the module docstring
  rather than left as a silent omission, as the phase file asked.
