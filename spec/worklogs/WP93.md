# WP93 — Web UI: the vehicle/drone picker and the character-sheet stat block

Phase P's third WP, and the one that makes WP91/WP92 reachable by a player. Until this landed, a
vehicle purchase was expressible only through the engine API or a hand-edited save file.

## Goal

A `_vehicles.html` picker section following the gear/cyberware category-grouped `<details>` shape,
plus a character-sheet section rendering each purchased vehicle's full printed stat block and its
derived Condition Monitor, with the running nuyen total.

## Log

### One stat-block helper, used by both renderers

The picker and the character sheet display the same nine printed stats plus the Condition Monitor,
in the same notation — `4/3` where the book prints an on-road/off-road pair, `—` for a drone's
Seating, `14R` for a restricted availability. Two independent renderings of that would be two places
to get the `None`-means-"same as on-road" convention wrong, so `vehicle_stat_block(vehicle)` lives in
`chummer5.web.routes.vehicles` and `chummer5.web.routes.character` imports it. The picker's rows are
that dict plus `id`/`quantity`/`subtotal`; the sheet's are that dict plus `quantity`.

### A peer section, not a fold into the gear picker

Same call WP20 made for Lifestyle and WP34 made for cyberware, for two reasons specific to this
catalog: a vehicle row is a fourteen-column table where a gear row is three, so one context builder
would be producing two unrelated row shapes; and 35 rows dropped into ~380 gear rows would be
invisible. The section sits after cyberware in `_chargen_body.html`, matching the order
`build_character` resolves the shared pool in.

### The shared Step Six pool now has six spenders, and threading the sixth found a bug in the fifth

Every section that spends from the Resources-priority nuyen budget takes its siblings' committed
costs as parameters (the cross-section wiring WP20 established). Adding vehicles meant touching all
five: `resources`, `lifestyle`, `cyberware`, `foci`, and `priorities` (which rebuilds every section's
context for a full-page render).

Doing that made a **pre-existing** hole visible. `submit_resources` and `submit_lifestyle` each
passed `foci_cost` to their *context* builder — so the "no longer fits" warning was correct — but not
to the `create_resources_selection` call that actually **accepts** the submission. A character with
bonded foci could commit gear or a Lifestyle over the real remaining budget, and the sheet (which
recomputes from committed selections) would then show a negative `nuyen_remaining`. Fixed in the same
lines that gained `vehicle_cost`; see `spec/decisions-log.md`'s 2026-08-01 entry for why that wasn't
deferred to its own WP. `cyberware` and `foci` never had the gap.

### Registry re-check (the WP77 clause) — nothing moved

WP93's own notes flag it as "exactly the kind of 'a UI WP moves the line' event" the `Kind` column
exists for, so it got checked rather than assumed: this WP offers a catalog that has **no** registry
rows yet (WP95 writes them), and it makes no existing quality or cyberware row newly reachable.
`Control Rig` — the one rigger-adjacent registry gap — became UI-reachable back with WP42's
full-catalog picker, as WP90 §4 already records. So the answer is "no change," recorded so the next
reader doesn't have to re-derive it.

## Design decisions

- **Quantity per row, expanded into repeated ids** — `_parse_vehicles` mirrors
  `chummer5.web.routes.resources._parse_gear` line for line, because the underlying rule is the same
  (`create_vehicle_selection` takes a flat, repeats-allowed list). An unparseable or negative
  quantity clamps to 0: a web-robustness clamp, not a rule offloaded onto the engine, exactly as
  `_parse_gear` documents for the identical case.
- **The route re-derives `resources_selection` after a successful purchase**, so `nuyen_remaining`
  (what the sheet and every other section read) reflects the new vehicle spend — the same fold
  `build_character` performs after resolving vehicles. Without it, buying a vehicle would leave every
  *other* section's displayed budget stale until the next full render.
- **`_other_section_costs(character)`** returns all five sibling spends plus `karma_converted` as one
  tuple. Vehicles is the last of six sections to join the pool, so reading them inline would be a
  12-line prelude repeated in both branches of the route.
- **An excluded row is unreachable by construction, twice over.** `_parse_vehicles` only reads form
  fields for rows in the *offerable* catalog, so a hand-crafted POST naming the GMC Banshee is
  ignored; and even if it were read, `create_vehicle_selection` validates against the same catalog
  and would reject it as an unknown id. The test asserts the observable property (it is not bought)
  rather than which of the two layers caught it.

## Traps hit

- **A mundane build can't take Resources E.** The over-budget test originally confirmed a character
  with Resources E (6,000¥) — which `submit_priorities` rejects, because Talent is forced to E for a
  mundane character and the other four letters are a bijection over A–D. The cheapest reachable
  Resources letter is **D** (50,000¥), so overrunning it with a single purchase needs the catalog's
  most expensive offerable row: the Fokker Tundra-9 at 300,000¥. Rewrote the test helper to derive
  the other three letters from the requested Resources letter (`sorted({"A","B","C","D"} - {letter})`)
  instead of hardcoding A/B/C.
- **`ruff` sorts `from chummer5.web.routes.vehicles import ...` before `..spells`** — appending the
  import next to `..skills` looked right alphabetically but isn't (`v` > `sp`). `ruff check --fix`
  sorted it.
