# WP94 — Surface the Matrix stat block on gear already being sold, and cap its Availability

Phase P's fourth WP, and the only one in the phase that adds no new purchase flow. Commlinks,
cyberdecks and rigger command consoles have been in `STARTER_GEAR_CATALOG` since WP21. What WP90 §3
found is that they arrived with their entire printed stat block thrown away at load time: a player
could buy a Fairlight Excalibur for 823,250¥ and the character sheet would show a line item and a
price. The second half of the same finding is that the 2026-07-21 Availability ≤ 12 ruling had never
been applied to flat-cost gear at all, so those over-cap rows were purchasable in the first place.

## Goal

Read the seven discarded XML fields into the loader, carry them through to the purchased item,
render them on the character sheet for those three categories, and apply the Availability cap to
exactly those three categories.

## Log

### The three tables print three different stat sets, and that turned out to be the whole design

The obvious implementation — one "Matrix stat block" with six labelled numbers — is wrong, and the
rulebook says so directly (p. 226): "Most devices (including commlinks) have only two Matrix
attributes: Data Processing and Firewall. Decks and hosts have all four, including Attack and
Sleaze." The XML agrees precisely, and the three printed tables agree with the XML:

| Category | Printed columns | XML fields present |
|---|---|---|
| Commlinks (p. 438) | Device Rating, Avail, Cost | `devicerating`, `dataprocessing`, `firewall` (last two always = Device Rating) |
| Cyberdecks (p. 439) | Device Rating, **Attribute Array**, Programs, Avail, Cost | `devicerating`, `attributearray`, `programs` |
| RCCs (p. 267) | Device Rating, Avail, Cost, Data Processing, Firewall | `devicerating`, `dataprocessing`, `firewall`, `programs` |

So `matrix_stat_block()` renders per-row whatever that row *has*, and the shape falls out of the
data rather than being three hand-written branches. Full citations in
`spec/rulebooks/learnings/phase-p.md`'s WP94 entry.

### `<attributearray>` stays one tuple, on purpose

The WP's own notes flagged this and it's worth restating: `"4,3,2,1"` is an *assignable* set the
decker distributes among Attack/Sleaze/Data Processing/Firewall (p. 439 prints it as one descending
array for exactly that reason), not four labelled columns. Storing it as four named fields would
have made the dataclass assert an assignment the rules leave to the player, and would have made the
display quietly wrong in a way nobody would notice. It is `tuple[int, ...]` on both `Gear` and
`StarterGearItem`, and renders as `4 3 2 1`.

### The one field loaded and deliberately not shown

Every RCC row in `gear.xml` carries `<programs>` equal to its Device Rating. **The core rulebook
prints no program-slot count for an RCC anywhere.** p. 267's table has no such column; p. 269's
rigger-cyberprograms sidebar establishes only that RCCs run programs and can't run two of a type;
and the one printed slot formula nearby ("equal to half its Device Rating, rounded up") is
explicitly a *drone* rule. Cyberdecks genuinely print a Programs column, so theirs is displayed.

The field is loaded anyway — the loader stays literal, as every `chummer5.data.*` module does — and
the display decision lives in `matrix_stat_block`. Recorded as a dated decisions-log entry because
the tempting default (render every populated field) would have published a Chummer-authored number
as an SR5 stat.

### The Availability cap needed a field nobody had loaded

`Gear` carried no `<avail>` at all — WP21 never needed one, and WP66's cap works off `RatingGear
.availability`. Adding `availability: str` (raw text, `R`/`F` marker intact) let
`_flat_availability_over_cap` reuse `parse_rating_availability`, which already returns `(0, N)` for
the bare `N`/`NR`/`NF` form every SR5 row in these categories uses. It fails closed on an
unparseable value and on a `slope != 0` result, which is not a shape SR5 produces for a flat-cost
item but is exactly the kind of thing a future data drop could introduce silently.

The cap lives in `build_starter_gear_catalog` behind a named frozenset, not inline: widening the
backfill later is then one edit in one obvious place, and the name itself documents that the
narrowness is deliberate.

### Transcribing all three tables, not sampling them

The acceptance criterion asked for "every retained row's stat block asserted." WP91 set a better
precedent on the vehicle side — transcribe the printed tables in full and assert every row,
including the ones policy removes — and it paid off there by catching a real XML error. Doing the
same here (27 rows across `PRINTED_COMMLINKS`/`PRINTED_CYBERDECKS`/`PRINTED_RCCS`) means the
6-row exclusion list is *derived* from the transcription plus the cap, not asserted independently
and left to drift. Unlike WP91, no divergence was found: all 27 rows match the XML exactly.

## Design decisions

- **Seven optional fields on `Gear`, not a nested `MatrixStats` dataclass.** Only 49 of 266 flat
  rows carry any of them and only 21 rows carry a full set; a nested optional object would add a
  level of indirection to every access for no invariant it could enforce.
- **Two frozensets, not one.** `_AVAILABILITY_CAPPED_GEAR_CATEGORIES` (engine, a purchasability
  rule) and `MATRIX_STAT_BLOCK_CATEGORIES` (web, a display decision) hold identical contents today.
  Kept separate because they answer different questions and a future backfill will very plausibly
  widen the cap without widening the display.
- **Display scoped to the three categories.** 21 other flat rows (RFID tags, credsticks,
  Electronics/Commlink accessories) carry a `<devicerating>`, and none of them prints a stat block
  in any gear table. `matrix_stat_block` returns `None` for them.
- **Nothing derives anything.** No Matrix rules exist in this project; this is record-and-display
  only, the discipline WP27 applied to out-of-scope Adept Powers and WP90 §5 restated for exactly
  these items.

## Traps hit

- **The save format needed no change, and checking that was the point.** Purchased gear round-trips
  by *name* (`resources_gear_args` → `create_resources_selection`), so the new fields re-resolve
  from the catalog on load. Had `StarterGearItem` been serialized structurally, the 6 capped rows
  would have made existing saves unloadable.
- **`Living Persona`'s `<devicerating>` is `{RES}`**, an attribute reference. Every parse fails
  closed to `None` rather than guessing; the row is `<hide/>`-marked and never reaches the catalog
  anyway, but the loader can't rely on that ordering.
- **One existing test compared a purchased `StarterGearItem` by full equality**
  (`test_create_resources_selection_within_budget`, using Meta Link — a commlink). It's the only
  such comparison in the suite, and it's a *good* test: it caught the field addition immediately.
  Updated to carry the stat block rather than loosened.
- **`Standard Rope` isn't a gear name** — it's `Standard Rope (100m)`. A reminder that this
  catalog's names carry parenthetical qualifiers more often than not.

  notes dict). Note for whoever picks it up: WP93's own worklog records that

  all, so the vehicle half needs a new loop, not just a field.

  frozenset to widen. Sized in `spec/decisions-log.md`'s 2026-08-01 and 2026-08-24 entries.

  under a category `<details>`. Worth revisiting if a rigger-focused UI pass ever happens.
