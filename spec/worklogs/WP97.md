# WP97 — The application shell: title bar, step nav, content pane

Phase W's first WP. It replaces the single-page accordion — fifteen stacked `<details>` sections in
`_chargen_body.html`, one open at a time — with the frame from the hand-drawn sketch
(`examples/ui/main_ui.png`): a title bar, a sidebar step nav, and one `#page` pane that shows the
selected step. No step's route, context builder, or form changed; only where each fragment is
mounted did.

## What landed

- **`chummer5.web.shell`** — the new non-router module the shell hangs off:
  - `STEP_PAGES`, the eleven nav entries in the sketch's order. Each lists the existing fragments it
    mounts, the `*_budget_warning` context keys that mark it stale, and whether it is enabled.
    Resonance and Bio are `enabled=False` with a reason (Finding 3).
  - `chargen_context`, which is `_chargen_body_context` moved out of `routes/priorities.py` with its
    content unchanged, minus the `open_section` key.
  - `nav_context`, which builds the nav items from a `chargen_context` result the caller already
    has.
- **`chummer5.web.routes.pages`** — `GET /` (the Priorities page), `GET /ui/page/{slug}`,
  `GET /ui/nav`, and `GET /character/sheet`, which moved here from `routes/character.py` and is now
  the Export page under its old URL. A page request with `HX-Request` gets `_page.html` plus the nav
  out of band. Any other request gets the whole shell (`base.html`). That includes a bookmark, a
  reload, and htmx's `HX-History-Restore-Request`. Disabled and unknown slugs return 404. Responses
  carry `Vary: HX-Request`.
- **`ChargenSession.open_section` → `current_page`**, which now holds a nav slug. Every step `POST`
  sets it to the slug of the page that step lives on, so all five Magic fragments set `"magic"`.
  `POST /character/load` and `/import-chum5` set it to `"export"`. Page `GET`s set it too.
- **`POST /ui/priorities` renders only `_priority_form.html`**, targeting `#priority-section` like
  every other step. It still builds its context through `chargen_context`, because the page's own
  "some selections no longer fit" line reads the `priority_stale_selections` aggregate. That line
  now points at the nav instead of "the sections below".
- **Templates.** `base.html` is now the shell. `_page.html` and `_step_nav.html` are new.
  `chargen.html`, `character_sheet.html`, and `_chargen_body.html` are deleted. In each of the
  fifteen step fragments: the root `<div>` gained `class="panel"`, the top-level `<details>`
  renders `open` unconditionally, and the `<summary>` lost its `⚠` conditional and gained
  `class="panel__heading"`. The "Confirm a metatype and priorities **above**" placeholders now say
  "**on the Priorities page**", and the priority form's "Talent section below" now says "Magic
  page".
- **`app.css`** rewritten against class hooks only (`.app-shell__*`, `.step-nav__*`, `.page*`,
  `.panel*`). The old sheet selected on `#chargen-body > div > details > summary`. It gained a few
  new tokens for the shell chrome and a narrow-screen layout where the nav becomes a wrapping row.
- **`test_web_accordion.py` → `test_web_shell.py`** (11 tests). About 50 existing web tests were
  re-pointed from `GET /` or the priorities `POST` response to the page that actually shows their
  step (see "Test exposure" below).

## Decisions

### The nav refreshes itself; routes don't render it

A priorities change can make any step stale, and fixing a step should clear its ⚠, so the nav has
to update after every mutation, on whatever page. I rejected adding an out-of-band nav to all
fifteen step `POST`s: each would need `chargen_context` just to draw the nav, and each future step
route would have to remember to do it. Instead, one `@app.middleware("http")` in `create_app` adds
`HX-Trigger: chargen-changed` to every `POST` answered with status < 400. The nav carries
`hx-get="/ui/nav" hx-trigger="chargen-changed from:body"`. The cost is one extra small `GET` per
change. Validation errors return 200, so they refresh the nav too, which is harmless.

The nav links set `hx-swap="innerHTML"` explicitly. Without it they would inherit the nav's own
`outerHTML` and replace `#page` itself instead of its contents. That is the one trap in this
arrangement.

WP99 should listen for the same event rather than add an out-of-band swap to every route as its
entry currently says. That is logged in the decisions log.

### Back/forward re-fetches instead of restoring a snapshot

The first browser walk showed the problem. Spend skill points → go to Priorities → lower the Skills
letter → press back. The Skills page came back from htmx's history cache exactly as it was before
the change, without the "No longer fits" warning, and its form was ready to post the stale state.
Setting `htmx-config` `historyCacheSize: 0` turns every back/forward into a history-restore request.
The page route already answers those with the full shell, so the restored page is fresh and
`current_page` follows.

That in turn meant moving the `<details>` store script from `<body>` to `<head>`. A history restore
swaps the body and runs its scripts, which would have added a second set of listeners over an empty
store on every back press.

### WP64's store was kept, trimmed (and Finding 2 was half wrong)

See the decisions log for the full argument. In short, the script had two jobs. The section
exclusivity job was accordion machinery and went. The job of remembering a sub-category's manual
open/closed state across a swap was the Phase U fix for categories snapping back open, and that
bug would have come straight back without it. What remains is about 20 lines keyed only on
`data-details-key`. It now also survives page swaps: collapse a skill category, go to Magic, come
back, and it stays collapsed (checked in the browser).

### The six 1:1 pages keep their `<details>`

The acceptance line was `grep -c '<details'` unchanged over the six moved templates, and it is
(1/1/1/1/4/1 before and after). The top-level `<details>` now renders `open` unconditionally, so
each page's panel can still be collapsed by hand. That is pointless on a one-panel page and mildly
useful on the three composite pages. Whether to drop it belongs with WP98's intra-page pattern
decision, not here.

### The composites are stacked, not designed

Skills, Magic, and Equipment mount their fragments in their old accordion order, each panel open.
That is enough for the nav to work end to end. It is deliberately not a design: WP98 owns that
decision.

## Traps hit

- **The `window` stores from the WP's second trap were fine.** `window.__skillFilterState` (WP83)
  is read and re-applied by the fragment's own script on every render, so it survives a page swap
  unchanged. The gear and spell filters keep no state outside their fragment, so they reset on a
  swap, the same as they did on a section swap. The store that actually needed care was the one the
  trap did not list, `base.html`'s own (see above).
- **Test exposure matched Finding 6.** Tests broke only where they read a step's content off `GET /`,
  or off the priorities `POST` response, which used to re-render every section. Rather than keep a
  "render all pages" helper, I pointed each test at the page that shows its step. I also converted
  the tests that were still passing but had gone vacuous: several `assert "X" not in response.text`
  checks against `GET /` would now pass trivially because the step is no longer on that page (Foci/
  Spirits/Mentor hidden for Mundane, the `requireparent` cyberware rows). Two tests asserted on the
  old `<summary>Foci`/`<summary>Spells` strings, and I updated those to the `panel__heading` form so
  the negative checks still mean something.

## Found, not fixed

**Every step form's submit button does a native GET.** Thirteen step forms carry an `hx-trigger`
that replaces htmx's default `submit` trigger. So "Update skills" and the other buttons, and Enter
in a text field, fall back to plain HTML submission to the current URL. Before this WP that reloaded
`/`. Now it loads `/ui/page/skills?<every field>`. That renders the right page but leaves the whole
form in the address bar. The browser walk hit this. The fix is one word per form, but it changes
every fragment's behaviour, so I left it out of a WP whose acceptance is "no step's contents
change". It is logged in the decisions log for a follow-up.
