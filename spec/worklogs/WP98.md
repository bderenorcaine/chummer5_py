# WP98 — The three composite pages: Skills, Magic, Equipment

Phase W's second WP. WP97 mounted the nav's three composite pages by stacking their old accordion
fragments in a column, each panel open. This WP gives them one intra-page pattern, used the same way
on all three pages: a tab strip over the page's sections. No fragment template, step route, or
context builder changed.

## What landed

- **`chummer5.web.shell`**:
  - `StepPage.fragments` + `warning_keys` became `sections: tuple[PageSection, ...]`.
  - A `PageSection` is one fragment with its own tab slug, label, `*_budget_warning` keys,
    `available` predicate, and `unavailable_reason`. `StepPage.warning_keys` is now the union over
    sections, so the nav's stale marker is unchanged. A page with more than one section is
    `tabbed`.
  - Magic has a `locked_note` for its empty state.
  - New `resolve_tab` (which tab shows, recorded per page) and `tabs_context` (the strip's items).
- **`chummer5.web.routes.pages`**:
  - `GET /ui/page/{slug}/{tab}` behaves like `/ui/page/{slug}`: a fragment for htmx, the full shell
    otherwise. It returns 404 for an unknown tab or for a single-section page.
  - `GET /ui/tabs/{slug}` returns the strip alone, for its self-refresh.
- **`ChargenSession.page_tabs`** holds each composite page's last-shown tab.
- **Templates**:
  - `_page.html` wraps each section of a tabbed page in `<section class="subpage">`, `hidden`
    unless current. An explicitly requested unavailable tab gets a `.subpage__unavailable` reason
    line.
  - New `_page_tabs.html` is the strip. Single-section pages render exactly as before.
- **`app.css`** has `.page-tabs*` rules plus four new tokens (`--tab-fg`, `--tab-hover-bg`,
  `--tab-current-accent`, `--tab-disabled-fg`), for light and dark.
- **Tests**:
  - `tests/unit/test_web_composite_pages.py` (16 tests).
  - `tests/integration/test_web_nav_walk.py`, the acceptance walk. It follows the nav's and every
    tab's own `hx-get` from priorities through skills, magic, and equipment. On each page it asserts
    that every section's fragment is present and exactly one is showing.

Tab labels: Skills has *Active skills* and *Knowledge & languages*. Magic has *Talent*, *Spells*,
*Adept powers*, *Bound spirits*, and *Foci*. Equipment has *Gear*, *Lifestyle*, and *Vehicles &
drones*. The tabs keep the old accordion order.

## Decisions

### Tabs, not retained `<details>` groups, and why they re-render

The phase file asked for the pattern to be decided before any of the three pages were written. The
full argument is in the decisions log. In short, two facts decided more than taste did:

- **Every fragment must stay in the page.** About 38 existing test requests `GET` a composite page
  and assert on one of its fragments. The acceptance requires those assertions to stay unchanged,
  which rules out "the server renders only the current section". So every section is rendered, and
  the inactive ones are `hidden`.
- **A tab switch must re-render, not toggle.** `POST /ui/talent` swaps only `#talent-selection`.
  After a Magician is confirmed, the Spells fragment already in the DOM is still the empty
  `<div>` it rendered for a Mundane character. This was true under the accordion too: I checked the
  pre-WP97 route, and no talent change ever refreshed a sibling. A client-side tab toggle would
  show that stale fragment. A tab link that fetches `/ui/page/magic/spells` cannot. So I built tabs
  as the nav's mechanism one level down, with no new JavaScript.

`<details>` groups would have met both constraints trivially, since they are what WP97 shipped.
They were rejected because they are the stacked column the WP exists to replace. On Magic, five
panels deep, the section a player wants is usually below the fold.

### Availability mirrors the fragment guards, pinned by a test

Each Magic fragment already hides itself behind a top-level `{% if %}` (Spells and Spirits for
Magicians, Powers for Adepts, Foci for either). A tab over an empty fragment would be a dead end, so
each `PageSection` carries a predicate that mirrors its guard. This is duplication.
`test_magic_tab_availability_agrees_with_each_fragments_own_guard` renders the page for no
character, Mundane, Magician, and Adept. For every section it asserts that the tab is a link exactly
when the fragment rendered content. I mutation-checked it: loosening `_is_adept` fails 4 cases.

An unavailable tab is a disabled `<span>` with its reason as `title`, the same form as the nav's
Resonance/Bio. Because a `title` is invisible on touch and easy to miss, Magic also shows one
visible `locked_note` line. It appears only when every tab except the one showing is unavailable,
which is Magic's real empty state: no character, or Mundane. A Magician sees just a greyed *Adept
powers* tab, with no note.

### Each page remembers its tab, but falls back rather than dead-ending

A nav click reopens the tab the player left (`page_tabs`). If that tab has since become unavailable,
because a Talent change took Spells away, the page falls back to the first available section. An
explicit tab URL to an unavailable section is different: it shows the reason, because silently
showing a different tab at `/ui/page/magic/spells` would be worse. The strip's self-refresh marks
the remembered tab even when the change just made it unavailable, so the strip always describes the
pane underneath it.

### No page-level Equipment budget line (left for WP99)

The entry suggested one shared nuyen line for Equipment. A line in `#page` would go stale on every
fragment `POST`. Keeping it fresh means a self-refreshing widget, and that is WP99's resource panel
built for one page. The panel will show that figure on every page. Logged for WP99 in the phase
file.

### The top-level `<details>` stays

WP97 deferred whether to drop each fragment's top-level `<details open>` to this WP. Dropping it is
a fragment edit, and this WP's acceptance is that fragments stay untouched. On a tab it is merely
redundant, not harmful: the panel heading repeats the tab label. It is left for whichever WP next
opens the fragments; WP102's string pass is the obvious candidate.

## Traps hit

- **`&` in tab labels.** *Knowledge & languages* and *Vehicles & drones* render as `&amp;`, so the
  test helper that finds a tab by label has to HTML-escape it first.
- **CSS `hidden`.** `.subpage` must never get a `display` rule, or the `hidden` attribute stops
  hiding it. This is the same class of constraint as WP84's "no `display` on a `tr`". It is noted in
  `app.css` and in the phase file's class-hook list for WP100.

## Found, not fixed

- **At 400px, a confirmed character's skill tables are wider than the viewport.** The Knowledge
  page measured 542px. The tab strip wraps correctly and ends at 380px. The overflow is the
  fragments' own tables, which this WP does not touch. It predates this WP.
- **The native-GET submit buttons (WP97's finding) are still open.** They are a fragment change,
  so they are out of scope for the same reason as above.

## Verification

- `pytest` 1371 passed (1354 before, plus 17 new). No existing test was edited. `ruff check` and
  `ruff format --check` are clean on `src` and `tests`, and `mypy src` is clean.
- A Playwright walk against a live `uvicorn`, headless Chromium, with no console errors:
  - Mundane Magic shows Talent current, four disabled tabs, and the locked note.
  - After confirming Magician on the Talent tab, with no reload, Spells, Bound spirits, and Foci
    become links, Adept powers stays disabled, and the note disappears.
  - Clicking Spells pushes `/ui/page/magic/spells` and shows only that section. Foci, then back,
    returns to the Spells tab.
  - Equipment → Lifestyle → Magic → Equipment reopens Lifestyle. A reload keeps Lifestyle.
  - A direct `GET /ui/page/skills/knowledge` renders the full shell on that tab.
  - At 400px the strip wraps inside the viewport.
